# script-import-normalize

用于“用户提供已有文本，希望整理成项目章节”的场景。这个 skill 的首要目标是防止非剧本文档被误写入章节目录。

## 触发时机

- 用户通过对话框附件上传 `.txt` 或 `.md`。
- 用户在输入框粘贴长文本，并表达“导入”“整理成章节”“按章节放进项目”等意图。
- 用户要求把已有剧本拆成第 1 章、第 2 章等项目章节。

## 非目标

- 不负责从零生成灵感种子。
- 不负责章节内润色、续写或重写。
- 不负责结构化剧情、分镜、候选图或排版。
- 不直接读写本地物理路径。

## 输入

执行前应基于以下上下文判断：

- 用户本轮消息。
- 附件或粘贴文本正文。
- 当前项目名称、workflow、章节列表和当前章节。
- 已有章节是否为空，是否存在被覆盖风险。

## 判断流程

1. 内容识别

   将输入先归类为：

   - `script`：有连续剧情、人物行动、场景或对白，可整理为剧本。
   - `story_prose`：像小说或故事正文，可询问是否按剧情节拍转为剧本章节。
   - `outline`：只有大纲、章节梗概或 bullet 列表，不应直接当剧本写入。
   - `worldbuilding`：世界观、角色设定、素材说明，不应写入章节正文。
   - `invalid`：太短、杂乱、与项目无关或无法判断。

2. 导入校验

   只有同时满足以下条件，才允许进入拆章计划：

   - 文本有足够连续的故事内容，而不是只有标题、编号或设定项。
   - 至少能识别一个可信章节，或用户明确允许先写入单章。
   - 不会在用户不知情的情况下覆盖已有非空章节。

3. 章节边界识别

   高可信边界：

   - `第 1 章`、`第一章`、`第1话`、`第 1 幕`、`第1回`
   - 带章节语义的 Markdown 标题，如 `# 第 1 章 雨夜`

   低可信边界：

   - 单独成行的 `1`、`2`、`3`
   - Markdown 标题 `# 1`、`## 2`

   低可信边界只有在多段都包含足够故事正文时才能采用，不能把普通编号列表、提纲编号或说明文档编号当章节。

4. 决策

   - `ready_to_import`：内容像剧本，章节边界可信，可以调用导入工具。
   - `needs_user_confirmation`：内容可用但需要用户确认，例如无章节边界、需要按剧情节拍拆章、会覆盖已有章节。
   - `reject`：内容不适合导入为章节，直接解释原因并给出修正建议。

## 输出契约

在调用写入工具前，先形成导入分析结果：

```json
{
  "decision": "ready_to_import",
  "contentType": "script",
  "reason": "识别到 3 个明确章节标题，正文包含连续剧情和对白。",
  "chapters": [
    {
      "order": 1,
      "title": "第 1 章 雨夜",
      "boundary": "explicit_chapter_heading",
      "summary": "主角在雨夜发现异常。"
    }
  ],
  "risk": null,
  "nextTool": "import_script_to_chapters"
}
```

拒绝导入时：

```json
{
  "decision": "reject",
  "contentType": "outline",
  "reason": "这份内容更像章节提纲，缺少可作为正文导入的连续剧情。",
  "chapters": [],
  "risk": "直接导入会把提纲误写成章节正文。",
  "nextTool": null
}
```

## 写入规则

- 只有 `decision = ready_to_import` 时，才允许调用 `import_script_to_chapters`。
- `needs_user_confirmation` 和 `reject` 都不能写章节文件。
- 写入后必须说明写入了几个章节、当前打开哪个章节、是否保留原文语义。
- 不要声称“我直接保存了本地文件”；应表述为“已通过系统工具写入章节草稿”。
