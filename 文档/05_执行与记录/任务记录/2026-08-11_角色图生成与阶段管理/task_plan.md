## 1. 任务目标

解决 AI 漫游项目角色图生成的两个核心问题：

1. **提示词信息源单薄**：角色图的生成提示词只来自当前章内容，且 first-write-wins 导致后续章节详细描写无法补充
2. **缺乏阶段建模**：角色有阶段性变化（年龄、衣着、气质），但系统没有阶段机制，图无法跟着变

## 2. 非目标

- 不做完全自动的"全书一键生成所有角色所有阶段图"
- 不破坏现有七阶段流程（剧本→结构→分镜→生图→候选→成稿→素材）
- 不新增独立的"角色定妆"步骤到主流程
- 不改变 Character 实体的基础字段（id/name/role/level/entityType）

## 3. 验收标准

### 必达标准

1. **信息源修复**：角色档案可以从多章信息聚合，不再是单章碎片
2. **阶段建模**：数据模型支持一个角色有多个阶段，每个阶段有独立的图和描述
3. **保脸换装**：新阶段图基于上一阶段图垫图生成，脸不变
4. **零破坏**：现有项目、现有角色、现有流程不受影响，兼容旧数据

### 期望标准

5. **全书扫描**（导入文稿项目）：《凡人修仙传》这种项目能从全书提炼角色设定
6. **冲突报警**（AI 原创项目）：逐章生成时检测到外貌冲突能提醒用户"可能是新阶段"

### 可选标准

7. **交互式定妆**：lead/recurring 角色支持 3 选 1 定妆流程

## 5. 关键设计决策（已确认 - 稳妥路线 A）

**用户决策**：先做稳妥路线（方案 3 - 图为王），跟 Midjourney、LlamaGen 等市面产品对齐

**核心理念**：图片是角色的核心，文字描述只是辅助

### 决策 1：定妆方式
**确认方案**：交互式定妆（3 选 1 或调整后生成）

**具体做法**：
- lead/recurring 角色在角色库显示"待定妆"状态
- 用户点击"定妆"按钮 → AI 根据当前 appearance 生成 3 张候选
- 用户选择其中一张，或提供调整意见重新生成
- 选中的图存为 `anchorAssetId`（锚点图）
- 后续所有生成都基于这张锚点图

**时机**：
- 不强制拦截主流程（用户可以跳过）
- 角色库页面主动入口
- 首次生成参考图时智能提醒（可跳过）

### 决策 2：阶段管理
**确认方案**：手动创建阶段 + 垫图生成

**具体做法**：
- 角色库支持"新增阶段"按钮
- 新阶段只需填写差异描述（如"改穿金色道袍、蓄短须"）
- 生成新阶段图时，以上一阶段的图为参考（editImage）
- 不做自动检测阶段冲突（后续可选）

**数据结构**：
```typescript
CharacterStage {
  id: string
  characterId: string
  stageOrder: number  // 1, 2, 3...
  fromChapterId: string | null  // 可选：从第几章开始
  visualDelta: string  // "改穿金色道袍、蓄短须"
  previewAssetId: string | null
  finalAssetId: string | null
}
```

### 决策 3：生图提示词改造
**确认方案**：参考图优先，文字降级为辅助

**当前逻辑**（问题）：
```typescript
// reference-prompt.util.ts:131
APPEARANCE: character.appearance || REFERENCE_PROMPT_DEFAULTS.appearance
```

**改造后**：
```typescript
// 有参考图时
APPEARANCE: "参考图片中的角色"  // 简短指向
ADDITIONAL_NOTES: character.appearance  // 补充细节

// 无参考图时
APPEARANCE: character.appearance  // 保持原样
```

### 决策 4：槽位合并（暂不实施）
**确认方案**：不做槽位结构化解析

**理由**：
- 稳妥路线专注"图为王"
- 槽位合并属于方案 2（创新路线）
- 如果"图为王"效果好，槽位合并的需求会降低
- 保持 `appearance` 为纯文本字段，简单追加合并即可

**简化合并逻辑**（如需要）：
```typescript
// 只做简单追加，不做结构化
const nextAppearance = existing.appearance 
  ? `${existing.appearance}；${description}`
  : description;
```

### 决策 5：全书扫描（暂不实施）
**确认方案**：不做全书扫描

**理由**：
- 全书扫描属于方案 1（创新路线）
- 稳妥路线先验证"图为王"的效果
- 如果效果好，再考虑全书扫描增强

### 实施优先级（稳妥路线）

**阶段 1（数据模型）- 0.5 天**：
- 建 CharacterStage 表
- 增加 Character.anchorAssetId 字段
- 编写 migration

**阶段 2（生图改造）- 0.5 天**：
- 修改 buildCharacterReferencePrompt，参考图优先
- 修改 buildCharacterReferenceStyleGuide，适配新逻辑
- 测试有图 vs 无图的提示词差异

**阶段 3（阶段 CRUD）- 1 天**：
- CharacterStage CRUD 接口
- 新增阶段时基于上一阶段图垫图生成
- 分镜生图时按章节选择对应阶段的图

**阶段 4（交互式定妆）- 1 天**：
- 角色库显示"待定妆"状态
- "定妆"按钮 → 生成 3 张候选
- 选择后存为 anchorAssetId
- 首次生成参考图时智能提醒

**阶段 5（测试与复核）- 0.5 天**：
- 验证主角定妆流程
- 验证阶段切换流程
- 验证生图质量提升

**总计：3-4 天**

## 8. 风险与缓解

### 风险 1：槽位 AI 解析不稳定

**风险**：AI 可能无法稳定输出结构化槽位，或输出格式不一致

**缓解**：
- 使用严格的 JSON Schema 强制结构化输出
- 如果失败，回退到纯文本合并（简单字符串拼接）
- 槽位解析失败不阻塞流程，只降级为"无槽位"模式

### 风险 2：阶段爆炸

**风险**：2574 章的项目可能产生几百个阶段，管理成本高

**缓解**：
- 冲突检测设置合理阈值，减少误报
- 阶段列表分页显示，不一次性加载全部
- 提供"合并阶段"功能，允许用户事后整理

### 风险 3：垫图质量不稳定

**风险**：editImage 换装的质量可能不稳定（之前吐槽过）

**缓解**：
- 阶段图生成支持"重新生成"（不满意可以重抽）
- 保留上一阶段图作为 fallback
- 文档中明确标注"阶段图也需要抽卡"

### 风险 4：全书扫描性能

**风险**：全书扫描可能很慢（几千章 × 几十个角色）

**缓解**：
- 异步后台执行，不阻塞主流程
- 按角色分批扫描，不是一次性扫全部
- 扫描结果缓存，不重复扫描同一角色

### 风险 5：旧数据兼容

**风险**：现有项目升级后可能出现字段缺失或格式错误

**缓解**：
- 所有新字段设置为可选（nullable）
- 读取旧数据时用 normalize 函数兜底
- 提供数据修复工具（如果发现问题）
