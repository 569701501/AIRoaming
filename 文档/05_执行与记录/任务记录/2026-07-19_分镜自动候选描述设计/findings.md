# 发现：分镜自动候选描述设计

## 代码事实

1. `ImageCandidatesWorkspace.createPromptDraft()` 默认依次读取：
   - 画面：`shot.comic.panelDescription`，只有它为空才回退 `shot.promptDraft`。
   - 动作：`shot.coreAction`。
   - 构图：`shot.comic.composition`，为空才回退 motion 构图。
2. 因此候选图页面不是缺少字段，而是正式分镜里的三段内容仍偏基础；用户不点 AI 优化时，页面只能原样继承基础内容。
3. `storyboard-shot-generate` 已要求单地点、单时刻、单机位和多人关系，但同一次模型调用还承担拆 beat、对白、漫画和 motion，多目标负载下不能稳定保证候选图描述的细度。
4. `assertStoryboardQuality()` 适合拦截明确错误，不适合用大量中文关键词硬判审美细节是否充分。
5. 现有 `shot-prompt-optimize` 是单镜、Preflight 后、用户显式触发的持久任务；直接在生成分镜时为每镜创建该任务会被 NewWorkGate 阻断，并产生 N 个任务与部分完成问题。
6. 分镜生成有两条生产路径：`StoryboardDialogueService.generateStoryboardWithAI()` 与 `PersistentTaskWorkerService.runShotProvider()`；新逻辑必须共用，不能只修页面主路径。
7. `promptDraft` 是单字符串且当前不是候选图三段事实源；把结构化三段 JSON 塞进它会破坏现有语义和可读性。

## 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 只加强第一次分镜 Prompt | 最省时、省调用 | 当前 Prompt 已很详细，真实结果仍会变薄；拆镜与视觉润色互相抢注意力 | 不足以单独解决 |
| 自动为每镜创建优化任务 | 复用现有能力 | 必须等 Preflight；N 次调用、N 个任务、可能部分成功 | 不采用 |
| 同一生成动作内做章节级第二段 | 专门处理详细度；一次用户操作；保存前可整体校验 | 增加一次文本调用和等待时间 | 推荐 |
| 新增平行 `candidateBrief` 对象 | 语义最显式 | 与现有三字段重复；编辑和上游变化后容易漂移 | 首版不采用 |

## 推荐流程

```text
用户点击生成分镜
  -> 第一段：拆镜与漫画/漫剧骨架
  -> 严格结构与剧情忠实检查
  -> 第二段：全章漫画视觉描述整理
  -> 只合并画面 / 动作 / 构图
  -> 再做固定问题与来源忠实检查
  -> 整体写入待确认分镜
  -> 用户确认
  -> 候选图工作台直接得到详细默认描述
```

## 失败与安全边界

- 第二段最多自动修复一次。
- 失败不得保存半章或覆盖旧 pending。
- 错误必须指出具体镜头序号和问题，而不是只显示内部错误。
- 第二段不得添加角色、道具、场景、剧情结果或对白，也不得改 motion。
- 图片 Provider、参考图编排和尺寸仍只在候选图阶段发生。

## 残留问题

- 用户已接受“生成分镜多等待一次文本调用，换取所有镜头默认描述更完整”的取舍。
- 首版采用整章一次整理，当前目标镜头范围通常为每 beat 一至两镜；超长章节的分组策略后置，但即使未来分组，对用户也必须保持一次动作和整体提交。

## 实施发现

1. 共享整理器位于 `apps/server/src/dialogue/storyboard-visual-brief.util.ts`，Dialogue 和持久 worker 均复用。
2. 第二段严格输出只有 `order/visualDescription/action/composition/promptDraft`；后端按构造方式冻结其他字段。
3. 字段细度、镜头一一对应、绑定角色点名、人类多人总数、群体范围、文字/跨地点/多时刻/不可见信息均在保存前检查。
4. 分镜骨架和详细说明各有一次独立定向返修预算；详细说明返修仍失败时不保存 pending。
5. 真实候选图页面已显示“生成分镜时已自动整理，可继续微调”“重新优化本镜头”“采用返修结果”，浏览器 error/warn 日志为空。
6. 历史正式分镜不会自动改写；页面实测中的旧镜头仍可能显示旧薄描述或旧问题，只有重新生成的新 pending 才应用新流程。
7. 端到端测试发现并修正 fake provider 对确认后 `beat.characters` token 的兼容：名称、本地结构 ID 和 `projectCharacterId` 都必须映射回结构角色，否则会产生空角色绑定；修正后完整三次文本调用链通过。
8. Scrutiny Review 发现双人输出示例漏写显式总人数，与后端硬规则冲突；示例已改为“林舟与许澄两人”，并增加资产测试保护。

## 实施阶段结论

采用“同一 `shot_generate` 内两段处理、整体 pending、单镜返修后置”的方案。实现、静态复核、真实页面复核和项目留痕均已完成；真实模型质量 A/B 与超长章节分组保留为后续证据驱动工作。

## 真实模型回归新增发现

1. “杀令入棺”重新生成在分镜骨架返修后失败，第二段详细说明未执行；旧正式分镜未被覆盖，原子失败边界有效。
2. 失败的 5 镜并没有地点切换，唯一共同命中项是构图用 `A→B→C` 表示阅读动线。
3. `storyboard-quality.util.ts` 当前把 `coreAction + panelDescription + composition` 合并后使用同一个 `PANEL_LOCATION_TRANSITION`，其中裸 `→` 同时承担了“地点跳转”和“构图阅读路径”两种含义。
4. 推荐修正是分域校验：内容字段继续拒绝裸箭头或地点转换词；构图字段允许箭头表达空间阅读动线，但仍拒绝“切到/转到/来到”等真实地点转换语言。不能简单删除全部地点切换检查。
5. 中文数量表达必须兼容“二人”和“两人”；人物数量冲突只与 `entityType=human` 的主体比较，creature/group 不得混入人类总数。
6. 固定章节正文常用“人物：（表演提示）「台词」”。逐字候选编译必须去掉冒号后的行首表演提示和成对外层引号，只保留真正可配音原句，否则模型正常输出台词正文也会被误判为改写。
7. 结构中的“字迹、屏幕数字、标牌内容”可以是剧情事实，但静态生图字段不能要求生成可读文字；生产 Skill 应把它翻译为正式事实已有的符位、光效、道具状态和人物可见反应，准确对白/旁白留在语义字段。
8. DB 同时存在正式 current 与新 pending Storyboard 时，候选图工作台只能投影 current 文档中的 Shot；按章节扫描所有 active Shot 会把 pending Shot 拿去匹配 current 文档并触发 `SHOT_NOT_FOUND`。
9. 最终真实输出为 12 镜 pending，第一段与第二段均一次通过；五类代表镜头在页面展开后均显示完整画面与构图，说明自动详细说明已进入真实用户路径。

## 群体范围失败新增发现

1. `entityType=group` 的角色名只说明“这是一个群体身份”，不等于镜头已说明人数或范围；因此“商队众人”必须继续被固定门拦截，不能通过放宽校验解决。
2. 首次 Prompt 虽有全局群体规则，但模型在长章节中仍可能遗漏某个镜头；后端应把已知道的绑定事实编译成逐镜小清单，不应让模型再做一次 ID→类型→数量规则的反推。
3. 一次返修只透传 `VISUAL_BRIEF_VISUAL_GROUP_COUNT_MISSING:shots[12]` 不够；返修 Prompt 需同时说明数组下标语义、需改的字段、必须保留的 group 名和不得虚构精确人数的边界。
4. 群体范围提取不能只枚举“商队成员”等通用名词；应用实际绑定 group 名构造安全识别，使“一群商队众人”可编译为 `groupCountHint=一群`。
5. 新的真实运行在详细说明首次 JSON 截断后使用一次整章返修成功；最终群体镜头全部带中性范围，pending 仍在用户确认门前，说明修复没有改变原子写入与确认边界。

## 最终结论

真实模型与真实页面验收再次通过。当前结果在事实覆盖、多人点名、群体范围、空间关系和画内文字隔离上满足硬门；部分多人句式仍带有“几人与一队/一群”的规则化表达，属于后续多样例审美评测项，不阻塞本次自动详细说明链路。
