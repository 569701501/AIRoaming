# 多角色镜头视觉引用方案复核计划

## 1. 目标

复核“把本镜头全部角色拼成一张多人角色参考板，再单独传场景图”是否应成为统一默认方案，并在现有角色、场景资产和三家图片 Provider 约束下，形成更稳妥、可追溯、可分阶段实现的推荐策略。

## 2. 非目标

- 不修改生产代码、数据库 Schema、页面字段或 Prompt。
- 不调用 OpenAI、豆包、Grok 等付费图片接口。
- 不宣称未执行的视觉质量 A/B 已通过。
- 不把角色 LoRA/Multi-LoRA 训练提前放入当前 P0。

## 3. 强制验收标准

- 至少比较：独立多参考、静态多人角色板、镜头感知合成/构图板、分层区域编辑、角色模型训练。
- 分开处理 `identity`、`environment`、`composition` 三类视觉约束，不能只解决引用图片张数。
- 给出 OpenAI、豆包、Grok 的明确编译规则和不兼容边界。
- 任何必需角色或场景都不得静默省略；容量不足时必须打包、换工作流、换 Provider 或阻止任务。
- 区分“节省图片槽位”和“节省图像输入 token/成本”，不做跨 Provider 的无证据承诺。
- 完成静态复核；运行/用户路径复核如未执行，必须明确记录为 `not_run`。

## 5. 阶段

### O1：Orchestrator 事实核对

状态：`complete`

- 读取产品、架构、任务、素材和模块事实源。
- 核对当前 `Shot`、角色视觉、场景视觉、CandidateGenerationSpec 和 Provider 上限。
- 复用 2026-07-17 真实图片 A/B，避免用推测覆盖已有证据。

### W1：Worker 候选方案比较

状态：`complete`

- 比较不同参考封装对身份、场景、构图、成本和实现复杂度的影响。
- 识别静态多人板的适用边界和潜在副作用。
- 形成按人数、镜头重点和 Provider 能力变化的自适应策略。

### W2：Worker 契约与落点

状态：`complete`

- 定义 Provider 无关的视觉需求与 Provider 编译后引用计划。
- 明确任务级派生参考、来源覆盖、缓存摘要和失败处理。
- 给出 P0/P1/P2 分阶段顺序。

### S1：Scrutiny Review

状态：`complete`

- 只读检查方案是否和现有事实源、任务来源追溯、素材路径及真实 A/B 证据冲突。
- 检查是否仍存在静默遗漏、伪质量承诺或不必要的数据模型扩张。

### R1：Runtime/User Review

状态：`not_run`

- 本轮不调用图片 Provider；记录为 `not_run`。
- 固定未来最小 A/B 语料、评分项和预算边界，不能用离线检查替代视觉验收。

## 6. 回滚与安全边界

- 本轮只修改 Markdown 留痕；如结论未获采用，可回退文档而不影响运行态。
- 不读取、输出或修改图片 Provider 凭据。
- 不触发已有项目的 GenerationTask，不改角色、场景、候选或定稿关系。

## 7. 最终结果

- 方案从“2 人以上统一合板”深化为按人数、焦点、构图和 Provider 能力变化的自适应 `ReferencePlan`。
- Grok 0～2 人优先独立参考；三人以上使用全员身份板或“焦点单图 + 其余角色板”，场景始终保持视觉覆盖。
- 构图在当前阶段如实保留为文字约束；结构化站位和场景构图板后置 P1，区域修复后置 P2。
- 静态复核为 `pass_for_design`；真实视觉 A/B 为 `not_run`，本轮 Provider 图片请求为 0。
