# 探索发现

## 1. 当前项目事实

- `Shot` 已保存 `coreAction` 和自由文本 `comic.composition`，但没有逐角色的结构化站位、景深、朝向、动作职责或画面重要度字段。
- 候选 Prompt 已把构图和动作写入文字合同；图片引用只有 `character_identity` 与 `scene_environment` 两类，当前没有独立的构图/布局图片通道。
- OpenAI、豆包、Grok 当前本地适配上限分别为 16、10、3。Grok 超限时固定保留两个角色和一个场景，第三个角色会被省略。
- 本项目已有角色 `preview_front`、四要素 `final_reference` 和无人场景参考。候选图合同禁止把完整四视图设定表直接作为 edit 底图。
- Server 目前只有 `pngjs`，角色/场景资产主要是 WebP；若做确定性裁切、缩放、合成和 WebP 输出，需要补齐图片处理能力。

## 2. 已有运行证据

- 2026-07-17 四人群像真实 A/B 中，豆包 2/2 只生成三人；Grok 虽按文字生成四人，但 2/2 省略两名角色的图像参考，因此只能判“人数和站位可见，身份锁定不完整”。
- Grok 的无人场景镜头因本地单参考比例策略 2/2 舍弃场景图，实际空间漂移；这证明必需条件改成纯文字会真实损失一致性。
- 双人镜头仍出现动作主客体反转和一次斜切分格，说明“角色与场景都入图”也不是构图和叙事关系的充分条件。

## 3. 市场事实

- 容量足够时，OpenAI、Seedream、Runway、Vidu 等产品/模型倾向保留独立命名参考。
- 容量受限时，Midjourney 官方建议把多人放进同一张参考图；这证明多人打包是合理兼容策略，但不是行业唯一默认。
- Runway/Seedream 等另用 Sketch、箭头、线框或构图参考表达站位；Adobe、Ideogram、Scenario 用选区/Mask 只修失败角色并保护已正确区域。
- Boords/LTX 把用户操作提升为角色、地点、道具等可复用实体，底层按工作流编译，而不是让用户手工管理模型图片槽位。

## 4. 初步判断

- 静态多人角色板确定能压缩图片槽位，但会降低每个角色的有效像素，并引入“设定表/拼贴/排队站立”的先验；它不应在 1～2 人且独立参考本来就能完整传入时强制使用。
- 更完整的问题不是 `N 张图如何塞进上限`，而是如何同时覆盖：谁是角色、角色站在哪里、场景是什么。
- 推荐方向应从“统一多人板”升级为“Provider 无关视觉需求 + 自适应引用编译 + 失败后区域修复”。

## 5. 方案比较

| 方案 | 角色身份 | 场景 | 构图/动作绑定 | 图片槽位 | 主要风险 | 建议位置 |
| --- | --- | --- | --- | ---: | --- | --- |
| 独立角色图 + 场景 | 高 | 高 | 主要靠文字，可另加构图图 | `N+1` | 超上限、输入成本随图片增长 | 容量足够时首选 |
| 静态全员身份板 + 场景 | 中 | 高 | 主要靠文字 | 2 | 单人像素下降、排队/拼贴先验 | 容量不足时兼容路径 |
| 焦点单图 + 其余角色板 + 场景 | 焦点高、其余中 | 高 | 主要靠文字 | 3 | 需要可靠判断焦点 | Grok 多人镜头的实用混合路径 |
| 身份板 + 场景构图板 | 中 | 高 | 高 | 2～3 | 构图标记可能泄漏；依赖结构化站位 | P1 A/B 方向 |
| 全角色直接贴入场景的镜头合成图 | 中到高 | 高 | 高 | 1 | 当前角色参考多为中性姿态且无透明底，容易把错误姿态、矩形底和拼贴感一起传给模型 | 不作为 P0 默认；有可靠抠图/姿态资产后再试 |
| 选整体候选后逐角色 mask 修复 | 高 | 保护已正确场景 | 高 | 多次请求 | 成本、延迟、Mask 交互 | 关键镜头质量保险 |
| LoRA/Multi-LoRA/ID Adapter | 长期角色可高 | 仍需场景通道 | 仍需构图通道 | Provider 相关 | 训练数据、绑定和维护成本 | 真实高频核心 IP 后置 |

## 6. 最终设计判断

- 最佳默认不是“永远一张多人板”，而是 `auto` 自适应编译：0～2 人优先独立参考；三人以上或槽位/输入预算不足时使用全员板或“焦点单图 + 其余角色板”。
- Grok 三人同等重要时可用“全员身份板 + 原始场景 + 构图板”；有明确焦点时可用“焦点单图 + 其余角色板 + 场景构图板”。当前没有结构化站位时，构图只能如实标记为 `prompt_only`。
- OpenAI/Seedream 在完整条件能放入容量时优先独立直传，不为跨 Provider 表面统一而主动降低身份分辨率。
- 不把所有角色、场景和构图压进一张巨型参考图；除非 Provider 只有一个图片入口，至少保持身份与场景/构图两个物理通道。
- 单板人数上限由“每个角色最小可读像素 + 景别 + 重要度”的 Provider A/B 决定，不使用一个未经验证的全局固定人数。
- 一次生成失败后不继续全图抽卡；关键镜头进入基于已选 `shot_master` 的单角色区域修复。
