# 代码事实

1. `reference-prompt.util.ts` 当前负责角色预览、角色定稿和场景参考图 Prompt。
2. `candidate-generation-spec.ts` 当前把分镜、角色、场景和画风组装为候选图 Prompt。
3. `image-prompt-profile.util.ts` 当前三个 Provider Profile 的最终文案相同，没有真正按模型能力做适配。
4. 旧 A/B 暴露出的水印、比例和参考图上限属于 Provider 参数/能力适配问题，不能单靠增加 Prompt 字数解决。

# 初步公开资料方向

| 来源 | 准备吸收的方法 | 使用边界 |
| --- | --- | --- |
| OpenAI 官方图像生成指南 | 多图输入、参考保真、明确编辑/生成意图、构图与约束表达 | 只用于 OpenAI Profile 和通用方法，不假定其他模型参数相同 |
| 火山引擎 Seedream 官方指南 | 连贯自然语言、主体/行为/环境、风格/色彩/光线/构图、应用目的 | 用于 Doubao Profile，不复制网传系统提示词 |
| xAI 官方图像文档 | 模型支持的生成、编辑、比例、分辨率和批量能力 | 只采用官方明确能力；参考图上限必须按实际 API 处理 |
| Midjourney 官方参考图文档 | 明确身份锚点、参考强度与风格竞争、不要依赖参考图自动补全细节 | 作为方法论，不把 Midjourney 参数写进当前 Provider Prompt |
| StoryDiffusion 官方仓库/论文 | 连续画面角色一致性、多角色长序列的一致性问题 | 作为工作流与评测参考，不把模型专有实现伪装成普通 Prompt 能力 |
| ComfyUI 官方 Area Composition 示例 | 多人物区域布局、主体串色和位置污染的控制思路 | 作为布局合同与测试设计参考；当前 API 无区域控制时要明确能力缺口 |

# 初步结论

- 需要设计“共享内容合同 + 任务类型模块 + Provider Profile”，而不是一条越来越长的万能 Prompt。
- 参考图必须声明角色：角色身份、场景空间、画风，不应让模型自行猜测每张图的用途。
- 多人物镜头要明确人物数量、左右/前后位置、动作关系和不可合并身份；当 Provider 参考图上限不足时，应由编译策略降级或阻断，而不是静默丢图。
- 无文字、无水印、无界面、无分格污染需要成为可测试的成图合同；但 Provider 自带水印参数必须在请求层关闭，Prompt 不能替代参数修复。

# R2 调研结论

完整来源对照、采用/拒绝清单、V2 Prompt 包、三 Provider 差异与固定评测设计，见：

`文档/04_方案与决策/2026-07-17_图片Prompt专业化调研与V2设计依据.md`

新增关键事实：

1. xAI 官方多图编辑上限为三张；当前 Grok 参考图预算必须据此显式排序或阻断。
2. 当前 Grok 单参考图被丢弃是本项目适配器为保留目标比例做出的选择，不是 Prompt 缺陷；V2 必须显式处理。
3. 火山引擎图片 API 的 `watermark` 是请求参数；当前固定开启水印与干净画面合同冲突。
4. StoryDiffusion 的长序列一致性主要来自专用机制，不能把示例 Prompt 当作一致性秘诀。
5. AI Comic Factory 值得吸收“逐格结构、稳定人物描述、文字与画面分离”，但不采用通用质量词堆砌和一次生成完整漫画页。
6. OpenAI、Seedream 和 xAI 对复杂指令与多参考图的表达习惯不同，三个 Profile 不应再共用同一最终字符串。

# R3 实现结论

1. 为保持真实 A/B 可比性，旧领域 `positivePrompt` 和三个 V1 直通 Profile 没有删除；V2 从同一 `sections + systemConstraints` 编译，不让测试手工复制第二套业务 Prompt。
2. 新任务默认使用 V2 Profile；DB 任务仍冻结 provider 类型、profile 和实际投递文本，历史任务不会被运行时替换。
3. 角色/场景参考模板默认 V2，但可显式生成 V1；参考资产、候选图和 Provider Profile 均有固定回归。
4. 双人合同明确动作发起者、承受者和反应者；多人合同明确准确人数、逐人一次、站位和职责；无人物合同排除路人、剪影与人形倒影。
5. 条件式特效合同只规定存在光效/天气/电力等事件时的来源、影响和主光关系，不要求普通镜头凭空增加特效。
6. Provider 实际参考图选定后才追加 Reference Roles，避免 Prompt 声称使用了随后因上限被裁掉的图片。
7. Doubao 水印和候选比例属于请求层修复，已与内容 Prompt 一起进入离线回归，但仍在文档中和 Prompt 质量分开记录。
8. Grok 单参考图问题仍是明确残留风险；R3 没有通过复制参考图或引入空白图等未经真实验证的方法规避。

# R4 静态复核结论

1. R3 的领域字段和五类镜头合同成立，生产页面字段与数据库 Schema 没有变化。
2. 5 个固定案例可以稳定编译 15 份 V2 Provider Prompt，三 Provider 文案不同且均未直通旧 `positivePrompt`。
3. 当前真实图片 A/B CLI 没有版本参数，调用 `compileImagePromptBaseline(suite)` 时会使用默认 V1；这是进入付费测试前的硬阻断。
4. OpenAI/Grok 的动态镜头合同仍沿用中文字符串前缀，说明 Provider 语言编译尚未完全收口；不应把中文前缀继续当作长期内部协议。
5. Grok 单参考图省略会使无人场景案例失去场景参考，属于 Provider 能力/比例策略差异，R5 评分必须单独标记，不能错误归因于 Prompt。
6. 参考资产 V2 目前仍是共享英文模板；候选图 Provider Profile 已适配，但参考资产 Provider Profile 是后续闭环项。
7. R4 结论为 `NOT_READY_FOR_PAID_AB`，R5 不放行；先进入 R4.1 修正测试入口与动态合同编译。

# R4.1 返工结论

1. `AIROAMING_SHOT_CONTRACT_V2` 作为内部结构化镜头合同替代中文前缀协议；合同继续存放在现有 `systemConstraints` 中，因此没有新增页面字段或数据库 Schema。
2. OpenAI/Grok 的镜头合同使用英文，Doubao 使用中文；固定语料 15 份 V2 Prompt 均不再出现旧中文合同前缀。
3. 真实测试入口强制显式选择 `v1|v2`，版本缺失时失败；两个版本的账本、槽位、目录和摘要完全隔离。
4. V1/V2 各有 15 条最终 Prompt manifest、30 个待执行槽位；两版 Prompt SHA-256 无重合，dry-run 真实请求均为 0。
5. Grok 单参考场景和群像三图上限已转为运行报告中的显式评分例外，必须由对应 warning 触发。
6. R4.1 离线门禁通过，状态提升为 `READY_FOR_USER_COST_AUTHORIZATION`；完整 R5 上限为 60 次请求，仍需用户明确同意。

# 预算决策

1. 用户明确要求停止生成图片，当前不得执行 V1/V2 真实图片 A/B。
2. R5 状态改为预算延期；已有 dry-run 账本不执行、不重试、不产生费用。
3. V2 当前只能表述为“代码与离线合同通过”，不能表述为“真实成图质量通过”。
4. 后续采用离线收口：保留 V1 回退能力、复用既有旧图片作为历史问题证据，但不把旧图冒充 V2 结果。

# 待重写 Prompt 包

## A. 参考资产

1. 角色预览图 Prompt：单角色身份锚点、清晰脸部/发型/服装与可复用中性呈现。
2. 角色定稿组合图 Prompt：正面半身、正面全身、侧面全身、背面全身，同一角色同一服装与比例。
3. 场景参考图 Prompt：空间关系、稳定地标、出入口、光线方向和禁止人物抢主体。

## B. 漫画静态候选图

1. 共享单格成图合同：只生成一个完整漫画格，不生成拼贴、分格、UI、字幕、水印或对话框。
2. 无角色环境建立镜头模块。
3. 单人情绪/动作镜头模块。
4. 双人对话/对抗镜头模块。
5. 多人调度镜头模块。
6. 动作、光效、环境特效镜头模块。

## C. 参考图与 Provider 编译

1. 参考图角色清单：逐图声明角色身份、场景空间或画风用途。
2. 必须保持项与允许变化项：身份、服装、人物数量、空间、构图和风格分别控制。
3. OpenAI Profile：利用多图逐图声明和高保真参考能力。
4. Doubao/Seedream Profile：采用中文连贯自然语言、明确用途和多图对象关系。
5. Grok Profile：按官方比例/分辨率与编辑能力编译，能力不足时显式降级或阻断。

## D. 漫剧独立包（不与漫画静态 Prompt 混用）

1. 漫剧起始关键帧 Prompt。
2. 漫剧结束/承接关键帧 Prompt。
3. 图生视频动作、表演和运镜 Prompt。

本轮优先完成 A～C；D 作为独立后续阶段设计和测试。

# 初步来源验证

- OpenAI 官方指南建议按“背景/场景 → 主体 → 关键细节 → 约束”稳定组织生产 Prompt，明确构图、人物尺度/视线/动作、需要保持的内容，并逐张说明多图输入的用途。
- Seedream 官方指南建议使用简洁连贯的“主体 + 行为 + 环境”，再补风格、色彩、光影和构图；明确图片用途，并在多图输入中说明每张图承担的对象和操作。
- xAI 官方文档把比例、分辨率、多图编辑等作为明确 API 能力，因此这些问题必须由 Provider 参数/Profile 共同处理，不能全部塞进通用文案。
- Midjourney 官方参考图文档强调参考图仍需配合详细文本，复杂细节不会自动精确保持；该原则可用于身份锚点设计，但 Midjourney 专有参数不会写入当前 Provider。
- StoryDiffusion 官方仓库将长序列角色一致性作为专门的注意力/工作流问题，说明连续漫画一致性不能被错误表述为“一条神奇 Prompt 就能解决”。
