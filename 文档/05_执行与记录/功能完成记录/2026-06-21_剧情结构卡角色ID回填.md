## 1. 功能摘要

剧情结构卡的 `StoryStructureCharacterCard` 新增 `projectCharacterId` 字段。用户确认剧情结构时，后端按角色名匹配/新建项目角色后，把项目角色 id 回填到结构卡，作为结构卡到项目角色库的稳定外键。详见 `文档/04_方案与决策/ADR-0006_剧情结构卡角色ID回填方案.md`。

## 2. 影响范围

- 类型契约：`packages/shared/src/dto.ts`（前后端共享类型源头）。
- 后端：`apps/server/src/projects/projects.service.ts`、`apps/server/src/dialogue/dialogue.service.ts`。
- 数据：`workspace/projects/{id}/chapters/{slug}/structure.json` 中 `characters[]` 每个元素新增 `projectCharacterId` 键。
- 前端：零改动（加字段向后兼容，已验证）。

## 4. 数据或协议变化

- `StoryStructureCharacterCard` 增加 `projectCharacterId: string | null`。
- `schemaVersion` 保持 1，不升级。旧 `structure.json`（无此字段）重读时由 normalize 补 null，不报错。
- `syncStoryStructureCharacters` 返回类型从 `LocalProject` 改为 `{ project: LocalProject; structureJson: StoryStructureJson }`，仅 `confirmChapterStoryStructure` 一处调用，已同步接线。
- AI 生成剧情结构时 prompt 明确约束不输出 `projectCharacterId`，该字段一律由后端回填。

## 5. 验证命令与结果

### 5.1 静态验证（Scrutiny Review）

| 命令 | 结果 |
| --- | --- |
| `corepack pnpm typecheck` | ✅ 三个包（shared / server / web）全部通过 |
| `corepack pnpm build` | ✅ 三个包构建成功，web 产物正常生成 |

边界检查：
- 空名角色（`card.name` 为空）：`if (!rawName) return` 跳过，`nextCards[index]` 保持 normalize 给的 `projectCharacterId: null`，不报错。
- id 回填独立于角色库变更：放在 `if (existing)` 分支的 hasChanges 判断之前，旧结构重新确认时即使角色库无变化也能补全 id。
- 浅拷贝不污染入参：`nextCards = structureJson.characters.map(card => ({ ...card }))`，回填的是新对象。

### 5.2 运行时验证（Runtime/User Review）

**未执行**：本次改动未做真实页面运行验证，原因与残留风险见第 7 节。需用户在本地跑 `corepack pnpm dev` 后按以下场景手动验证：

1. 新建项目 → 写剧本 → 完成本章 → 生成剧情结构（pending 预览，`projectCharacterId` 应为 null）→ 确认结构 → 检查 `workspace/projects/{id}/chapters/chapter-001/structure.json`，每个 character 应带 `projectCharacterId: "char_xxx"`。
2. 确认后检查项目角色库：自动建出对应角色，角色 id 与结构卡 projectCharacterId 一致。
3. 第 2 章重复同一角色：确认后结构卡 projectCharacterId 应与第 1 章相同（靠 name 匹配到同一角色）。
4. 旧 structure.json 兼容：把无 projectCharacterId 的旧文件放进项目重启，应正常读取；重新确认后应回填 id。
5. 前端回归：剧情结构页正常显示、字段级编辑（笔图标）保存后 projectCharacterId 不丢失。

## 6. 已知风险

- **运行时未验证**：项目当前无自动化测试套件，本次只完成静态构建验证，真实数据落盘和前端回归依赖用户手动确认。
- **角色档案编辑能力缺失**：后端 `PATCH /projects/:projectId/characters/:characterId` 已支持改 name/role/level 等，但前端无编辑档案 UI（`updateProjectCharacter` 事件链路是死代码）。本次不补，记录为已知限制。后续如放开角色名编辑，需同步更新所有章节结构卡里的 name，否则跨章节 name 关联会断。

## 7. 后续建议

- 补一次真实运行时验证（按第 5.2 节场景），确认落盘 structure.json 带 id、角色库 id 一致。
- 视产品需要，单独立项做"角色档案编辑页"，接通已存在的后端能力。
- 若后续要让前端按 projectCharacterId 做结构卡→角色详情直查，需改 `StoryStructureWorkspace.vue` 的 name 匹配 Map（当前 L371/381 按 name 建 Map）。
