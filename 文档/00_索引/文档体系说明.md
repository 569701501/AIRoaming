## 1. 设计目标

AI漫游的文档体系要解决四个问题：

- 让项目从原始种子开始可以逐步长大，而不是靠聊天上下文续命。
- 让 AI 每次进入项目时知道先读什么、信什么、改哪里。
- 让有持续价值的功能从计划、实现、验证到完成都有记录。
- 让产品、架构、协议和执行记录分层存放，避免同一个问题散落多处。

## 2. 文档分层

### 2.1 长期事实源

长期事实源描述“当前系统是什么”。它们应该被持续维护，而不是按日期堆叠。

| 分区 | 内容 |
| --- | --- |
| `01_愿景与产品` | 产品定位、用户、流程、MVP、范围边界 |
| `02_架构与契约` | 架构、数据模型、任务协议、路径契约 |
| `03_模块梳理` | 模块职责、依赖、主流程、接口边界 |

### 2.2 方案与决策

方案与决策描述“为什么这样做”。它们允许按日期和主题沉淀，因为决策过程本身有历史价值。

| 分区 | 内容 |
| --- | --- |
| `04_方案与决策` | 功能方案、ADR、技术选型、风险评估 |

### 2.3 执行与证据

执行与证据描述“做了什么、测了什么、还剩什么”。它们是功能留痕的主体。

| 分区 | 内容 |
| --- | --- |
| `05_执行与记录` | 任务计划、进度、发现、完成记录、里程碑 |
| `06_测试与验收` | 验收策略、测试报告、截图、样例输出、回归记录 |

### 2.4 模板、归档与原始来源

模板服务后续复制，历史归档和原始来源保留项目演进脉络。

| 分区 | 内容 |
| --- | --- |
| `90_模板` | 功能方案、任务记录、完成记录、模块梳理模板 |
| `98_历史归档` | 被推翻的试错、旧规则、已不再默认阅读的历史材料 |
| `99_原始种子` | 最初种子文档、早期未展开草稿 |

## 3. 文档状态枚举

| 状态 | 含义 |
| --- | --- |
| `draft` | 草案，尚未成为事实源 |
| `active` | 当前有效事实源或规则 |
| `in_progress` | 正在执行或验证 |
| `superseded` | 已被新文档替代，保留历史 |
| `archived` | 归档，仅供追溯 |

## 4. 文档命名规则

| 文档类型 | 命名 |
| --- | --- |
| 长期事实源 | 使用清晰中文名，不加日期，例如 `核心数据模型.md` |
| 方案文档 | `YYYY-MM-DD_<主题>_方案.md` |
| ADR | `ADR-0001_<决策名>.md` |
| 任务目录 | `YYYY-MM-DD_<任务短名>/` |
| 完成记录 | `YYYY-MM-DD_<功能名>.md` |
| 验收报告 | `YYYY-MM-DD_<功能名>_验收报告.md` |

## 5. 单一事实源规则

- 当前产品范围只以 `01_愿景与产品` 为准。
- 当前技术契约只以 `02_架构与契约` 为准。
- 当前模块边界只以 `03_模块梳理` 为准。
- 历史方案、历史归档、原始种子、聊天记录不能直接覆盖当前事实源。
- 如果历史文档与当前事实源冲突，以 `status: active` 的事实源为准。

## 6. 何时需要新建文档

| 场景 | 动作 |
| --- | --- |
| 新功能从想法进入正式设计 | 新增方案文档或任务记录 |
| 有重大取舍不可轻易逆转 | 新增 ADR |
| 复杂功能开始开发 | 按需新增任务三件套 |
| 有持续价值的功能完成 | 新增功能完成记录 |
| 数据模型、任务协议、路径变化 | 更新对应长期事实源 |
| 测试或验收完成 | 新增验收报告或在任务记录中补证据 |

普通讨论、小修、被推翻的页面试错不强制新增正式记录；需要保留时放入 `98_历史归档`。
