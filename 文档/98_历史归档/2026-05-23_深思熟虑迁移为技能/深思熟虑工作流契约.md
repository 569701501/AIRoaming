## 1. 目标

“深思熟虑”不是单纯使用更强模型，也不是多写一段计划。它是一套适合复杂任务的执行协议：先明确事实源，再拆阶段，再执行，再复核，再留痕。

AI漫游引入该协议后，复杂任务必须做到：

- 不靠聊天记忆推进。
- 不把计划、过程、发现和完成结果混在一个文档里。
- 不在验证前宣称完成。
- 不让一个执行者同时承担实现、审查和验收三种角色。
- 每次阶段推进都有证据、阻塞原因或用户确认点。

## 3. 适用场景

以下任务必须使用深思熟虑工作流：

| 场景 | 例子 |
| --- | --- |
| 跨模块功能 | 故事到分镜、图片候选、排版导出 |
| 影响数据模型 | 新增 Project/Shot/Asset/Task 等表 |
| 影响任务协议 | 新增或修改生成任务输入输出 |
| 影响素材路径 | 改 workspace 目录、导出包、manifest |
| 需要 UI + 后端 + 文件系统 | 漫画图候选生成与选择 |
| 需要真实验收 | 导出 PNG/PDF/MP4、端到端流程 |
| 用户明确说“深思熟虑” | 直接进入该协议 |

以下任务可以不使用完整协议：

- 单个文案修正。
- 单份文档小改。
- 无状态的小样式修正。
- 一次性查询或解释。

## 4. 核心模型

AI漫游采用简化版三角模型：

```text
Orchestrator（当前主 Agent）
  -> 读取事实源
  -> 建立任务记录
  -> 拆分阶段
  -> Worker 执行阶段
  -> Scrutiny Review 静态复核
  -> Runtime/User Review 运行或用户路径复核
  -> 更新事实源
  -> 写完成记录
```

在当前 Codex 协作形态下，可以由同一个 AI 在同一线程中扮演这些角色，但必须在文档和行为上分离职责。

## 5. 角色职责

### 5.1 Orchestrator

负责：

- 读取事实源。
- 判断是否进入深思熟虑。
- 创建任务目录和三件套。
- 拆分阶段。
- 决定何时继续、阻塞或请求用户确认。
- 在验证通过后更新路线图、事实源和完成记录。

不负责：

- 在没有任务计划时直接做复杂实现。
- 用聊天结论替代文档事实源。
- 在验证前宣布完成。

### 5.2 Worker

负责：

- 只执行当前阶段。
- 修改代码或文档。
- 记录改动文件。
- 提供验证命令、输出、截图或样例。
- 写固定 `Handoff` 交接。

不负责：

- 自行判定整个任务完成。
- 跳到下游阶段。
- 私自改变事实源边界。

### 5.3 Scrutiny Review

负责：

- 只读复核改动。
- 检查任务计划、完成标准、数据模型、接口契约是否一致。
- 检查静态命令、单测、类型检查、结构检查结果。
- 检查 Handoff 是否与真实改动矛盾。

不负责：

- 生成新功能。
- 修复问题。
- 替代运行态验收。

### 5.4 Runtime/User Review

负责：

- 验证真实用户路径、页面、导出物、文件、素材包、任务事件。
- 对 UI 和生成产物做可用性检查。
- 记录截图、样例输出、导出文件或人工验收结论。

不负责：

- 替代静态审查。
- 把局部跑通等同于完整完成。

## 6. 单一事实源

| 事实类型 | AI漫游事实源 |
| --- | --- |
| 产品范围 | `文档/01_愿景与产品/` |
| 技术契约 | `文档/02_架构与契约/` |
| 模块边界 | `文档/03_模块梳理/` |
| 方案与取舍 | `文档/04_方案与决策/` |
| 执行状态 | `文档/05_执行与记录/任务记录/<任务>/task_plan.md` |
| 过程日志 | `文档/05_执行与记录/任务记录/<任务>/progress.md` |
| 发现与风险 | `文档/05_执行与记录/任务记录/<任务>/findings.md` |
| 完成结果 | `文档/05_执行与记录/功能完成记录/` |
| 验收证据 | `文档/06_测试与验收/` 或任务目录内验证章节 |

规则：

- `task_plan.md` 只记录阶段、状态、决策和退出标准。
- `progress.md` 只记录做了什么、改了什么、测了什么。
- `findings.md` 记录发现、证据、风险、缺口和技术判断。
- 完成记录只在功能完成后创建。
- 聊天内容不能替代上述文件。

## 7. 标准目录

复杂任务目录：

```text
文档/05_执行与记录/任务记录/YYYY-MM-DD_<任务短名>/
  task_plan.md
  progress.md
  findings.md
  handoff.md            # 可选，阶段交接较多时使用
  evidence/             # 可选，截图、导出物、日志摘要
```

## 8. 阶段状态

| 状态 | 含义 |
| --- | --- |
| `pending` | 未开始 |
| `in_progress` | 正在执行 |
| `blocked` | 阻塞，等待用户、工具或事实源 |
| `needs_review` | 已产出，等待复核 |
| `complete` | 已通过验收 |
| `cancelled` | 明确取消 |

## 9. 标准执行流程

### 9.1 启动

1. 读取 `文档/README.md` 和 `文档/00_索引/AI上下文入口.md`。
2. 读取与任务相关的产品、架构、模块事实源。
3. 创建任务目录。
4. 写入 `task_plan.md` 初版。
5. 在 `findings.md` 记录首轮发现。

### 9.2 执行

1. 每次只推进一个阶段。
2. 阶段开始前更新 `task_plan.md` 状态。
3. 执行时持续更新 `progress.md`。
4. 遇到新事实、风险或决策时更新 `findings.md`。
5. 阶段完成后写 Handoff。

### 9.3 复核

1. Scrutiny Review 检查静态证据。
2. Runtime/User Review 检查真实用户路径或导出物。
3. 若发现 P0/P1 问题，回到 Worker 修复。
4. 若缺少用户确认，标记 `blocked` 或 `needs_review`。

### 9.4 完成

1. 更新长期事实源。
2. 更新路线图或模块文档。
3. 写功能完成记录。
4. 记录验证结果和残留风险。

## 10. Handoff 固定格式

每个阶段完成时，必须在 `progress.md` 或独立 `handoff.md` 中写：

```md
## Handoff

### 完成
- 

### 未完成
- 

### 证据
- 

### 命令记录
- `命令` -> exit 0，证据：

### 发现的问题
- 

### 流程遵守
- 已读取事实源：
- 已更新任务记录：
- 未越界修改：

### 给复核者的重点
- 
```

如果某项为空，也必须写 `- 无` 或说明原因。

## 11. 复核口径

### 11.1 Scrutiny Review 清单

- [ ] 是否读取了正确事实源。
- [ ] 是否只推进当前阶段。
- [ ] 是否更新 `task_plan.md / progress.md / findings.md`。
- [ ] 改动是否符合数据模型、任务协议和素材路径契约。
- [ ] 静态验证命令是否执行。
- [ ] Handoff 是否与改动文件一致。
- [ ] 是否有未说明的残留风险。

### 11.2 Runtime/User Review 清单

- [ ] 用户路径是否跑通。
- [ ] 页面是否可操作。
- [ ] 任务状态是否可见。
- [ ] 导出文件是否存在且可打开。
- [ ] Asset、Candidate、Task 等关系是否可追溯。
- [ ] 截图、样例或人工验收是否记录。

## 12. 阻塞规则

遇到以下情况必须停止：

| 情况 | 处理 |
| --- | --- |
| 事实源冲突 | 写入 findings，等待决策 |
| 用户需求不明确且影响架构 | 请求用户确认 |
| 数据模型无法自洽 | 停止实现，先修模型 |
| 任务协议不明确 | 先补协议 |
| 验证工具缺失 | 记录缺失并给出替代验证 |
| P0/P1 复核问题 | 回到 Worker 修复 |

## 13. AI漫游专属阶段建议

M1 故事到分镜闭环建议阶段：

```text
阶段 1：需求与事实源恢复
阶段 2：工程与数据模型初始化
阶段 3：故事输入与结构化任务
阶段 4：分镜生成与编辑
阶段 5：静态复核
阶段 6：端到端用户路径验收
阶段 7：完成记录与事实源同步
```

M2 分镜到漫画图候选建议阶段：

```text
阶段 1：角色/场景/Asset/Candidate 模型
阶段 2：图片任务协议与 mock provider
阶段 3：候选图 UI 和选择锁定
阶段 4：文件路径与素材注册
阶段 5：静态复核
阶段 6：生成与锁定用户路径验收
阶段 7：完成记录与事实源同步
```

## 14. 与 Aurora 原始实现的差异

| Aurora 原始机制 | AI漫游迁移方式 |
| --- | --- |
| `workflow.json` 是流程状态唯一事实源 | 早期先用 `task_plan.md` 承载任务状态，后续可引入 JSON workflow |
| `validation-contract.md` 是验证合同 | 早期用验收清单，复杂生成链路成熟后再独立成验证合同 |
| Worker 必须创建 Git 版本 | 当前项目未要求每阶段提交，先记录改动文件和验证证据 |
| Scrutiny/Runtime 是隐藏子 Agent | 当前由 Codex 在文档中分角色执行，后续可实现为真实 agent |
| Phaser 运行态验证 | AI漫游替换为网页工作台、任务状态、导出物和素材追溯验证 |
