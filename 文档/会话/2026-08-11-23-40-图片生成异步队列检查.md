# 图片生成后台调用异步队列检查

## finding

- 入口：`POST /api/tasks`（`apps/server/src/tasks/tasks.controller.ts`）→ `TasksService.create()`，HTTP 立即返回任务（status: queued），不阻塞等待生成。
- 两种模式（`AIROAMING_PERSISTENCE_MODE` 环境变量决定，默认 db）：
  - **内存模式**：任务存 `TasksService` 内存 Map；`create()` 后 fire-and-forget 调 worker；`image_generate` 走 `ImageCandidateService.runTaskSerialized()`，内部用 `imageQueue` Promise 链做进程内串行队列（一次只跑一个图片任务，防 provider 限流）。进程重启任务丢失。
  - **DB 模式**：任务写 `generationTask` 表；`main.ts` 启动 `PersistentTaskWorkerService.start()`，`setInterval(250ms)` 轮询 DB，`claimNext()` 事务 CAS 抢占 + lease/claimToken + heartbeat 续约；`running` 标志保证单实例内一次只处理一个任务（串行）。支持重试 maxAttempts、取消 cancelRequestedAt、优先级 priority、延迟 nextRunAt、心跳。等价"DB 即队列 + 轮询 worker"，**不是** Redis/BullMQ/Celery 等外部队列中间件。
- `image_generate` handler 注册：DB 模式在 `PersistentTaskWorkerService` 构造器 `handlers.set("image_generate", runImageProvider)`；内存模式在 `ProjectsService.onModuleInit()` `setWorker("image_generate", imageCandidate.runTaskSerialized)`。
- 前端：`AppShell.vue` taskPoller/runtimePoller 每 1800ms 轮询 `/tasks` 与运行时快照刷新状态。
- 图片 provider：`ImageProviderService`（Runware / Grok / OpenAI 兼容 / 豆包），全部是 `fetchWithTimeout` 同步等待 HTTP 返回（请求内同步阻塞等待 provider 出图），异步只体现在"任务级后台执行"，provider 调用本身是同步 await。

# finding（补充）

- 图片并发被代码写死为串行，三处：① 内存模式 `ImageCandidateService.imageQueue` Promise 链；② DB 模式 `PersistentTaskWorkerService.runOnceInternal` 的 `if (this.running) return null`（单实例全局串行，一次一个任务）；③ `TASK_DEFAULTS` 中 image 相关任务 slotCount=1。**换支持并发的服务商不改代码，并发不会自动提升**。
- 已有半成品机制：`task_concurrency_slots` 表 + concurrencyKey/concurrencySlots（任务创建时预注册槽位池），但 `claimNext()` 未真正按槽位限流，仅 `layout-publication.service.ts` 手动用槽位。
- `ImageProviderService` 内 provider 调用全部同步 fetch，无 429 退避重试；任务级重试 maxAttempts=3，`isProviderFailure` 正则（provider/ECONN/timeout）判断 retryable，429 不在匹配范围。
- provider 配置结构：settings 中 `openaiImageProvider/doubaoImageProvider/grokImageProvider/runwareImageProvider/activeImageProvider`，无并发上限字段。
- 用户诉求：当前服务商 API key 只支持单并发，未来换服务商可能支持多并发，需要方案设计。
