# finding

- 当前数据模型和文档都把 `Chapter` 定为项目内创作的一等工作单元；章节内剧本、结构化剧情、分镜、候选图、排版和导出都优先绑定 `chapterId`。
- 固定「章节剧本」格式当前包含：剧本名称、章节标题、基础方向、本章方向、剧本亮点、视觉基调、剧本正文、本章结尾。
- 现有格式已有 `一句话梗概`，但它只描述当前章节，不等于用户说的“情节概要”。
- 用户提到的“情节概要”来自按集规划的写法，例如 `1-2 集：剧情内容`；在本项目漫画链路里不能直接把“集”作为当前主单位，否则会和 `Chapter` 冲突。
- 用户补充最终目标是“通过漫画生成漫剧”。现有文档把轻漫剧放在 P0.5 / M4，交付物是图片序列时间轴、TTS、字幕、BGM 和 MP4；`tts_generate/video_export` 目前尚未强制单个 `chapterId`，视频草稿模型仍未落地。
- 用户补充灵感链路缺少中间产物：用户问灵感后先得到 3 个灵感种子，选中一个后不应直接生成章节正文，而应先生成可确认的「剧本大纲」；用户确认大纲后，再生成章节内容。
- 当前代码和文档仍是旧链路：`generate_inspiration_seeds` 后用户选择第 N 个会触发 `generate_script_from_seed`，后端生成固定格式「章节剧本」并写入当前章节；这与新增的「剧本大纲确认层」冲突。
- 用户已确认：大纲确认后第一版只生成当前一章，不按大纲一次性创建或生成多章。
- 用户确认剧本大纲的交互：大纲内容必须在对话中展示并询问用户是否确认；用户确认后继续生成第一章内容；用户说“不行”或提出修改要求时，应重新生成剧本大纲，循环直到用户确认为止。
- 剧本大纲是项目级固定格式产物，必须保存到项目下，不能只存在于聊天消息；格式包含基础信息、主要角色、情节概要三块，用户给出的古装重生示例只表示格式，不能代入内容。

# web_search


# goal

设计“情节概要”在漫画章节工作流中的归属：既保留它对长线节奏规划的价值，又不破坏当前按 `Chapter` 推进的事实源。

# approach

建议把“情节概要”拆成三个层级判断：

- 项目/篇章级“情节概要”：描述多个章节范围，例如 `第 1-2 章：...`，用于整体剧情规划，不建议重复写进每个章节正文。
- 章节级“本章情节概要”：只描述当前章节的开端、发展、转折、结尾，可进入固定「章节剧本」。
- 漫剧级“集”：后续视频/漫剧导出单位，可由一个或多个漫画章节组合而来，不应在当前漫画剧本阶段替代 `Chapter`。

灵感链路建议改为四层产物：

- `灵感种子`：3 个轻量候选方向，用于选择，不直接写章节。
- `剧本大纲`：选中灵感后生成的项目级/篇章级规划，应持久保存，固定包含基础信息、主要角色、情节概要。
- `章节剧本`：用户确认大纲后才生成并写入当前章节的正文产物。
- `漫剧集映射`：后续轻漫剧阶段再决定一集对应一个或多个漫画章节。

项目级「剧本大纲」固定格式：

```md
# 剧本大纲

## 一、基础信息
剧集名称：
题材风格：
剧集篇幅：
剧集章数：
剧情简介：

## 二、主要角色
角色名（定位）：

## 三、情节概要
第 1 - 2 集：
```

大纲确认后的章节生成策略：

- 第一版只生成当前第 1 章或当前打开章节。
- 剧本大纲里可以包含多章规划，但不自动创建全部章节。
- 后续章节应由用户进入对应章节后，基于已确认大纲逐章生成。
