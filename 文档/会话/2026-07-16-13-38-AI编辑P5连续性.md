# finding

- 当前 `script-chapter-editing` 只读取当前编辑器正文，没有读取上一章正式正文，因此 P4 能保护章内字段，但不能执行跨章 P5。
- A4 已有可靠的上一章正式版本查询和正文摘要；可复用查询原则，但编辑中的当前章允许非空 Working Copy，不能复用 A4 的空章门禁。
- `update_chapter_draft` 当前通过通用写入形成 legacy pending，没有 A4 的持久来源密封。本轮只实现运行时上一章来源、落稿版本围栏和连续性退化检查，不伪造完整 revision provenance。
- DB-only 浏览器复核发现：非流式对话生成期间，页面轮询线程会把仍在运行的消息误判为中断。根因是活动消息集合只登记流式请求；现已统一登记流式和非流式消息，并增加精确回归。

# goal

在不改变页面、章节 Markdown 和用户确认步骤的前提下，让第 N 章 AI 改写读取上一章当前正式全文，并在上一章版本变化时拒绝落稿；若改写前已有承接锚点，改写后不得把它丢失。

# approach

- DB-only 编辑链读取当前章序及上一章当前正式 `ChapterScriptVersion`；第 1 章明确跳过。
- Prompt 注入上一章完整只读正文，并明确后一章卡不是既成事实。
- P5 固定规则只做“不得退化”：源稿已承接上一章而改写稿不再承接时触发；源稿原本未承接时不冒充自动修复。
- 写 pending 的同一数据库事务复核上一章版本 ID 和摘要，避免模型运行期间来源变化后落入过期结果。
- legacy file-mode 保持原行为；revision pending 的持久来源密封另行设计。

# result

- 第 N 章 AI 改写会读取第 N-1 章当前正式全文；第 1 章明确跳过，缺失前章时在模型调用前阻断。
- P5 只检查“已有承接不得被改没”，并在写 pending 的事务内复核上一章 ID、版本和摘要；不把源稿原有缺口强行补成创作事实。
- 页面、章节 Markdown、数据库 Schema、A5 用户步骤和导入路线均未改变；revision pending 仍按 `kind=legacy` 保存，持久来源审计继续作为后续边界。
- 聚焦 4 files / 40 tests、类型检查、E2E 类型检查、三包构建和 Skill 校验通过；DB-only Chromium 路径连续 3/3 通过。
