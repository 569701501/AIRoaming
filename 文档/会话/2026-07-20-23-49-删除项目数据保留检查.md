- 当前正式 SQLite 为 `db_only/activated`，`PRAGMA integrity_check=ok`，约 3.1 MB；库内 4 条 Project 记录（1 active、3 deleting）、5 个章节、52 个 Asset（51 ready）、60 个任务。正式 workspace 约 78 MB、51 个文件。
- 图片 Provider 明文凭据使用 macOS Keychain，DB 仅保存 opaque `secretRef`/fingerprint；删除代码仓库不会自动清理 Keychain。
- 仓库内仍有旧 file-mode `workspace/` 约 2.3 MB，以及其中一份 28 KB 的章节恢复包；删除仓库会一并删除这些旧资料，但不会影响仓库外 DB-only 正式运行根。
- 仓库外存在 2026-07-18 sealed cutover backup、迁移前 workspace 备份和凭据修复前 SQLite 备份；这些备份早于 2026-07-19 的当前 51 个 ready Asset，不能视为当前完整备份。
- 应用内删除项目是破坏性流程：先把 Project 标记 `deleting` 并创建 `project.delete_files` Outbox，处理后删除项目素材目录，再 purge 项目相关 DB 行、任务和对话数据。
- 当前 DB 的 3 条删除事件均为 `pending/attempt=0`；源码中标准启动没有通用 Outbox 后台消费者，因此这些项目尚未完成物理/DB purge。残留数据不是备份，后续事件被处理时仍会删除。

# result

- 当前实际答案：在应用中点击删除后，项目会先从正常项目列表退出并标记为 `deleting`，但现有通用 Outbox 清理没有被标准运行入口消费，因此数据库行、章节、任务和素材仍可能保留。
- 现场证据：3 个已删除项目仍在数据库，3 条 `project.delete_files` 均为 `pending/attempt=0`；其中已删除的“测试”仍有 2 个章节、52 条 Asset、60 条任务和约 78 MB 素材文件。
- 设计目标仍是硬删除：清理事件被处理并执行 purge 后，该项目的数据库业务事实、任务、对话和素材都会被删除，不会长期保留。
