# approach

- 以现有失败对话为真实复现证据，读取结构生成 Prompt、运行时返回、JSON 提取和一次修复链；构造最小只读/测试反馈信号验证最可能原因。
- 已用真实 OpenCode 会话响应离线重放：主响应稳定复现质量门问题，修复响应稳定复现“没有可解析的 JSON”，且两次生产 Prompt 确认为同一份。
- 根治梳理按五层推进：输入数据契约、确定性质量门、模型运行隔离、修复状态机、用户可见失败语义；每层单独做可证伪差分，再决定模块 seam。
- 建议把根治收口成两个深模块：Shared 的 `ChapterScriptFactsCompiler` 统一解析每场角色事实并提供 strict publish / legacy-compatible read 两种策略；Server 的 `StoryStructureGenerationService` 统一服务对话和持久任务，内部通过原生 JSON Schema 运行时端口生成、用同一份 facts 做质量门、按失败类型最多执行一次定向重试。
- 结构生成使用每次任务独立的 OpenCode session 和隔离 runtime root，指定专用无工具 Agent/System；不再复用通用对话 session，也不再读取仓库 `AGENTS.md`。主响应读取 `info.structured`，文本 JSON 提取只留给明确的旧链兼容，不作为新结构生产主路径。
- 新正式正文发布时要求「出场人物」只写稳定角色名，状态/电话/门外/遗照/新闻说明移到剧情描写、人物动作、对白或旁白；历史版本读取时确定性去掉尾部括号说明、禁止在括号内部按斜杠拆名，并忽略全括号非角色说明，同时产生兼容 warning。
- 重试仍保持外部模型调用最多 2 次：第一次失败若为 protocol/schema 则第二次只修格式；若为 domain quality 则第二次只修语义；runtime/source contract 不盲重试。最终失败保留两次 attempt 和首次问题，不再只显示最后一个解析错误。
