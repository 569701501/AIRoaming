# finding

- 用户桌面存在“凡人修仙传”小说文件夹；单文件十几兆，当前无法直接作为对话附件交给 AI 完整读取。
- 文件夹内有 `1.txt`（15,296,200 bytes，GB18030）和 `2.txt`（13,949,765 bytes，UTF-8），合计约 29.2 MB、解码后约 1321 万字符。
- 当前 Web 使用 `File.text()` 读取全部附件并把全文放进对话 JSON；本机 4310 服务实测 90 KB 请求进入路由、110 KB 返回 `413 Payload Too Large`，因此正文尚未进入 RawSource 或 AI。
- `1.txt` 若按当前 UTF-8 `File.text()` 读取会产生约 909 万个替换字符，属于确定性乱码。
- 当前 RawSource 会按空行拆段；两份小说规范化后约产生 155,239 + 110,330 个 paragraph block。现有 12,000 字 block 上限不能减少这种短段数量，单次 `createMany` 和后续 AI 分层都不适合该规模。
- 现有长稿分析虽有 48,000 字叶子 / 72,000 字合并预算，但当前按短段计入固定开销并串行调用；整本小说会导致大量 AI 调用，不能作为章节标题已明确时的默认拆法。
- `1.txt` 是原作《凡人修仙传》，正常内容规模约 2446 章，但原始标题存在重复、错号、乱序、卷名与章名同一行等脏数据；不能按标题候选机械删除正文。
- `2.txt` 是《凡人修仙之仙界篇》，正文约 1394 章并含两篇外传；质量更好，但仍有相邻重复标题、章号倒序和错号。
- 两份文本合计约 3842 个可靠内容单元；按原始标题直接切会得到约 3971 个候选单元并引入重复与错序。
- `ScriptChapterList.vue` 对全部章节直接 `v-for`，项目快照也按全量章节组装；一次创建数千个项目章节会使普通工作台、批处理和后续 AI 任务失去可用性。

# web_search

- Scrivener 官方的 `Import and Split` 会按用户指定的分隔符把长文拆成 Binder 内独立章节/场景，证明“导入预览后形成章节树”是成熟交互，但其来源仍属于单个项目。
- Atticus 会根据 Heading 1、分页符或连续空行识别章节，并把章名放进左侧导航；适合借鉴规则拆章与人工重排。
- Novelcrafter 从首页导入并先预览识别出的幕、章、场景；确认后直接创建小说项目，全部章节进入项目的 Plan、章节选择与手稿侧栏。跨作品共享的是角色和世界观 Codex，不是整本原文。
- Sudowrite 的 `Import Novel` 会直接创建新项目，自动识别章界并把各章拆成项目内独立文档，同时建立 Story Bible；它也没有“先建全局原著资产、再另行绑定项目”的主流程。
- Atticus、Scrivener 同样把导入结果直接变成当前书籍/项目内的章节树，而非可跨项目复用的整本原著。
- Dify 把 Knowledge 作为应用之外的独立知识资产并供多个应用检索，这适合知识问答/RAG，但不代表顺序创作型小说产品的主流交互。此前把该模式直接套到小说制作流程上，结论偏复杂。
- Novelcrafter 的系列级 Codex 可跨作品共享，并由用户控制多少资料进入 AI；适合借鉴“角色/世界观复用 + 按需上下文”，不适合作为整本正文复用的证据。
- Gemini Notebook 支持单来源最高 200 MB / 50 万词并允许选择当前来源，但 notebook 彼此隔离；大文件入口值得参考，项目间不可复用不适合照搬。
- OpenAI File Search 将文件上传/索引与模型调用分离，并允许限制检索结果数量以降低 Token 和延迟；本功能首版不需要向量化，只需本地章节索引和精确范围读取。

# goal

判断超大本地小说为何无法通过当前上传链路，并给出不会丢正文、不会把整本塞进一次模型上下文、能够可靠整理章节的方案。

用户进一步确认希望把能力拆成独立功能，并把 Token 消耗作为首要约束：全书上传、编码转换、章节识别和异常检查默认必须做到 0 AI Token。

用户进一步提出把该能力放到项目外的全局左侧菜单，拆章结果作为资产保存，并在创建项目时选择关联。

用户已认可全局原著资产方案，继续讨论项目首次进入后的章节选择体验。

用户要求把竞品式修正方案代入当前项目实际代码评估，明确能否落地、哪些可复用、哪些必须先改。

# approach

- 先只读检查小说文件和现有导入实现。
- 区分“文件保存容量”“请求体容量”“模型上下文容量”和“拆章批处理容量”。
- 本轮先讨论与诊断，不创建项目、不修改小说、不实施代码。
- 推荐增加独立的“大型原著导入”：流式上传，服务端识别 UTF-8/GB18030，以确定性规则生成章节目录和异常清单；整本只作为来源库保存，用户选定范围后再按章整理，AI 不读取整本。
- 产品入口进一步收敛为独立的“长篇小说拆章”：默认纯程序处理；只有用户主动选择“AI 判断疑难边界”或“整理当前章节”时才调用模型。
- 通过文件摘要、章节正文摘要和结果缓存保证重复上传、重试、再次打开不重复花费 Token；疑难边界只发送标题附近的小窗口，禁止发送整本或全量正文目录。
- 竞品复核后，用户流程改为小说产品的主流方式：从“长篇拆章”完成预览确认后，直接执行“基于此小说创建项目”，而不是让用户再到创建项目弹窗寻找和绑定资产。
- 创建后把全部原著章节的标题、顺序和来源范围一次性登记为项目内章节结构；首次打开第 1 章，左侧用搜索、卷分组和虚拟滚动章节树导航，不使用数千项普通下拉，也不要求用户逐章“创建制作章节”。
- 全部章节可见不等于全部交给 AI：正文仍按当前章延迟读取，改编、分镜和摘要只在用户处理当前章时调用模型，从而保留低 Token 目标。
- 全局“长篇拆章”可以保留为大文件预处理入口和历史导入记录，但不向用户暴露复杂的“资产版本绑定 / 制作快照 / 再次选来源”心智。
- 原著章节与漫画制作章节分离；推荐把原作和仙界篇作为两个来源/项目，外传作为仙界篇下的独立分区。
- 当前项目代入结论为有条件可行：`ChapterScriptPending/Version` 之后的按章链路可复用；必须先把项目聚合/Workbench 改为轻目录 + 当前章读取，并将 B4 从整批自动调用改为用户显式的单章处理。
- 用户界面直接展示全部来源章节，底层来源绑定保持不可见；创建后默认第 1 章，浏览和切章 0 Token，只有“整理本章”进入现有 materialize/verify/pending 确认链。
- 七个步骤必须共用搜索、卷分组、跳章和虚拟滚动的章节导航器，并把 `chapterId` 写入所有章节级步骤 URL。
- 首次落地先试导入原作前 10～20 章，验证编码、目录、正文边界与异常提示，再建立全书索引。

# result

已确认当前普通附件链路无法可靠处理这两份小说：请求体先触发 413，第一份还会被错误解码，放宽大小后仍会产生约 26.5 万段和过多 AI 调用。正确方向是独立的大型原著导入、章节索引预览、异常人工确认和按需按章 AI 整理；不应要求用户手工拆分，也不应一次把全书创建成漫画制作章节。

竞品复核和当前代码适配审计进一步收敛：用户流程应直接“拆章后创建项目并看到全部目录”，但当前全量 `LocalProject/WorkbenchSnapshot`、章节控件和 B4 自动 Worker 不能直接承受。实施必须先完成轻量目录读模型、统一章节导航/路由和单章 AI 门禁。
