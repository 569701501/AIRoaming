# finding

- 章节方案文档已明确 `Chapter` 是项目内一等工作单元，章节级承载剧本、结构化剧情、分镜、候选图、排版和导出；项目级继续承载角色、世界观、通用场景和共享素材。
- 当前 UI 信息架构已把 `/projects/:projectId/script/:chapterId` 作为推荐章节定位路由，并要求剧本步骤有章节列表或章节切换器。
- 核心数据模型已新增 `Chapter` 和 `ChapterScriptVersion`，但当前代码中的共享 DTO、后端 `LocalProject`、`WorkbenchSnapshot.story`、剧本保存接口和对话 prompt 仍围绕项目级单份 `sourceText`。
- 当前 `GenerationTaskTarget` 代码类型还没有 `chapter` target，也没有 `chapterId` 字段；文档里的生成任务协议已经先行要求章节内任务携带 `chapterId`。
- 素材文件契约总体合理，但项目级 `exports/pages`、`exports/video` 与章节级 `chapters/{chapterSlug}/exports` 同时存在，后续实现时需要明确：章节导出物放章节目录，项目级 exports 用于跨章节合集或素材包。

# result

复核结论：设计方向稳妥，建议继续推进。关键优点是把长篇创作的工作单元从 Markdown 标题提升为可追溯实体，并把后续产物统一挂到 `chapterId`，这能支撑分镜、候选图、排版和导出追溯。主要实现风险不在方案本身，而在迁移顺序：应先补共享 DTO、后端章节服务、`WorkbenchSnapshot` 的 `chapters/currentChapter`，再改前端章节列表；不要直接从 UI 层把章节塞进现有 `snapshot.story.sourceText`。
