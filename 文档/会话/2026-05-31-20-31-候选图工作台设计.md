# web_search


# goal

设计候选图工作台的信息架构、生成/锁定链路和数据边界，确保与已确认分镜、排版导出、素材包契约对齐。
补充目标：纳入角色定稿图前置流程，保证候选图生成前关键角色已有可复用的视觉参考。

# approach

推荐 M1 采用“按当前章节、按 Shot 逐镜头生成和锁定”的工作台：

1. 入口只允许 `Chapter.status = storyboard_done` 且存在正式 `storyboard.json`。
2. 右侧工作台以镜头队列 + 当前镜头候选图网格 + 生成参数/提示词检查为主。
3. `selected` 只是临时选择，`locked` 才写入 `Shot.lockedCandidateId` 并成为排版输入。
4. 批量生成只生成缺候选或未锁定镜头，不覆盖历史候选。
5. 全章所有需要排版的 Shot 都有 locked candidate 后，章节推进到 `images_done`，解锁排版导出。

早期位置假设已废弃：不再把“角色定稿”作为剧情结构页下方子流程，也不放到候选图页作为前置子流程。当前确认的产品口径是新增独立项目级阶段 `项目角色库`，放在 `剧本` 与 `剧情结构` 之间。

强制策略已收口：主角和常驻角色必须在项目角色库阶段完成角色定稿图，才能进入剧情结构；本章重要角色可建议定稿但不作为硬门槛，临时/路人角色不强制。

角色层级建议：AI 在剧本大纲和章节剧情结构中自动判断角色层级，UI 暴露为可编辑标签。建议枚举为 `lead`（主角）、`recurring`（常驻角色）、`chapter`（本章重要角色）、`extra`（临时/背景角色）。其中 `lead/recurring` 必须完成角色定稿图，`chapter` 默认建议定稿但可跳过，`extra` 默认不强制。

项目级记录建议：主角和常驻角色应落到项目级 `Character`，并以 `Character` 作为唯一正式事实源。后续剧情结构、分镜、候选图和漫剧相关 prompt 可以从 `Character` 派生 AI 可读上下文；章节结构中的同名角色应关联已有项目角色，而不是新建重复角色或维护第二份并列角色事实。

角色定稿锁定建议：角色定稿图在没有被任何漫画候选图使用前可以重生成、替换和编辑；一旦某个角色参考图被用于生成 `Candidate`，旧参考图不能被覆盖或静默替换。后续如需改角色形象，应创建新的角色视觉版本/新参考图，并提示会导致后续新图与旧漫画不一致；已生成的旧 Candidate 保留对旧参考图的追溯。

新增阶段建议：可以把主流程从 6 步调整为 7 步，在 `剧本` 与 `剧情结构` 之间新增 `项目角色库`。该步骤是 project scope，不绑定单一章节；它读取项目级剧本大纲/导入剧本提取的主要角色，生成项目级 `Character` 草稿、角色层级、角色定稿候选图和锁定主参考图。剧情结构、分镜和候选图后续都读取该角色库。

已确认决策：主流程调整为 `剧本 -> 项目角色库 -> 剧情结构 -> 分镜工作台 -> 候选图工作台 -> 排版导出 -> 素材包`。`lead` 和 `recurring` 角色必须在项目角色库阶段完成角色定稿图；否则剧情结构保持阻塞。该结论已同步到 `文档/01_愿景与产品/核心用户流程.md`、`文档/02_架构与契约/核心数据模型.md`、`文档/03_模块梳理/模块总览与依赖.md`。

已确认 UI 决策：项目角色库沿用项目工作区两栏形态。左侧公共 AI 对话注入 `project_characters` prompt，负责生成角色、解释 AI 判断、重生成角色图和按用户要求调整；右侧是正式项目角色库工作区，承载 `Character[]`、角色层级、角色描述、候选图、定稿状态和锁定提示。聊天内容必须经用户确认或受控工具写入，才进入正式项目角色库。
