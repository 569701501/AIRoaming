# finding

- 当前事实源声明 G1 已物化 44 个 Prisma model、194 个 trigger；本轮需要从 schema、migration SQL、trigger DSL 和业务调用代码反向核对设计理由与合理性。
- 用户明确要求只按当前实际代码讨论，不修改代码、Schema、迁移或业务行为。
- 44 个模型分为 4+6+10+5+9+4+6 七组。`0003_story_storyboard_preflight` 是 10 表的 migration 分组，不是把一份剧情文档拆成 10 份真值：Story/Storyboard/Preflight 仍分别由 `documentJson` 保存完整权威文档，Scene/Beat/Shot 表为可重建关系投影与稳定身份。
- 结构化剧情直接涉及 `StoryVersion` + Scene/Beat 两投影；加上跨版本的 `ChapterScene` 及 `SceneVisual` 共 5 表。Storyboard 另有 4 表，Preflight 另 1 表。用户所说“9 表”更接近 Story+Storyboard 两个子域，不是单个 StoryDocument。
- 投影不是全部死表：Storyboard Repository 会通过 Beat/Scene 投影建立 Shot 关联，任务 guard 读 StoryboardShotProjection，资产与预检读 ChapterScene/Shot。但 `StorySceneProjection` 在普通 TypeScript 运行路径主要被写入，实际读取更多来自 SQL formalize guard，其价值与成本最值得重新审视。
- 194 trigger 的客观构成是 97 BEFORE UPDATE、55 BEFORE INSERT、39 BEFORE DELETE、3 AFTER UPDATE。只有 3 个 `materialize` trigger 会 INSERT/UPDATE 其他表，均属于 Task claim/heartbeat/finish；其余 191 个主要是拒绝非法写入。
- 严格以 `_scope_insert/_scope_update` 命名的 trigger 是 51 个。其中一部分是组合外键可覆盖的 project/chapter owner 一致性；另一部分同时校验 target 状态、active Project、nullable 兼容、多态 source 或两个父表之间的相容性，不能只用普通 FK 表达。
- Schema 已在 Asset/Candidate/CandidateLock/GenerationTask 等位置使用复合 FK，因此其他表使用 scope trigger 不是因为 Prisma/SQLite 一律做不到。current/pending pointer 含父自身非空 ID 时，复合 FK + `ON DELETE SET NULL` 确有结构性困难，这类 trigger 更合理。
- “审计/记账”的核心实体是 MigrationRun/Issue/ImportedSource、DialogueToolResult、TaskAttempt、CandidateLockRevision、LayoutRevision、OutboxEvent 等显式表。现有 trigger 多数只保护不可变与状态转移，并没有自动记录全局业务审计日志。
- 自建生成链是：Markdown 实施契约 + 硬编码 relation/字段分类 + CHECK/trigger DSL → 1.3MB machine manifest → `schema.prisma` 和 0001–0008 migration SQL；另有 Prisma 标准 `generator client` 生成 ORM client。
- 自建生成/验证相关 TypeScript 与测试约 12,313 行，manifest 28,957 行，0008 migration 344KB。当前工作区仅因 `apps/server/package.json` 新增 `db:verify` script（该文件被纳入 manifest source closure），`g1:manifest:check` 就报 `G1_SCHEMA_MANIFEST_STALE`，显示契约闭包的耦合面过宽。
- `PrismaService` 默认 persistence mode 仍是 `file`；只有显式 `AIROAMING_PERSISTENCE_MODE=db` 时才连接并使用该数据库。DB Repository、G2 版本链与 importer 已有实际代码，但全量 DB-only 激活仍未完成。
- 用户进一步要求给出“不影响现有进度、不过度耗时”的修复顺序。低风险方向不是立即合表或批量删除 trigger，而是冻结 0001–0010 历史基座、先收窄 G1 manifest source closure，后续只用类似 0009/0010 的小型 overlay migration 演进。
- `PersistentTaskRepository` 当前直接依赖 3 个 materialize trigger：claim 只更新 `GenerationTask`，trigger 创建 `TaskAttempt` 并占用 slot；heartbeat 由 trigger 同步 slot；finish 由 trigger写回终态/重试态并释放 slot。因此这 3 个 trigger 是状态机实现的一部分，不能作为第一批删除对象。
- 新增 0011 之类迁移不能只写 SQL；G1/G2/G3 runtime ledger 目前精确匹配允许的 migration 集合，必须同步扩展 ledger/catalog，否则启动会把新迁移视为 unexpected。
- 用户认可止损方向并提出四项盲点：生成器冻结与 importer 的依赖、source closure 修改工期、复合 FK 的 DELETE 等价性、投影审计可能被无限延期；另外要求明确生成器最终是永久保留还是走向退役。
- 代码复核确认 importer 各 slice 本身不导入 G1 生成器；当前 `db:import` 仅支持 shadow 和 12 个独立 slice，`final` 明确 fail-closed，且全量编排、Layout/Export、Dialogue/provider/read model、backup/activate 尚未完成。因此 importer 尚未定型，但可以继续迭代而不扩展 G1 生成器。
- 当前工作区新增的 `MigrationVerifyService` 会调用 `loadCurrentG1SchemaManifestV1()`，并把 G1 manifest digest 写成 `effectiveSchemaManifestDigest`。该 digest 会因无关 supporting source 改动变化，且 manifest 仍为 `effectiveStage=G1, appliedOverlays=[]`，没有表达 0009/0010；它目前不是准确的“当前发布 Schema 身份”。
- G1 manifest 的摘要逻辑没有 source role 分层：全部 supporting source digest 都进入 `sourceDocuments`，随后整个 unsigned manifest 参与 canonical SHA-256。收窄 closure 不是只删一行；至少要同步两个 allow-list、artifact 与测试。但 Schema/migration 渲染只消费模型/约束，supporting source 摘要本身不会进入 `schema.prisma` 或 migration SQL 字节。
- 生成器最终命运建议采用渐进 B：G1 生成器先冻结为历史复现工具，0011+ 改用手写 `schema.prisma`/migration 与轻量 overlay contract；DB-only、备份恢复和一个稳定周期完成后退役生成 DSL/write CLI，只保留历史 manifest、0001～0010 artifact、迁移 checksum 与必要特征测试。
- 0011 前需要建立独立的 release schema identity：按 SQLite 引擎、按序 migration name/checksum、`schema.prisma` 摘要及 overlay contract 版本计算，不再用 G1 source-provenance digest冒充。现有 G1/G2/G3 分层 ledger 应收敛为单一当前 release catalog。
- 现有 SQLite trigger semantics 覆盖 purge DELETE，但没有覆盖“scope trigger 改复合 FK 后”的 DELETE/SET NULL/CASCADE/RESTRICT 等价矩阵。未来替代必须在真实 SQLite 验证 parent DELETE、部分 NULL、全 NULL、级联/限制、事务回滚和 `foreign_key_check`。
- `StorySceneProjection` 没有普通应用业务读取，但 `trg_story_versions_formalize_guard` 直接依赖它校验 Json 与关系投影一致；importer 也把它作为 provenance 实体写入。因此它不是零依赖表，后续必须把“投影表 + formalize guard + importer provenance”作为一个整体审计。
- 用户已授权执行止损方案，并要求检查 Luna 并行代码和执行文档。已建立 ADR-0015，决定 G1 生成器渐进退役、发布 Schema identity 从 G1 source digest 分离。
- 新 release identity 只读取 `schema.prisma` 与全部有序 migration SQL；无关 package script 不影响身份，新增 migration 自动改变 identity，但 runtime 未登记 migration 仍 fail-closed。
- G1 source closure 已移除完整 `apps/server/package.json`，从 19 份缩为 18 份；manifest digest 更新，Schema 与 0001～0010 SQL 字节未变。
- Luna M4 verifier 草稿已保留并修正：改用 release identity；复合来源 digest 不再误按单文件比较；只读测试比较账本 verification 前后不变。M4 仍只算基础实现，不宣称完整完成。

# result

当前方案的出发点是高强度 DB-only 切换、直接 SQL/importer 也不能破坏历史、任务和跨作用域关系；因此选择了权威 Json + 关系投影 + 大量 fail-closed trigger + 可重放生成链。设计意图可理解，且稳定身份、版本史、current pointer、任务尝试、来源绑定等建模有实际用途。

但结合当前单机/单 NestJS 写入者、Prisma Repository 已使用短事务与 codec、DB-only 尚未激活的现状，44 表本身不一定错，194 trigger 与约 1.23 万行生成基础设施则明显过重。合理保留的应是 FK/unique/check、必要的 current pointer scope、正式历史不可变和少量并发 fencing；纯 owner 一致性、应用层已事务化的状态流程、SQL 中的大段 JSON 投影比对、Task 三表自动 materialize 与过宽的 manifest source closure 值得优先简化。

最小可行优化是先修复过宽的 source closure，并把 0001–0010 与 G1 大生成器标记为冻结基座；在当前 DB-only/importer 里程碑完成前不合表、不删 trigger、不重写历史迁移。后续每次只通过一个小型 overlay 迁移处理 5–10 个已由复合 FK/应用事务覆盖的低风险 guard，并配套 runtime ledger 和 DB-mode 回归。Task 的 3 个 materialize trigger 必须等 Repository 显式承担 Attempt/Slot/终态事务后再单独处理。

盲点复核后方案修正为：第一阶段不能只做 closure 收窄，还必须把 release schema identity 从 G1 source digest 中分离，否则 `db:verify/activate` 会绑定一个既受无关脚本影响、又未包含 0009/0010 的错误身份。生成器采用渐进退役而非永久保留；投影读取审计在“全量 shadow importer 两轮通过、final cutover 前”自动触发，实际删表仍在 DB-only 稳定周期后单独执行。

执行结果：已完成 ADR-0015、release Schema identity、G1 package closure 收窄、Luna M4 基础实现纠偏和事实源修复；server 45 files/255 tests、G1 三项、Prisma validate、workspace typecheck 与 diff check 全绿。Schema、0001～0010 和 trigger 字节未变；真实 DB、workspace、backup/activate 未触碰。M4/full importer/backup/activate 的未完成边界已明确写入 handoff。
