# finding

- 候选图 Prompt 已包含镜头级角色名、外观、人物数量和多人不得漏人/合并/串职责合同；provider 参考指引也会声明每张图对应的角色。
- DB-only 任务从已确认出图准备快照中取当前 shot 的角色视觉与场景视觉，任务和候选图会保存真实使用的参考资产。
- OpenAI 候选图最多取 16 张参考，Doubao 最多 10 张，Grok 最多 3 张。Grok 超限且存在场景参考时，当前硬编码保留“两个高优先级角色 + 场景”，因此三人同镜会省略第 3 个角色参考图，这是当前多角色不一致的直接结构性原因。
- DB 出图准备对 `lead/recurring` 优先选用 `final_reference`，但候选图干净底图契约要求单人参考；四视图组合图直接作为 edit 输入仍有设定表/分格污染风险。
- 项目已经保存各角色的 `preview_front` 单人身份锚点和 `final_reference` 定稿视觉；当前缺少 Provider 无关视觉需求和自适应引用编译。容量不足时需要把多个角色机械拼成临时身份板，但 0～2 人且独立引用可完整传入时不应强制合板。Server 当前只有 `pngjs`，而角色资产主要是 WebP；正式实现还需补齐可解码、裁切、缩放和合成 WebP 的确定性图片处理能力，不需要重新调用模型生成角色。
- 当前 `Shot` 只有 `coreAction + comic.composition` 自由文本，没有逐角色结构化站位、前后层次、大小、朝向和动作职责；静态多人身份板只能解决“是谁”，不能独立解决“谁站哪里、做什么”。
- 标准 DB 的真实三人镜头表明三张同为 864×1152 的 final 同时存在横向四格和 2×2 排版，固定裁取正面格位不安全。最终方案让 final 只作批准证据，物理身份输入使用单人 preview；新 final 记录精确 preview `sourceVisualId`，旧空来源资产只在存在唯一可验证的更早 preview 时兼容。

# web_search

- OpenAI 官方 Image Edits 支持一张或多张输入，示例实际使用 4 张参考，GPT Image 2 默认高保真处理全部输入；官方同时承认跨多次生成的角色一致性仍可能失败。当前项目的“16 张上限”是本地 adapter 设置，不应写成 OpenAI 官方承诺。
- Seedream 官方支持复合多图编辑，公开 API 资料写明最多 10 张输入；Prompt 应明确“图一/图二/图三”的职责，还可用箭头、线框和涂鸦控制位置。
- xAI 官方 Multi-Image Editing 单次最多 3 张源图且顺序有意义，并支持 multi-turn editing；官方没有要求“三个角色优先、场景改文字”，这是本地产品策略。
- Boords/LTX 把角色、地点、道具作为可复用项目资产；Runway 采用命名参考、角色与场景分路径迭代、Sketch 构图；Midjourney 对多角色建议把多人放在一张参考图并配合 Editor；Adobe 用选区、对象/全图参考保护背景；Leonardo 把角色、内容、风格、姿态/深度/边缘拆成不同控制通道。
- 主要来源：OpenAI Developers、xAI Docs、火山引擎、Runway、Midjourney、Adobe、Boords、LTX Studio、Leonardo 官方文档；完整链接已写入 `文档/04_方案与决策/2026-07-19_多角色与场景一致性平台调研.md`。
- 补充代表性产品工作流：Boords/LTX 将角色、地点、道具资产化但不公开底层图片封装；Runway 最多 3 张命名 Reference，复杂场景建议角色/场景分路径迭代；Vidu 公开支持 1～7 个角色、场景、构图等命名参考；Midjourney 只有 1 张 Omni Reference 并明确建议多人放同一张图；Adobe/Ideogram 用选区与 mask 保护背景并定向换角色；Scenario 用图片合成或 Character Multi-LoRA 后再 Canvas 分角色修复；Freepik 用 8～25 张图片训练长期 Custom Character。
- 市场结论：不存在一个所有平台都采用的单一方案。完整产品的共同点是“资产库 + provider 编译 + 失败后局部修复”；多人角色板是槽位受限时有官方先例的默认均衡路径，独立多参考是容量足够时的高保真路径，LoRA/Multi-LoRA 只适合大量复用的核心 IP。

# goal

调研热门创作平台和主要图像模型如何处理“三个角色 + 场景”的双重一致性，并在用户确认后实施 P0：必需引用不可静默丢失、Grok 单参考实际使用、容量不足时确定性多人身份板和完整覆盖证据。

# approach

在已完成本地链路审计和市场调研的基础上，把方案从“两个以上角色统一合板”深化为 `ShotVisualRequirementSet -> ReferencePlan` 自适应编译：容量足够时优先独立身份参考，容量不足时使用全员身份板；P0 已完成直接引用/全员身份板、场景独立输入、来源追溯和失败关闭，结构化构图与局部修复后置。

# result

- 用户判断成立：角色和场景都属于必需视觉条件；把场景或第 3 个角色改成纯文字会损失一致性，只能算止损降级，不能作为合格方案。
- 已新增正式调研报告 `文档/04_方案与决策/2026-07-19_多角色与场景一致性平台调研.md`，区分底层 API 能力、热门产品工作流和 AI漫游推荐架构。
- 推荐先建立 provider 无关的完整 `ShotVisualRequirementSet`，再编译成直接多图、确定性打包参考、分层区域编辑或不兼容；任何 `required=true` 条件都必须能追溯到实际 provider 输入，禁止静默删除。
- OpenAI/Seedream 具备三角色+场景独立四图能力，容量与输入预算允许时应优先独立直传；不为跨 Provider 表面统一而主动降低身份分辨率。Grok 的 0～2 人镜头也优先独立引用；三人以上改用全员身份板或“焦点单图 + 其余角色板”，场景仍保持视觉覆盖。
- 生成后仍需分别检查每个角色的存在、身份、服装、站位，以及场景地标、空间和光向；参考全部入图是必要条件而非 100% 保证。
- 用户提出把本镜头全部角色资产合成一张多人角色参考板。深化复核后确认：该方案确定节省图片槽位，是容量受限时的重要兼容路径，但不应成为所有人数和 Provider 的固定默认；只有固定压缩总像素时才可能同步节省图像输入 token，不能跨 Provider 承诺必然节省 token。
- 多人板是任务级内存派生输入，不新增或替代现有角色资产；只接受每个角色的单人 `preview_front`。真实 final 排版不统一，禁止固定模板裁图；只有 final 而没有可用 preview 时失败关闭。
- 新一轮深度复核后推荐收口为四档：默认自动模式按人数、焦点、构图复杂度和 Provider 能力选择直传/身份板/混合计划；质量优先模式保留独立重点角色；失败候选通过 mask 只修错误角色；只有跨大量章节长期复用的核心 IP 才评估 Character LoRA/Multi-LoRA。
- Grok 的更优三槽分配：三人同等重要时“全员身份板 + 原始场景 + 可选构图板”；有明确焦点时“焦点单图 + 其余角色板 + 场景构图板”。当前没有结构化站位时，构图必须如实标记为 `prompt_only`，不能伪装已视觉锁定。
- 不建议把全部角色、场景和构图再压成一张巨型拼图；除非 Provider 只有一个图片入口，至少保持身份与场景/构图两个物理参考通道。
- `$deep-think` 方案复核留痕位于 `文档/05_执行与记录/任务记录/2026-07-19_多角色引用方案复核/`；静态结论为 `pass_for_design`，真实新策略视觉 A/B 为 `not_run`。
- 用户已确认按推荐方案实施；P0 已完成并留痕于 `文档/05_执行与记录/任务记录/2026-07-19_候选图必需引用编译/`。
- 最终实现为 `candidate_reference_plan_v1`：Grok 单参考实际编辑，容量内独立直传，超限只合并角色并保留独立场景，成功计划强制 `omittedRequired=[]`；缺失、损坏、来源无效、final-only 或技术容量超限均在联网前失败。
- 新 final 保存实际 preview `sourceVisualId`；候选任务优先沿该来源冻结身份锚点，旧空来源资产只接受唯一可验证的更早 preview，避免角色后续更换预览后与既有定稿错配。
