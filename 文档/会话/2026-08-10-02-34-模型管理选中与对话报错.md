# 2026-08-10 模型管理选中不生效与对话报错

# finding

## 现象（用户报告）

1. 设置页模型管理里把某个对话模型「设为当前」，回到对话框，顶部模型选择器显示的不是那个模型，需要用户重新选。
2. 图片模型设为当前后，生成图片时应该调用它。
3. 用对话模型对话时报错。

## 运行环境事实

- dev 实例：web 5173 / api 4310 / OpenCode serve 4396；`AIROAMING_PERSISTENCE_MODE=db`（`local-dev.cli.ts` 强制 DB-only），SQLite 在 `~/.airoaming/data/db/airoaming.sqlite`。
- 本机是 Linux → `SecretStoreService` 落到 `UnavailableSecretStore`（只有 darwin 才有 Keychain）。
- 遗留文件 `workspace/settings/app-settings.json` 在 DB 模式下**完全不被读取**（`readSettings()` 直接走 `readDatabaseSettings()`）。

## 根因 1：DB 模式 active 指针不持久化（对话/图片两个问题的同一个根因）

- `PUT /api/settings/models/:id/activate` 的**响应体**里 `active` 是对的，但紧接着 `GET /api/settings` 又变回旧值。实测：
  - `PUT .../model_grok/activate` → 响应 `model_grok active=true`
  - `GET /api/settings` → `model_self active=true`，`model_grok active=false`
- 原因：`writeDatabaseSettings()` 写 `app_preferences` 时用的是 `settings.aiKey.providerId` / `settings.activeImageProvider`（固定槽位），**没有写 `activeTextModelId` / `activeImageModelId` 指向的模型行**。`readDatabaseSettings()` 又反过来从 `defaultTextProviderId` / `activeImageProviderId` 推导 active，于是 activate 的结果被立刻丢弃。
- 代码里原有注释「DB 模式不持久化 active 指针」是当时的已知限制，正是本次要修的东西。

## 根因 2：Linux 上模型密钥不持久（对话报错的根因）

- 添加模型时填的 API Key：DB 模式走 `keyFingerprint = fingerprintSecret(...)` + `runtimeManagedModelSecrets`（**纯内存**），fingerprint 落库，明文重启即失。
- `prepareRuntimeSecrets()` 在 DB 模式下直接跳过 managed model 密钥恢复（`if (!isDatabaseMode())`）。
- 结果：进程重启后 `configured=true`（fingerprint 在库里）但 `getRuntimeAIKeySettings().apiKey = null` → OpenCode 不同步 auth → 调用中转 401/500 → `OPENCODE_EMPTY_RESPONSE` / `Internal Server Error`。
- 实测复现：新建带正确密钥的 `diagtimicc` 模型（同进程内内存里有 key）→ 先 activate 再对话 → `status=completed, content=OK`；只传 `model` 不 activate → 失败。证明「必须 activate 才能拿到凭证」+「凭证只在内存」两点。

## 根因 3：前端对话模型选择器数据源不是「模型管理设为当前」

- `workbench-store.loadRuntimeModels()` 用 `GET /api/ai-runtime/models`（OpenCode registry）的 `default`/第一项覆盖 `selectedDialogueModel`，而不是 `settings.models` 里 `kind=text && active` 的那条。
- 该函数在每次 `openProject()` 后调用 → 进入项目就把用户在设置页的选择覆盖掉。
- 发消息时 `model: this.selectedDialogueModel`，所以既显示错、也发错。

## 其他相关事实

- `getRuntimeAIKeySettings()`（对话）与 `getRuntimeImageProviderSettings()`（图片）**已经**跟随 `activeTextModelId` / `activeImageModelId`，服务端运行时接线是对的，坏在上面 3 点。
- 图片协议按 `providerId` 关键字推断：含 doubao/grok/runware → 对应协议，否则 openai（`inferImageProviderType`）。
- DB 约束 `ck_credential_metadata_text_owner_shape`：text 行 `configured=1` 时 `secret_ref` 必须为 NULL（fingerprint 非空即可）；image 行可以有 secret_ref。这限制的是**落库字段**，不限制我们把明文放进本机 secret store。
- 无任何测试锁定模型管理相关 DOM。

# 关键决策

- 新增 `FileSecretStore`（0600 文件，root 默认 `<dataRoot>/secrets`，可用 `AIROAMING_SECRET_STORE_ROOT` 覆盖），非 darwin 平台生产使用；`FakeSecretStore` 保留为其子类，测试语义不变。
- DB 模式模型密钥：明文进 SecretStore，text 行 `secret_ref` 仍写 NULL（守住 G1 CHECK），靠稳定 credentialId `managed_<kind>_model_<providerId>` 恢复。
- 恢复失败（条目缺失/指纹不匹配）不抛错，只当作未配置，避免旧数据把服务启动打挂。
- `app_preferences.default_text_provider_id/active_image_provider_id` 改为指向 active managed model 的 provider 行，成为 active 指针的持久化载体（不新增表/迁移）。
