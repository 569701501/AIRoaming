# finding

- 文档口径：`项目角色库` 是项目级步骤，位于剧本和章节级剧情结构之间；`Character` 挂项目，供多个章节复用。
- 代码口径：`resolveWorkflowCurrentStepKey` 只有在当前章节非 draft 且项目角色库未 ready 时，才把当前步骤推到 `project_characters`；如果项目角色库已 ready，第二章完成剧本后会直接进入 `story_structure`。
- 当前缺口：第二章或后续章节出现新常驻/重要角色时，没有“角色增量检查/补齐”机制；用户可能不知道是否需要回项目角色库，也可能跳过新角色定稿。
- 当前 `project_characters` 对话工具会从已确认剧本大纲或当前章节提取角色，但它仍表现成完整“项目角色库”步骤，容易和按章流水线混在一起。
- 2026-06-02 已完成实现迁移：`PROJECT_WORKFLOW_STEP_KEYS` 改为 `project_story -> story_structure -> storyboard -> image_preflight -> image_candidates -> layout_export -> asset_package`；`project_characters` 不再是顶部主流程步骤，只保留 `/characters` 项目资产页。
- 2026-06-02 后端和前端 `resolveWorkflowCurrentStepKey` 均不再用角色库 ready 状态阻塞 `story_structure`；`storyboard_done` 后进入 `image_preflight`，用户确认出图准备后写入 `preflight.json`，确认记录与当前分镜匹配且派生检查仍通过时才进入 `image_candidates`。
- 2026-06-02 新增 `ImagePreflightWorkspace.vue`，读取正式分镜、项目角色库和任务队列，检查出镜角色绑定、必需角色定稿图和运行中的角色图任务；顶栏新增“角色库”入口。

# goal

梳理“项目角色库”作为项目级事实源与“章节逐章生产”之间的关系，避免每章回项目角色库的流程别扭，同时保留新角色补齐能力。

# approach

建议把项目角色库拆成两个语义：

1. 项目角色库初始化：项目级门槛，通常在确认剧本大纲或导入整本剧本后做一次，锁定主角和常驻角色。
2. 章节角色增量检查：章节级轻量检查，发生在每章剧本完成后、剧情结构生成前；只在发现新常驻/重要角色或角色引用缺失时，提示补入项目角色库，否则直接进入剧情结构。

用户反馈：还需要继续想“项目角色怎么放”，暂不急着确认实现。后续讨论重点应从“是否每章回角色库”转为“项目角色库作为入口/资产页/章节检查面板分别放在哪里最顺”。

2026-06-02 继续思考：

- 更准确的拆法不是“项目角色库放在主流程里还是移出去”，而是把角色拆成两类依赖：
  1. `角色档案`：名字、身份、层级、描述、关系，是剧情结构和分镜理解角色的文本事实源。
  2. `角色视觉定稿`：预览图、定稿图、视觉版本，是候选图生成和后续漫剧镜头一致性的视觉事实源。
- `角色档案` 应在剧本大纲确认后自动生成第一版，并作为项目级常驻资料；后续章节可增量补充。
- `角色视觉定稿` 不一定要阻塞剧情结构和分镜，但必须在候选图生成前完成当前章节出镜角色的定稿/确认。
- 因此，“项目角色库”不适合继续作为章节流水线里的第 2 个线性步骤；更适合变成项目级常驻入口 + 各章节生成前的依赖检查。
- 可能的新主流程：`剧本 -> 剧情结构 -> 分镜工作台 -> 角色/素材检查 -> 候选图工作台 -> 排版导出 -> 素材包`；其中“角色/素材检查”只检查当前章节出镜角色是否都能用于出图，不承担完整项目角色库管理。
- 项目级常驻入口可叫 `角色库` 或 `项目角色`，放在项目工作区顶部/侧边的项目资产入口中，而不是章节步骤条中。
- 参考市面流程后的修正：只在“候选图前检查本章出镜角色有没有定稿图”作为唯一入口太晚，也不符合多数 AI storyboard 工具。更合理的是在 `剧本/大纲 -> 剧情结构/分镜` 之间自动抽取“本章角色/Elements”，但不要求全部视觉定稿；在进入候选图生成前，把本章 shot 中真实出镜角色绑定到已有角色资产或补建角色资产，再用已确认视觉参考出图。
- 因此新候选流程应不是“先分镜，最后才发现没角色”，而是“三次出现角色”：
  1. 大纲/剧本阶段：生成项目角色候选。
  2. 剧情结构/分镜阶段：生成本章出镜角色清单并与项目角色库做匹配。
  3. 候选图阶段：只检查 shot 已绑定的出镜角色是否有可用视觉参考。

2026-06-02 术语澄清：

- `项目角色库` 仍然是流程的一部分，但不建议继续作为顶部主流程条里的线性阶段。
- 更准确的产品定义是：`项目角色库` 是项目级常驻资产模块，承载角色档案、预览图、定稿图、视觉版本和锁定状态。
- 主流程中保留的是“角色相关动作”，而不是把整个角色库固定成每章必经页面：
  1. 剧本大纲确认后自动初始化项目角色库。
  2. 剧情结构/分镜阶段自动引用并增量发现角色。
  3. 分镜后、候选图前通过“出图准备”检查本章出镜角色是否已有可用视觉参考。
- 这样可以避免后续每写一章都被迫回到完整项目角色库，同时又不会让候选图阶段才第一次发现角色缺失。

2026-06-02 追问补齐：

- 用户指出仅说明“项目角色库作为常驻入口”还不完整，必须明确：
  1. 用户进入角色库后哪些字段可以改、什么时候不能改。
  2. 角色库里到底包含哪些角色。
  3. 后续章节出现的新角色如何自动加入或提示加入。
- 当前代码已有 `ProjectCharacter.level = lead / recurring / chapter / extra`、`status = draft / needs_reference / finalized / in_use`，以及 `source = script_outline / imported_script / manual / story_structure`，可承接这套设计。
- 建议角色库包含四类角色：主角、常驻角色、本章重要角色、临时/背景角色。主角和常驻角色必须有定稿图；本章重要角色默认先有文字档案和预览图，只有跨章复用或进入候选图时才补定稿；临时/背景角色默认不强制进入定稿流程。
- 修改边界建议：未出图使用前，角色文字档案、层级、预览图、定稿图都可改；已用于候选图后，旧角色视觉版本锁定，后续修改应新建视觉版本，只影响新生成内容。
- 新角色增量入口建议：剧情结构生成后产生本章角色清单并做角色库匹配；匹配不到的角色进入“待入库/本章角色候选”。用户可确认加入项目角色库、合并到已有角色、标记为临时角色或忽略。分镜和出图准备再次校验镜头出镜角色绑定，避免漏网。

2026-06-02 用户视角复盘：

- 如果把“角色图片定稿”放在剧情结构前硬阻塞，用户体验会变差：用户只是想继续整理剧情结构，却被图片生成速度、失败和挑图打断。视觉定稿更应该阻塞候选图，而不是阻塞剧情结构。
- 如果把项目角色库完全藏成常驻入口，用户会缺少安全感，不知道角色一致性是否已经处理。因此主流程仍需要一个明确的“出图准备/视觉准备”检查点。
- 推荐修正：`剧本 -> 剧情结构 -> 分镜工作台 -> 出图准备 -> 候选图工作台 -> 排版导出 -> 素材包`。
- `项目角色库` 作为项目资产入口常驻存在；在剧本大纲确认后自动初始化核心角色，在剧情结构和分镜阶段自动补充/匹配本章角色，在出图准备阶段完成本章必需角色参考图。
- 右侧角色库不应完全只读。用户作为创作者会自然期待能直接点小笔修改角色名、角色描述、层级和备注；AI 对话是辅助入口，不应是唯一修改入口。未被候选图使用前可直接修改；已使用后修改会创建新视觉版本或提示影响范围。
- `本章重要 chapter` 不能简单等同于“不需要定稿”。如果该角色在当前章多次出镜、有台词、近景或影响剧情，即使只出现一章，也应该在出图准备中要求至少确认可用参考图；临时/背景 `extra` 才可以只用文字描述。
