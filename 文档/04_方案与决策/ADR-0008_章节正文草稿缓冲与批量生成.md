## 1. 状态

已采纳。

## 2. 背景

章节正文（sourceText）原先**没有草稿缓冲层**：AI 通过 `writeChapterDraftFromAI` 写入即直接覆盖正式 `script.md` 落盘，用户无法"先检查再确认生效"。对比剧情结构、分镜阶段都有 pending 机制（写预览→用户确认才转正式），唯独章节正文缺失。

这导致两个问题：
1. 用户让 AI 批量生成整本剧本时，AI 会直接覆盖多个章节的正式内容，用户没机会拒收写得不好的章节。
2. ADR-0005 把"生成内容类"拒绝做成真工具，导致 AI 无法自主连续写入多章——但这其实是产品需求，不该被技术坑绑死。

## 3. 决策

### 3.1 引入章节正文草稿缓冲（仿分镜 pending 机制）

新增 `ChapterPendingSourceText` 类型 + `chapter.pendingSourceText` 字段 + `script-pending.json` 文件。AI 生成正文时写入 pending 缓冲，不碰正式 sourceText。用户确认后才转正式。

存储设计（照抄 storyboard.pending.json）：
- 落盘：`chapters/{slug}/script-pending.json`（完整对象 JSON，含正文+来源追溯）
- 读盘：`readPendingChapterSourceText`
- 挂载：`LocalChapter.pendingSourceText`（每章独立，单草稿）
- snapshot 暴露：通过 `toChapterDetail` 转换

### 3.2 确认/丢弃草稿独立动作

- `confirmChapterPendingSource`：pending→正式 sourceText，产生正式 revision（source=ai_tool），清 pending。
- `discardChapterPendingSource`：删 pending，正式不变。
- **不绑定 completeChapter**（完成本章是推进状态，确认草稿是采纳内容，两件事解耦）。

### 3.3 AI 批量生成走"边生成边建章"（方案 C）

批量生成时不预先建空章节骨架，而是循环里每生成一章前 `ensureChapterExists(order)`（不存在就建）。理由：大纲是自由文本（"第 1-2 集：xxx"），不是结构化章节列表，硬解析不可靠；让 AI 多输出一轮规划又复杂；边生成边建最自然。

循环逻辑：
```
for order in [start, start+count):
  ensureChapterExists(order)          # 不存在就建
  if chapter.sourceText 非空: break   # 碰已有正式内容停（保护用户内容）
  sourceText = AI 生成该章正文
  writeChapterDraftFromAI(pending)    # 写入 pending 缓冲
```

### 3.4 覆盖边界：严格碰非空停

碰已有正式 sourceText 的章节立即停下，返回已停位置。不覆盖用户已有内容。这个判断在循环内每章生成前检查。

### 3.5 不改 ADR-0005 真工具边界

批量生成仍走伪工具调用（dialogue.service 识别意图→调 projects.service），不做成 OpenCode 真工具。因为正文从来不当工具参数传——后端从 AI response.content 直接拿正文，避开了 ADR-0005 担心的"长文本当参数超限"。

### 3.6 上限保护

`MAX_BATCH_CHAPTERS = 20`，防止"生成全部"时 AI 失控无限生成。

## 4. 被否决的备选

### 4.1 否决：AI 先输出章节规划 JSON 再建空章节（方案 A）
大纲是自由文本，让 AI 多输出一轮结构化章节规划增加复杂度且质量不可控。边生成边建更自然。

### 4.2 否决：正则解析大纲"剧集章数"建空章节（方案 B）
大纲字段是自由描述（"每集 2 章共 6 集"），正则解析不可靠。

### 4.3 否决：把章节写入做成 OpenCode 真工具
ADR-0005 已论证生成内容类不适合真工具。本场景正文不当参数传，伪工具调用已够用。

### 4.4 否决：草稿缓冲存内存
章节正文是核心产物，进程重启不能丢，必须落盘。

## 5. 已知限制

- **单草稿**：一个章节同时只有一份 pending，新生成覆盖旧的。不做多版本草稿对比。
- **"全部确认"批量入口未做**：二期前端只做逐章确认。批量确认入口推迟（当前批量生成返回的是 DialogueToolResult，多章 pending 靠 SSE 逐章 patch，前端逐章确认即可）。
- **写盘性能**：批量循环每章 ensureChapterExists + writeChapterDraftFromAI 两次写盘，量大时慢。MVP 可接受。
- **runtime 未验证**：三期只做静态验证，真实批量生成质量依赖用户手动测试。

## 6. 影响范围

### 6.1 类型契约
- `packages/shared/src/dto.ts`：ChapterPendingSourceText 接口；ChapterDetail.pendingSourceText；Confirm/Discard Response；DialogueToolResult.tool 加 generate_multiple_chapters。

### 6.2 后端
- `projects.service.ts`：LocalChapter 字段+初始化；script-pending.json 读写；confirm/discard/applyPending/ensureChapterExists 方法；writeChapterDraftFromAI 改走 pending。
- `dialogue.service.ts`：createGenerateMultipleChaptersToolResult 多章循环；resolveBatchChapterRange 意图识别；入口分支接入；3 处文案改草稿提示。

- `ProjectWorkbenchView.vue` + `AppShell.vue`：事件链。

## 7. 风险与回滚

| 风险 | 应对 |
| --- | --- |
| LocalChapter 初始化漏加/误清 pendingSourceText | 一期 Scrutiny 已主动发现并回退 2 处误清（confirm 结构/分镜） |
| 批量生成 AI 质量下降 | 单章 prompt 不变外层循环；每章带完整大纲上下文 |
| "碰非空停"误判 | 判断 sourceText.trim().length > 0，严格 |
| 无限生成 | MAX_BATCH_CHAPTERS=20 上限 |

回滚：删除 pendingSourceText 字段与相关方法，writeChapterDraftFromAI 恢复直接写 sourceText。已落盘的 script-pending.json 会被忽略。

- ⏳ Runtime：用户"生成整本"→ 多章 pending 落盘、碰非空停、逐章确认生效。
