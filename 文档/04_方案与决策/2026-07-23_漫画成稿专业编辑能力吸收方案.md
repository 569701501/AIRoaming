# 漫画成稿专业编辑能力吸收方案

## 1. 结论

专业漫画编辑能力适合继续放在第 6 步“漫画成稿”，但不能把任一第三方完整编辑器直接嵌入当前产品。

推荐路线是：

1. 保留 `LayoutDocument`、Shared Editor Command、Working Copy、人工保护、不可变 Revision 与 Server RenderScene 作为唯一事实源。
2. 先完成包含完整 `LayoutDocument V2` 的正式版本、预检和 publication 链路，并修正当前简化预览与真实渲染之间的偏差。
3. 按 ADR-0016 把 Konva 落为 Web 交互 adapter，补齐拖拽缩放/旋转手柄、框选、多选变换、平移缩放、吸附和对齐线；Konva 不保存业务状态，也不参与正式导出。
4. 直接开放当前协议已经支持、但 UI 尚未完整呈现的气泡样式、富文本、拟声字和图层能力。
5. 新气泡轮廓、文字阴影/发光和非破坏滤镜等新增可见语义，只能作为后续 `LayoutDocument V3` 候选；实施前需新 ADR 明确修订 ADR-0011/ADR-0019 的非目标边界，并同时升级命令、保护、预检、渲染器和黄金图。
6. AI 修图、背景移除、局部重绘和 Image2Image 可以从“漫画成稿”发起，但结果必须走现有任务、Candidate、Asset、用户选择与 CandidateLockRevision 来源锁定链路，不能把 ComfyUI/A1111/Forge 私有状态塞进画布文档。

这里的核心不是“再造一个 Photoshop”，而是让用户在自动完整成稿后，用少量、直接、可撤销的动作把例外修好。

### 1.1 实施结果（2026-07-24）

用户已接受本方案并授权直接实施。当前结果为：

| 阶段 | 状态 | 已落地事实 |
| --- | --- | --- |
| P0 | complete | V1/V2 Revision、Preflight、来源替换与 Publication 联合契约；V2 完整/可见双摘要；forward-only migration；V2 RenderPlan/Manifest；权威 Pending 与手机只读预览 |
| P1 | complete | `konva@10.3.0` 已作为纯 Web 交互 adapter 接入，覆盖选择/框选/多选、拖拽/变换、crop、气泡尾巴、平移、滚轮缩放和辅助线；Konva JSON、scale、viewport 均不落盘 |
| P2 | complete | 四类气泡、RGBA、描边、padding、垂直对齐、尾巴、对象透明度、SFX 语义预设、真实字体面、锁定/显隐/图层顺序已在现有字段和命令内显性化 |
| P3/P4 | deferred | 新轮廓、阴影/发光、滤镜、像素修图和 AI 派生图片仍需新 ADR 或既有 Candidate/Asset 来源链，不在本次实现中 |

真实浏览器已通过：

```text
V2 自动成稿
→ 候选定稿变化
→ 同 Shot 全 appearance 来源替换
→ Undo/Redo
→ 来源覆盖 warning 确认
→ V2 LayoutRevision
→ V2 layout_publication
→ 桌面 ready
→ 手机只读 current publication
```

历史 V1 出版路径保持通过。具体测试、截图和复核见
`文档/05_执行与记录/任务记录/2026-07-24_漫画成稿专业编辑实施/`。

## 2. 当前事实与真正缺口

### 2.1 已经具备

当前项目不是从零搭建漫画编辑器。正式模型和实现已经覆盖：

| 领域 | 当前能力 |
| --- | --- |
| 文档 | 页漫/条漫、Canvas、画格、自由图、文字、气泡、图层顺序、阅读顺序 |
| 画格与图片 | 矩形/圆角矩形、非破坏 `contain/cover`、zoom、offset、crop rotation、flip、来源绑定 |
| 文字 | 横排、竖排、受控字体、字号、字重、斜体、颜色、字距、行高、对齐、描边、字符范围富文本 |
| 气泡 | `speech/thought/shout/caption` 四类、填充、描边、内边距、垂直对齐、单尾巴、内嵌富文本 |
| 编辑 | 元素变换、排序、锁定、隐藏、批量对齐/分布、Undo/Redo、自动保存 |
| 智能成稿 | 零设置完整初稿、整章/场景/页段/选区重排、先预览后应用、字段级人工保护 |
| 正式链路 | V1 已有预检、不可变 LayoutRevision、确定性 HTML/SVG RenderScene、PNG/PDF/条漫 publication |

因此，用户建议中的画格层、图片层、文字层、气泡层和图层管理，已经有内部领域模型。不能再引入一套第三方 JSON 作为平行事实源。

### 2.2 实施前最高优先级缺口（已关闭）

实施前自动成稿已经生成 `LayoutDocument V2`，但 V2 正式链路尚未闭合。本次已经完成：

```text
V2 Working Copy
→ V2 Preflight
→ 包含完整 V2 文档的 LayoutRevision
→ 带完整文档/可见投影双摘要的 RenderPlan
→ Publication
```

Web 现已提供明确的“成稿预检 → 保存 Revision → 出版预检 → 提交出版任务”四步状态；V2 不再被正式版本或出版链路拒绝。

实施前另有两项偏差，本次也已关闭：

- AI 当前/新排法缩略对比只是简化几何预览，没有完整复现真实 crop、flip、字体、气泡路径和尾巴。
- 手机只读预览的图片语义没有完整复现 `contain/crop/flip/rotation`。

在引入更复杂视觉效果前，AI Pending 应用前必须提供可展开的权威视觉预览；简化缩略图只能继续作为结构导航。手机只读预览必须修复为复用权威 RenderScene 语义，不能只加“非 WYSIWYG”提示。

### 2.3 交互层缺口

生产 Web 当前使用绝对定位 DOM 和 Pointer Event，只完整实现单对象拖动与属性面板数值编辑。尚缺：

- 画布内缩放、旋转和裁切手柄；
- 框选、套索、多选整体拖动/缩放/旋转；
- 平移、滚轮缩放、适配视口；
- 吸附、对齐线、等间距提示；
- 画布内气泡尾巴控制柄。

这些是 Konva 最有价值的落点，也是 ADR-0016 已经采纳但生产代码尚未完成的部分。

## 3. 推荐分层

```text
用户操作
  ↓
Web 交互 adapter（Konva + DOM 富文本输入）
  ↓ 只提交内部 Editor Command
LayoutDocument V1/V2/V3 + Working Copy + 人工保护
  ↓
不可变 LayoutRevision
  ↓
Shared RenderPlan + Server HTML/SVG RenderScene + 固定 Chromium
  ↓
PNG / PDF / 条漫切片
```

AI 图片修改走另一条受控路径：

```text
成稿内“编辑这张图”
  ↓
Server GenerationTask
  ↓
派生 Candidate / Asset
  ↓
用户预览、选择并形成新 CandidateLockRevision
  ↓
来源替换预览
  ↓
Editor Command + 来源追溯
```

### 3.1 不可破坏的边界

- 不保存 Konva node、stage JSON、Fabric JSON、Comical `data-comical` 或第三方滤镜私有状态。
- 不使用 Konva `toDataURL()` 或编辑器 DOM 截图作为正式导出。
- 不启用第二套 Undo/Redo；拖动过程中只维护临时交互状态，结束时提交一个内部命令或一个 batch。
- Konva Transformer 的 `scaleX/scaleY` 必须在提交时归一化为内部 `width/height`，节点 scale 恢复为 1。
- 图层事实仍是 `LayoutCanvas.elements[]`，阅读顺序仍是独立协议；Konva Layer/Group 只用于视图投影。
- 用户命令继续经过 V2 actor 和保护映射，不能绕过 geometry/crop/text/style/tail/source 等人工保护。

## 4. 第三方项目采用矩阵

| 项目 | 结论 | 在本项目中的正确位置 | 不采用的部分 |
| --- | --- | --- | --- |
| Konva.js | **采用** | Web 交互 adapter：命中、选择、Transformer、框选、手势、辅助线和临时反馈 | 不作为领域模型、撤销事实源或正式 renderer |
| Comical-JS | **观察/短 PoC，不默认接入** | 参考尾巴交互和气泡参数；若要验证，只做统一坐标、内部气泡/尾巴模型映射后的保存恢复和正式导出限时 PoC | 不持久化 Comical JSON 或 `data-comical`，不让 Paper.js/DOM/SVG 形成第二套气泡与导出链 |
| Manga Editor Desu | **只参考** | 参考工具组织、上下文属性、气泡预设、滤镜和 AI 图片工作流 | 不复制代码、资产、字体或整套 UI，不作为运行时依赖 |
| TUI Image Editor | **只参考；极特殊场景可隔离** | 参考单图裁剪、旋转、基础滤镜清单；若未来确需，只能作为进入成稿前的隔离单图工具 | 不进入主画布，不与 Konva/Fabric 建双对象模型；若使用必须关闭 usage statistics |
| React Komik | **只参考抽象** | 参考 Strip/Panel/Character/Balloon 的组件词汇 | 技术栈和依赖过旧，不直接依赖 |
| Komiko | **只参考产品方向** | 参考角色库、AI Comic Studio、图像到动画等产品组织 | 仓库只有展示性 README 且无 LICENSE，不是可集成开源库 |

### 4.1 许可证和维护判断

以下为 2026-07-23 的官方 GitHub/npm 时间快照，后续进入生产依赖前必须重新核验版本、许可证和维护状态：

- [Comical-JS](https://github.com/BloomBooks/comical-js) 使用 [MIT](https://github.com/BloomBooks/comical-js/blob/master/LICENSE)，npm 0.4.0 与默认分支最近提交均为 2026-07-17。它不负责气泡内文字和样式 UI，并采用 Canvas/SVG/DOM 与 `data-comical` 状态，和当前 Konva/内部 renderer 并非天然兼容。
- [Konva](https://github.com/konvajs/konva) 使用 [MIT](https://github.com/konvajs/konva/blob/master/LICENSE)，10.3.0 发布于 2026-04-30，默认分支最近提交为 2026-07-16；库化程度和维护状态适合承担交互 adapter。漫画语义、业务 JSON、文字排版和正式导出仍由本项目负责。

- [React Komik](https://github.com/sonnylazuardi/react-komik) 使用 [MIT](https://github.com/sonnylazuardi/react-komik/blob/master/LICENSE)，默认分支最近提交为 2016-09-27；开发栈停留在早期 React/Fabric 世代，只适合读组件抽象。

MIT 依赖进入生产后也必须保留上游版权与许可声明，并纳入发行物第三方许可清单。

## 5. 哪些能力放在“漫画成稿”

### 5.1 直接放入

| 能力 | 理由 |
| --- | --- |
| 画格、图片、文字、气泡的直接变换 | 属于成稿最后一公里，且内部模型已支持 |
| 多选、框选、吸附、对齐线、视口缩放 | 只提升操作效率，不改变正式文档语义 |
| 图层顺序、锁定、显隐、阅读顺序 | 已有命令和数据事实 |
| 横排/竖排文字与基础描边 | 已有 RichText 与 renderer |
| 四类气泡的颜色、描边、泡体/描边 alpha、整对象透明度、内边距、尾巴控制 | 已有协议字段；UI 必须区分 RGBA alpha 与 `transform.opacity`，并避开当前隐式轮廓保留色对 |
| 拟声字入口和受控文字预设 | 已有 `TextElement.semantic="sfx"`，不必新增元素类型 |
| 局部智能重排、避让人物、整理气泡 | 已有 Pending、预览、应用、撤销和人工保护闭环 |

### 5.2 可以从成稿发起，但不把结果藏进画布状态

| 能力 | 正确落点 |
| --- | --- |
| AI 重绘、Image2Image、背景移除、局部修复 | 生成派生 Candidate/Asset，用户选择并锁定为新 CandidateLockRevision，再预览和确认来源替换 |
| 自动漫画 tone 或复杂网点化 | 优先烘焙为可追溯派生 Asset；若要求随时可调，再进入 V3 非破坏效果 |
| 图片放大、修复 | 生成新 Asset/Candidate，不覆盖原文件 |
| ComfyUI/A1111/Forge | 作为 Server provider/capability，不由浏览器直接连接用户本机后端 |

### 5.3 暂不放入

- 画笔、橡皮、套索像素修图、节点工作流；
- 通用无限白板、通用持久 Group、复杂蒙版和混合模式；
- 40 多种无语义约束的气泡一次性全量堆入；
- AI 自动改写对白并直接覆盖成稿；
- 编辑完成后绕过 Revision/Preflight 直接下载 Canvas 截图。

## 6. 分阶段路线

### P0：先闭合可交付链路

目标：智能自动成稿能够形成正式不可变版本和真实出版物。

#### P0.1 正式版本与双摘要

- `LayoutRevision.documentJson` 保存完整、规范化的 `LayoutDocument V2`，包括 automation、对白 binding/disposition 和人工 protection；不能只保存 V1 可见投影。
- V2 Revision 行写入 `schemaVersion=2`，JSON 的 `kind/schemaVersion` 必须与行值一致；数据库继续使用 `LayoutRevision.documentDigest` 表示完整 V2 摘要，RenderPlan/manifest 以 `revisionDocumentDigest` 复制并冻结这个值。
- forward-only migration 必须扩展 Revision insert/seal/immutable trigger，使 V2 能从同一 `canvases` 可见结构生成并密封 `LayoutSourceBinding`；历史 V1 行不回填、不改摘要。
- Shared 的 Revision detail/history/create/restore/preflight 响应升级为按 `documentKind/schemaVersion` 判别的 V1/V2 union，例如 `LayoutRevisionDetailV1 | LayoutRevisionDetailV2`；禁止把 V2 塞入现有 `LayoutRevisionDetailV1`。
- 新建 `layout_render_plan_v2` 与 `layout_publication_manifest_v2`，同时保存 `revisionDocumentDigest` 和 `visibleDocumentDigest`；后者表示 `V2 → V1` 确定性可见投影摘要。
- publication task 同时冻结 `revisionDocumentDigest`、`visibleDocumentDigest`、`rendererVersion` 和 policy identity。
- Worker 先核验不可变 Revision 的完整摘要，再重新投影并核验可见摘要，最后核验 RenderPlan/manifest；不得把 V1 投影写回 Revision，也不得用投影摘要冒充 Revision 摘要。
- 历史恢复必须原样恢复完整 V2；恢复后 automation、bindings、dispositions、protections 和全文摘要都与该 Revision 一致。
- V1 Revision 保持不可变，继续按原 V1 codec、preflight、`layout_render_plan_v1` 和 manifest 路径预览；不能重新解释旧 `documentDigest` 字段。若用户要把历史 V1 再次出版，仍遵循现有“恢复到草稿/保守升级 → 保存新的当前 Revision → 出版”，本文不新增直接出版任意历史 Revision 的能力。
- migration 与 API 回归必须同时覆盖：V1/V2 insert、source binding seal、immutable、detail/history 判别、完整恢复和旧 V1 出版路径。

#### P0.2 V2 正式预检

在现有 V1 可见内容门禁之外，创建包含 V2 文档的 LayoutRevision 前必须验证：

- Storyboard 当前正式对白/旁白 100% 被 binding 或合法 disposition 覆盖，无静默改写；
- binding、balloon、Shot、speaker 和 `user_suppressed` tombstone 引用完整，无重复或悬空；
- composition/source digest、current CandidateLockRevision 集合和 lock-set digest fresh；
- protections 指向存在对象和合法 scope，无悬空、重复或不适用于对象类型的保护；
- V2 可见投影可被 V1 strict codec 接受，且投影摘要稳定；
- 现有来源 stale、缺图、缺字体、文字溢出、低分辨率、画布外元素和 warning acknowledgement 门禁继续生效。

#### P0.3 真实用户路径

用户路径不是含糊的“一键导出”，而是：

```text
正式版本预检
→ 逐项确认 warning
→ 保存包含完整 V2 文档的 LayoutRevision
→ 出版预检
→ 逐项确认 publication warning
→ 创建持久 Publication Task
→ 查看不可变 Artifact
```

必须分别验收：

1. 无 warning 直接通过；
2. warning 未确认时阻断，逐项确认后通过；
3. error 存在时禁止创建 Revision/Publication；
4. 预检后 Working Copy 摘要或来源发生并发变化时，旧 acknowledgement/digest 失效并要求重新预检。

#### P0.4 权威预览与来源恢复

- AI Pending 的小缩略图可保留为结构概览，但用户点击“使用这版新排法”前必须能展开用权威 Shared RenderScene 语义生成的完整视觉预览。
- 手机只读页必须完整复现图片、画格、文字和气泡语义，不允许只显示简化 `object-fit: cover`。
- 固定页漫、条漫 fixture，至少覆盖 `contain/cover`、zoom、offset、crop rotation、flip、画格圆角/边框、层序、`transform.opacity`、横排/竖排、受控字体、字符范围富文本、四类气泡和尾巴。
- 当候选定稿变化导致 V2 stale 时，提供 V2 感知的来源替换预览：Server 只读解析受影响元素和新 CandidateLockRevision，用户确认后以 V2 user command/batch 更新来源并建立 `source/crop` 保护，同时保留 automation、bindings、dispositions 和既有 protections；同一 Shot 的所有出现位置必须在同一 batch 中更新到同一个 CandidateLockRevision。
- 完整恢复路径固定为：

```text
候选定稿变化
→ 新 CandidateLockRevision / lock-set digest
→ 当前 V2 显示 stale
→ 用户查看来源替换预览
→ 显式提交 V2 command batch
→ 重新预检并创建新 Revision
```

旧 Revision 和旧 publication 永不改写。

#### P0.5 入口回归

- 无 Working Copy 且来源齐全：只触发一次零设置自动成稿；
- 已有 V2：直接恢复，不重复生成；
- 候选未齐：不初始化、不写库，允许返回候选图；
- 宽度小于 1024px：只读，不初始化、不保存、不提交编辑命令；
- dirty/conflict：保留现有 autosave、CAS、冲突提示和本地 recovery；
- 历史 V1：继续预览/出版；打开可编辑 V1 时遵循现有保守 V2 升级。

验收：

- 保存包含 V2 文档的 Revision → 继续编辑 → 恢复该 Revision后，完整 V2 摘要一致；旧 V1 Revision 仍可预览/出版。
- 同一 V2 的桌面权威预览、Pending 展开预览、手机只读和正式 artifact 使用相同 `visibleDocumentDigest`/RenderScene 输入；固定 Chromium 下预览截图按冻结 golden 与明确像素阈值比较，正式 artifact 的重复输出要求字节与 SHA 完全一致。
- Server 集成测试覆盖双摘要、V2 特有 preflight、来源替换和并发摘要失效；publication golden 覆盖页漫 PNG/PDF 与条漫切片；Playwright 覆盖上述完整用户路径。

### P1：完成 Konva 交互 adapter

目标：不改变文档协议，把“能编辑”提升为“好编辑”。

#### P1.1 视口与单选基础

- Konva Stage/Layer 只投影非文字交互几何和命中区域；
- 选择框、单选移动/缩放/旋转；
- 平移、滚轮/触控板缩放、适配视口；
- locked/hidden 对象正确命中或跳过；
- 首个切片保留当前右侧 `LayoutRichTextEditor` 作为唯一文字写入面，不同时引入画布内编辑。

#### P1.2 多选与漫画专用手柄

- 框选、Shift/Cmd 多选、整体移动/缩放/旋转；
- 边缘/中心吸附、对齐线、等间距提示；
- 图片裁切模式只修改 `CoverCrop`，不误改画格 transform；
- 气泡尾巴控制柄只提交内部 tail 字段；
- 需要画布内直接改字时，再增加定位到文字/气泡上的 DOM contenteditable overlay：双击进入文字模式时禁用 Konva Transformer/drag，IME composition 期间不提交半成品命令，选区、粘贴、快捷键、Esc/blur 提交和焦点恢复均有测试。

验收：

- `LayoutDocument → Konva 投影 → Editor Command → 新 LayoutDocument → 重投影` 单向闭环；
- 单选和多选的每次完整手势只产生一个 history entry；多选使用一个 batch；
- Transformer `scaleX/scaleY` 归一化为内部 width/height 后重置为 1；
- zoom/DPR 不改变业务坐标；pointer cancel 不产生命令；
- locked/hidden、crop 与 tail 手势不越权修改其他字段；
- Undo/Redo 后完整文档摘要回到手势前/后；AI apply、Server reload 和冲突恢复后节点从文档完整重建；
- 不写入任何 Konva 私有 JSON；正式导出摘要不受 viewport、DPR 或选择状态影响。
- 正式 artifact 的实际字节/摘要不受 viewport、DPR、selection、Transformer 和 guides 影响。
- adapter 级挂载测试覆盖 pointer/zoom/焦点互斥，Playwright 覆盖单选、多选、crop、tail、Undo/Redo 和键盘可达性。P1.1 只要求右侧文字输入获得焦点时 Stage 快捷键与拖拽不介入；composition、Esc/blur 和 overlay 焦点恢复用例只在画布 DOM overlay 实际进入 P1.2 时强制。

### P2：释放已有协议能力

目标：以较低风险获得明显的漫画专业感。

- 气泡样式面板：四类语义下提供少量经过验收的外观预设；每个预设只展开为现有 `fillColor/strokeColor/strokeWidth/padding/verticalAlign` 字段，不写 `shapePresetId`，不暗改 `balloonKind`、文字或尾巴。
- 配色必须双向保护 `resolveLayoutBalloonVisualRoleV1()` 的 thought/shout 保留色对：普通 speech 不能“撞入”保留色对；已经依赖保留色对显示 thought/shout 轮廓的 speech 也不能因改色“离开”并退回普通轮廓。此类对象在 P2 禁用任意配色，只允许保持对应保留色对；每个 kind/preset 都增加 renderer golden。无法证明双向安全的任意配色整体推迟到 V3。
- UI 明确区分：`transform.opacity` 会让泡体、描边和文字整体透明；`fillColor/strokeColor` 的 RGBA alpha 只改变泡体或描边。
- 拟声字入口：基于现有 `TextElement.semantic="sfx"` 和 `text.set_semantic` 提供字体、描边、旋转和配色预设；验证保存恢复、正式渲染和 V2 `style/text` 保护。
- 完整图层管理器：锁定、显隐、排序和阅读顺序提示；本阶段不加入“改名”，避免在“只开放已有命令”名义下暗增协议。
- 富文本入口整理：横排/竖排、字体、字重、字距、行高、描边和段落对齐；
- 预设始终展开为现有显式字段和命令 batch，不保存不透明 preset 状态。

验收：

- 不升级 Schema；
- 所有新入口都能 Undo/Redo、自动保存、恢复并通过现有 renderer；
- 智能重排按实际动作尊重用户形成的 `geometry/style/text/tail` 保护；SFX 旋转和整对象透明度属于 `geometry`。
- Shared reducer/inverse 测试覆盖每种 preset 与 SFX；UI E2E 覆盖保存恢复和保护；renderer golden 覆盖页漫/条漫、横竖排和四类气泡。

P0 是发布硬门，但不要求所有开发工作绝对串行。P1.1 与纯现有字段的 P2 可以在 P0 契约冻结后并行开发；任何一项都不能在 P0 未通过时宣称形成可交付“漫画成稿”。

### P3：经新 ADR 批准后再评估 LayoutDocument V3

ADR-0011 和 ADR-0019 当前明确把滤镜、混合模式等排除在首版/智能成稿范围外。V3 不是本文自动授权的实施阶段；只有真实用户返修数据证明需要，且新 ADR 明确 amend/supersede 现有边界后，才评估：

- 更多受控气泡轮廓与显式、版本化 `shapePresetId`；
- 显式 `visualRole`，消除通过颜色反推气泡轮廓的隐式耦合；
- 文字阴影、发光、渐变或有限 SFX 效果；
- 非破坏亮度、对比度、饱和度、灰度、tone/halftone；
- 必要的蒙版或 blend。

连接气泡、多尾巴不是单纯外观字段，涉及 tail 数组、对象连接拓扑、删除语义和独立保护；不进入 V3 首个 appearance 切片，若未来需要必须另行设计。

V3 至少需要：

| 位置 | 要求 |
| --- | --- |
| Schema/Codec | 新增明确的 `BalloonAppearance`、`TextAppearance`、`ImageAppearance`，严格限值和规范化 |
| 命令 | 每个新字段有 reducer、inverse、batch 和 changed-field 证据 |
| 人工保护 | 新增版本化 `appearance` scope；不改变现有 `style` 含义，图片 appearance 不能错误套用文字/气泡 style |
| 数据库 | 扩展允许的 `documentKind/schemaVersion`，只允许前向升级 |
| Preflight | 校验参数、溢出、分辨率、字体和 renderer capability |
| RenderPlan/Renderer | Web、只读预览和 Server 使用同一版本化语义 |
| 版本身份 | 升级 renderer/policy identity，重跑 PNG/PDF/条漫黄金图 |
| 迁移 | V2 的 automation/bindings/protections 原样保留；V1 先执行现有保守保护升级再进入 V3；所有既有可见对象在新 `appearance` scope 上沿用现有 `explicit_preserve` reason，用户显式释放后智能能力才可修改；历史 Revision 永不重写 |

不能把新效果字段塞进 V2 `automation`。V2 的设计承诺是“可见内容无损投影为 V1”，新增滤镜、阴影或新轮廓会破坏这个契约。

`shapePresetId`、balloon/image/text effect policy 都必须使用不可变版本身份；注册表更新不能让同一旧文档产生不同像素。

### P4：按真实需求评估专业图片处理

优先顺序：

1. 先使用派生 Asset 解决 AI 修图、背景移除、放大和复杂 tone；派生结果必须由用户选择并形成新 CandidateLockRevision，不能仅凭 Asset ID 直接进入布局；
2. 只有用户明确需要“在成稿中随时无损调参”，才扩展 V3 非破坏参数；
3. 不把完整 TUI Image Editor 或 Manga Editor Desu 嵌入主工作台。

## 7. 气泡设计的特别约束

当前 `balloonKind` 同时参与对白类型覆盖和智能成稿评分，不只是视觉外观。后续不能把 40 种轮廓继续塞进 `balloonKind`。

推荐拆分：

```json
{
  "balloonKind": "speech",
  "appearance": {
    "shapePresetId": "soft_ellipse_v1",
    "fillColor": "#FFFFFFFF",
    "strokeColor": "#111111FF",
    "strokeWidth": 3
  }
}
```

- `balloonKind`：对白语义，继续限定 `speech/thought/shout/caption`；
- `shapePresetId`：不可变、版本化的受控视觉轮廓；只属于经 ADR 批准的 V3，不进入 P2；
- 颜色、描边和效果：显式字段；
- 自动成稿先按语义选少量默认预设，用户再手调；
- 不通过 fill/stroke 颜色反推轮廓或视觉角色。

少量高质量、语义明确的预设，比一次性复制 40 多种样式更适合自动排版、质量评分、可访问性和稳定导出。

## 8. UI 原则

- 首次进入仍给出零设置完整成稿，不要求用户先学专业工具。
- 专业能力随选中对象出现在上下文属性区，不把全部按钮铺满工作台。
- 默认层级是“直接修例外”；高级属性可渐进展开。
- 画布交互和右侧精确数值输入并存。
- 所有智能动作先预览、后应用，可一次撤销，并清楚显示受人工保护而未改变的内容。
- 成稿内图片 AI 动作使用“生成一个可替换版本”的语言，避免误导为原图被就地覆盖。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 引入第二套状态/撤销/导出 | 第三方只做不持久化业务状态的 adapter；selection、viewport、dragging 等临时状态只留在会话内，唯一业务输入输出是内部文档和命令 |
| 专业能力掩盖 V2 无法出版 | P0 是硬前置，P1/P2 不代替正式闭环 |
| 预览与 artifact 偏差扩大 | 高级能力前先闭合权威预览语义；每次 policy 变更重跑 golden |
| GPL 或无许可证代码污染 | Manga Editor 只研究，不复制；Komiko 只看产品；依赖进入前生成许可清单 |
| Comical 与 Konva 双坐标/双渲染 | 默认不接；若 PoC，先过缩放平移、保存恢复、Undo 和统一导出四道门 |
| TUI/Fabric 与 Konva 双画布 | 不进入主工作台；必要时隔离为单图派生工具 |
| 画布内 AI 结果失去来源 | 所有结果创建 Task/Candidate/Asset，用户选择并锁定成新 CandidateLockRevision，更新 lock-set digest 后再用来源替换预览/命令应用 |
| 功能膨胀为通用图片软件 | 用真实返修数据决定 P3/P4，不以竞品功能数量驱动范围 |

## 10. 已接受决策

用户已确认并按以下方向完成本轮实现：

1. 接受“能力进入漫画成稿，但第三方完整编辑器不进入生产依赖”。
2. 接受发布依赖顺序为 `P0 含 V2 文档的正式出版 → P1 Konva 交互 / P2 已有能力显性化 → 经新 ADR 决定是否进入 P3 V3 视觉效果`；P1.1/P2 可在 P0 契约冻结后并行，但不能绕过 P0 交付。
3. Comical-JS 不作为默认气泡内核；只有新气泡轮廓需求被确认时，才做限时技术 PoC。
4. 图片滤镜、背景移除和 AI 重绘优先走 `Task → Candidate/Asset → 用户选择 → CandidateLockRevision → 来源替换预览`，不扩张当前 V1/V2 画布协议。
5. 本文状态改为 `active`，作为当前已实施边界的事实源；P3/P4 仍需新的用户决策与 ADR，不能由本次授权自动扩张。
