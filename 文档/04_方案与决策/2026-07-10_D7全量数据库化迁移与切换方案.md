# D7 全量数据库化迁移与切换方案

## 1. 文档定位

用户已为 D7 选择 B：立即全量数据库化。本方案不再讨论“要不要上数据库”，而是回答：

1. 什么叫 AI漫游的“全量数据库化”。
2. 哪些数据必须进入数据库，哪些字节仍应留在文件系统或密钥存储。
3. 当前 workspace 和内存状态怎样安全迁入，缺失历史怎样诚实处理。
4. 怎样切换、验证、回滚，并防止数据库和旧 JSON 变成双主源。

本方案的 D71–D76 已全部由用户确认，状态转为 `accepted`，并由 `ADR-0012_全量数据库化切换与持久任务边界.md` 采纳。2026-07-11 已补充 proposed 的 G1 逐阶段开发文档、Schema/旧数据映射和迁移验收清单；它们仍不等于开发授权。开始修改 Prisma schema、业务代码、数据库或真实 workspace 数据前，必须完成整套开发文档并由用户明确授权。

## 2. 结论摘要

### 2.1 推荐目标

> 数据库成为所有权威业务事实、关系、状态、修订、任务与可查询元数据的唯一可写事实源；图片、音视频、PDF、ZIP 等大文件继续放在受控 workspace，数据库用 Asset 记录其稳定存储键、摘要、大小、来源和状态；秘密进入系统密钥存储或加密存储，不进入普通业务表。

“全量数据库化”不等于“所有文件字节塞进 SQLite”，而是：

- 项目、章节、角色、结构、分镜、候选、定稿、画布、导出、任务、对话和待确认状态不再以 JSON/Map 为权威来源。
- Markdown/JSON 可以作为导入、导出、诊断或只读历史快照，但不能继续被应用读写为第二套业务事实。
- 每个素材文件必须有数据库 Asset 行；没有 Asset 的文件是待清理孤儿，有 Asset 但没有物理文件是完整性故障。
- 进程内 Map 只能做可重建缓存、活动连接或短生命周期锁，服务重启不能丢失用户已提交的事实。

### 2.2 已确认的切换方式

用户已确认采用：

> 可重复影子导入验证 + 短暂停写窗口 + 一次 DB-only 切换 + 旧元数据只读封存。

不推荐让生产路径长期双写数据库和 workspace JSON。两个存储之间没有共同事务，任何一次磁盘错误、进程退出或后续字段新增都会制造分叉事实。

## 3. 当前实现事实

### 3.1 Prisma 只是未接线骨架

当前 `apps/server/prisma/schema.prisma` 只有 6 个模型：

1. `Project`
2. `StoryVersion`
3. `Shot`
4. `Candidate`
5. `Asset`
6. `GenerationTask`

代码核验结果：

- lockfile 实际解析到 Prisma `6.19.3`。
- 仓库没有 `prisma/migrations/`，没有 `_prisma_migrations` 对应的数据库文件。
- `apps/server/src` 没有 `PrismaClient`、`PrismaService` 或任何 Prisma CRUD 调用。
- 当前脚本只有 `prisma validate`，只能证明 schema 语法有效，不能证明数据库已创建或业务已接入。
- 现有模型缺少 Chapter、Character、对话、pending 状态、定稿修订、LayoutRevision、ExportRevision 等当前正式领域对象。

因此 D7 不是“把少数遗漏 JSON 补进现有表”，而是一次主事实源迁移。

### 3.2 项目业务事实仍由整棵文件树承载

`ProjectRepository` 使用 `Map<string, LocalProject>` 作为进程内 identity map，启动后从 workspace 恢复，并在多数变更后顺序重写项目树：

| 当前文件 | 主要内容 | 当前问题 |
| --- | --- | --- |
| `project.json` | 项目元数据、当前章节、版式 | status 固定写 draft，运行时又另行派生 |
| `workflow.json` | 七步状态快照 | 与章节、任务和产物状态重复，容易漂移 |
| `script-outline.md/json` | 项目大纲正文与元数据 | 正文和元数据分离，跨文件无事务 |
| `shared/characters.json` | 项目角色 | 引用 Asset ID，但只能靠应用校验 |
| `shared/assets.json` | 素材索引 | 物理文件与记录无数据库约束 |
| `chapter.json` | 章节、正文摘要、版本指针 | 与 `script.md`、revision 文件重复 |
| `script.md` | 当前章节正文 | 加载优先级高于 chapter.json，可能产生双事实 |
| `script.versions/*.md` | 章节剧本版本 | 只能通过目录扫描恢复 |
| `script.revisions/latest.json` | 最近一次 AI 写入来源 | 只保留 latest，且与 chapter.json 重复 |
| `script-pending.json` | 待确认章节正文 | 确认状态依赖文件存在 |
| `structure.json` | 剧情结构版本 | 整体 JSON，缺少数据库引用约束 |
| `storyboard.json` | 正式分镜 | Shot 只存在文档内部 |
| `storyboard.pending.json` | 待确认分镜 | 与正式分镜靠文件名区分 |
| `preflight.json` | 出图准备确认 | 来源分镜关系靠 ID 与时间戳校验 |
| `candidates.json` | 候选记录 | 与素材、任务、镜头关系靠应用校验 |
| `layout/layout.json` | 当前排版 | 现有骨架尚无不可变修订 |
| `tasks/*.input/output/error.json` | 部分任务证据 | 不是任务索引，且只有部分任务写入 |

`saveProject` 是多次顺序 `writeFile`，没有临时文件交换或跨文件事务。中途失败时，项目树可能处于新旧混合状态。

### 3.3 关键运行态会随服务重启丢失

| 运行态 | 当前保存位置 | 后果 |
| --- | --- | --- |
| `GenerationTask` 列表与状态 | `TasksService.tasks Map` | 重启后任务中心清空，运行任务无法恢复 |
| task worker 注册与执行 | `workers Map` + Promise 队列 | 无 lease、heartbeat、重启接管 |
| 图片候选串行队列 | `ImageCandidateService.imageQueue` | 只保证当前进程串行 |
| 角色/场景参考图队列 | `CharacterReferenceService.characterReferenceQueue` | 只保证当前进程串行 |
| 对话线程、消息、工具结果、OpenCode session 映射 | `DialogueService.threads Map` | 刷新服务后对话历史消失 |
| 待导入剧本、灵感种子、大纲 | 3 个 pending Map | 用户待确认内容消失 |
| 待确认剧情结构 | `pendingStoryStructures Map` | 服务重启后无法继续确认 |
| 活动流式消息集合 | Set | 这是合法的短运行态，但最终消息状态必须持久化 |

`storyboard.pending.json` 与 `script-pending.json` 已开始补部分持久化，但整体仍不一致。

### 3.4 真实样例盘点

对当前 workspace 做只读盘点，未读取或输出任何密钥值：

| 指标 | 结果 |
| --- | ---: |
| 项目 | 1 |
| 章节 | 2 |
| 文件 | 82 |
| 总体积 | 约 54 MB |
| WebP | 64 |
| JSON | 14 |
| Markdown | 4 |
| Character | 12 |
| Asset 记录 | 67 |
| 正式 Shot | 15 |
| Candidate | 27 |

完整性正面证据：

- 67 条 Asset 记录均找到物理文件。
- Character 的参考图引用均能找到 Asset 记录。
- 27 个 Candidate 均能找到 Asset 和正式 Shot。

不可恢复缺口：

- Candidate/Asset 共引用 55 个唯一 taskId。
- 只有 1 个 taskId 存在 input/output artifact。
- 其余 54 个只能从 Candidate 与 Asset meta 恢复有限来源，不能伪造完整输入、状态、耗时或错误历史。

迁移必须把有完整证据的任务标为只读 `legacy_imported`，其余标为不可执行 `legacy_stub` 并使用 `partial/reference_only` 表达证据完整度；不可冒充完整成功任务，也不可自动重试。

## 4. 目标存储边界

| 数据类别 | 目标权威来源 | 文件系统角色 | 说明 |
| --- | --- | --- | --- |
| 项目、章节、状态、当前指针 | 数据库 | 只读导出/备份 | D1 版式锁定由数据库约束和服务校验共同保证 |
| 剧本、大纲、结构、分镜版本 | 数据库 Text/Json + 关系投影 | 可导出 Markdown/JSON | 不再从文件反向覆盖数据库 |
| 角色、场景、镜头、候选、定稿修订 | 数据库关系表 | 无权威 JSON | 需要外键、唯一约束和历史查询 |
| Layout Working Copy / Revision | 数据库 Json 文档 + 来源绑定表 | 导出预览文件 | 富文本和复杂对象保留结构化 Json，来源关系可查询 |
| 任务、尝试、输入、输出、错误 | 数据库 | 可选诊断导出 | task artifacts 不再承担任务索引 |
| 对话线程、消息、工具结果、待确认内容 | 数据库 | 不保存普通业务副本 | OpenCode session ID 是运行时映射字段，不是业务事实本身 |
| 图片、音频、视频、PDF、ZIP | Asset 表 + workspace 文件 | 保存真实字节 | Asset 保存 storageKey、sha256、bytes、mime、来源和状态 |
| Export manifest | 数据库 Json + 导出目录副本 | 随交付物复制一份 | 数据库是查询事实，文件副本便于独立交付 |
| 非秘密设置 | 数据库 | 可选配置导出 | 主题、provider ID、model ID、base URL 可入库 |
| API Key / token | 文本模型归 OpenCode 本地 auth；图片模型归后端 SecretStore | 不进入普通 workspace | 普通业务数据库只保存配置状态、secretRef/fingerprint，不保存明文 |
| UI 选择、缩放、抽屉开关 | 前端会话状态 | 不持久化或本地偏好 | 不进入领域数据库 |
| 可重建缓存、活动 SSE 集合 | 内存 | 无 | 重启后可从数据库恢复或安全丢弃 |

## 5. 关系表与 Json 文档的边界

SQLite 并不要求把所有结构拆成极细的表。当前 Prisma 6.19.3 已支持 SQLite `Json` 字段，但高级 Json 过滤仍有限。D73 已确认采用“关系核心 + 版本化 Json 文档 + 可重建投影”：

### 5.1 必须关系化

- 所有需要外键、唯一性、跨步骤引用、历史查询或事务切换的实体。
- 例如 Project、Chapter、Character、Shot、Asset、Candidate、CandidateLockRevision、GenerationTask、LayoutRevision、ExportRevision、ConversationThread。
- `Shot.currentCandidateLockRevisionId` 与新修订在同一事务提交。
- CandidateLockRevision、LayoutRevision、ExportRevision 不允许原地更新内容。

### 5.2 适合版本化 Json

- 剧情结构完整文档、分镜完整文档、LayoutDocument、RichTextDocument、task input/output/error、预检报告和导出 manifest。
- 这些文档必须有 `schemaVersion`、digest 和稳定 ID；不能保存任意无版本 JSON 字符串。
- 需要被跨模块引用的部分同时生成关系投影，例如 StoryVersion 的 Scene/Beat、StoryboardVersion 的 Shot、LayoutRevision 的图片来源绑定。
- 投影只能由版本服务在同一事务内生成或重建，不能成为第二个独立写入口。

### 5.3 不保存为普通 Json 字符串

- 新 schema 不继续使用 `structureJson String`、`inputJson String` 这种“JSON 塞字符串”的形式。
- 使用 Prisma `Json` 或明确 Text 字段；读取时仍需共享 schema 校验和版本迁移。

## 6. 目标模型分组

下表是 D7 目标领域，不是本轮可直接复制的最终 Prisma schema：

| 分组 | 首批模型 | 关键规则 |
| --- | --- | --- |
| 项目与章节 | Project, Chapter | Project.currentChapterId；comicFormat 创建后普通更新不可改 |
| 剧本与结构 | ProjectScriptOutlineVersion, ChapterScriptVersion, ScriptRevision, StoryVersion, StoryProjection | 版本不可变；current 指针事务切换 |
| 分镜 | StoryboardVersion, Shot, ShotCharacter | Shot 绑定正式版本；重排和编辑产生新版本或受控修订 |
| 角色与场景 | Character, CharacterVisualVersion, Scene | 视觉版本与 Asset 分离；被引用版本不可覆盖 |
| 生成 | GenerationTask, TaskAttempt | 状态机、lease、heartbeat、取消、重试、来源 digest |
| 候选与定稿 | Candidate, CandidateLockRevision | 收藏不驱动下游；current lock revision 事务更新 |
| 素材 | Asset, AssetReference | storageKey + sha256 + bytes + status；引用可审计 |
| 成稿 | LayoutWorkingCopy, LayoutRevision, LayoutSourceBinding, ExportRevision | Working Copy 可变，正式修订/导出不可变 |
| 对话 | ConversationThread, ConversationMessage, DialogueToolResult, PendingDialogueArtifact | 按 project + step + chapter 隔离；待确认状态可恢复 |
| 运维 | MigrationRun, OutboxEvent | 记录导入来源、校验结果、文件操作和删除恢复 |

## 7. 任务持久化与恢复

`GenerationTask` 表必须成为任务中心的唯一事实源；进程内 worker 只负责消费。

首版建议字段：

- `status/phase/progressPercent`
- `targetType/targetId/chapterId`
- `input/output/error` Json
- `sourceDigest/sourceRevisionIds`
- `attempt/maxAttempts/nextRunAt`
- `leaseOwnerId/leaseExpiresAt/heartbeatAt`
- `cancelRequestedAt/startedAt/finishedAt`
- `idempotencyKey/concurrencyKey/needsReview`

恢复规则：

1. 新任务先提交数据库，再由 worker 领取。
2. worker 通过条件更新领取 queued task，不能只把 ID 放入 Promise 链。
3. `running` 且 lease 过期时，只有可安全重放的任务才进入 `retrying + nextRunAt`；无法确认外部副作用的任务进入 `failed` 并记录 `WORKER_INTERRUPTED/needsReview=true`。
4. 取消先写 `cancelRequestedAt`；运行任务由 worker 协作中断并确认后才进入 `cancelled`，不能只改终态而让外部调用继续。
5. 任务结果必须在事务中检查项目仍存在、来源 digest 未变化，再登记 Candidate/Asset 或修订；每类任务还必须使用 idempotency key、已有产物检查和重复写保护。
6. 每次尝试追加不可变 `TaskAttempt`；provider 网络调用、文件哈希和大文件写入不放进长数据库事务。
7. 所有图片 provider 任务使用同一 `concurrencyKey`，V1 并发 1，替代分散的业务 Promise 队列。
8. 本地单用户首版使用单进程 worker，不同时引入 Redis/BullMQ；但任务状态不能再依赖内存。

## 8. 素材文件一致性

数据库无法与文件系统做一个共同 ACID 事务，因此需要显式状态和补偿：

1. 文件先写入同一 workspace 文件系统的临时路径。
2. 关闭文件并计算 `sha256/bytes/mime/width/height`。
3. 数据库创建 `Asset(status=staged)` 和来源记录。
4. 使用同文件系统原子 rename 移到最终 storageKey。
5. 数据库事务连接业务实体并标记 `ready`。
6. 启动恢复任务处理：staged 超时、物理孤儿、ready 但文件缺失、待删除文件。

删除项目也不能直接“数据库 cascade + rm”假装原子：

- 先在事务中把 Project 标记 `deleting`、取消任务并写 OutboxEvent。
- 文件 worker 幂等删除项目目录。
- 成功后完成数据库删除/墓碑；失败则可继续恢复，不允许删除一半后项目从 UI 消失且无记录。

## 9. 迁移实施阶段

### M0：冻结契约与建立迁移历史

- 设计目标 schema 和显式 `onDelete/onUpdate`。
- 生成并提交第一份 `prisma/migrations`；以后不能只改 schema 或使用 `db push` 作为正式升级流程。
- 增加 PrismaService、数据库健康检查、foreign key/integrity 检查和独立测试数据库。
- 明确 SQLite 数据库文件放在受控应用数据目录，不放项目子目录，也不放网络文件系统。

### M1：数据库仓储与 DB-only 业务垂直切片

- 建立 Project/Chapter/Version/Asset/Task 基础仓储和事务边界。
- 先用新建测试项目走数据库闭环，不读取真实 workspace 项目。
- 保持旧文件应用仍可运行，但两种模式不能同时对同一项目写入。

### M2：只读审计与幂等导入器

- 扫描所有 JSON/Markdown、版本目录、任务 artifact 和 Asset 文件。
- 产生 machine-readable MigrationReport，不修改源文件。
- 导入保留现有 ID、时间戳、版本号和相对 storageKey。
- 每条导入记录保存稳定 `migrationSourceKey`；重复运行只校验/更新同一迁移记录，不复制实体。
- 对 54 个缺完整 artifact 的任务创建同 ID 的 `legacy_stub`，只保存能证明的引用与证据；有完整 artifact 的 1 个任务按只读 `legacy_imported` 导入。

### M3：影子导入演练

- 从真实 workspace 备份副本导入一次性 SQLite 数据库。
- 校验实体计数、唯一约束、外键、digest、文件存在、Asset 摘要、current 指针和来源关系。
- 运行项目列表、章节读取、结构/分镜、候选、素材和任务历史的只读对照。
- 导入器必须可重复运行且报告结果稳定，才能进入切换。

### M4：停写切换

1. 应用进入维护模式，拒绝新的项目写入与任务创建。
2. 等待或取消运行任务；所有未完成 pending 状态要么持久化导入，要么由用户明确放弃。
3. 备份整个 workspace、设置密钥存储和目标数据库；记录 manifest/digest。
4. 对新数据库执行 `prisma migrate deploy`。
5. 执行最终导入与完整校验。
6. 将应用切到 `PERSISTENCE_MODE=db`，旧元数据目录改为只读封存。
7. 在仍未重新开放写入前完成冒烟测试；失败则恢复旧版本和切换前快照。
8. 验证通过后才重新开放写入。

### M5：DB-only 观察期

- 业务读写只访问数据库；不得在查询失败时静默回退 JSON。
- 原 workspace JSON/Markdown 保持只读快照，可用于审计和灾难恢复，不能继续同步。
- 每次启动执行 migration status、数据库完整性、任务 lease 和 Asset 文件抽样检查。
- 完成至少一次真实章节读写、候选任务、项目重启恢复、排版/导出和删除副本演练。

### M6：收缩旧路径

- 删除 `ProjectRepository` 的 workspace 业务读写职责和整树重写路径。
- 保留 AssetStorage、导出器、备份/恢复和显式 Markdown/JSON 导入导出工具。
- 将旧元数据移出活动项目目录或加只读标记，保留到验收退出标准满足后再由用户决定归档期限。

## 10. 回滚边界

回滚分为两个时间点：

| 时间点 | 可回滚方式 | 限制 |
| --- | --- | --- |
| 重新开放写入前 | 停新版本，恢复旧应用和切换前 workspace 快照 | 推荐的完整回滚窗口 |
| DB-only 已产生新写入后 | 回滚到仍兼容当前 DB schema 的应用版本，或恢复数据库备份 | 不能直接启动旧 file-only 应用，否则会丢失/分叉新写入 |

Prisma Migrate 不提供可依赖的自动数据 down migration。正式回滚依赖：

- expand-and-contract 兼容发布；
- 数据库与 workspace 备份；
- 切换闸门前不开放写入；
- 每个不可逆清理都有独立确认。

## 11. SQLite 与未来 PostgreSQL

当前仍推荐本地单用户阶段使用 SQLite：部署简单、真实数据量小、与既定技术方向一致。但必须接受：

- SQLite 即使使用 WAL 也只有一个 writer；长事务会阻塞写入。
- WAL 不适合把数据库放在网络文件系统。
- 启用 WAL 前需在 E0 验证运行时 SQLite 版本、checkpoint 和备份策略；不能仅靠 schema 决定。
- Prisma migration SQL 与 provider 绑定；将来 SQLite 切 PostgreSQL 需要新的迁移/基线和数据迁移流程，不能复用同一套 SQLite migration.sql。

当前 Prisma 事务支持 SQLite `Serializable`。D3 的新修订 + current 指针更新适合短事务，但 provider 网络请求、图像生成、文件写入和哈希不能放在事务内。

## 14. 已确认 D71：切换模式

### 方案 A：影子导入验证 + 短暂停写一次切换（推荐）

- 正式切换前，可以对真实备份重复导入临时数据库并做对照。
- 切换时暂停写入，最终导入校验通过后，数据库立即成为唯一可写事实源。
- 旧 JSON/Markdown 保留为只读快照，不再被应用读取兜底或继续写入。

优点：没有运行期双主源；回滚窗口清晰；最符合当前单用户、本地项目和“立即全量数据库化”。

代价：需要一次短暂停写；切换前必须把导入器和校验做到足够可靠。

### 方案 B：短期数据库 + JSON 双写，再停止 JSON

- 新版本同时写数据库和旧文件，观察一段时间后再关闭文件写入。

优点：表面上可以持续用旧文件对照。

代价：数据库与文件系统没有共同事务；必须处理一边成功一边失败、字段演进、顺序差异和补偿队列。对当前只有一个真实项目的本地应用，复杂度高于收益。

### 方案 C：长期数据库 + JSON/Markdown 双向同步

- 用户或旧代码可以改文件，应用也持续写数据库并尝试互相同步。

优点：文件始终可直接阅读和编辑。

代价：无法定义唯一事实源；冲突、丢字段、版本回退和任务来源漂移会成为永久问题，与 D7 目标冲突。

### 14.1 D71 最终决定

用户连续确认选择 A。正式边界为：

- 切换前允许对 workspace 备份反复执行影子导入和校验，但影子数据库不承接正式业务写入。
- 正式切换进入维护模式，冻结业务写入与新任务；最终导入和完整性检查通过后才开放 DB-only 写入。
- 切换后旧 JSON/Markdown 只读封存，应用不得把它们作为读取兜底、写入目标或同步来源。
- 重新开放写入前失败，可以恢复 file-only 应用与切换前快照；DB-only 已产生新写入后，不允许直接退回 file-only 版本。
- 不建设运行期数据库 + JSON 双写补偿层，也不建设双向同步。

## 15. 已确认 D72：首版数据库引擎

### 方案 A：本地 SQLite 单引擎，保持 PostgreSQL 可迁移（推荐）

- D7 首版只部署一个本地 SQLite 数据库，由当前单个 NestJS 服务进程访问。
- schema 优先使用 Prisma 跨数据库共同能力：字符串 ID、DateTime、Json、显式索引、唯一约束和外键动作。
- 不把 SQLite 数据库放到网络文件系统；是否启用 WAL 必须在 E0 验证实际运行时 SQLite 版本、checkpoint、备份和故障恢复。
- 当产品进入多人、远程部署、多服务实例或持续写竞争时，再执行独立 SQLite → PostgreSQL 数据迁移。

优点：符合当前本地单用户产品形态；部署和备份简单；D7 可以集中解决事实源、版本、任务与迁移，而不是同时建设数据库运维平台。

代价：只有一个 writer；未来转 PostgreSQL 需要新的 provider-specific migration history 和数据迁移演练。

### 方案 B：本轮直接使用 PostgreSQL

- 现在就部署本地或远程 PostgreSQL，并把 D7 所有 schema、migration、备份与运行环境按 PostgreSQL 建设。

优点：并发写、多实例、远程部署和未来团队协作的上限更高。

代价：当前只有本地单用户和单服务进程，却要立即承担数据库进程、账户、端口、安装升级、备份恢复和部署运维；会扩大本轮范围。

### 方案 C：首版同时支持 SQLite 与 PostgreSQL

- 同一版本允许用户选择两种 provider，并维护两套 migration history、集成测试、备份恢复和运行配置。

优点：部署选择最多。

代价：Prisma migration SQL 与 provider 绑定，不能共用；首版迁移与故障矩阵接近翻倍，最容易让“全量数据库化”迟迟无法真正切换。

### 15.1 D72 最终决定

用户连续确认选择 A。正式边界为：

- D7 首版只部署一个本地 SQLite 数据库，并只允许当前单个 NestJS 服务进程访问业务数据库。
- 数据库文件放入应用管理的本地数据目录，不放到 NAS、共享盘、云盘同步目录或其他网络文件系统。
- schema 和业务查询优先使用 SQLite/PostgreSQL 共同支持的 Prisma 类型与操作；“可迁移”不代表共用 migration history。
- 是否开启 WAL 不作为默认前提，必须先在 E0 验证实际 SQLite runtime、checkpoint、在线备份、异常退出和恢复行为。
- 多用户协作、远程部署、多个服务实例或持续写竞争中的任一条件成立时，触发独立的 SQLite → PostgreSQL 评估、provider-specific migration 与数据搬迁演练。
- V1 不交付双 provider 运行开关、双 migration history、双引擎集成测试或 SQLite/PostgreSQL 在线同步。

## 16. 已确认 D73：关系表与复杂文档边界

这个决策不是“关系数据库和 Json 二选一”，而是决定哪类事实由关系约束保证，哪类复杂文档保持整体结构，以及如何同时满足查询与版本演进。

### 方案 A：关系核心 + 版本化 Json + 可重建投影（推荐）

- Project、Chapter、Character、Shot、Asset、Candidate、CandidateLockRevision、GenerationTask、LayoutRevision、ExportRevision、ConversationThread 等需要身份、外键、唯一性、当前指针、跨阶段引用或历史查询的对象进入关系表。
- 剧情结构、分镜源文档、LayoutDocument、RichTextDocument、任务 input/output/error、预检报告和 export manifest 作为不可变或受版本控制的 Prisma `Json` 文档保存，并携带 `schemaVersion`、digest 与稳定 ID。
- 需要检索或跨模块引用的文档片段生成“关系投影”：例如从 StoryVersion 文档提取 Scene/Beat 索引，或从 LayoutRevision 提取图片来源绑定。
- 投影由版本服务在保存文档的同一事务中生成，也能从权威文档重建；业务代码不能单独编辑投影，因此它不是第二个事实源。
- 不继续使用 `structureJson String`、`inputJson String` 这类把 JSON 当普通字符串保存的模型。

优点：关键关系可由数据库约束和查询；复杂文档仍能整体版本化；D3 的影响分析与 D4/D5 的富文本/画布不会被拆成大量脆弱小表。

代价：需要共享 Json schema 校验、文档升级器、digest 规则和投影重建测试；保存复杂版本时必须保证“文档 + 投影 + current 指针”同事务一致。

### 方案 B：所有内容完全关系化

- Scene、Beat、分镜节点、画格、文字 run、气泡轮廓、样式属性和任务输入字段都拆成独立表与行。

优点：每个细粒度字段都可直接 SQL 查询、约束和局部更新。

代价：富文本与 LayoutDocument 会产生大量表、排序列、连接关系和 migration；文档结构每次演进都会放大 schema 变更、联表查询与兼容成本，不适合当前仍在收口的编辑器模型。

### 方案 C：以 Json 文档为主，只保留少量顶层关系表

- 只把 Project、Chapter 等顶层对象关系化，角色、镜头、候选、定稿、任务和布局来源大多嵌入 Json 文档。

优点：首批导入和模型变化最简单，接近当前文件树的表达方式。

代价：无法可靠使用外键、唯一约束和事务切换来保证 D1/D3；跨阶段查询、任务恢复、影响预览、素材删除保护和历史来源追踪都会重新依赖应用层扫描。

### 16.1 “投影”的通俗定义

投影可以理解为“从权威版本文档自动生成的关系索引”。例如 StoryVersion 的完整结构 Json 是事实源，`StorySceneProjection` 只保存可查询的 scene/beat ID、顺序和引用。投影损坏时应能从原文档重建，任何页面都不能绕过版本服务直接改投影。

### 16.2 D73 最终决定

用户确认选择 A。正式边界为：

- 身份、外键、唯一约束、当前指针、跨阶段引用、任务状态和历史检索进入关系表。
- 剧情结构、分镜源文档、LayoutDocument、RichTextDocument、任务载荷、预检和 manifest 使用带 `schemaVersion`、digest 与稳定 ID 的 Prisma `Json`。
- 可查询的 Scene/Beat、Shot 来源和 Layout 来源绑定由权威版本文档生成关系投影；投影不得被页面或普通 CRUD 独立修改。
- 保存正式版本时，“Json 文档 + 关系投影 + current 指针”必须在同一数据库事务内完成；投影必须有确定性重建命令与一致性测试。
- 新模型禁止继续增加 `structureJson String`、`inputJson String` 一类把 JSON 当普通字符串保存的字段。

## 17. 已确认 D74：按调用运行时划分密钥所有权

### 17.1 当前代码与澄清

- `SettingsService` 当前把文本 provider、OpenAI 图片、豆包图片和 Grok 图片的 `apiKey` 都作为明文字段写入 `workspace/settings/app-settings.json`；`.gitignore` 只能阻止误提交，不能保护静态文件。
- 文本对话发送前，`OpenCodeRuntimeService.syncConfiguredAuth()` 会向本机 `127.0.0.1` 上的 OpenCode `PUT /auth/{providerId}`；这里的“发送给 OpenCode”不是发送到 OpenCode 云端，而是交给本机 `opencode serve` 保存和调用模型服务商。
- OpenCode 自己的本地 `auth.json` 属于其正常凭据机制。用户明确接受它保存文本模型 key；问题在于 AI漫游不应再把同一文本 key 重复存进自己的 JSON 或 SQLite。
- 图片生成由 `ImageProviderService` 在 NestJS 后端直接调用，不经过 OpenCode，因此图片 key 必须由 AI漫游后端拥有并安全保存。

### 17.2 修正版方案 A（已确认）

#### 文本模型凭据

- OpenCode 本地 `auth.json` 是文本模型 key 的权威存储；AI漫游不复制或导入该文件内容。
- 用户从 AI漫游设置页新增、替换文本 key 时，后端通过 localhost 一次性交给 OpenCode；AI漫游只保存 `providerId/modelId/baseUrl/configured/fingerprint/updatedAt` 等非秘密元数据。
- 清除或替换文本 key 时调用 OpenCode 对应 auth 操作；数据库备份和 AI漫游 workspace 不包含该 key。

#### 图片模型凭据

- NestJS 内建立唯一 `ImageCredentialStore`/`SecretStore` 接口；系统凭据库可用时，macOS 使用 Keychain、Windows 使用 Credential Locker、Linux 桌面会话使用 Secret Service。
- 无桌面会话时允许使用只读环境变量或由部署密钥提供主密钥的加密存储；禁止把加密主密钥与密文文件并排保存。
- 数据库只保存 `credentialId/providerId/secretRef/source/fingerprint/configured/updatedAt`；OpenAI 图片、豆包和 Grok 各自独立，不共用文本模型 key。
- “后端保存”是指密钥静态加密、只允许 NestJS 运行时读取；调用图片 provider 时，明文只在后端进程内短暂存在并通过 HTTPS Authorization 发送，不得持久化或返回前端。
- 设置 API 只接受一次性写入、替换和清除；成功后前端只能读取配置状态、来源和 fingerprint，不再返回 key 首尾预览。
- 请求日志、错误详情、GenerationTask input/output/error、task artifact、数据库、workspace、导出物和普通备份均不得出现图片 key；日志中必须对 `authorization/apiKey/token` 字段统一脱敏。

#### 迁移与清理

1. 文本 key：若旧 `app-settings.json` 有值，先通过 localhost 写入并验证 OpenCode 已配置，再从 AI漫游设置文件移除；不读取或整体迁移用户全局 OpenCode auth。
2. 图片 key：逐个写入 ImageCredentialStore，读取校验 fingerprint 后，数据库写非秘密 metadata，再原子移除旧明文字段。
3. D71 的旧元数据快照必须先脱敏；不能原样封存包含任何图片 key 的旧 settings 文件。
4. 替换或清除图片 key 后，立即失效后端内存缓存；既有运行任务可完成或按 D75 取消规则终止，但新任务只能读取新凭据。

### 17.3 D74 最终决定

用户先选择 A，随后明确修正边界：OpenCode 保存文本模型 key 没有问题；图片模型由后端直接调用，必须由后端安全保存且不得暴露任何持久化或接口明文。以上修正版 A 为正式口径。

## 18. 已确认 D75：首版任务执行底座

### 18.1 当前代码证据

- `TasksService` 使用进程内 `Map` 保存任务，创建后立即 `void runRegisteredWorker()`；服务重启后任务、顺序和 worker 绑定全部丢失。
- 当前 `maxAttempts=1`，失败只记录 `retryable`，没有自动重试、backoff、TaskAttempt、lease、heartbeat 或启动恢复。
- `cancel()` 会直接把任务标为 `cancelled`，但运行中的 provider 请求没有统一 AbortSignal；状态可能先显示取消，外部调用和文件写入仍在继续。
- Candidate、Character/Scene reference 分别使用 Promise 链串行；它们是限流手段，不是持久队列，重启后无法恢复。
- D72 已确认本地 SQLite 单引擎和单 NestJS 进程；当前产品量级尚不需要额外 Redis 服务或多机 worker。

### 方案 A：数据库任务表 + 单进程持久 worker/lease（推荐）

- `GenerationTask` 是唯一业务事实源，`TaskAttempt` 保存每次尝试；进程内只保留唤醒信号和当前 AbortController，不保存权威队列。
- 同一 NestJS 进程运行 worker：入队后主动唤醒，同时保留短周期数据库扫描兜底；即使丢失内存通知，`queued/retrying` 任务仍会被发现。
- worker 用短事务原子 claim 任务并写 `leaseOwnerId/leaseExpiresAt/heartbeatAt/attempt`；provider 网络调用、哈希和文件写入全部在事务外执行。
- 执行语义为 at-least-once，不承诺绝对 exactly-once。每类任务必须有 idempotency key、来源 digest、已有产物检查和重复回写保护。
- 启动时扫描过期 `running` lease：可安全重试的任务进入 `retrying + nextRunAt`；无法判定是否已产生外部副作用的任务进入 `failed` 并标记 `WORKER_INTERRUPTED/needsReview`，不盲目重跑。
- 排队任务可直接原子取消；运行任务先写 `cancelRequestedAt`，worker 协作中断后才进入 `cancelled`。无法中断的 provider 响应回来后不得覆盖已经取消或来源过期的正式事实。
- 使用 `concurrencyKey` 管理资源通道：首版所有图片 provider 任务默认同通道并发 1，替代分散的两个 Promise 队列；本地轻量导出可定义独立通道。
- 重试只针对明确可重试错误，使用有限次数与 backoff；每次尝试独立记录错误、开始/结束和产物，不改写旧 attempt。

优点：满足当前本地单用户部署，不引入 Redis；任务重启恢复、取消、重试、来源隔离和审计都以同一 SQLite 事实源完成。

代价：需要自己实现 claim、lease、heartbeat、backoff、启动恢复和故障注入测试；未来多实例时仍要复核 SQLite 写竞争或迁移 PostgreSQL/BullMQ。

### 方案 B：本轮直接引入 BullMQ + Redis

- Redis/BullMQ 承担调度、锁、延迟重试和多 worker；数据库继续保存业务任务与历史。

优点：成熟的分布式队列、并发、stalled recovery 和多机扩展能力，未来吞吐上限更高。

代价：本轮立即新增 Redis 进程、部署、备份和监控；还必须用 Outbox 解决“数据库任务已创建但 Redis job 未入队”或反向成功的问题。BullMQ 最坏情况下仍是 at-least-once，幂等和来源校验不能省略。

### 方案 C：任务写数据库，但继续依赖当前 Promise/void 调度

- 把 `GenerationTask` 行持久化，创建时仍直接触发当前内存 worker 和 Promise 串行链。

优点：改动最小，任务列表重启后还能看见。

代价：重启后的 queued/running 任务不会自动恢复；取消仍可能只改状态不停止执行；数据库只是“任务日志”，没有成为真正执行底座，与 D7 目标不符。

### 18.2 D75 最终决定

用户确认选择 A。正式任务执行契约为：

1. `GenerationTask` 是任务生命周期、排队顺序和当前执行权的唯一事实源；每次 claim 新建 `TaskAttempt`，结束时只允许一次终结写入，终结后不可改写；进程内 `Map/Promise` 不再承载权威任务状态。
2. 首版由同一个 NestJS 服务进程运行持久 worker；新任务写入数据库后主动唤醒 worker，同时使用数据库轮询兜底，避免内存通知丢失后任务永久停留。
3. claim 必须在短事务内原子完成，并写入 `leaseOwnerId/leaseExpiresAt/heartbeatAt`；provider 网络请求、文件写入、摘要计算和渲染不得放进长数据库事务。
4. 执行语义为 at-least-once。每种任务必须定义 `idempotencyKey`、`sourceDigest`、已有产物检查和重复回写保护，不能承诺不存在的 exactly-once。
5. 服务启动时扫描过期 lease：可安全重放的任务按有限重试与 backoff 进入 `retrying`；无法确认外部副作用的任务进入 `failed`，记录 `WORKER_INTERRUPTED` 与 `needsReview=true`，不盲目再次调用供应商。
6. `queued/retrying` 可直接原子取消；`running` 先写 `cancelRequestedAt`，worker 确认协作中断后才写 `cancelled`。迟到的 provider 响应不得覆盖已取消任务、已过期来源或新的 current 指针。
7. 使用 `concurrencyKey` 统一资源通道。V1 所有图片 provider 任务共享并发 1 的图片通道，替换 Candidate 与 Character/Scene reference 中分散的 Promise 链；轻量本地导出可使用独立通道。
8. V1 不引入 Redis/BullMQ、不运行多个业务 worker 进程。出现多服务实例、远程部署、持续队列积压或需要跨机器 worker 时，再联合评估 PostgreSQL、BullMQ/Redis 与 Outbox。

这是一项已接受但尚未实现的目标契约；当前代码仍是内存任务与 Promise 串行队列。

## 19. 已确认 D76：缺失旧任务历史迁移口径

### 19.1 当前数据证据

- 当前只读样例中，Candidate 与 Asset 共引用 55 个唯一 `taskId`。
- 只有 1 个 `taskId` 能找到完整 task artifact；另外 54 个只能证明“某条 Candidate/Asset 曾记录过这个 ID”，无法证明原始输入、provider、尝试次数、开始/结束时间或最终生命周期。
- 67 个 Asset 对应物理文件均存在，因此可以保留“产物和引用存在”的证据；但“文件存在”不能反推出某个任务一定以 `succeeded` 正常结束。

### 方案 A：保留原 taskId，导入不可执行 legacy stub（推荐）

- 有完整 artifact 的 1 个任务按完整历史任务导入为 `recordKind=legacy_imported/provenanceStatus=complete`，并只迁移来源能证明的字段；它仍是历史只读记录，不进入新队列。
- 其余 54 个 ID 创建同 ID 的非执行记录：`recordKind=legacy_stub`、`provenanceStatus=reference_only|partial`、`retryDisabled=true`、`maxAttempts=0`、`importSource=workspace`、`importedAt`。
- Candidate/Asset 保持对原 `taskId` 的外键引用；`observedEvidence` 只记录可验证的引用、文件路径、摘要、来源文档和 artifact 是否存在。
- 无证据的 input/output/error/provider/attempt/startedAt/finishedAt 保持空值，不根据文件时间或目录名猜测。
- `legacy_imported/legacy_stub` 均不进入 active queue、claim、取消或重试；界面只在历史/来源区域显示，不能混入“排队中/执行中/失败可重试”列表。
- 可执行生命周期与来源完整度分开表达：`recordKind=runtime` 才能拥有可执行状态；`legacy_stub.status=null`，不得把它伪装为 `succeeded/failed/cancelled`。若完整旧证据能证明终态，只能在 `legacy_imported` 上保存该已证明终态。
- 重复导入按原 `taskId` 幂等合并；只有发现更强的原始证据时才提升 `provenanceStatus`，不得覆盖已经确认的历史字段或降级证据。

优点：保留 Candidate/Asset 到原任务 ID 的完整关系，统一历史查询和来源追溯，同时诚实表达“我们只知道引用存在”。

代价：任务模型需要把“可执行生命周期”和“迁移来源完整度”分开；历史页面也要解释 legacy stub，不能把所有行都展示成普通成功/失败任务。

### 方案 B：只导入完整任务，其余引用降级为字符串

- 只把有完整 artifact 的 1 个任务导入 `GenerationTask`。
- 另外 54 个 Candidate/Asset 的任务外键置空，仅保留 `legacySourceTaskId` 字符串。

优点：可执行任务表最纯粹，schema 较简单。

代价：绝大多数旧产物失去统一外键和任务历史查询能力；后续每个来源页面都要同时处理 `taskId` 与 `legacySourceTaskId`，会削弱 D3/D7 的版本谱系。

### 方案 C：根据现有产物推断并补造成功任务

- 根据 Asset 是否存在、文件时间、目录或 Candidate 状态，推断 provider、输入、时间与 `succeeded` 状态，生成看似完整的历史任务。

优点：迁移后任务列表表面最完整。

代价：把推测写成事实，会污染审计、重试、成本、来源 digest 和故障分析；文件存在也无法证明任务正常结束。该方案不推荐。

### 19.2 采纳理由

推荐 A。它保留原 ID 和关系，又不会伪造不存在的任务详情；后续详细 schema 只需把 `recordKind/provenanceStatus` 与 D75 的可执行 lifecycle 明确分层。

### 19.3 D76 最终决定

用户确认选择 A。正式边界为：

1. 新系统可执行任务使用 `recordKind=runtime`；旧完整记录使用 `legacy_imported`；只有引用证据的旧 ID 使用 `legacy_stub`。
2. `legacy_imported/legacy_stub` 一律历史只读、禁止 claim、取消、重试和新增 attempt；需要重新生成时必须创建新的 runtime task，并绑定当前有效来源。
3. Candidate/Asset 保留原 taskId 外键；旧 taskId 不降级为散落在各表中的字符串字段。
4. `provenanceStatus` 使用 `complete/partial/reference_only`，只允许随更强原始证据单向提升；每个已恢复字段必须能追溯到证据来源。
5. `legacy_stub.status=null`，未知 input/output/error/provider/时间/attempt 保持空；文件存在、Candidate 状态或文件时间均不能推断任务成功。
6. 导入器按原 taskId 幂等；重复影子导入结果必须一致，发现完整 artifact 时可以把 stub 提升为 `legacy_imported`，但不能静默覆盖相互冲突的证据。

- 没有把二进制文件或明文密钥误定义为普通业务数据库内容。
- 当前 Prisma 未使用、workspace 主事实、内存任务/对话和真实样例缺口均有代码或只读数据证据。
