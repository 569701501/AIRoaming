## 1. 状态

已采纳。

## 2. 背景

AI漫游当前只有两份原始种子文档：产品文档和技术架构参考文档。种子已经表达了方向，但还不足以支撑后续持续开发：

- 产品范围需要拆成可执行 MVP。
- 技术架构需要明确数据模型、任务协议和素材路径。
- 文档需要正规、AI 可读。
- 每个功能完成后需要有稳定记录。
- 后续复杂任务需要像 AuroraPlatformWeb 的 `long_task` 一样保留计划、进度和发现。

## 3. 决策

### 3.1 建立九段式文档目录

采用以下目录：

```text
文档/00_索引
文档/01_愿景与产品
文档/02_架构与契约
文档/03_模块梳理
文档/04_方案与决策
文档/05_执行与记录
文档/06_测试与验收
文档/90_模板
文档/99_原始种子
```

### 3.2 MVP 主线聚焦漫画生成闭环

MVP 主线确定为：

```text
故事输入 -> 剧情结构化 -> 分镜生成/编辑 -> 漫画图候选生成 -> 候选选择/锁定 -> 漫画排版导出
```

轻漫剧保留在 P0.5，只做基础合成，不抢主线复杂度。

### 3.3 功能完成必须留痕

每个功能完成后新增：

```text
文档/05_执行与记录/功能完成记录/YYYY-MM-DD_<功能名>.md
```

### 3.4 复杂任务使用三件套

复杂任务使用：

```text
task_plan.md
progress.md
findings.md
```

## 4. 理由

| 决策 | 理由 |
| --- | --- |
| 文档分层 | 避免产品事实、方案过程和执行记录混在一起 |
| MVP 聚焦漫画 | 角色一致性、分镜可控、候选选择是产品能否可用的核心 |
| 轻漫剧 P0.5 | 视频容易膨胀，先用已锁定漫画图做基础合成 |
| 任务三件套 | 复杂任务需要恢复上下文、记录发现、避免重复犯错 |
| 完成记录 | 保证每个功能都有可追溯的交付说明和验证证据 |

## 5. 影响

### 正向影响

- AI 进入项目时有明确入口。
- 后续功能开发有记录模板。
- 数据模型和任务协议更早固定，减少返工。
- 原始种子被保留，但不再承担长期事实源。

### 代价

- 文档数量增加。
- 每次功能完成需要多一步记录。
- 开发前需要先读相关事实源。

## 6. 替代方案

### 6.1 继续维护两份大文档

放弃原因：

- 难以记录功能完成历史。
- AI 很难判断哪些内容是当前事实、哪些是旧设想。
- 数据模型和任务协议会埋在长文中，不利于实现。

### 6.2 一开始做完整视频生产工具

放弃原因：

- 视频复杂度会掩盖漫画主链路问题。
- MVP 最需要验证的是分镜、候选、选择、排版，而不是复杂视频。

## 7. 验收标准

- `文档/README.md` 能作为总入口。
- AI 能从 `AI上下文入口.md` 理解项目当前状态。
- 产品、架构、数据、任务协议、素材路径有独立事实源。
- 功能完成记录和任务记录有模板。
- 原始种子有归档位置。
