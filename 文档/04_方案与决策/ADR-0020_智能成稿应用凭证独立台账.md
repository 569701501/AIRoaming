# ADR-0020 智能成稿应用凭证独立台账

## 1. 决策状态

已采纳。本决策只修正 ADR-0019 实施中的应用幂等证据存放位置，不改变“任务只生成建议、应用独立校验、正式版本与出版不自动创建”的产品边界。

## 2. 背景与问题

`layout_compose` 的任务输出可以可靠保存来源密封的初稿或重排命令，但任务成功不等于结果已经应用。用户可能在网络丢响应、刷新、重启或重复点击后再次请求应用，系统必须区分：

- 任务尚未应用；
- 初次成稿已经创建了哪一份 `LayoutWorkingCopy`；
- 重排结果已经创建了哪一份 `PendingEditorCommandSet`；
- 目标在应用后是否又被用户修改。

原开发方案假设现有关系模型足够，并考虑把应用结果附在任务记录上。代码核验发现，`GenerationTask.observedEvidenceJson` 受数据库约束限定为 legacy import evidence，运行时 `layout_compose` 不能复用；终态任务和任务输出也必须保持不可变，不能在应用阶段回写“已应用”状态。把凭证放到前端本地存储、Asset metadata 或可变 Working Copy metadata 都不能提供跨重启、跨客户端和事务内的 exactly-once 证据。

## 3. 决策

新增窄关系模型 `LayoutCompositionApplication`，作为 `layout_compose` 应用边界的不可变、每任务至多一条凭证。

### 3.1 记录内容

| 字段 | 含义 |
| --- | --- |
| `taskId` | 已成功的章节级 `layout_compose` 任务；全局唯一 |
| `projectId/chapterId` | 与任务、目标一致的作用域 |
| `result` | `initial_working_copy` 或 `pending_command` |
| `targetId` | 实际创建的 Working Copy 或 Pending command ID |
| `baseDocumentDigest` | 初次成稿为 null；重排为预览所基于的文档摘要 |
| `resultDocumentDigest` | 应用或预览后的 V2 文档摘要 |
| `targetRowVersion` | 创建时的目标行版本 |
| `createdAt` | 首次应用时间 |

该表不保存完整漫画文档、命令批次、Provider 输出、自由文本或正式版本内容。完整建议仍只在不可变 `GenerationTask.outputJson`，当前可编辑内容仍只在 `LayoutWorkingCopy`，待确认重排仍只在 `PendingEditorCommandSet`。

### 3.2 写入和重放规则

1. 初次成稿在同一业务事务内创建 V2 Working Copy 和应用凭证。
2. 重排在同一业务事务内创建 Pending command 和应用凭证；不直接修改 Working Copy。
3. 同一 `taskId` 只能有一条凭证，数据库拒绝更新凭证。
4. 重复 apply 先读取凭证，再验证目标仍存在且摘要、行版本和作用域匹配：
   - 目标仍是刚应用的状态：返回 `replayed`；
   - 用户已修改 Working Copy、预览已应用/放弃或目标不再匹配：返回明确冲突，不再写入。
5. 凭证只接受同作用域、`recordKind=runtime`、`type=layout_compose` 且已成功的任务；数据库 trigger 同时验证实际目标。
6. 项目删除继续走既有 Outbox 清理顺序，先删除应用凭证，再删除其目标和任务；不引入数据库级级联删除。

### 3.3 不变量

- 任务成功与应用成功仍是两个不同事实。
- 不修改终态 `GenerationTask`，不复用 legacy import evidence 字段。
- 不建立第二套 Working Copy、Revision、publication 或文件事实源。
- 不允许应用凭证绕过来源 current 校验、Working Copy CAS、人工保护或 Pending 预览。
- 应用凭证不能被用作“用户已经接受视觉质量”的证据。

## 4. 被否决的备选

| 备选 | 否决原因 |
| --- | --- |
| 回写 `GenerationTask.outputJson` | 破坏终态任务输出不可变性，也混淆生成结果与后续应用事实 |
| 复用 `observedEvidenceJson` | 数据库明确限制为 legacy import evidence，运行时任务不合法 |
| 写入 Working Copy automation metadata | 重排只创建预览时没有新的 Working Copy；后续编辑也会改变摘要，不能证明 exactly-once |
| 只依赖 Pending/Working Copy 查询猜测 | 无法稳定证明目标由哪次任务创建，丢响应和重复应用存在歧义 |
| 存在前端 localStorage | 不能跨设备、重启或事务恢复，也不能防止服务端重复写入 |

## 5. 影响与代价

- migration `0018_layout_document_v2_working_copy` 新增一张小型不可变台账及作用域/目标验证 trigger。
- Prisma 新增一个关系模型；Project、Chapter、GenerationTask 增加只读关系。
- 项目删除流程增加明确的凭证清理顺序。
- M4 需要覆盖初次应用、重排预览、丢响应重放、目标变化冲突和重启恢复。
- 代价是增加一个持久模型；收益是应用语义可证明、可恢复，不把业务幂等建立在猜测或可变记录上。

## 6. 验证标准

- [x] 同一 initial 任务重复 apply 不创建第二份 Working Copy。
- [x] 同一 reflow 任务重复 apply 不创建第二份 Pending command。
- [x] 初次应用后用户修改 Working Copy，再次 apply 返回冲突且不覆盖。
- [x] Pending 已应用或放弃后，原任务不得重新创建相同预览。
- [x] Server 重启后仍能根据凭证返回安全 replay 或冲突。
- [x] 非 `layout_compose`、非成功任务、跨项目/章节和错误目标均由服务层或数据库拒绝。
- [x] 凭证更新由数据库拒绝，项目删除按显式顺序完成。
