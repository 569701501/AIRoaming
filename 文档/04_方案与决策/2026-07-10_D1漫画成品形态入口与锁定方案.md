# D1 漫画成品形态入口与锁定方案

## 1. 本轮只解决什么

本方案只细化 D1，不进入功能开发，也不展开自由画布、气泡、局部重绘、数据库全量迁移或提示词工程的完整实现。

2026-07-10 用户已确认采用本方案：字段显示名使用“漫画版式”，入口放在现有创建项目弹窗；顶层只保留竖向条漫和分页漫画，四格归入布局模板。

2026-07-11 用户再次澄清：项目库中的创建按钮、`CreateProjectModal.vue`、提交调用和创建成功后进入第 1 步“剧本”的路径均已存在。D1/G3 只扩展现有弹窗，不新建创建入口、页面、向导或中间步骤。

用户已经确认：

1. 项目一开始必须选择漫画成品形态。
2. 选择控件默认值为空，不能替用户默认选择。
3. 创建项目后，漫画成品形态不能直接修改。
4. 选项需要参考市面主流漫画形态。
5. 入口确定放在现有“创建项目”弹窗。

用户曾提出字段显示名使用“漫画分格”。静态复核发现该词已在当前文档和代码中稳定表达漫画画格、三/四格布局、分格线和画布格子，不适合再同时表示条漫/分页漫画这一项目级阅读结构。最终确认：

- 领域正式术语继续使用“漫画成品形态”。
- 创建弹窗字段显示名使用更短的“漫画版式”。
- “漫画分格”保留给画布中的三格、四格、自由分格和格子调整。

上述术语和顶层枚举均已确认。详细开发仍需等待 D7 数据库迁移和总开发方案排期。

## 2. 现有事实与冲突

### 2.1 当前代码已经有对应字段

项目已有 `comicFormat`：

```text
vertical_scroll
page_horizontal
four_panel
```

它已经影响：

- 出图准备中的漫画形式说明。
- 角色/场景参考图 prompt。
- 候选图默认请求尺寸。
- 排版页面格式与默认宽高。
- 项目列表、工作台快照与本地 `project.json`。

因此 D1 不需要新增含义重叠的 `workType` 或 `outputType` 字段，应该收紧现有 `comicFormat` 的语义和写入规则。

### 2.2 当前实现与用户决策正好相反

| 事项 | 当前实现 | D1 新决策 |
| --- | --- | --- |
| 创建入口 | 只有项目名称 | 必须增加成品形态 |
| 默认值 | 后端缺省为 `vertical_scroll` | 默认空，用户必须明确选择 |
| 创建后修改 | 第 1 步“剧本”可修改 | 创建后不可直接修改 |
| 枚举层级 | 条漫、页漫、四格并列 | 需要重新判断四格是否属于顶层形态 |

现有产品文档明确写着“创建项目只保留项目名称，漫画格式后置”，所以 D1 一旦最终确认，必须同步修改产品流程、数据契约、模块说明和测试，不能只改弹窗。

## 3. 术语收口

用户口语中的“类型”在当前项目里有两个不同含义。为避免后续数据库和接口混乱，推荐使用以下正式术语：

| 正式术语 | 代码对象 | 是否可变 | 说明 |
| --- | --- | --- | --- |
| 项目媒介类型 | `ProjectType` | 当前不讨论 | 现有 `comic/light_motion/mixed`；D6 已后置，近期创建项目仍只用 `comic` |
| **漫画成品形态** | `ComicFormat` / `comicFormat` | **创建后不可变** | 决定连续滚动还是固定分页，是 D1 真正要锁定的对象 |
| 布局模板 | `LayoutPreset` / `layoutPresetId` | 可变 | 例如四格、三格、电影宽格、对话密集页；属于画布起始布局 |
| 发布规格 | `ExportProfile` / `exportProfileId` | 可变且需版本化 | 例如某平台宽度、切片高度、文件格式和体积限制；平台规则变化不应改变项目形态 |

用户界面推荐字段名为“漫画版式”，不推荐写“项目类型”“作品类型”或“漫画分格”：

- “漫画版式”能直接对应条漫/页漫这两种最终阅读结构。
- “漫画分格”在项目现有语言里已经对应 `Shot.comic` 画格、`PanelPlacement` 格子以及排版画布中的分格布局。
- 如果创建字段也叫“漫画分格”，用户会合理期待下拉项是单格、三格、四格或自由分格，而不是竖向条漫和分页漫画。

## 4. 市面主流形态复核

以下资料均于 2026-07-10 核验：

| 来源 | 公开事实 | 对 AI漫游的启发 |
| --- | --- | --- |
| [看漫画投稿指南](https://www.kanman.com/about/409275.html) | 官方投稿要求直接使用“条漫、页漫”两类表述 | 国内漫画交付的顶层划分可收敛为条漫与页漫 |
| [快看投稿入口](https://www.kuaikanmanhua.com/webs/send/letter) | 官方建议面向手机漫画阅读的条漫 | 竖向条漫应作为重要选项，但不能替用户默认选择 |
| [Tapas 发布说明](https://help.tapas.io/hc/en-us/articles/1260802028970-Series-Basics-How-to-publish-a-comic-episode-on-Tapas) | 单话图片宽度固定、总高度不限，并提供桌面/移动预览 | 条漫需要连续阅读预览和自动切片导出 |
| [Clip Studio 新建画布](https://help.clip-studio.com/en-us/manual_en/210_file/Creating_a_New_Canvas.htm) | 在新建入口先选 Webtoon 或 Comic，后续设置随项目类型变化；模板是另一个设置 | 支持把成品形态放在项目创建入口，并把模板与形态分开 |
| [Clip Studio Webtoon 导出](https://help.clip-studio.com/en-us/manual_en/540_comic/Webtoons.htm) | 长画布可连续导出或按高度切分为 JPG/PNG | 条漫形态应驱动预览和导出策略，而不是只改变标签 |
| [Amazon KDP 固定布局漫画](https://kdp.amazon.com/en_US/help/topic/G9GSTY4LTRT39D4Z) | 漫画、漫画书与 manga 使用 fixed layout、页面和 panel view | 分页漫画是独立且长期存在的主流交付形态 |

### 4.1 推荐的 V1 顶层选项

| 枚举 | 用户文案 | 说明 | 推荐状态 |
| --- | --- | --- | --- |
| `vertical_scroll` | 竖向条漫 | 手机连续滚动阅读；使用长画布、可分段图片导出 | 保留 |
| `paged_comic` | 分页漫画 | 固定页面阅读；支持单页、跨页和后续 PDF/印刷规格 | 用它替代含义过窄的 `page_horizontal` |

### 4.2 不建议继续作为顶层选项的内容

#### 四格漫画

“四格”描述的是页面或片段内有四个格子的叙事模板，不是阅读容器。四格可以出现在竖向条漫里，也可以出现在固定页里。继续与条漫、页漫并列，会把“成品形态”和“布局模板”混成同一个枚举。

推荐迁移为：

```text
ComicFormat = vertical_scroll | paged_comic
LayoutPreset = four_panel | three_panel | dialogue_dense | cinematic | custom
```

布局模板不需要在创建项目时选择，进入排版/画布后再选，并允许更换。

#### `page_horizontal`

分页漫画不等于横屏漫画。它可能是竖版单页、横版单页、跨页或印刷尺寸。推荐把正式枚举改成 `paged_comic`，页面方向和尺寸由后续页面/发布规格表达。

#### 轻漫剧、混合项目

D6 已确认后置，不应出现在本轮漫画成品形态下拉框中。

#### 印刷漫画、电子书

印刷、PDF、EPUB 或平台电子书描述的是交付渠道与技术规格。它们应建立在“分页漫画”之上，通过发布规格选择出血、分辨率、页面方向和文件格式，不再占用一个不可变项目形态。

#### 单幅漫画、绘本或插画

单幅内容没有当前七步章节流水线所依赖的连续镜头和章节成稿语义；绘本也有不同的文字流和页面模型。它们可以成为未来新的项目媒介类型，但不建议为了让下拉框看起来丰富而提前混入 D1。

#### 自定义

不建议首版提供“自定义成品形态”。它会绕过锁定契约，使画布、导出和验收失去确定边界。高级用户以后可在某种成品形态内部选择自定义页面或导出规格。

## 5. 入口位置推荐

### 5.1 放在项目库的“创建项目”弹窗

推荐直接扩展现有 `CreateProjectModal.vue`，不增加新页面或创建向导。

字段顺序：

```text
项目名称
漫画版式      [ 请选择漫画版式 ▼ ]
              根据选择展示一句用途说明
              创建后不可直接修改

取消                          创建项目
```

原因：

1. `comicFormat` 是项目级且不可变，必须在项目记录建立前确定。
2. 它影响所有章节、候选图默认比例、画布结构和导出，放到第 1 章或排版阶段都太晚。
3. 现有弹窗只增加一个必要字段，仍保持轻量，不需要再造一套 onboarding。
4. Clip Studio 等创作工具也是在“新建”入口先定项目形态，再展示形态相关设置。

### 5.2 具体交互

- 原生下拉框默认值为 `""`，第一项为禁用占位“请选择漫画版式”。
- 选择“竖向条漫”后显示：“适合手机连续滚动阅读，后续按长画布与分段图片导出。”
- 选择“分页漫画”后显示：“适合固定页阅读，后续按页面、跨页与 PDF/图片序列导出。”
- 字段下固定提示：“创建后不可直接修改；选错时需要新建或复制为另一项目。”
- 未选择时“创建项目”按钮禁用；提交时仍由服务端再次验证。
- 不增加推荐默认值，也不把竖向条漫排在带“推荐”字样的占位项中，避免用户无意识确认。

### 5.3 创建后的展示位置

| 位置 | 展示方式 | 是否可编辑 |
| --- | --- | --- |
| 项目卡片 | 小型“竖向条漫/分页漫画”标签 | 否 |
| 工作台项目头部 | 当前成品形态标签 | 否 |
| 第 1 步剧本元信息 | 只读字段 + 锁定说明 | 否 |
| 排版/导出页 | 作为画布容器和导出 profile 的上游约束 | 否 |

当前 `ProjectStoryPanel.vue` 中的“漫画格式”下拉框必须改为只读展示；不能只在创建弹窗锁住，仍让 PATCH 接口修改。

## 6. 数据与接口契约

### 6.1 共享领域枚举

推荐目标：

```ts
export const COMIC_FORMATS = ["vertical_scroll", "paged_comic"] as const;
export type ComicFormat = (typeof COMIC_FORMATS)[number];
```

四格改为布局模板枚举，不再属于 `ComicFormat`。

### 6.2 创建接口

`CreateProjectRequest.comicFormat` 从可选改为必填：

```ts
interface CreateProjectRequest {
  name: string;
  type: "comic";
  comicFormat: ComicFormat;
}
```

服务端规则：

- 缺失或空值：`400 COMIC_FORMAT_REQUIRED`
- 不在正式枚举：`400 COMIC_FORMAT_INVALID`
- 不再调用“缺失就回退 `vertical_scroll`”的 normalize 逻辑处理新建请求。
- 创建成功后把值写入正式项目记录和数据库。

### 6.3 更新接口

推荐从 `UpdateProjectDraftRequest` 删除 `comicFormat`。同时服务端保留防御性校验：如果旧客户端仍传入该字段且值与现值不同，返回：

```text
409 COMIC_FORMAT_IMMUTABLE
```

传入相同值也不建议继续接受并写回；过渡期可忽略，完成客户端升级后从接口 schema 移除。

### 6.4 数据库存储

D7 已选择“立即全量数据库化”。进入实际开发时，新的 `Project` 表至少需要：

```text
comic_format  TEXT NOT NULL
```

应用层只允许正式枚举值；数据库迁移脚本必须生成映射和异常报告。SQLite 不应依赖前端校验保证合法性。

这一字段属于项目身份的一部分，普通更新服务不提供写入口。未来若提供“复制为另一成品形态”，应创建新 `Project.id` 并执行显式转换任务，而不是原地 UPDATE。

## 7. 旧数据迁移

当前实际 workspace 只有一个项目，已明确保存：

```text
全职猎人暗黑大陆 -> vertical_scroll
```

推荐通用迁移规则：

| 旧值 | 新值/动作 |
| --- | --- |
| `vertical_scroll` | 保持 `vertical_scroll` |
| `page_horizontal` | 迁移为 `paged_comic` |
| `four_panel` | 保留 `layoutPreset=four_panel` 意图，但成品形态本身有歧义；列入 `format_confirmation_required`，由用户一次性选择竖向条漫或分页漫画 |
| 缺失或非法值 | 不静默回退；把项目列入 `format_confirmation_required` 迁移报告，用户确认一次后才能完成导入 |

迁移必须可重复执行且幂等。正式切换前输出：项目 ID、旧值、新值、处理状态和异常原因。

## 8. 与后续自由画布的边界

D1 锁定的是“最终阅读容器”，不是把画布做成死模板：

- 竖向条漫项目仍可在长画布内自由摆放、缩放、旋转、裁切图片和文字图层。
- 分页漫画项目仍可自由新建页面、调整页面内格子和跨页布局。
- D4/D5 选择的高自由编辑能力必须在对应容器边界内工作。
- 更换画格数量、四格模板或某页方向，不等于改变项目成品形态。

因此“形态不可变”与“画布高自由”不冲突：前者稳定交付契约，后者提供容器内部创作自由。

## 9. 需要顺手修正的现有耦合

当前 `getCandidateRequestedSize(comicFormat)` 直接用项目成品形态决定每一张候选图的宽高比：

```text
vertical_scroll -> 1024 × 1536
page_horizontal -> 1536 × 1024
four_panel -> 1024 × 1024
```

这在高自由画布下不够准确：分页漫画可以有竖格，条漫也可以有横向大场景。

推荐边界：

1. `comicFormat` 只提供镜头的默认画幅建议。
2. 分镜或画格增加可覆盖的 `targetAspectRatio` / `frameSpec`。
3. 候选图生成规格优先使用镜头/画格目标比例，再回退到项目形态默认值。
4. 该解耦应进入后续自由画布和候选图详细方案，D1 第一阶段不必同时重写全部生成逻辑，但必须留为显式依赖，不能继续把二者当成同一概念。

## 10. 分阶段实施建议

实际开发时按以下垂直切片执行；本轮只写方案：

### D1-A：领域契约与迁移规则

- 最终确认 `vertical_scroll/paged_comic`。
- 将 `four_panel` 移到布局模板。
- 定义旧枚举迁移和异常报告。
- 更新共享类型、数据契约与正式文档。

### D1-B：创建入口闭环

- 创建弹窗增加必选空值下拉框。
- 前端禁用无效提交。
- 服务端执行必填、枚举和不可变校验。
- 创建后直接进入现有工作台路径，不增加中间页面。

### D1-C：数据库正式存储

- 配合 D7 把 `comic_format` 写入新 Project 模型。
- 导入当前 workspace 项目并生成迁移报告。
- 数据库成为正式写源后，验证重启与重新读取不改变值。

### D1-D：创建后只读与下游贯通

- 剧本步骤移除可编辑下拉框。
- 项目卡、工作台和排版页展示只读形态。
- 出图准备、候选规格、画布和导出继续读取同一个正式字段。

### D1-E：验证与文档同步

- 完成 API、服务、迁移和 UI 测试。
- 更新产品用户流程、核心数据模型、模块依赖、接口契约和端到端验收。
- 用竖向条漫和分页漫画各创建一个真实项目，验证后续步骤读取一致。

## 11. 验收标准

### 11.1 用户路径

- 创建项目时“漫画版式”下拉框初始为空。
- 不选择成品形态不能创建。
- 选择两种形态均能创建并直接进入第 1 步剧本。
- 项目卡和工作台能看见已选形态。
- 创建后任何普通页面都不能修改该字段。

### 11.2 API 与数据

- 缺失、空值和非法枚举均被服务端拒绝。
- 旧 PATCH 客户端无法改变已创建项目的形态。
- 数据库字段非空，迁移后值与原项目一致。
- 服务重启、重新载入和任务执行后字段不漂移。
- 不存在新项目静默默认 `vertical_scroll` 的路径。

### 11.3 下游一致性

- 出图准备、候选图、画布、导出和 manifest 读取同一个 `comicFormat`。
- 竖向条漫进入长画布/切片导出路径。
- 分页漫画进入页面/图片序列路径。
- 四格只作为布局模板出现，不再改变项目身份。

### 11.4 测试建议

- shared：枚举、DTO 编译和旧值迁移映射测试。
- server：创建必填/非法/合法、不可变 PATCH、迁移幂等、重启恢复测试。
- web：创建弹窗空值、选择说明、提交 payload、创建后只读测试。
- E2E：分别创建竖向条漫与分页漫画，走到工作台并检查快照和下游展示。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 用户选错但无法修改 | 项目无法按预期交付 | 创建入口明确说明；后续提供“复制为另一形态”的转换能力，不原地修改 |
| 枚举重命名影响旧数据和测试 | 数据加载失败 | 独立迁移函数、异常报告、兼容读取期和幂等测试 |
| 把四格移出顶层后用户觉得选项减少 | 误以为不再支持四格 | 在排版模板中明确提供四格，并在创建说明中解释“稍后可选模板” |
| 形态继续决定所有候选比例 | 高自由画布仍受限 | 后续引入镜头/画格级目标比例，项目形态只提供默认值 |
| D7 全量数据库迁移范围过大 | D1 交付被数据库工程拖慢 | 先冻结 D1 领域契约；实现时把 D1 创建闭环作为数据库迁移后的第一个垂直验证切片 |

## 13. 本方案最终结论

1. 在现有项目库“创建项目”弹窗中，项目名称下方增加必选的“漫画版式”下拉框。
2. 下拉框默认空，只提供“竖向条漫”和“分页漫画”两个顶层选项。
3. 复用并收紧 `comicFormat`，不新增重复字段。
4. 创建后从 UI、DTO、服务和数据库四层共同保证不可直接修改。
5. 把 `four_panel` 迁移为可变的布局模板，把 `page_horizontal` 更名为 `paged_comic`。
6. 发布平台的尺寸和切片规则属于可变、可版本化的 `ExportProfile`，不与不可变的项目成品形态绑定成一个枚举。

本方案已进入 `accepted`，正式决策见 `ADR-0009_项目创建时锁定漫画版式.md`。接受方案不等于授权开始开发；仍需等待总开发文档与阶段排期。
