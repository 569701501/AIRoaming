1阶段 1 · 候选图体验（任务 A/B/C）

任务 A：单格重画 —— 明确语义（新批次，旧批保留）

低难度
现状问题

「再生成一组」和「生成候选」emit 的 payload 完全相同（只有 shotId + candidateCount），前端不告诉后端"这是重画"，也不清理旧候选。后端无条件 push，重复生成会无限累积候选且 UI 平铺，用户分不清哪组是哪次生成的。

设计：引入"批次(batch)"概念
  • 每个候选关联到生成它的 taskId（后端已存 candidate.taskId，dto.ts L1089） taskId 天然就是批次标识：一次"生成/重画"=一个任务=一批候选。无需新增字段。
  • 前端按 taskId 分组展示候选，每组标"第 N 次生成"（用任务 createdAt 排序） 改动：ImageCandidatesWorkspace.vue 的 selectedCandidates computed 改为按 taskId 分组
  • "重画此镜"做成与"生成"平级的一等按钮，文案明确为"重新生成（保留旧批）" 消除"再生成一组"的语义模糊；旧批次自动归入历史区（任务B配合）
改动文件
  • apps/web/src/components/workbench/ImageCandidatesWorkspace.vue selectedCandidates 改按 taskId 分组；按钮文案改"重新生成"；新增批次标签
  • apps/web/src/stores/workbench-store.ts（可选） generateImageCandidates 不需改签名，批次天然由 taskId 体现
数据流（改后）
用户点「重新生成」 → emit generateCandidates {shotId, count}
  → store.createTask(新 taskId)
    → 后端 push 新候选(带新 taskId)
  → runtime 拉回 snapshot
    → 前端 selectedCandidates 按 taskId 分组
      → "第1次"(task-A) | "第2次"(task-B) | ...  ← 批次清晰

任务 B：候选版本历史/批次展示（5 态 UI 落地）

中难度
现状问题

后端定义了 5 态 CandidateStatus = "generated" | "selected" | "locked" | "rejected" | "superseded"，但前端只展示"锁定/未锁定"两种视觉。用户挑一张后，其他候选无法明确"废弃"或"保留备选"，多组候选之间无区分。

设计：批次折叠 + 废弃/备选操作
  • 候选按批次(taskId)分组，最新批次默认展开，旧批次默认折叠（点击展开看历史） 对标 LlamaGen Version History；旧批不挡视线但随时可回看
  • 每张候选增加两个轻操作：「废弃」(status→rejected) 和 「设为备选」(status→selected) 让 5 态真正可用；锁定仍是主操作，废弃/备选是次操作
  • 废弃的候选灰态显示并可"恢复"（status→generated）
  • 锁定一张时，同批次其他候选自动转"备选"(selected)，旧批次已锁的转 superseded 后端 lockCandidate 已有部分此逻辑（image-candidate.service.ts L254-262），前端补充展示
改动文件
  • ImageCandidatesWorkspace.vue 候选网格改分组+折叠；候选卡加废弃/备选按钮；状态视觉(locked绿/selected蓝/rejected灰)
  • api.ts + workbench-store.ts 新增 setCandidateStatus(candidateId, status) action（若无现成）；或复用 lock + 前端本地标记
候选状态视觉对照
状态含义视觉来源
generated刚生成正常展示生成时默认
selected备选（可被快速切回）蓝色边框用户标记/锁定时其他转此
locked本章锁定绿色高亮+🔒lockCandidate
rejected废弃灰色半透明用户标记
superseded已被新锁定替代灰色小字lockCandidate 时旧锁
简化决策："废弃/备选"是否需要新后端 API，取决于是否要持久化。若只在 session 内标记，纯前端即可（snapshot.candidates 本地改 status）。若要持久化跨刷新，需补一个 PATCH /candidates/:id/status。建议 P0 先做持久化版（数据一致性更重要），单接口改动小。

任务 C：prompt 可见（不可编辑）

中难度
现状问题

prompt 拼装在 store 私有函数 buildCandidatePositivePrompt（workbench-store.ts L81-99）里，直接塞进任务 input，用户完全看不到。出图不满意时，用户无法判断"是 AI 理解错了哪部分"，只能盲目重试。

设计：生成前展示 prompt 预览
  • 把 buildCandidatePositivePrompt 从 store 私有提升为组件可调用的 getter 或抽到 utils/workbench-preflight.ts 作为纯函数，store 和组件共用
  • 候选图工作台在"生成候选"按钮上方，加一个可折叠的 prompt 预览区 展示：画面描述 / 构图 / 角色 / 风格 / 组合后的完整 prompt；默认折叠，点开看
  • P0 只读不可编辑（编辑后置 P1） 先解决"看不到"的透明度问题；编辑会引入 prompt 持久化和版本问题，复杂度高
  • 已生成的候选，展示其 promptDigest（后端已存）方便对比"这张图是哪个 prompt 出的" 候选卡角标显示 digest 前6位
prompt 预览区结构
┌─ 出图 Prompt（点击展开/折叠）─────────────┐
│  画面:  {shot.comic.panelDescription}      │
│  构图:  {shot.comic.composition}           │
│  角色:  {shot.characters.join}             │
│  风格:  {format} / {artStyle}              │
│  ─────────────────────────────────────     │
│  完整 prompt:                               │
│  {buildCandidatePositivePrompt(shot)}       │
│                              [折叠]         │
└────────────────────────────────────────────┘
改动文件
  • apps/web/src/utils/workbench-preflight.ts 或新 utils/candidate-prompt.ts buildCandidatePositivePrompt / getCandidateImageSize 提为纯函数
  • workbench-store.ts generateImageCandidates 改调提取后的纯函数
  • ImageCandidatesWorkspace.vue 新增 prompt 预览折叠区；候选卡加 digest 角标

2阶段 2 · 分镜体验（任务 D/E/F）

任务 D：分镜缩略预览（已锁候选图回显）

低难度
现状问题

分镜工作台 StoryboardWorkspace.vue 完全不读 snapshot.candidates，镜头卡里没有任何缩略图、候选图计数、locked 标记。用户在分镜阶段看不到"这个镜头已经画成什么样了"，必须切到候选图工作台才能看。

设计：镜头卡头部加缩略图 + 状态标
  • 镜头卡头部（shot.order 旁）加小缩略图（已锁定候选的图） 数据全通：shot.lockedCandidateId → candidates.find → assetId → api.projectAssetFileUrl
  • 缩略图旁加状态标：🔒已锁定 / 📷N张候选 / ○未生成 让分镜阶段就能看到每个镜头的出图进度
  • 复用 ImageCandidatesWorkspace.vue L158-165 + L345-350 的缩略图范式 getCandidatePreviewUrl(assetId) = api.projectAssetFileUrl(projectId, assetId)，现成
  • 有候选图但未锁定时，缩略图区显示最新一张候选的小图+数量 不只是看锁定图，未锁定的也能预览，辅助排序决策
改动文件
  • apps/web/src/components/workbench/StoryboardWorkspace.vue shot-card-head 加缩略图区；新增 getCandidatesForShot(shotId) 辅助；需从 props 拿 snapshot.candidates
无需新 API：snapshot 已含 candidates 和 assets 数组，projectAssetFileUrl 现成。纯前端 join + 渲染。

任务 E：分镜拖拽重排 + 批量重编号

中难度
现状问题

镜头列表是普通 v-for，无拖拽。删除镜头时已有 map(order=index+1) 重排范式（StoryboardWorkspace.vue L350），但无法主动调整顺序。order 字段存在但弱（可能有空洞），后端 normalize 按排序但不重排值。

设计：拖拽重排 + 重编号
  • 引入 vuedraggable（vue3 拖拽库，轻量），镜头列表改为可拖拽 vuedraggable 是 Vue3 标准拖拽方案；原生 HTML5 drag-drop 在嵌套表单里体验差
  • 拖拽完成后，workingJson.shots.map((s,i)=>({...s, order:i+1})) 紧缩 order 复用 removeShot L350 已有范式，保证 order 连续
  • 调 persistIfFormal → 整体 PATCH（updateChapterStoryboard） 无需新 API，复用现有全量替换通道
  • 顶部加「重新编号」按钮（批量重编号），逻辑同上 防止历史 order 有空洞；与拖拽共用同一个 reorder 函数
⚠ 关键风险：分镜改动会让候选图失效。 storyboard.service.ts L238-241：任何分镜 update 会把 images_done 回退到 storyboard_done。 处理：拖拽/重编号后，若该章已有候选图，弹确认提示"调整镜头顺序后，已生成的候选图和排版将失效，需要重新生成，是否继续？"。已锁定候选的镜头（lockedCandidateId）拖拽后保留锁定关系（按 shot.id 关联，不按 order）。
改动文件
  • apps/web/package.json · 新增依赖 vuedraggable
  • StoryboardWorkspace.vue shot-list 改 vuedraggable；新增 reorderShots()；顶部加"重新编号"按钮；拖拽确认提示

任务 F：批量生成全章未锁镜头

低难度
现状问题

15 个镜头要逐个点"生成候选"，没有"一键全章生成"。后端串行队列 runTaskSerialized（image-candidate.service.ts L46-58）已就绪，前端只需循环调用 createTask。

设计：一键生成未锁镜头
  • 候选图工作台顶部加「生成全部未锁镜头」按钮 过滤 shots.filter(s=>!s.lockedCandidateId)，对每个调 generateImageCandidates(shotId, 默认1张)
  • 批量生成默认每镜1张（快），用户可先调 candidateCount 再点批量 批量场景优先"广撒网先看效果"，满意再单独多生；对标 Dashtoon/LlamaGen
  • 已锁定镜头跳过；已有候选但未锁的镜头可选"是否追加" 避免重复生成已锁的；未锁的允许追加新批次
  • 生成中显示整体进度（N/M 镜头完成） 复用任务队列刷新；tasks 列表已有状态
改动文件
  • ImageCandidatesWorkspace.vue 顶部加"生成全部未锁"按钮 + emit generateAllUnlocked
  • workbench-store.ts 新增 generateAllUnlockedShots() action：循环调 createTask
  • AppShell.vue + ProjectWorkbenchView.vue 事件接线
后端无需改动：串行队列已就绪，多个 createTask 会自动排队串行执行（降限流）。前端循环创建即可。

3执行顺序与依赖关系

顺序任务依赖预估改动验证方式
1A 单格重画(批次语义)无1 组件 + 可选 store多次重画候选按批次分组
2B 候选5态UIA（批次概念）1 组件 + 1 API(可选)废弃/备选/锁定状态正确
3C prompt可见无1 util + store + 组件生成前能看到完整prompt
4D 分镜缩略预览无（独立）1 组件镜头卡显示已锁图缩略
5E 拖拽重排+重编号无依赖 + 1 组件拖拽后order连续+提示失效
6F 批量生成无（独立）组件 + store + 接线一键生成全部未锁镜头
建议执行顺序：A→B→C（阶段1一起完成、一起验证）→ D→E→F（阶段2）。A/B 有依赖（批次概念），C/D/E/F 互相独立可并行。每个任务完成后单独 typecheck，阶段末跑 test。
