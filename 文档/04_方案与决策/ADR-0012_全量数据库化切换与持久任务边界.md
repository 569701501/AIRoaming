# ADR-0012 全量数据库化切换与持久任务边界

## 1. 状态

已采纳，尚未实现。

本 ADR 固化 D7 的产品与架构边界，不授权立即修改业务代码、Prisma schema、真实数据库或 workspace；实现前仍需逐阶段开发文档、迁移演练与用户确认。

## 2. 背景

当前 Prisma 仅有 6 个未接线模型，没有 migration、数据库文件、PrismaService 或业务 CRUD。项目事实仍主要由 `ProjectRepository` 内存索引与 workspace JSON/Markdown 承载；任务、对话和多类 pending 状态也依赖 Map/Set/Promise，服务重启不能完整恢复。

真实只读样例中，1 个项目包含 67 个 Asset、27 个 Candidate 和 55 个唯一 taskId；素材引用完整，但只有 1 个 taskId 有完整 artifact，另外 54 个只能证明被 Candidate/Asset 引用。D1、D3 和 D4/D5 又要求不可变修订、事务切换、来源 digest、历史查询和确定性导出，因此数据库迁移不能只做表结构扩充。

## 3. 决策

### 3.1 数据库成为唯一业务事实源

- Project、Chapter、Character、Shot、Candidate、CandidateLockRevision、GenerationTask、LayoutRevision、ExportRevision、ConversationThread、current 指针和待确认业务状态进入数据库。
- 图片、音视频、PDF、ZIP 等大字节继续由受控文件存储承载；数据库中的 Asset 保存稳定 `storageKey/sha256/bytes/status/source`。
- 内存只保留可重建缓存、活动连接、短锁、worker 唤醒信号和当前 AbortController。
- 切换后应用不得在数据库查询失败时静默回退旧 JSON/Markdown。

### 3.2 一次 DB-only 切换

- 正式切换前可对真实备份重复执行只读审计与影子导入。
- 切换时进入维护模式，冻结业务写入和新任务；最终导入、完整性检查和冒烟通过后一次切到 DB-only。
- 旧 JSON/Markdown 脱敏后只读封存，不再作为读取兜底、写入目标或双向同步来源。
- 重新开放写入前失败可恢复旧应用与切换前快照；DB-only 产生新写入后，不允许直接退回 file-only 版本。

### 3.3 首版数据库与文档边界

- 首版只使用应用受控本地目录中的 SQLite，且只由单个 NestJS 服务进程访问；不把数据库放在 NAS、共享盘或云盘同步目录。
- schema 和仓储优先使用 SQLite/PostgreSQL 共同能力，但两种 provider 不共用 migration SQL。
- 身份、外键、唯一约束、current 指针和跨阶段引用关系化。
- 剧情结构、LayoutDocument、RichTextDocument、任务载荷、预检和 manifest 使用带 `schemaVersion/digest/stableId` 的 Prisma Json。
- 可查询投影只能由权威版本文档生成；文档、投影和 current 指针必须同事务提交，业务代码不得独立写投影。

### 3.4 凭据按调用运行时分治

- 文本模型 key 由本机 OpenCode auth 权威保存；AI漫游只做 localhost 单向写入、替换或清除，并保存非秘密 metadata。
- OpenAI、豆包和 Grok 图片 key 由 NestJS 后端 `ImageCredentialStore/SecretStore` 安全保存；数据库只保存 `credentialRef/source/fingerprint/configured/updatedAt`。
- 图片 key 不得出现在前端响应、SQLite、普通 JSON、日志、GenerationTask、artifact、导出和普通备份中；明文只允许在后端内存短暂存在并通过 HTTPS 使用。

### 3.5 SQLite 持久任务与单进程 worker

- `GenerationTask` 是排队、生命周期和当前执行权的唯一事实源；每次 claim 新建 `TaskAttempt`，终结后不可改写。
- 同一 NestJS 进程运行 worker；数据库轮询是可靠兜底，内存通知只用于降低延迟。
- claim 使用短事务和 `leaseOwnerId/leaseExpiresAt/heartbeatAt`；provider 请求、文件写入、哈希和渲染在事务外执行。
- 执行语义为 at-least-once。任务类型必须定义 `idempotencyKey/sourceDigest`、已有产物检查和重复回写保护。
- 过期 lease 只有在可安全重放时才进入有限重试；无法确认外部副作用时进入 `failed`，记录 `WORKER_INTERRUPTED/needsReview=true`。
- 运行中取消先写 `cancelRequestedAt`，worker 确认协作中断后才进入 `cancelled`；迟到结果不得覆盖已取消任务、过期来源或新的 current 指针。
- V1 所有图片 provider 任务使用同一 `concurrencyKey=image-provider` 且并发为 1；不引入 Redis/BullMQ 或多进程 worker。

### 3.6 旧任务使用历史记录与 legacy stub

任务记录必须区分：

| `recordKind` | 含义 | 是否可执行 |
| --- | --- | --- |
| `runtime` | 新系统创建的正常任务 | 是，按 D75 状态机执行 |
| `legacy_imported` | 旧 artifact 足以证明完整或部分历史 | 否，只读历史 |
| `legacy_stub` | 只能从 Candidate/Asset 证明原 taskId 存在 | 否，只读来源占位 |

同时使用 `provenanceStatus=complete/partial/reference_only` 表达证据完整度，并遵守：

1. Candidate/Asset 保留原 taskId 外键，不降级为散落的 `legacySourceTaskId` 字符串。
2. `legacy_imported/legacy_stub` 禁止 claim、取消、重试和新增 attempt；重新生成必须创建新的 runtime task，并绑定当前来源。
3. `legacy_stub.status=null`、`maxAttempts=0`、`retryDisabled=true`；未知 input/output/error/provider/时间/attempt 均保持空。
4. 文件存在、Candidate 状态和文件时间不能推断 `succeeded/failed/cancelled`。
5. `observedEvidence` 只记录可验证引用、来源路径、摘要和 artifact 存在性；每个恢复字段必须能追溯到证据。
6. 导入按原 taskId 幂等，provenance 只能随更强证据单向提升；证据冲突必须进入 MigrationReport，不得静默覆盖。

## 4. 被否决的备选

### 4.1 长期数据库与 JSON 双写或双向同步

数据库与文件系统没有共同事务，会形成永久双主源、字段漂移和补偿复杂度。

### 4.2 首版直接 PostgreSQL 或同时支持双引擎

当前是本地单用户、单服务进程；立即承担 PostgreSQL 运维或双 migration history 会扩大迁移范围。多人、远程部署、多实例或持续写竞争出现后再单独评估。

### 4.3 本轮直接 BullMQ/Redis

当前不需要多机 worker，却会新增 Redis、Outbox、部署和监控；BullMQ 也不能消除 at-least-once、幂等和来源校验要求。

### 4.4 任务只写数据库但继续依赖 Promise 调度

只能保留任务列表，不能实现重启恢复、真实取消和 lease 过期处理，数据库没有成为执行底座。

### 4.5 丢弃旧 taskId 或根据产物补造成功任务

丢弃 taskId 会破坏 Candidate/Asset 来源谱系；根据文件存在补造成功状态会把推测写成事实，污染审计、重试、成本和故障分析。

## 5. 影响与后果

- D7 是主事实源切换，不是增补几张表；必须先建立 migration history、仓储接口、事务边界和只读审计导入器。
- 数据库与素材文件使用 staged → rename → ready 和恢复扫描，不承诺跨数据库/文件系统 ACID。
- 所有旧文件写入口、内存权威状态和分散图片 Promise 队列最终都必须移除或降级为可重建运行态。
- D1、D3 和 D4/D5 的版式锁定、修订式返修、LayoutDocument、预检和不可变导出可以共享同一数据库版本基础。
- SQLite → PostgreSQL、单进程 worker → BullMQ/Redis 均是后续独立迁移，不作为首版隐藏双实现。

## 6. 实施前置条件

进入开发前必须另行完成：

1. 逐字段 Prisma schema、索引、唯一约束、CHECK、外键动作和首份 migration。
2. `recordKind/provenanceStatus/status` 的数据库约束与队列查询证明，确保 legacy 记录不可能被 claim。
3. ImageCredentialStore 跨平台原型、无桌面会话回退和统一日志脱敏验证。
4. SQLite runtime、WAL/checkpoint/backup、异常退出和恢复原型。
5. 数据库/文件两阶段提交、过期 lease、取消竞态、重复执行和导入证据冲突的故障注入测试。
6. M0–M6 的阶段任务、退出闸门、备份恢复命令和用户验收清单。

## 7. 验证标准

- 同一 workspace 备份重复影子导入后，实体计数、外键、摘要、文件检查和 MigrationReport 一致。
- 55 个旧 taskId 全部保留；有完整证据的历史任务只导入可证明字段，缺失任务成为不可执行 legacy stub。
- legacy 记录不会出现在 active queue，不会获得 lease、产生新 attempt 或被重试；重新生成创建新 runtime task。
- 服务重启后 queued/retrying 任务可恢复，过期 running lease 按安全性分流，重复执行不产生第二次正式回写。
- 运行中取消只有在 worker 确认后进入终态，迟到结果不能污染新的 current 来源。
- 图片 key 迁移、读取、替换、清除和调用全程不进入数据库、日志、任务或导出。
- 切换后旧 JSON/Markdown 无业务读写，数据库失败不会静默回退旧事实源。
