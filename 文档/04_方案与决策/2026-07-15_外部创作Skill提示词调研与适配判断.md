# 外部创作 Skill 提示词调研与适配判断

## 1. 结论先行

外部资料里确实有能明显补强 AI漫游剧本质量的方法，但不应把任何一个外部 Skill 整体搬进项目。

建议吸收的是一组互相衔接的质量门槛：

1. 灵感阶段先判断冲突发动机、人物压力、情绪钩子、视觉承诺和结局潜力。
2. 大纲阶段把“事件列表”升级为有因果、有升级、有伏笔回收、有结局方向的推进链。
3. 章节阶段要求每个场景存在目标、阻碍、压力、潜台词、转折和后果。
4. 改写阶段先诊断最高层问题，再按结构、人物、场景、对白、文字的顺序修订。
5. 所有阶段增加不可见自检和固定回归样例，但不把分析过程输出给用户。

建议第一版保持现有工具、JSON 字段、Markdown 格式、用户确认点和阶段边界不变，只增强生成规则与测试。这样能先验证质量收益，不把“提示词优化”扩大成一次协议和 UI 改造。

本调研最初不修改生产 Skill；2026-07-16 用户采用 A+ 简化方案后，P1～P6 已按本项目五个公开 Skill、七个模型阶段完成生产接线和固定回归，且没有改变页面内容字段。

## 2. 调研范围与判断口径

### 2.1 本轮查看的项目资产

- `script-inspiration-seeding`
- `script-outline-drafting`
- `script-chapter-drafting`
- `script-chapter-editing`
- `dialogue-prompt.util.ts` 中对应的运行时动态 prompt
- Script Collaboration Agent、AGENTS 模板和受控工具边界

### 2.2 来源优先级

1. 官方 Skill 编写指南和官方 Skill 示例。
2. 有原始 `SKILL.md`、可追溯工作流和明确许可证的创作类仓库。
3. 与中文小说、漫画、短剧相近，但许可证或适配边界需要谨慎处理的仓库。
4. 搜索摘要、二次转载和只展示“爆款提示词”的页面不作为施工依据。

### 2.3 每项方法的判断问题

- 它解决的是可重复问题，还是只适合某个作品？
- 能否放进 AI漫游当前阶段，而不跨越大纲、章节、分镜边界？
- 是否需要项目当前没有提供的上下文？
- 是否改变现有输出协议或用户确认点？
- 能否用固定样例验证，而不是只凭主观感觉？
- 许可证是否允许直接复用；若不明确，是否只借鉴抽象方法？

## 4. 项目现状与真正缺口

调研起点的 4 个创作 Skill 优点是边界清楚、格式稳定、写入受控。问题不是“完全没有提示词”，而是质量标准偏薄，模型知道要输出什么，却不够清楚什么算好。后续双流程落地时另保留第 5 个公开 Skill `script-import-normalize`，内部编排导入分析、忠实整理和验证，不与创作 Prompt 混用。

| Skill | 当前保留项 | 当前缺口 | 直接后果 |
| --- | --- | --- | --- |
| 灵感种子 | 固定生成 3 个方向；不提前写大纲和章节；JSON 稳定 | 缺少冲突发动机、人物压力、情绪钩子、视觉承诺、结局潜力和真正差异化标准 | 三个方向可能只是换名字、换设定，内核相似 |
| 项目大纲 | 固定 Markdown；项目级；用户确认后才写章节 | 缺少因果链、冲突升级、人物推动力、伏笔回收、结局方向 | 容易成为“然后发生 A、然后发生 B”的事件清单 |
| 章节起草 | 单章节、固定格式、受控保存 | 缺少场景目标、阻碍、压力、潜台词、转折、后果和连续性自检 | 场景可能有对白但没有变化，章节推进感弱 |
| 章节改写 | 返回完整更新稿；不跨项目边界 | 缺少修订类型、最高层诊断、事实保护、修订顺序和改后自检 | 容易只润色句子，或改好文风却改坏剧情事实 |

另一个实现事实是：当前真实生成 prompt 由 `dialogue-prompt.util.ts` 直接构建。仅在 `SKILL.md` 下新增 `references/` 文件，并不能自动保证运行时会读取它。因此后续计划必须先确定生产规则的单一事实源和同步校验，不能只把外部方法写进文档。

## 5. 推荐吸收包

### P1：灵感质量门槛

**适用 Skill**：`script-inspiration-seeding`

每个候选方向在模型内部至少通过以下检查：

- 核心反差：什么东西本不该同时成立，却同时成立？
- 情绪钩子：观众第一反应是好奇、担忧、惊讶、期待还是共鸣？
- 人物压力：为什么偏偏是这个主角，为什么现在必须行动？
- 冲突发动机：谁或什么会持续阻止主角，而不是只制造一次意外？
- 视觉承诺：这个方向能稳定产生可画的动作、空间、物件或关系变化吗？
- 结局潜力：故事有可以走向的选择、代价或反转，不是只有设定展示。

三个候选必须至少在“主角压力、冲突发动机、视觉承诺”三个维度上明显不同，不能只换名称和世界观包装。

**拒绝项**：只有氛围、只有设定、只有一句反转、需要大量说明才能成立的方向。

**第一版协议建议**：不增加 JSON 字段；把这些维度压缩进现有 `logline`、`coreConflict`、`visualHook` 和 `firstChapterDirection`。

### P2：因果大纲与结局方向

**适用 Skill**：`script-outline-drafting`

大纲内部必须明确：

- 主角表面想要什么、真正需要面对什么、当前错误认知或逃避是什么。
- 触发事件如何打破原状态。
- 每个主要节点为什么由前一个节点导致，用“因此”或“但是”连接，而不是“然后”。
- 阻力如何升级，选择的代价如何变大。
- 前面提出了哪些问题或承诺，后面如何兑现、反转或有意延后。
- 结局方向是什么，高潮要求主角做出什么关键选择。

**第一版协议建议**：不新增大纲章节标题；把人物推动力写进“主要角色”，把因果链、升级和回收写进“情节概要”，把结局方向写入现有结尾部分。这样先提升内容，不破坏页面解析和用户习惯。

**拒绝项**：强制所有项目套三幕式、英雄之旅或固定节拍表。结构模型可以作为内部参考，但不能成为所有题材的硬模板。

### P3：章节场景契约

**适用 Skill**：`script-chapter-drafting`

每个场景在模型内部至少回答：

- 谁在这一场想得到什么？
- 什么人在阻止，或什么条件让目标更难？
- 压力如何增加，角色必须暴露什么选择或性格？
- 对白表面说什么，实际在争取、回避或隐藏什么？
- 场景在哪一点发生转折？
- 场景结束后，信息、关系、位置、危险或决定有什么不可逆变化？
- 这个后果如何“因此”或“但是”地引出下一场？

章节开头要快速建立人物、地点和当前问题；章节结尾必须出现变化、揭示、决定、代价或新的压力，但不强制每章都是夸张悬崖。

**输出边界**：这些是内部规划和自检，不把“场景目标 / 阻碍 / 转折分析”输出给用户；最终仍只返回现有固定格式章节 Markdown。

### P4：分层修订

**适用 Skill**：`script-chapter-editing`

改写前先识别用户要的是哪一层：

1. 连续性修复：时间、地点、人物知识、伤势、道具、关系和已发生事实。
2. 发展性修订：剧情功能、角色推动力、因果和高潮。
3. 场景与对白修订：目标、阻碍、节奏、潜台词和转折。
4. 文字修订：句子、重复、节奏、语气和错字。

若用户已经说清楚，就直接执行，不额外增加确认轮次。若多个问题同时存在，优先修最高层故障：故事核心与事实 → 人物与因果 → 场景与对白 → 句子。

**保护契约**：未被要求改变的项目事实、角色身份、章节位置、固定格式和已确认情节必须保留；不能为了“写得更顺”擅自发明事实。

### P5：连续性检查

**适用 Skill**：章节起草、章节改写

建议检查：时间、地点、人物已知信息、关系、伤势、道具、未兑现承诺和上一场造成的状态变化。

但第一版只能使用运行时真实提供的上下文。当前若只给项目大纲和当前章节，就不能在提示词中宣称已检查所有前后章节。后续是否扩充相邻章节、版本事实或连续性摘要，应在实施计划中单独核对数据来源。

### P6：固定评测与触发测试

**适用范围**：5 个公开 Skill、7 个模型阶段全部

不要以“看起来更像好文案”作为唯一验收。至少建立以下测试：

- 正向触发：该 Skill 应在什么请求下执行。
- 反向触发：什么请求不应执行该 Skill，避免跨阶段。
- 格式回归：JSON、Markdown 标题、完整稿输出保持不变。
- 质量样例：候选是否真正差异化；大纲是否有因果；场景是否有转折；改写是否保留事实。
- 禁止项：不越权写文件、不声称不存在的上下文、不提前生成下一阶段内容。
- 对照验证：同一输入分别运行旧规则和候选规则，盲看哪一个更符合评分表。

## 6. 明确不采纳的做法

| 不采纳项 | 原因 |
| --- | --- |
| 把所有创作与导入能力合成一个巨型 Storytelling Skill | 会破坏创作侧四阶段和导入侧忠实分析边界，增加误触发和上下文噪声 |
| 整段复制外部 `SKILL.md` | 外部文件绑定自己的目录、工具、故事资料和输出协议；也会制造许可证与维护问题 |
| 强制所有题材套三幕式、英雄之旅或固定节拍 | 会让题材同质化，且不适合所有短篇、日常、悬疑或非线性叙事 |
| “每章必爽、开头即高潮、结尾必悬崖” | 只适合部分网文类型，会损害情绪铺垫和节奏变化 |
| 在最终章节中输出思维链或场景分析表 | 用户需要的是可用章节稿，内部检查不应污染固定格式 |
| 自动连续重写多轮，直到模型自判通过 | 成本与结果不可控，也可能越改越偏；应由固定样例和明确上限约束 |
| 把英文“AI 味词表”直接当中文创作质量标准 | 语言特征不等价，容易误伤正常风格；应检查具体问题和上下文 |
| 用“去 AI 检测分数”作为主验收 | 不能证明剧情、人物、连续性或漫画可画性更好 |
| 把视频时间轴、镜头参数、素材槽直接塞进剧本 Skill | 这属于后续分镜和素材阶段，会破坏当前职责边界 |
| 在没有输入事实时宣称做了全局连续性核验 | 这是虚假保证；检查范围必须与真实上下文一致 |

## 7. 建议拍板的方案

### 推荐方案 A：稳健增强

一次性批准 P1～P6 作为目标，但实施时保持以下边界：

- 不改现有 JSON 和 Markdown 对外格式。
- 不增加用户确认步骤。
- 不合并创作侧 4 个 Skill，也不把导入 Skill 合入创作 Prompt。
- 不进入分镜、素材或视频链路。
- 不直接复制外部段落，以中文项目术语重新编写。
- 生产 `SKILL.md`、动态 prompt、Agent 说明和测试必须保持一致。
- 任何连续性承诺只覆盖实际注入的上下文。

这是本调研的推荐结论。

### 备选方案 B：同时改输出结构

在大纲中新增“故事核心、主角推动力、因果推进、结局方向”等显式区块，在灵感 JSON 中新增质量维度字段。

这会让质量结构更显性，但会扩大到解析、页面、保存协议和兼容性改造。除非用户明确希望页面也展示这些字段，否则不建议与第一轮提示词增强一起做。

### 不建议方案 C：导入一个外部完整 Skill

看似最快，实际上最容易破坏当前阶段边界、输出协议和运行时一致性，也难以形成可维护测试，不建议。

## 8. 用户拍板项

请用户确认以下三项即可，后续计划不再重复讨论已确认方向：

1. 是否采用推荐方案 A，即 P1～P6 全部纳入目标？
2. 是否确认第一版不改现有对外 JSON / Markdown 格式，不新增用户确认步骤？
3. 是否确认把方案 B 的显式字段和 UI 变化留作独立候选，不交给本轮 Luna？

如果三项都确认，下一步才编写给 Luna 的无排期连续施工计划。计划只写依赖顺序、验收门槛、失败处理和证据，不写工期、完成日期或等待时间。

## 9. 静态复核结论

`Scrutiny Review: pass_for_user_decision`

- 来源已追溯到官方文档、原始仓库或原始 Skill 文件。
- 重点借鉴来源具有明确 MIT 许可证；许可证不明确或用途受限的来源未进入直接复用建议。
- 推荐内容未覆盖项目固定格式、阶段边界、用户确认和受控写入契约。
- 推荐项均能落到具体 Skill 和可验证样例。
- 本轮未执行运行时测试，因为尚未修改生产资产；Runtime/User Review 当前为 `pending_user_decision`。
