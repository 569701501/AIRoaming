## 1. 背景

用户当前已推进到“候选图工作台”，但对候选图之前的“出图准备”是否必要、是否做得足够好没有把握。本调研围绕 GitHub 上较热门或高度相关的 AI 漫画 / 图像生成 / 漫画处理开源项目，判断它们是否存在类似“生成前检查、角色/场景/风格资产准备、分镜版本放行”的能力，并反推 AI漫游应保留和增强的设计。

## 2. 当前 AI漫游设计摘要

AI漫游当前链路是：

```text
剧本 -> 剧情结构 -> 分镜工作台 -> 出图准备 -> 候选图工作台 -> 排版导出 -> 素材包
```

当前“出图准备”的实际职责已经收窄为章节级检查点：

| 检查项 | 当前处理 |
| --- | --- |
| 正式分镜 | 只读取当前章节正式 `storyboard.json`，待确认分镜不能进入候选图 |
| 分镜版本 | `preflight.json` 记录 `sourceStoryboardId/sourceStoryboardUpdatedAt`，分镜变化后需要重新确认 |
| 角色绑定 | 镜头 `characterIds` 必须匹配项目角色库或结构角色 |
| 角色定稿 | `lead/recurring` 必须定稿；`chapter/minor/extra` 出镜超过 1 次才强制定稿 |
| 场景绑定 | 镜头 `sceneId` 必须匹配本章剧情结构场景卡 |
| 场景参考图 | 缺场景参考图只 warning，不阻塞候选图 |
| 风格上下文 | 自定义画风只 warning，不阻塞候选图 |
| 放行结果 | 通过后写 `preflight.json`，候选图任务注入参考图资产 ID |

判断：这个设计不是多余步骤，而是把“角色一致性、分镜版本、引用资产和生成任务追溯”变成业务门禁。开源生态里大多数工具没有做到这一层。

## 3. 调研样本

调研分为三类：漫画垂直项目、通用热门图像生成工作台、漫画处理生产管线。

| 项目 | 热度/状态 | 类型 | 与出图准备相关的事实 |
| --- | ---: | --- | --- |
| [AI Comic Factory](https://github.com/jbilcke-hf/ai-comic-factory) | 约 1.3k stars，已归档 | 文字到漫画 demo | LLM + SDXL 生成 comic panels，非单体可一键运行，依赖多 provider；缺完整章节生产与生成前资产门禁 |
| [StoryDiffusion](https://github.com/HVision-NKU/StoryDiffusion) | 约 6.4k stars | 一致性生成算法 / demo | 强项是长序列角色一致性，支持 comics generation demo；不是完整漫画生产工作台 |
| [PrintFilm](https://github.com/yuanzhongqiao/printfilm) | 约 2.8k stars | 漫剧 / 短剧工作台 | 明确采用 Script-to-Asset-to-Keyframe：先剧情分镜，再角色/场景资产，再关键帧/视频，再导出 |
| [AI-Comic-Generator](https://github.com/Dapeng960208/AI-Comic-Generator) | 约 11 stars | 小型漫画生产工作台 | JSON 驱动，角色一致性检查，三视图，单格重画，批量生成，后台任务；热度低但设计贴近 |
| [MangaGen](https://github.com/BluePointDigital/mangagen) | 约 14 stars | 本地优先漫画工作台 | 项目素材桶、生成历史、批量队列、provider route、项目导入导出；热度低但架构参考价值高 |
| [Komiko](https://github.com/Story-Engine-Inc/Komiko) | 约 45 stars | 商业平台开源入口 | 强调角色库、AI canvas、comic studio，但仓库更像产品展示入口 |
| [ComfyUI](https://github.com/Comfy-Org/ComfyUI) | 约 120k stars | 通用节点式生图工作台 | 节点/图工作流很强，可保存和复用复杂 workflow；没有漫画章节级业务门禁 |
| [AUTOMATIC1111 WebUI](https://github.com/AUTOMATIC1111/stable-diffusion-webui) | 约 164k stars | 通用 Stable Diffusion WebUI | txt2img/img2img/inpaint/prompt matrix/参数试验强；没有故事、分镜、角色资产门禁 |
| [Fooocus](https://github.com/lllyasviel/Fooocus) | 约 50.8k stars | 简化生图工具 | 降低参数心智，支持 image prompt、variation、inpaint；不处理漫画生产链路 |
| [InvokeAI](https://github.com/invoke-ai/InvokeAI) | 约 27.6k stars | 专业创意图像工作台 | canvas、workflow、gallery、图像元数据召回较成熟；没有漫画章节级 preflight |
| [Krita AI Diffusion](https://github.com/Acly/krita-ai-diffusion) | 约 10.3k stars | 绘画软件插件 | 在 Krita 内做 inpaint/outpaint/ControlNet/IP-Adapter，适合后期修图；没有业务门禁 |
| [manga-image-translator](https://github.com/zyddnys/manga-image-translator) | 约 10.2k stars | 漫画翻译处理管线 | OCR、inpainting、typesetting 等阶段化处理；不是原创出图，但说明漫画工具需要阶段管线 |
| [comic-translate](https://github.com/ogkalu2/comic-translate) | 约 2.8k stars | 漫画翻译 app/插件 | 流程包含 Text Detection、OCR、Inpainting、Translation、Text Rendering；强调 pipeline 化 |

> 星标和状态为 2026-07-09 通过 GitHub 页面/API 查询所得，只作为热度参考。

## 4. 是否存在类似“出图准备”的能力

| 能力 | AI漫游 | 漫画垂直 demo | 通用生图工作台 | 漫画处理管线 |
| --- | --- | --- | --- | --- |
| 章节级流程状态 | 有 | 少数有雏形 | 无 | 有阶段管线但不是原创生成 |
| 正式分镜版本门禁 | 有 | 少见 | 无 | 类似“当前输入文件/页面”管线，但不对应分镜 |
| 角色库与角色定稿 | 有 | 部分有角色一致性 | 依赖用户手工用 LoRA/IP-Adapter/参考图 | 无原创角色库 |
| 场景/风格资产准备 | 部分有，当前 warning | 部分有 | 以 prompt/reference/workflow 形式存在 | 以页面检测/修补参数存在 |
| 生成前检查清单 | 有 | 基本没有独立成步骤 | 没有业务检查，仅参数/节点是否可运行 | 有任务阶段，但不是创作门禁 |
| 候选图多选与锁定 | 有 | 多数弱 | 有批量/seed/variation，但没有 Shot 级锁定 | 不适用 |
| prompt 可见可编辑 | 当前弱 | 小项目多支持 | 强 | 强配置化 |
| 单格重画 / 局部修改 | 当前弱 | 小项目支持 | 强，尤其 inpaint/variation | 强，尤其 inpaint/text rendering |
| 生成历史/追溯 | 部分有 | 小项目有雏形 | Invoke/MangaGen 较强 | 较强 |

结论：开源热门通用工具在“生成与修图能力”上强，但很少有漫画业务层的 preflight。漫画垂直项目知道要做角色一致性、单格重画和批量生成，但大多是 demo 或低星项目。AI漫游的出图准备在“生产门禁与追溯”上是正确方向，应保留。

## 5. 应该保留的设计

| 保留项 | 原因 |
| --- | --- |
| 出图准备作为独立步骤 | 它解决的是候选图前的生产风险，不是 UI 冗余 |
| 只读正式分镜 | 防止待确认分镜污染候选图和排版 |
| `preflight.json` 绑定 `storyboardId/updatedAt` | 这是分镜变更后的失效机制，通用工具通常没有 |
| 角色定稿硬门槛 | 一致性是漫画生成最大痛点，StoryDiffusion、PrintFilm、AI-Comic-Generator 都把一致性放在核心 |
| 场景参考图 warning 不阻塞 | 场景参考有价值，但早期全阻塞会拖慢主线 |
| 候选图任务读取 preflight 参考图 | 保证候选图可追溯到角色/场景/分镜来源 |
| 一镜多候选 + 显式锁定 | 比“一次整页生成”更接近真实生产和返修 |

## 6. 应该增强的设计

### 6.1 P0：候选工作台必须补的能力

| 建议 | 说明 |
| --- | --- |
| prompt 预览与可编辑 | 当前系统拼 prompt，但用户看不到。建议每个镜头生成前展示“本次出图提示词”，允许局部编辑后生成 |
| “重画此镜”升为一等操作 | “再生成一组”语义不够明确。建议改为“追加一组候选”，旧候选保留；另设“废弃本轮” |
| 候选轮次/批次 | 每次生成形成一组 `candidateBatch`，便于用户比较“第 1 轮 / 第 2 轮” |
| 批量生成全章未锁镜头 | 参考 MangaGen / AI-Comic-Generator 的批量队列，长章节逐镜头点击成本高 |
| 候选状态用起来 | 前端显示 `generated/locked/rejected/superseded`，至少支持“保留备选 / 废弃” |
| 生成历史面板 | 记录 prompt、negative prompt、参考图资产、provider、模型、尺寸、seed/参数和任务 ID |

### 6.2 P1：出图准备可以增强但不应变重

| 建议 | 说明 |
| --- | --- |
| 输出“镜头出图包” | 在 confirm preflight 时生成只读 `render_context` 或 `shot_context_bundle`：shot、角色参考图、场景参考图、风格片段、默认 prompt、版本信息 |
| 场景参考图资产化入口 | 仍不阻塞，但从 warning 可以直接跳转到剧情结构页生成/上传场景图 |
| 风格板/项目画风片段 | 自定义画风不阻塞，但应可沉淀为项目级 style reference |
| 分镜变更差异提示 | 当分镜变更导致 preflight 失效时，提示哪些镜头/角色/场景影响候选图 |

### 6.3 P2：后置能力

| 能力 | 后置原因 |
| --- | --- |
| ComfyUI 式节点图编辑器 | 太重，容易偏离漫画生产主线 |
| 完整 canvas 自由排版 | 排版导出 M1 先稳定一镜一页，复杂 canvas 可后置 |
| 局部 inpaint / mask 编辑 | 很有价值，但适合候选锁定后的精修阶段，不应阻塞主链路 |
| 视频关键帧 / 漫剧生成 | PrintFilm 方向值得参考，但属于 P0.5/P1 轻漫剧链路 |

## 7. 最终判断

AI漫游当前“出图准备”的方向是对的，甚至比多数开源项目更像真正可持续生产的漫画工作台。不要删除，也不要退回“分镜后直接生成图”的一把梭。

真正需要调整的是边界：

- 出图准备只做“能不能出图”的检查和版本放行。
- 角色图、场景图、风格资产的创建和编辑不要塞回出图准备，入口跳转即可。
- 候选工作台要承担“怎么出、出几张、怎么重画、怎么锁定、怎么追溯”的主体验。

推荐下一步产品方向：

```text
出图准备 = 出门检查单 + 生成上下文快照
候选工作台 = 单镜头生成 / 批量生成 / 多候选比较 / prompt 可编辑 / 锁定与废弃 / 生成历史
```

这样既保留 AI漫游的生产级优势，又吸收通用工具在 prompt 透明、迭代、inpaint、批量队列上的成熟经验。
