## 2. 记法与全局裁决

字段记法：

```text
logicalName:PrismaType[?][=default]@physical_column
```

- 无 `?` 为 `NOT NULL`；有 `?` 为 nullable。
- 无 `=...` 为无 Prisma/数据库语义默认值；调用方必须显式提供。
- `=uuid()` 是 UUID v4；`=now()` 是创建时间；`=@updatedAt` 是 Prisma update-time 行为，不冒充 SQLite server default。
- 所有表名使用稳定 `snake_case`，可数集合通常使用复数；`chapter_script_pending`（每章单例集合）与 `credential_metadata`（mass noun）是显式冻结例外。所有物理列名使用 `snake_case`。
- `Json` 必须由对应 codec 产生；schemaVersion 与 digest 不允许页面独立伪造。
- 摘要统一 `sha256:<64 lowercase hex>`；顺序字段从 1 开始；`row_version` 从 0 开始。

实现裁决：

| 主题 | 冻结结论 | 理由/责任 |
| --- | --- | --- |
| Prisma | `prisma` 与 `@prisma/client` 精确 `6.19.3`；closed/open/free-text 标量统一使用 Prisma `String`，闭合值域由 Shared codec + SQLite CHECK + manifest 固定，不使用 Prisma enum 形成第二份值域 | 不在 DB 切换同时升级 major；若早期 Schema 字典仍写“使用 enum”，以本实施裁决为准 |
| ID | 新行 `String @default(uuid())`；singleton 使用固定 literal；Importer 可显式传稳定重键 ID | 新 runtime UUID v4；legacy scoped ID 稳定重键 |
| 历史来源 nullable | 只有各模型显式标记为 nullable 的 legacy source/prompt/profile/task/layout/manifest 字段可为 null；runtime 由分支 CHECK/Repository/trigger 加严；Preflight 来源不全时不插入伪修订 | 不用 mtime、空串或当前 policy 伪造旧事实 |
| 开放词汇 | `Character.role`、`Asset.role`、多态 `sourceType/targetType/aggregateType` 是 `controlled-open string`，只做非空/格式与 codec 校验 | 不伪造 Prisma enum，不让 SCH-04 错报缺 CHECK |
| Outbox 状态 | `pending/processing/processed/failed`；重试回到 `pending + availableAt` | 不另造 `retrying` 真值 |
| 历史删除 | Project/Chapter 下历史实体 FK 精确使用 `onDelete=Restrict`，依显式删除顺序 | 防裸 cascade 破坏历史/文件边界 |
| 私有值对象 | Version projection、TaskAttempt/TaskSource、ExportArtifact 使用 `Cascade` | 父行消失后无独立意义 |
| current/pending pointer | 简单 FK `SetNull`，另用 0008 scope/status trigger | 复合 FK 含父自身非空 ID 时无法安全 SetNull |
| Export scope | 新增非空 `scopeKey`：`project` 或 `chapter:<chapterId>`；唯一 `(projectId, scopeKey, kind, revision)` | 避免 SQLite nullable unique 漏洞 |
| forward FK | 0003/0004/0007 可引用后续 0004/0006/0007 表；SQLite 允许先声明后建目标表，fresh deploy 完成后统一 `foreign_key_check=0`；Prisma 无法稳定表达者在 0008 用 trigger | 不静默省略跨阶段关系 |
| comicFormat | G1 即 `NOT NULL`、无默认、两值 CHECK；更新不可变 trigger 归 G3 | M0-A 不提前宣称 G3 完成 |
| G4/G5 | 保留兼容字段；G1 已声明的 CandidateLock/LayoutRevision/ready Export 不可变进入 0008；线性链和完整 runtime 状态机后置 | 避免阶段越权 |

### 3.1 String 字段穷尽分类

字段只有以下三类；Pass 2 manifest 对每个 Prisma `String` 字段必须给出且只给出一类，缺失或重复分类都失败。

| 类别 | 字段 | owner/约束 |

## 5. `0001_persistence_and_migration`

### 5.1 `PersistenceState` → `persistence_states`

```text
id:String="primary"@id
storageContractVersion:Int=1@storage_contract_version
activationState:String="shadow"@activation_state
cutoverRunId:String?@cutover_run_id
sourceManifestDigest:String?@source_manifest_digest
effectiveSchemaManifestDigest:String?@effective_schema_manifest_digest
activatedAt:DateTime?@activated_at
firstBusinessWriteAt:DateTime?@first_business_write_at
lastVerifiedAt:DateTime?@last_verified_at
createdAt:DateTime=now()@created_at
updatedAt:DateTime=@updatedAt@updated_at
```

- PK：`id`。FK：非空 `cutover_run_id -> migration_runs.id onDelete=Restrict onUpdate=NoAction`（同 migration 内 forward declaration）。
- CHECK：`ck_persistence_states_singleton`、`ck_persistence_states_activation_state`、`ck_persistence_states_digest_format`、`ck_persistence_states_activation_shape`：`shadow` 要求 cutover/source/effective/activated/firstWrite 全空；`ready_for_activation` 要求 cutover/source/effective 非空且 activated/firstWrite 为空；`db_only` 要求 cutover/source/effective/activated 非空；`recovery_required` 只接受两种精确形状：未建立切换身份时 cutover/source/effective/activated/firstWrite 全空，或 cutover/source/effective 全非空、activated 可空/非空且 firstWrite 只有在 activated 非空时才可非空。
- trigger：
  - `trg_persistence_states_initial_insert`：唯一首行也只能以 `id=primary,state=shadow,storageContractVersion=1` 且 cutover/source/effective/activated/firstWrite 全空插入；`trg_persistence_states_no_second_row` 拒绝第二行，`trg_persistence_states_no_delete` 永久拒绝 DELETE，不能删后重插伪造激活历史；
  - `trg_persistence_states_cutover_run_insert/update`：ready/db_only 或带切换身份的 recovery 引用的 run 必须 `kind=final,status=succeeded`，且 run.sourceManifestDigest 与本行 sourceManifestDigest 相同、run.verificationJson.effectiveSchemaManifestDigest 与本行 effectiveSchemaManifestDigest 相同；source 摘要标识迁移输入 workspace/data，effective 摘要标识当前发布 Schema，二者不得复用或互相解释；
  - `trg_persistence_states_activation_transition`：未激活（activatedAt=null）的 shadow/ready/recovery 可按 `shadow→ready_for_activation|recovery_required`、`ready_for_activation→shadow|db_only|recovery_required`、`recovery_required→shadow|ready_for_activation|recovery_required`；已经激活（activatedAt非空）的 recovery 只能 `recovery_required→recovery_required|db_only`，db_only 只能 `db_only→db_only|recovery_required`，不能经 recovery 间接回 ready/shadow；
  - `trg_persistence_states_activation_first_write`：`activatedAt` 的首次写入只允许与 `ready_for_activation→db_only` 同一 UPDATE 发生，且该行必须引用 source/effective 摘要均一致的 succeeded final run；shadow、未激活 recovery 或 INSERT 均不得预填 activatedAt。`firstBusinessWriteAt` 的首次写入只允许在 OLD/NEW 均为已激活 `db_only` 时发生，不能与首次激活合并、不能在 recovery 首写；
  - `trg_persistence_states_identity_immutable` 永久保护 id/storageContractVersion/createdAt；未来 contract version 只能由显式 migration 替换 versioned schema/trigger，业务 UPDATE 不得改。`trg_persistence_states_activation_identity_immutable` 在 activatedAt 一旦非空后保护 activatedAt/cutoverRunId/sourceManifestDigest/effectiveSchemaManifestDigest 不可清除或改写；
  - `trg_persistence_states_first_write_monotonic`：firstBusinessWriteAt 只允许 null→非空一次，写后不可清除或改写。
- `firstBusinessWriteAt IS NOT NULL` 必须蕴含 `activatedAt IS NOT NULL`；未建立切换身份的 recovery 五项全空；已建立切换身份的 recovery 必须保留并复核原 succeeded final run 的 source/effective identity，已激活后只能返回 `db_only`。启动与 ACT 验收必须把 effectiveSchemaManifestDigest 与当前发布包的 effective manifest digest 精确比较，不能拿 sourceManifestDigest 代替。
- 合法同状态健康更新显式保留：只改变 lastVerifiedAt/updatedAt 且所有激活身份/状态字段不变时，shadow/ready/db_only/recovery 均可 UPDATE；状态 trigger 不得误伤 verifier 心跳。
- `firstBusinessWriteAt` 非空后的 file-only 启动拒绝仍由应用启动门禁验证；数据库不尝试自动回滚应用模式。

### 5.2 `MigrationRun` → `migration_runs`

```text
id:String=uuid()@id
kind:String@kind
status:String="running"@status
importerVersion:String@importer_version
sourceManifestDigest:String@source_manifest_digest
snapshotManifestDigest:String?@snapshot_manifest_digest
decisionsDigest:String?@decisions_digest
reportDigest:String?@report_digest
countsJson:Json?@counts_json
countsSchemaVersion:Int?@counts_schema_version
verificationJson:Json?@verification_json
verificationSchemaVersion:Int?@verification_schema_version
errorCode:String?@error_code
startedAt:DateTime=now()@started_at
finishedAt:DateTime?@finished_at
createdAt:DateTime=now()@created_at
```

- index：`ix_migration_runs_status_started_at(status, started_at)`。
- CHECK：`ck_migration_runs_kind`、`ck_migration_runs_status`、`ck_migration_runs_json_pairs`、`ck_migration_runs_terminal_time`、`ck_migration_runs_digest_format`。
- trigger：`trg_migration_runs_running_insert` 只允许 `status=running,finishedAt=null`，终态报告/verification/error 为空；`trg_migration_runs_state_transition` 只允许 running→blocked|succeeded|failed 同次首次写 finishedAt，terminal 不可重开。final→succeeded 还要求 snapshot/decisions/report digest、counts/verification pair 全部完整，verification codec 表示 integrity ok/FK 0/manifest match，且不存在 `severity=blocker AND resolutionStatus!='resolved'` 的 MigrationIssue。
- `trg_migration_runs_terminal_immutable_update/delete` 保护完成后的 input/report/status 并拒绝删除 audit history。它与 5.4 的 issue insert/update/delete guard 共同防止先把 run 自报 succeeded、再补/删 blocker 后供 Persistence 激活。
- `verificationSchemaVersion=1` 的 `MigrationVerificationV1` 至少固定以下可由 trigger 检查的 object keys：`integrityCheck='ok'`、`foreignKeyViolationCount=0`、`failedLedgerCount=0`、`migrationChecksumStatus='verified'`、`effectiveSchemaManifestDigest=sha256:*`、`sourceManifestDigest=本行 sourceManifestDigest`、`openBlockerCount=0`。最终 run 的独立新连接 verifier 生成该对象；字段缺失、类型错误或值不符不能 succeeded。DB 形状门禁不替代 verifier 真实执行证据和命令退出码。


#### 6.1.1 `DEL-00` Project deleting 根写栅栏

所有 project-scoped Repository/Command 在 UoW 进入首个业务 statement 前都以同一事务读取 Project，并使用稳定错误码 `PROJECT_DELETING` 拒绝普通 mutation；数据库对最危险的 late write 再提供 trigger 防线，不能只靠页面隐藏按钮。

| 操作 | Project active | Project deleting |
| --- | --- | --- |
| 新建/修改 Working Copy、pending、dialogue、version、Candidate/Lock、Layout/Export | 按各自 CAS/状态机执行 | 普通业务入口全部拒绝；只允许既存运行态的取消、失败收敛与协调 purge |
| runtime Task create / source seal / claim / retry | 允许；仍需 policy、source、slot、lease 门禁 | create/seal/claim/retry 全部拒绝；queued/retrying 原子取消，running 只允许 heartbeat 到取消确认，以及 fenced cancelled/failed finish |
| Asset INSERT / staged→ready / current pointer | 允许；仍需 Outbox、ready 与 scope 门禁 | 禁止新 Asset、禁止晚到 ready、禁止任何 current/pending pointer 变化；既存 staged/ready 只允许进入 deleting-cleanup |
| `asset.promote` | active 分支可 rename + ready | 只能按 handler registry 删除匹配 temp/final 并 staged→deleting，不得 ready |
| `asset.delete` / `project.delete_files` | 只在显式删除命令事务创建 intent | 允许幂等恢复；project handler 要等 active runtime task=0 且其他文件事件收敛 |
| 项目 DB purge | 拒绝 | 只在 12.4 的 processed delete event + active runtime task=0 + 应用 maintenance closed 全部成立时按显式顺序执行 |

SQL manifest 至少把 active guard 写入：Task initial/seal/claim/retry；Asset unready INSERT/ready transition；Candidate/Lock INSERT；Project/Chapter/Character/ChapterScene/Shot 的 current/pending pointer UPDATE。其他普通 mutation 由统一 UoW `ProjectWriteGate` + API 集成测试穷尽；任何新 project-scoped Command/Repository 未登记在该 gate 时 `DEL-00` 失败。trigger 的 ABORT code 统一使用 `PROJECT_DELETING`，避免不同表自行发明不可聚合的错误。

#### 7.10.1 `PREFLIGHT_SOURCE_UNRESOLVED` 切换前决议

唯一允许的 V1 resolution：

```json
{
  "decisionSchemaVersion": 1,
  "action": "drop_current_preflight_and_reconfirm_after_cutover",
  "projectId": "<issue project>",
  "chapterId": "<issue chapter>",
  "acknowledgedConsequences": [
    "legacy_preflight_not_imported_as_formal_revision",
    "current_preflight_pointer_is_null",
    "new_candidate_work_blocked_until_reconfirmation"
  ]
}
```

- shadow/audit run 可保持 issue open；用于激活的 final run 必须在仍 running 时写上述 strict resolutionJson、`resolutionStatus=resolved/resolvedAt`，并把 canonical decision 纳入 `decisionsDigest`。Importer 无权替用户自动生成该决议。
- 应用该决议时目标 DB 不插伪 PreflightRevision，`Chapter.currentPreflightRevisionId` 必须为 null；旧文件摘要/路径证据只留在 ImportedEntitySource、MigrationIssue 和脱敏 legacy archive。
- final verifier 因该 issue 已 resolved 可得到 `openBlockerCount=0`；这不是把 blocker 降级为 warning，而是用户明确接受“放弃旧 current、切换后重确认”的迁移处置。
- DB-only 后 NewWorkGate 从“currentPreflight=null + 最近 resolved action”派生 `PREFLIGHT_RECONFIRMATION_REQUIRED_AFTER_MIGRATION`，拒绝 shot_prompt/image 新任务。用户基于 current Storyboard、Character/Scene Visual、comicFormat 重新运行并确认 Preflight V2 后，新建正式 PreflightRevision、切 current，门禁自然消失；不得复活或改写旧 preflight。
- 本契约只定义决议协议，不代表当前已取得真实项目决议，更不授权 M4。

### 7.11 `FormalProjectionRegistryV1`（不新增模型）

formalize trigger 只支持下表 schemaVersion/path；G1 base 必须允许当前 runtime `StoryStructureJson/StoryboardJson` V1 和 legacy V1，不能把 G2 Codec 偷前置。V2 path 先在 registry 声明，G2 overlay 上线后新 runtime/pending confirm 必须编码 V2；升级时遗留 runtime V1 pending 先由 Codec 显式重编码 V2，既有 confirmed V1 历史仍合法不可变。unsupported version 不得确认/current。JSON1 负责可直接比较的结构集合，semanticDigest 仍由 Codec 重算。

| parent | owner/path | projection mapping |
| --- | --- | --- |
| Story V1/V2 | `$.chapterId = StoryVersion.chapterId`；V1 runtime 还要求 `$.sourceScriptVersionId` 与 parent source_script_version_id null-safe 等值；legacy V1 若 embedded 缺失/null 可按关系直接证据保留 parent，但 embedded 一旦非空必须相等。V2 不保存该 embedded key。Scene array=`$.scenes`；Beat array=`$.beats` | Scene：`sceneKey=$.id`、`order=json_each.key+1`、`name=$.name`、`chapterSceneId` 必须 lookup 同章 `ChapterScene.sceneKey=$.id`。Beat：`beatKey=$.id`、`order=$.order=json_each.key+1`、`summary=$.summary`；`$.sceneId` null→chapterSceneId null，否则 lookup 同章 ChapterScene.sceneKey。Scene/Beat projection 数量必须分别等于两个 JSON array 长度，无多余/缺失/重复 key/order。 |

- `status=unconfigured` 必须 configured=0；`status=configured` 必须 configured=1；`rotating/clearing` 在旧 ref 仍可用时保持 configured=1 与完整 ref/fingerprint，只有安全切换/删除完成后才进入 configured/unconfigured；`error` 可为 0 或 1，但 configured=1 时仍必须满足 owner 对应的 ref/fingerprint 形状。
- `image_secret_store` 的 secretRef 由 adapter 生成，精确格式为 `airoaming:image:v1:<uuid-v4>`；它只是受控 account handle，不含 provider、路径或密钥片段。`opencode/environment` 的 secretRef 始终为 null。fingerprint 使用精确 `sha256:<64 lowercase hex>`，不是 preview；M1.6 仍必须执行 sentinel 字节扫描，因为 CHECK 不能数学上证明任意字符串不是秘密。
- `trg_credential_metadata_provider_owner_insert/update` 反查 ProviderConfig.runtimeKind：text 固定只接受 `opencode`；image 接受 `image_secret_store|environment`，其中 `environment` 是无桌面会话下的显式只读部署凭据，不是把明文写入 DB 的后门。providerConfigId/owner 创建后不可改写；与 9.2 的 provider identity immutable 共同阻止先挂错 owner 或事后改 runtimeKind。
- `trg_credential_metadata_status_transition` 冻结清理状态机：`clearing` 只允许保持 clearing，或在匹配 `secret.delete_old_ref` 已 processed 的证据下进入 `unconfigured` 并同次把 configured/ref/fingerprint 清空；禁止回到 configured，也禁止跳到 rotating/error。其他状态转换仍必须满足本节 configured/ref/fingerprint 形状。
- `ProviderConfig.providerId` 是逻辑 provider 身份，禁止原地更新。修改 displayName/modelId/baseUrl/enabled 仍在同一行 CAS；如果用户要把配置从 provider A 改成 provider B，必须创建新的 ProviderConfig（及其 CredentialMetadata）、验证新 credential、原子切 AppPreference 指针，再按 clear/Outbox 流程清理旧 metadata，最后才允许删除旧 ProviderConfig。不得把“编辑 providerId”实现为绕过 immutable trigger 的 UPDATE。
- `trg_credential_metadata_secret_ref_update/delete` 冻结 image_secret_store 生命周期：
  - 配置是 null→新唯一 ref；同一个 versioned ref 的 fingerprint 不得原地改变；
  - 旋转是先写/验证新 ref，再在同一 DB 事务先插 payload 含 OLD.secretRef 的 pending `secret.delete_old_ref` Outbox，后把 metadata 切到新 ref；
  - clear 第一步只把 status 切 clearing，仍保持 configured=1 与旧 ref/fingerprint；worker 删除秘密并把匹配 Outbox processed 后，第二个事务才允许 clearing→unconfigured 并清空 ref/fingerprint；
  - 非空 ref 的 UPDATE/清除缺少上述对应 Outbox 证据即 ABORT；当前 ref 非空时 DELETE 永远拒绝。ref 已空且 status=unconfigured 的 metadata 才可显式删除，因此 ProviderConfig 的 Restrict 不能被用来遗留秘密。
- Outbox 匹配至少固定 `eventType=secret.delete_old_ref,aggregateType=credential_metadata,aggregateId=metadata.id,payload.oldSecretRef=OLD.secretRef`；event payload codec 禁止保存秘密值，只保存不透明 ref。OpenCode/environment 无 secretRef，仍由 Settings command 与 provider adapter 的成功证据控制 clear。

```ts

  schemaVersion: 1;
  policyVersion: string;

  chapterId: string | null;
  consumerType: string;
```

- claim 的唯一入口被冻结为两只 trigger：
  - `trg_generation_tasks_claim_validate`：`BEFORE UPDATE OF status,attempt,lease_owner_id,lease_token,lease_expires_at,heartbeat_at,started_at ON generation_tasks WHEN OLD.record_kind='runtime' AND OLD.status IN ('queued','retrying') AND NEW.status='running'`。要求 owner Project active、seal 非空、cancelRequestedAt 为空、`OLD.nextRunAt IS NULL OR OLD.nextRunAt<=NEW.heartbeatAt`、`NEW.attempt=OLD.attempt+1<=maxAttempts`、owner/token/expiry/heartbeat 完整、expiry>heartbeat；首次 claim 写 `startedAt=heartbeatAt`，重试保持原 startedAt；concurrencyKey 非空时必须存在空闲 slot。
  - `trg_generation_tasks_claim_materialize`：同一 WHEN 的 `AFTER UPDATE`；按 `(concurrency_key,slot_no ASC)` 选最低空闲 slot 并写 task/owner/token/expiry，随后 INSERT 当前 TaskAttempt。无 concurrencyKey 不占 slot；任一 UPDATE/INSERT 或事后存在性校验失败都 `RAISE(ABORT)`，整个原 UPDATE 回滚。
- Service 生成 UUID v4 claimToken 和单一 `claimAt`，把 `heartbeatAt=claimAt`；trigger 写 Attempt 的 `attemptNo=NEW.attempt`、`workerId=NEW.leaseOwnerId`、`claimToken=NEW.leaseToken`、`startedAt=createdAt=NEW.heartbeatAt`。Attempt.id 不依赖 Prisma default，0008 固定使用并测试下列 SQLite UUID v4 表达式（version nibble=4、variant∈8/9/a/b）：

```sql
lower(hex(randomblob(4))) || '-' || lower(hex(randomblob(2))) || '-4' ||
substr(lower(hex(randomblob(2))), 2, 3) || '-' ||
substr('89ab', ((instr('0123456789abcdef', substr(lower(hex(randomblob(1))), 1, 1)) - 1) % 4) + 1, 1) ||
substr(lower(hex(randomblob(2))), 2, 3) || '-' || lower(hex(randomblob(6)))
```

- heartbeat 的唯一入口是 Task UPDATE + 两只 trigger：`trg_generation_tasks_heartbeat_validate` 在 BEFORE 阶段用 OLD Task 与 OLD Slot/未完成 Attempt/token 做 fencing，要求 heartbeat 单调增加、NEW expiry>NEW heartbeat、身份不变；`trg_generation_tasks_heartbeat_materialize` 在 AFTER 阶段把同 token Slot.leaseExpiresAt/updatedAt 原子同步为 NEW leaseExpiresAt/heartbeatAt，并做事后等值校验，失败即回滚原 Task UPDATE。无 concurrencyKey 跳过 slot。Slot.updatedAt 精确取 claimAt、每次 heartbeatAt、最终 Attempt.finishedAt。
- 结果预写只允许 `OLD.status=running`、当前未完成 Attempt 与 Task/Slot/leaseToken 全部一致且不改变 lease identity/expiry 时更新。终结的唯一入口是当前 `TaskAttempt` 的 null→terminal UPDATE：Service 可先在仍 running 且 fenced 的 Task 上写 output/error/nextRunAt，然后写 Attempt outcome/error/artifactRefs/finishedAt；`trg_task_attempts_finish_validate` 校验 token、payload shape 与重试条件，`trg_task_attempts_finish_materialize` 在该同一 statement 中先把 Task 映射为 succeeded/cancelled/retrying/failed、写/清相应时间与 lease，再释放匹配 slot。failed/interrupted 只有 `attempt<maxAttempts`、预写 future nextRunAt 且 owner Project 仍 active 时进入 retrying，否则 failed；Project 已 deleting 时 recovery/finish 只能收敛 cancelled/failed，不能产生新 retrying。lease recovery 复用 outcome=interrupted 的同一路径，不能单独清 slot或留下 active Attempt。任何子动作失败回滚 Attempt UPDATE。
- `trg_generation_tasks_running_fencing_update` 对结果预写和由 finish trigger 发起的 Task 状态转换核对当前 Attempt/Slot/token；heartbeat 使用上述 OLD-validate/AFTER-materialize，不能用“先要求 Slot 等于 NEW expiry”的即时循环。直接把 running Task 改终态、先清 slot、终态后遗留占槽均拒绝。claim/heartbeat/finalize 的 claimToken 语义在 Prisma 字段命名为 `leaseToken`、物理列 `lease_token`；TaskAttempt/Slot 使用 `claim_token` 并必须相等。
- `trg_generation_tasks_runtime_state_transition` 穷尽 runtime 状态图：queued/retrying 只允许走 claim→running，或以同次 cancelRequestedAt/finishedAt 进入 cancelled；running 只允许由已终结当前 Attempt 的 finish materialize 进入 succeeded/cancelled/retrying/failed；terminal 行任何 UPDATE/重开拒绝。retrying 必须无 lease/finishedAt 且有 future nextRunAt，terminal 必须清 lease/nextRunAt 并写唯一 finishedAt。legacy execution guard 继续拒绝任何 lease、claim、取消、重试或 Attempt。

```text
attempt:Int=0@attempt
maxAttempts:Int=3@max_attempts

leaseOwnerId:String?@lease_owner_id
leaseToken:String?@lease_token
leaseExpiresAt:DateTime?@lease_expires_at
lastErrorJson:Json?@last_error_json
createdAt:DateTime=now()@created_at
updatedAt:DateTime=@updatedAt@updated_at
processedAt:DateTime?@processed_at
idempotencyKey:String@idempotency_key
```

- unique：`uq_outbox_events_idempotency_key(idempotency_key)`、`uq_outbox_events_lease_token(lease_token)`（多个 null 合法，只保证当前存储的非空 token 不冲突）。Outbox terminal 会清 token，历史永不复用不能由该索引证明；Service 每次 claim 生成新 UUID v4，生成器/故障注入测试负责拒绝复用。
- index：`ix_outbox_events_claim(status, available_at, created_at)`、`ix_outbox_events_recovery(status, lease_expires_at)`、`ix_outbox_events_aggregate(aggregate_type, aggregate_id)`。
- 无多态 aggregate FK；payload codec 与 recovery 扫描负责目标一致性。
- CHECK：`ck_outbox_events_status`、`ck_outbox_events_attempt_range`、`ck_outbox_events_schema_version`、`ck_outbox_events_digest_format`、`ck_outbox_events_lease_shape`、`ck_outbox_events_processed_time`。
- `maxAttempts=3` 是 G1 M0-A 显式实施裁决，不由调用方任意扩大。
- trigger：
  - `trg_outbox_events_pending_insert`：INSERT 只能 `status=pending,attempt=0,maxAttempts=3,processedAt=null` 且 lease 全空；禁止直接插 processing/processed/failed，包括不能伪造已 processed 的 `project.delete_files` 作为 purge 证据；
  - `trg_outbox_events_intent_immutable`：eventType/aggregateType/aggregateId/payloadJson/payloadSchemaVersion/payloadDigest/maxAttempts/idempotencyKey/createdAt 全部从 INSERT 起不可改；
  - `trg_outbox_events_attempt_transition`：仅 `pending→processing` 必须 `NEW.attempt=OLD.attempt+1<=maxAttempts`；processing 心跳及 processing→pending|processed|failed 必须保持 attempt，其他增减一律拒绝；
  - `trg_outbox_events_state_transition`：pending 只能在 `OLD.availableAt<=NEW.updatedAt` 时→processing，并保持 availableAt；processing 可同状态 heartbeat，或→pending|processed|failed；processing→pending 仅在 `attempt<maxAttempts` 时允许并要求 `availableAt>updatedAt`，到上限必须 failed/processed；pending 原地提前 availableAt、failed/processed 重开或提前 claim 都拒绝；
  - `trg_outbox_events_lease_shape`：pending→processing 首次写完整 owner/token/expiry 且 expiry>updatedAt；processing→pending/terminal 同次清空 lease，其他状态 lease 全空；
  - `trg_outbox_events_lease_fencing`：processing→processing heartbeat 只能保持 owner/token，令 updatedAt 与 expiry 单调增加；禁止不增 attempt 就换 worker/token。过期接管必须由持有 OLD token 的 recovery CAS 先 processing→pending 清 lease，再由下一次 pending→processing 增 attempt、取得新唯一 token；retry/terminal 也以 OLD token 条件更新；
  - `trg_outbox_events_processed_immutable`：只有 processing→processed 同次首次写 processedAt，其他状态必须为空；terminal freeze 谓词必须是 `OLD.status IN ('processed','failed') AND (<任一受保护列变化>)`，括号覆盖完整 changed-set，不能因 AND/OR 优先级误伤 pending claim、processing heartbeat/retry/completion；processed/failed 后任何 UPDATE 拒绝；
  - `trg_outbox_events_no_delete`：pending/processing/terminal 全部拒绝普通 DELETE；外部副作用意图和 processed purge/secret 证据不能消失，未来 retention 必须另立显式 maintenance overlay 与审计，G1 不提供豁免。
- `eventType/aggregateType` 是 registry 管理的 controlled-open string；首版 registry 至少包含 G1 字典列出的五类事件。

## 12. `0008_sqlite_checks_triggers_indexes`

### 12.1 实施方式

SQLite 不能用普通 `ALTER TABLE` 给既有表补完整 CHECK。0001～0007 先建立 44 个表、PK、基础 unique/index/FK；0008 对需要 inline CHECK 的表使用受控 table-rebuild：

```text
connection open
  -> PRAGMA foreign_keys=OFF（必须在事务外）
  -> TEMP guard 读回 PRAGMA foreign_keys，唯一值必须为 0
  -> BEGIN IMMEDIATE
  -> CREATE TABLE <table>__new（最终列/FK/CHECK）
  -> INSERT INTO <table>__new (...) SELECT ... FROM <table>
  -> DROP old + RENAME
  -> 按本契约显式稳定名称重建 unique/index/trigger
  -> 事务内 TEMP guard 断言 pragma_foreign_key_check 计数为 0
  -> COMMIT
  -> PRAGMA foreign_keys=ON（事务外）
  -> connection close
  -> 独立 verifier 新连接显式 PRAGMA foreign_keys=ON 并读回 1
  -> verifier 断言 integrity_check=exactly one ok、foreign_key_check=0、manifest/checksum/ledger 正常
```

- 0008 不新增模型/业务列，不更改 nullable/default，不进行 legacy 值映射。
- rebuild 前后列顺序、类型、nullable/default 与本文字段块逐项一致；任何无法复制的旧行使 migration 失败，不静默 normalize。
- COMMIT 前任一步失败都由显式事务回滚；COMMIT 后不再放可失败的 schema guard，避免“schema 已提交但 migration ledger 失败”。`foreign_keys=ON` 只影响当前连接，不是数据库文件持久属性。
- forward FK 在最终 fresh deploy 完成后必须全部有目标表。
- migration 中的 FK-count guard 负责让违例在 COMMIT 前失败；deploy 后的独立 verifier 仍必须分别执行 `integrity_check`、`foreign_key_check`，不用一项代替另一项。
- 2026-07-11 E0 已在唯一临时根验证 Prisma CLI/@prisma `6.19.3` + SQLite `3.51.0`：成功库 2 个 migration 完整应用并可幂等复跑；故意在 rebuild/index/trigger 后、COMMIT 前失败时返回 `P3018`，原 schema/数据完整且新对象全部回滚，下次 deploy 因 failed ledger 返回 `P3009`。fresh/shadow DB 失败直接丢弃重建；非 fresh DB 必须人工 inspect 后才能 `migrate resolve --rolled-back`，禁止自动跳过。

M0-A r7 新增的生产入口 `buildG1MigrationPlanV1` 是纯 renderer：只从 current manifest 返回 `migration_lock.toml + 0001～0008` 九个 artifact 的精确 path/bytes/SHA-256、43 张 rebuild 表的一对一列复制映射和固定 inventory，不读取 SQLite、不写仓库。0001～0007 严格按 `model.migration` 分组创建 44 张基础表及 named PK/FK/unique/index；0008 在事务外执行 `PRAGMA foreign_keys=OFF` 后，先用 TEMP CHECK guard 从 `pragma_foreign_keys` 读回唯一值并要求精确为 0，才允许 `BEGIN IMMEDIATE`；随后只 rebuild 43 张含 CHECK 的表，`chapter_scenes` 因无 CHECK 不重建。每张 rebuild 表在 DROP 旧表前必须同时通过 row-count equality 与全列双向 `EXCEPT` difference-count=0 的事务内 hard guard；静态一对一 column mapping 不能替代运行时值集合等价。最后安装 194 个 trigger，并在 COMMIT 前执行可失败的 `pragma_foreign_key_check` guard。

Schema 写入口 `writeG1PrismaSchemaV1` / `g1:schema:write` 与 migration writer `writeG1MigrationPlanV1` / `g1:migration:write` 均不接受 skip 参数：写任何 staging byte 前必须从生产 review verifier 得到同一 current manifest 的精确 `required=2/received=2/accepted=2/status=accepted/allowed=true/blocking=[]/sealed bundle non-null`，atomic rename 前再次复验 manifest、attestation-set 与 bundle digest 未变化。Schema 只允许从 signed manifest 计算 expected bytes 后同目录 staging+fsync+atomic replace；write 不要求旧 Schema 已正确，因此 2/2 后可以修复 missing/stale/tampered Schema，只有只读 `g1:schema:check` 才要求 current bytes 已逐字一致。migration writer 在首尾两次 gate 附近都必须把 current `schema.prisma` 与 `buildG1PrismaSchema(current manifest)` 逐字比较，防止签收后 Schema 被篡改仍生成 SQL。否则写入口失败，正式 `apps/server/prisma/migrations/` 不存在且既有 Schema bytes 不变。r7 当前仍为 `0/2 pending false`，因此这里只允许纯 renderer、只读 check 与 marker-owned 临时 SQLite 干跑，不允许正式落盘。

正式 migration tree 写入后还必须由 `checkG1MigrationArtifactTreeV1` / `g1:migration:check` 从同一 accepted gate、current manifest 和 exact Schema 重新派生 signed plan，逐字验证唯一九个 path、bytes、SHA-256、目录 entry set 与 regular single-link file identity；extra/missing/tampered/symlink/hardlink 全部失败。任何正式 `prisma migrate deploy` 都必须在调用前后各运行一次该 check；fresh deploy 写入与其 checksum 相同的篡改 SQL 不构成证明，不能用 `_prisma_migrations` 自洽替代 signed artifact-tree freshness。当前 r7 0/2 时 check/write 均 fail closed，且不得为了检查创建 migration 目录。

临时 SQLite 干跑已把同一纯计划连续完整执行两次，逐项验证 `44 tables / 556 scalar / 44 PK / 70 unique / 60 index / 105 named FK / 195 CHECK / 194 trigger`、fresh/shadow exact-8 ledger checksum、`integrity_check=ok`、`foreign_key_check=0`、两次规范化 `sqlite_master` digest 相同，并证明 0008 前合法行逐字保留；verifier 自身先执行 `PRAGMA foreign_keys=ON` 并精确读回 1，不能依赖迁移连接或 Node 默认值，处于外层事务使 ON 无效时必须失败。把 copy SELECT 改成同 row-count 但改写 `updated_at` 的负例会由双向全列差集 guard 回滚，orphan FK、artifact 篡改/缺失及 fresh/shadow ledger 缺失/checksum/failed 路径同样 fail closed。另用“先开启外层事务再执行 0008”证明 SQLite 会忽略事务内 `PRAGMA foreign_keys=OFF`，pre-transaction TEMP guard 会在任何持久 rebuild/trigger 改动前失败并保持七步 Schema/ledger。精确 Prisma CLI `6.19.3` 的 marker-owned 集成探针先预创建空 SQLite 文件（该版本对不存在文件会报 P1003/engine failure），随后真实 `migrate deploy` 完整应用 8 条，第二次返回 no pending；新连接由 verifier 主动启用 FK 后通过 exact inventory/ledger。另一临时树先 deploy 0001～0007、注入 orphan、再加入 0008，真实得到 P3018 且 Schema/数据回滚、failed ledger 保留，下一次 deploy 得到 P3009；这同时证明 SQLite runner 没有给 migration SQL 再套一个会破坏显式 `BEGIN IMMEDIATE` 的外层事务。当前 ledger API 只表达 fresh/shadow exact-8 success policy，不兼容 `migrate resolve` 后的生产恢复历史；非 fresh 人工 inspect/resolve 与审计 policy 延后 M0-B 单独实现。该证据仍只是 marker-owned temp 实现验证；正式仓库 migration 未生成，SCH-01～03 的 current-digest 正式历史仍须在 r7 2/2 后执行。

### 12.2 CHECK 完整清单

Pass 2 独立 manifest 必须为每个 `ck_*` 写入完整 `normalizedExpression`，而不只是名称。以下是唯一允许的基础谓词模板；manifest 须展开到具体表/列/值：

```sql
-- non-null closed enum；nullable 版外层显式加 column IS NULL OR (...)
column IN ('value_1', 'value_2')

-- Boolean；每个 Boolean 列独立存在
typeof(column) = 'integer' AND column IN (0, 1)

-- Int 范围；nullable 版同样显式 IS NULL OR
typeof(column) = 'integer' AND column >= minimum

-- integer-only（当前仅 priority）；不臆造业务下界
typeof(column) = 'integer'

-- nullable bounded SQLite numeric（当前仅 Candidate.score；NaN 在 bind 前由 codec 拒绝）
column IS NULL OR (
  typeof(column) IN ('integer', 'real')
  AND column >= -1.7976931348623157e308
  AND column <=  1.7976931348623157e308
)

-- sha256 digest；nullable 版显式 IS NULL OR
length(column) = 71
AND substr(column, 1, 7) = 'sha256:'
AND substr(column, 8) = lower(substr(column, 8))
AND substr(column, 8) NOT GLOB '*[^0-9a-f]*'

-- image SecretStore ref；credential_metadata.secret_ref 外层显式 IS NULL OR
length(column) = 55
AND substr(column, 1, 19) = 'airoaming:image:v1:'
AND substr(column, 20) = lower(substr(column, 20))
AND substr(column, 28, 1) = '-'
AND substr(column, 33, 1) = '-'
AND substr(column, 34, 1) = '4'
AND substr(column, 38, 1) = '-'
AND substr(column, 39, 1) IN ('8', '9', 'a', 'b')
AND substr(column, 43, 1) = '-'
AND length(replace(substr(column, 20), '-', '')) = 32
AND replace(substr(column, 20), '-', '') NOT GLOB '*[^0-9a-f]*'

-- Json；用 CASE 避免 malformed JSON 先触发 json_type 错误
CASE WHEN json_valid(column) = 1
  THEN json_type(column) = 'object' -- 或逐字段冻结的 'array'
  ELSE 0
END

-- controlled-open string；nullable 列在外层显式加 IS NULL OR
typeof(column) = 'text'
AND length(trim(column)) > 0
AND instr(column, char(0)) = 0
```

#### 12.2.1 `CheckTemplateRegistryV1` 与 physical binding

Pass 2 不手抄 195 份彼此漂移的表达式，也不允许只存 constraint 名称。权威源使用“版本化完整模板 + 每个物理 key 的显式参数绑定”，generator 只做纯展开：

```ts
interface CheckTemplateV1<Args> {
  templateId: string;
  templateVersion: 1;
  argsKeys: readonly string[];
  expand(args: Args): { normalizedExpression: string };
}

interface PhysicalCheckBindingV1 {
  name: `ck_${string}`;
  table: string;
  ownerStage: "G1" | "G2" | "G3" | "G4" | "G5";
  templateId: string;
  templateVersion: 1;
  args: Readonly<Record<string, string | number | boolean | null | readonly string[]>>;
  sourceSection: string;
}
```

冻结规则：

1. 每个 `ck_*` 恰好一个 binding；重复、漏项、多项、未知 template、未知/缺失 arg 都是 completeness error。
2. template 必须生成完整 SQL predicate，不返回列名、自然语言或 predicate fragment；binding 不能额外拼接自由 SQL。独有跨字段 shape 使用 `explicit-state-shape-v1`，其 `expression` 参数本身就是本契约受审的完整 canonical SQL，不是绕过模板审查的 escape hatch。
3. canonical SQL：普通物理标识符使用未加引号的 snake_case；物理列 `order`、`index` 是 SQLite keyword，必须精确写成双引号标识符 `"order"`、`"index"`，带 row alias 时写 `NEW."order"`/`OLD."index"`/`alias."order"`。字符串只用单引号并以 `''` 转义；关键字/函数大小写以模板字面量为准；逗号后一个空格；无注释、无尾分号；全部 ASCII whitespace 折叠为单空格；IN 值按闭合值域表顺序，不能由 generator 字母重排。
4. nullable 不是隐式改写：`nullable=true` 必须由模板明确生成 `column IS NULL OR (...)`；Json 用 CASE 防 malformed；digest/path/secretRef/Boolean/integer/numeric 的完整 V1 表达式均由本节固定模板展开。
5. 生成后 manifest 保存 templateId/version/args 与 `normalizedExpression` 两者；hash 同时覆盖 binding 和展开结果。verifier 重新展开并逐字比较，防止只改结果或只改参数。
6. 模板源与 binding 只能来自本文及本文引用的 registry section，禁止读取 `schema.prisma`、migration SQL 或 SQLite 反向生成期望值。

storageKey 的展开表达式必须同时拒绝：空串、`/` 开头、Windows drive prefix、任意反斜杠、NUL、`//`、整段 `.`/整段 `..`（开头、中间和结尾）。该 CHECK 应用于 `ImportedEntitySource.sourceStorageKey`、`MigrationIssue.storageKey`、`Asset.storageKey`；nullable 列使用显式 null 分支。symlink/realpath 越界无法由 SQLite 判定，仍由 AssetStorage/Legacy reader 的 canonical path guard 负责。

以下类型清单在 Pass 2 必须逐列展开；“全部”以字段名匹配与下列显式补充的并集计算，不能只检查示例：

- Boolean：`ProviderConfig.enabled`、`CredentialMetadata.configured`、`PreflightRevision.ready`、`GenerationTask.retryDisabled/needsReview`。
- positive Int（`>=1`）：`PersistenceState.storageContractVersion`；所有业务 `version/order/revision/schemaVersion`；`Candidate.index/generationSpecVersion`、`TaskAttempt.attemptNo`、`TaskConcurrencySlot.slotNo`，以及 `countsSchemaVersion/verificationSchemaVersion/detailSchemaVersion/errorSchemaVersion/evidenceSchemaVersion/artifactSchemaVersion/profileSchemaVersion/manifestSchemaVersion` 等所有具体 Json 版本列。

- Float：只有 `Candidate.score`，使用上方 exact numeric/±Infinity 谓词；本阶段没有 `0..1` 范围。NaN 是 Codec 单测，不冒充 SQLite 非法直写用例。
- Digest：所有 `*Digest`、`Asset.sha256`、`CredentialMetadata.fingerprint`；非空值必须是上述 71 字符格式。
- controlled-open：每一列建立稳定名 `ck_<physical_table>_<physical_column>_nonempty` 并展开上述 exact predicate；nullable 列加 null 分支。vocabularyOwner 仍在 manifest 单独登记，非空 CHECK 不把开放词汇伪装成 enum。

物理化约定同时冻结如下，避免 generator 临场猜 timing/error code：

- 名称以 `_insert/_update/_delete` 结尾的压缩项分别展开为对应事件；同一职责写成 `insert/update` 时生成两只 trigger。未显式写 `UPDATE OF` 的 UPDATE trigger 固定 `updateColumns=[]`（表示监听全部 UPDATE），不能擅自优化列集合；已在本契约给出 `UPDATE OF` 的必须逐列原样记录。
- 所有 validate/guard/scope/immutable/initial/state/lifecycle/fencing 类 trigger 都是 `BEFORE`；只有名称或职责明确为 `materialize` 的 trigger 是 `AFTER`。若未来需要新的 AFTER trigger，必须在 overlay 逐只明示。
- 没有独立 transition `WHEN` 的通用 guard 使用 `normalizedWhen='1'`，并把完整违例谓词放入 body；已明确 transition WHEN（如 Task claim、heartbeat、Attempt finish）的必须使用精确 transition predicate，不得退化为 `1` 后漏掉分支。
- 每只拒绝型 trigger 的稳定 SQLite RAISE literal 固定为 `AIR_G1:<physical_trigger_name>`；normalizedBody 形如 `SELECT RAISE(ABORT, 'AIR_G1:<physical_trigger_name>') WHERE <完整违例谓词>`。一只 trigger 有多条独立违例时可有多条 SELECT，但顺序也属于 manifest。materialize trigger 的最终事后断言同样用自己的 literal。`PROJECT_DELETING` 是应用层统一领域错误；SQL adapter 将所有命中 deleting guard 的上述 `AIR_G1:*` literal 规范化映射为该错误，不把动态字符串写进 RAISE。
- SQLite 三值逻辑必须 fail closed：required JSON key/type/shape 不得只写会在缺 key 时得到 NULL 的 `NOT (a AND b)`；使用 `IS/IS NOT` 或 `COALESCE((完整合法谓词),0)`，并以真实 SQLite 缺 key/null/错 type 负例证明会 RAISE。MigrationVerification effective digest 与 Layout canvases/elements/provenance shape 属本轮强制样例。

#### 12.3.1 `TriggerTemplateRegistryV1` 与 physical binding

194 个 G1 base physical trigger 同样使用完整 template DSL；模板负责 SQL，不把自然语言职责当 body：

```ts
interface TriggerTemplateV1<Args> {
  templateId: string;
  templateVersion: 1;
  argsKeys: readonly string[];
  expand(args: Args): {
    timing: "BEFORE" | "AFTER";
    event: "INSERT" | "UPDATE" | "DELETE";
    updateColumns: readonly string[];
    normalizedWhen: string;
    normalizedBody: string;
    errorCode: `AIR_G1:trg_${string}`;
  };
}

interface PhysicalTriggerBindingV1 {
  name: `trg_${string}`;
  table: string;
  ownerStage: "G1" | "G2" | "G3" | "G4" | "G5";
  templateId: string;
  templateVersion: 1;
  args: Readonly<Record<string, string | number | boolean | null | readonly string[]>>;
  sourceSection: string;
}
```

冻结规则：

1. 每个 physical key 恰好一个 binding，且展开结果必须与 key 的 table/name/event 一致。缺 binding、重复、未知 arg、空 `normalizedBody`、`normalizedWhen='0'`、UPDATE OF 拼错列都直接 completeness failure。
2. 共用模板只覆盖语义真正同构的模式：singleton、owner/scope existence、identity immutable、terminal immutable、parent terminal set seal、Project purge 三条件、Project active write guard、ready Asset guard、append-only、claim fencing。模板参数必须列出完整受保护列、owner join、允许状态/transition 与例外，不能用 `columns='*'`、`predicate='TBD'`。
3. 独有状态机/JSON 投影/Task claim-heartbeat-finish/Outbox/Credential/Export 原子化使用 `explicit-trigger-v1`；binding 的 args 必须包含完整 timing/event/updateColumns/when/bodyStatements/errorCode，并在本文对应模型章节受审。`explicit` 是完整定义载体，不允许自然语言或空壳。
4. canonical body 是有序 statement 数组以 `; ` 连接、无尾分号；每条拒绝 SELECT 使用该 physical name 的固定 RAISE literal。nullable 列一律 `IS NOT`；owner/scope 子查询明确表、列和状态；SQL whitespace/quote/identifier 规则同 12.2.1，包括 `order/index` keyword 列的双引号。
5. manifest 同时保存 templateId/version/args 与六项展开结果；canonical hash 覆盖二者以及 binding 顺序。verifier 从权威 template/binding 重展开，逐字比 fresh SQLite 的 normalized trigger SQL。
6. base bindings 按 `(table,name)` BINARY 升序；overlay 只能新增或显式替换带版本 key，不能删除/放宽 base。模板与绑定禁止读取待测 `schema.prisma`、migration SQL 或 SQLite。

### 12.4 业务不可变与受控删除

“不可变”首先表示禁止业务 `UPDATE` 覆盖正式历史，不等于永远不能删除项目：

1. immutable `UPDATE` trigger 无豁免，任何正式行内容覆盖都拒绝。
2. 项目 purge 是 immutable DELETE 的唯一例外。每个相关 DELETE trigger 都必须沿 owner 链反查并同时证明：所属 Project `lifecycle_status='deleting'`；存在 `outbox_events(event_type='project.delete_files', aggregate_type='project', aggregate_id=<projectId>, status='processed')`；该 Project 不存在 `record_kind='runtime' AND status IN ('queued','running','retrying')` 的 GenerationTask。缺任一项立即 ABORT。
   - `trg_projects_purge_delete_guard` 即使 Project 完全为空也执行三条件；active 空项目不得直接 DELETE。
   - `trg_chapters_purge_delete_guard` 沿 projectId 执行同三条件；普通业务没有绕过项目 purge 的独立 Chapter 硬删入口。
   - Pass 2 根据 44 模型 FK/owner graph 穷尽所有“自身为历史根”或“DELETE 会 Cascade 私有历史”的父表并列出 delete guard，至少覆盖 Project/Chapter、Script/Story/Storyboard/Preflight、Character/Scene/Visual、Asset/Candidate/Lock、Conversation/Tool/Pending、GenerationTask/Attempt/Source、Layout/Binding、Export/Artifact；不得只依赖某个恰好存在的 child trigger。
   - `PurgeOwnershipRegistryV1` 对 44 表做 exactly-once 机器分类：9 个 global/cross-project 表；25 个 project history/cascade root；8 个 project private child；2 个 project ephemeral state（`chapter_script_pending`、`layout_working_copies`）。每个 history/cascade root 必须登记自身 DELETE guard，private child 必须登记精确 guard；manifest 校验表集合、owner path、guard table/event/name 一一对应。Registry 另以 `activeDialogueAllStateDeleteGuard=true` 精确标记 `conversation_messages/dialogue_runtime_sessions/pending_dialogue_artifacts` 三表，三者 guard 的 normalized WHEN 必须为 `1`，不得只保护 terminal 状态。
   - 本轮补齐此前缺失的 root guard：`trg_chapter_script_revisions_purge_delete_guard`、`trg_chapter_scenes_purge_delete_guard`、`trg_scene_visuals_purge_delete_guard`、`trg_shots_purge_delete_guard`、`trg_characters_purge_delete_guard`、`trg_character_visuals_purge_delete_guard`、`trg_project_context_facts_purge_delete_guard`、`trg_conversation_threads_purge_delete_guard`。它们即使 owner 为空子树也执行三条件，不能依赖 Cascade 恰好触发某个 child guard。
3. maintenance closed 无数据库持久真值，明确由应用层 MaintenanceCoordinator 在进入 purge 事务前另行证明；它不能被弱化为只看 Project.deleting。数据库三条件与应用 maintenance 条件共同成立才是受控 purge。
4. 显式删除顺序先删私有 projection/value rows，再删历史实体，最后删 Chapter/Project；Asset 字节删除成功前不进入 DB purge。
5. 正常业务 API 不暴露任意 history DELETE；除上述协调项目 purge 外没有其他 immutable DELETE 豁免。

对 active dialogue 的关闭性单独冻结：`ConversationMessage.running`、`DialogueRuntimeSession.active`、`PendingDialogueArtifact.pending` 及各自所有终态均走同一三事实 DELETE guard。只具备 deleting、只具备 deleting+processed outbox、或缺少“无 active runtime task”证明都必须 ABORT；三事实齐备才可按协调 purge 顺序删除。pending artifact 不得借 DELETE 释放唯一 active slot。

因此 SCH-11/SCH-12 必须验证普通路径不可改写/再终结；另有删除专项测试证明 active 空 Project、active 空 Chapter、带/不带 child 的绕父 cascade 均失败，deleting Project 只有满足三条件并按显式顺序才可清理，避免 schema 永久锁死项目。

- CHECK 必须比对完整规范表达式；trigger 必须比对 timing/event/updateColumns/WHEN/body；index 必须比对列顺序、ASC/DESC 和 unique；FK 必须比对双方列顺序与精确 action。

- manifest 的权威输入只允许本文、`G1任务与Outbox实施注册表` 及显式 source data；generator 禁止读取待测 `schema.prisma`、migration SQL 或 SQLite 来生成期望值。manifest 必须记录 `manifestSchemaVersion/sourceDocuments/sourceSections/canonicalization`，canonical JSON 摘要覆盖 556 scalar、relationFields、CHECK normalizedExpression、trigger timing/event/updateColumns/WHEN/body、Task/Outbox/PurgeOwnership registry 与 overlay ownership。

### 13.2 摘要绑定的双审与派生门禁

主 Agent 对首版 Pass 2 交付做增量复核时发现 P0：base manifest 的 `reviewGate` 永久写死为 `0/2 pending false`，却没有摘要绑定的 attestation/report 协议和可执行检查入口，因此即使两名 Reviewer 完成工作，机器也永远无法真实到达 2/2。修复方式不是直接把 JSON 改成 `accepted`，而是把 base artifact 与 derived gate 分离：

1. base manifest 的 `reviewGate` 永久保持 `acceptedReviews=0`、`status=pending`、`migrationGenerationAllowed=false`。它表达“base artifact 自身不携带外部审查事实”，生成、check 或 review-check 都不得回写该字段。
2. `g1:manifest:review-check` 每次从落盘 artifact、当前 23 个 sources（20 个 TypeScript、2 个权威 Markdown 与 `apps/server/package.json`）和固定 review bundle 重新计算 derived gate。输入中的 `manifestDigest/status/completeness/requiredReviews/digestVerified/sourcesCurrent` 必须来自实际 artifact 与 fresh source 逐字比较，不能硬编码为通过。
3. 落盘 JSON 非法、摘要格式或自摘要非法、source stale、manifest 非 `ready_for_scrutiny`、completeness 非 0、review 数或角色不符均 fail closed。derived gate 只在同一 current digest 的精确 2/2 accepted 时给出 `migrationGenerationAllowed=true`；不会修改 base JSON。

固定 review round 和目录为：

```text
reviewRoundId = g1-m0a-pass2-r7
root = 文档/05_执行与记录/任务记录/2026-07-11_G1至G5连续实施/reviews/g1-m0a-pass2-r7

contract_consistency.attestation.json
contract_consistency.review.md
sqlite_dsl_machine.attestation.json
sqlite_dsl_machine.review.md
review-bundle.v1.json
```

前四个文件是两名 Reviewer 各自拥有的 raw submission，不直接授权 derived gate；即使四个 raw 文件都存在但尚无 canonical sealed snapshot，门禁仍只能得到 `0/2 pending`。两份 attestation 必须分别使用角色 `contract_consistency` 与 `sqlite_dsl_machine`，拥有不同且 canonical 的 `reviewerId`，并声明 `independentFromWorker=true`；二者都必须绑定同一 `reviewRoundId`、同一 current manifest digest、各自精确 report 相对路径及 report SHA-256。Reviewer finding code 禁止使用保留前缀 `G1_REVIEW_`，该 namespace 只属于 derived gate protocol code，防止 flat blockingCodes 中发生身份碰撞。Worker/父编排不得代写 Reviewer 的 report 或 attestation。

`review-bundle.v1.json` 是父编排/Orchestrator 发布的派生 sealed snapshot，不属于任一 Reviewer。发布命令为：


publisher 逐字读取所选角色的 raw attestation/report；raw 必须是可无损 round-trip 的 UTF-8，禁止 decoder replacement character 把非法 bytes 悄悄改写。publisher 把 exact text bytes、各自 digest、固定 logical path、round/role/manifest 组装成 canonical `envelopeBytes`；不合成结论、不改变 verdict。第二代必须 byte-for-byte 复制第一代的 `envelopeBytes`，拒绝 stale expected digest、重复角色、round/manifest 漂移和并发 publisher。第一名 Reviewer 即使 `rejected` 或含 open P0/P1，仍允许第二名独立 Reviewer 按 CAS 发布；最终 derived gate 继续根据两份真实结论保持 rejected，不能因第一份结论阻塞收齐第二份证据。

sealed snapshot 固定包含 `schemaVersion/reviewRoundId/manifestDigest/previousBundleSnapshotDigest/envelopes/bundleSnapshotDigest`。`envelopeDigest` 覆盖 exact `envelopeBytes`；`bundleSnapshotDigest` 覆盖除自身字段外的 canonical snapshot payload。第一代必须 `previous=null + 1 envelope`，第二代必须 `previous=<上一代 digest> + 2 envelopes`。Reader 返回的 `bundleSnapshotDigest` 必须与实际读取 bytes 自摘要一致，并同时进入 derived output 与 `attestationSetDigest`，因此不同发布代不能冒充同一审查集合。

以下任一条件都阻止 migration：

- sealed snapshot 缺失时保持 pending；sealed 中角色缺失/重复、reviewerId 重复或非独立，或 fixed root 出现未知持久文件；
- attestation digest/round stale，report 缺失、被篡改或摘要不一致；
- verdict 为 `rejected`，或任一 current review 存在 open P0/P1；open P2 只作为 advisory，但不能掩盖其他阻塞；
- 同一 finding code 的 severity 冲突、attestation 结构/时间/路径非 canonical，或 verifier 无法证明 artifact 自摘要及 sources current。

`evaluatedAt` 不读取当前时间：0 review 固定为 `1970-01-01T00:00:00.000Z`，有 review 时取所有有效 attestation 的最大 `reviewedAt`。derived gate 使用固定字段顺序的 JSON 加结尾换行；同一 manifest、bundle 和 report bytes 重复运行必须字节一致。

文件系统边界同样 fail closed：workspace 与固定目录链逐级绑定 canonical `dev/ino` identity；raw attestation/report 和 sealed snapshot 都拒绝 symlink、非 regular file、hardlink 与超限（raw attestation 1 MiB、raw report 5 MiB、sealed 16 MiB）。raw 各自未超限不代表两层 JSON escaping 后的 candidate 一定未超限；publisher 必须在 rename 前先对最终 candidate bytes 执行 16 MiB 检查，并用同一 reader codec 完整重验 canonical/self/envelope/report/attestation/round/role/manifest。只有该 candidate 验证通过后才能写同目录 `wx` temp、file fsync，并在 lock marker 已写入并同步 `round/role/manifest/previous/new digest/sealed count/recovery token` 后进入 rename。

atomic rename 是唯一 commit point，但“已可见”与“已 durable clean”必须分开表达：rename 前任何错误都是 `not_committed`，不得改变上一代 sealed bytes；若 temp/lock 清理本身异常，残留 entry 继续让 reader fail closed，不能宣称所有失败都一定无残留。rename 已生效、首次 bundle directory fsync 尚未成功时发生错误，publisher 返回非零的结构化 `committed_recovery_required`，携带 new `bundleSnapshotDigest`、previous digest、failure stage 与 recovery token，原 lock marker 保留，普通 reader 固定 `publishLocked`。首次 bundle directory fsync 成功后，新 generation 已 durable committed；其后 lock close/unlink 失败且 marker 仍在，仍返回 `committed_recovery_required` 并阻止 reader。若 unlink 已生效，仅 final directory fsync 失败，则返回非零 `committed_cleanup_warning` 和 new digest；此时 reader 可读取 durable bundle，崩溃至多让 stale lock 重新出现并 fail closed，不得虚构中间从未存在无 lock 窗口。

恢复只允许复制 publisher 返回的完整 identity 运行 `g1:manifest:review-recover`：API/CLI 必须逐项校验 recovery token、round、role、manifest、previous/new digest 与 sealed count，并以同一 codec 读回 final snapshot；先再次 fsync bundle directory，确认提交 generation，再 unlink marker 并 final fsync。token 或任一 identity 不同则 marker 保留、reader 继续 blocked；recovery 输出本身始终 `migrationGenerationAllowed=false`，只有随后独立 `review-check` 才能判断 gate。

derived reader 只读单一 sealed 文件：路径校验后使用一个 FD 做 open/fstat/read/post-fstat，并从这一次完整 bytes 解析所有 envelope；不再顺序读取四个 mutable 路径。pathname 初始 stat 与 open FD 必须都是 regular file、`nlink=1` 且身份一致；同一 inode 的追加、等尺寸改写后恢复已知 mtime、读后新增 hardlink，或只删除 pathname 而没有替换，均 fail closed。若完整读取后发生生产形态的 `rename(temp, target)` 原子覆盖，只在 pathname 当前是不同 dev/ino 的 regular `nlink=1` inode，且旧 FD 的 dev/ino/size/mtime 保持读前值、`nlink` 严格从 `1→0` 时，才按已读取旧 bytes 线性化并返回旧 snapshot facts 及其正确 `bundleSnapshotDigest`；旧 FD 在覆盖后变为 `nlink=0` 是被新 pathname 取代的证据，不应先误判成初始 hardlink。新路径属于下一次调用，不能把新旧 Reviewer facts 混合。canonical JSON、self/envelope/raw digest、round/role/manifest/path、report 与 attestation 任一 tamper 都失败。协议 JSON/稳定错误只输出 code/digest/count/status，不输出 report 内容或绝对路径。

命令退出契约：0 review 输出 `pending`；1 份 accepted 且无 blocking 仍输出 `pending`；首份 verdict=`rejected` 或仍含 open P0/P1 时立即输出 `rejected`，但 publisher preflight 仍允许另一角色按 CAS 提交独立事实；2/2 accepted 且无阻塞才输出 `accepted`。除最后一种外均 `migrationGenerationAllowed=false` 并以非零退出。未来 0001～0008 migration generator 必须在同一流程调用该 verifier（或同一底层 API）并断言 derived `migrationGenerationAllowed=true`，禁止只读取 base manifest 的静态字段，也禁止用手工参数绕过。

实施期 frontmatter 的 `status: in_progress` 曾表示 M0-A Schema/migration 尚未实现，不承担记录 Reviewer 是否 2/2 的职责。该阶段已经完成并随 ADR-0015 退役；历史 manifest 和 sidecar 不再接受重建或重新签收，任何新 Schema 变化都必须走新的 forward-only migration 与独立 overlay contract。
