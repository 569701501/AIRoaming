# G3-M 施工包：维护、快照与运行态封口

## 1. 目标

实现同一旧 file 进程内可证明的停写、运行态封口和不可变 snapshot。G3 的只读 comic-format audit 只能作为 inventory，不能替代本协议。

## 2. MaintenanceCoordinator

### 2.1 状态机

```text
open -> draining -> closed
closed -> open                 仅切换失败且尚未激活时
closed -> handed_off           旧进程已交给 DB 进程，终态
```

非法跳转均返回稳定错误；进程重启不得把 closed 状态伪装成已排空。正式 C1 要求不重启旧进程。

### 2.2 mutation lease

```ts
runMutation<T>(operation: string, execute: () => Promise<T>): Promise<T>
```

- open 时先原子增加 activeMutations，再执行，finally 减少。
- draining/closed/handed_off 时拒绝新 lease，HTTP 映射 503 MAINTENANCE_MODE。
- 已取得 lease 的请求允许完成；draining 等待 activeMutations=0。
- 只读请求、health 和本地 maintenance status 不取 mutation lease。
- 内部 tool callback、对话写入、task create/claim、worker completion 也必须经过同一 coordinator，不能只拦 Controller。

### 2.3 participant

```ts
interface MaintenanceParticipant {
  name: string;
  beginDrain(): Promise<void>;
  status(): Promise<{ active: number; queued: number; blockedReason: string | null }>;
  sealRuntimeState(): Promise<unknown>;
  reopen(): Promise<void>;
}
```

首版必须注册：Projects mutation、Dialogue send/stream、Tasks create/worker、ToolCallback、Settings write。任何 participant active/queued 非零都不能 closed。

### 2.4 同进程管理入口

使用 /api/_local/maintenance/status|drain|close|bundle|reopen；只接受 loopback remote address，并校验 X-AIRoaming-Maintenance-Token。

token 文件路径必须由 AIROAMING_MAINTENANCE_TOKEN_FILE 显式提供，权限 0600；响应和日志不输出 token。生产命令不得提供关闭校验的 flag。

CLI：

```text
maintenance status --base-url <loopback-url> --token-file <path>
maintenance drain  --base-url <loopback-url> --token-file <path> --timeout-ms <n>
maintenance close  --base-url <loopback-url> --token-file <path>
maintenance bundle --base-url <loopback-url> --token-file <path> --output <staging>
maintenance reopen --base-url <loopback-url> --token-file <path>
```

缺任一显式参数都失败，不读取默认真实路径。

## 3. Runtime bundle

### 3.1 生成条件

只允许 state=closed、activeMutations=0、activeStreams=0、queued/running/retrying legacy task=0 时生成。

### 3.2 envelope

```json
{
  "schemaVersion": 1,
  "kind": "airoaming_runtime_bundle_v1",
  "createdAt": "2026-07-12T00:00:00.000Z",
  "participants": [],
  "conversationState": {},
  "pendingDialogueState": {},
  "legacyTaskTerminalState": [],
  "unobservableBeforeBridge": [],
  "redaction": { "schemaVersion": 1, "redactedCount": 0 },
  "payloadDigest": "sha256:..."
}
```

payloadDigest 是排除自身后对 canonical JSON 的 SHA-256。数组按稳定 identity 排序；时间来自一次 run clock，不参与 source entity ID。

### 3.3 保密与诚实边界

- Authorization、apiKey、token、cookie、provider 原始敏感响应统一由 CredentialRedactor 处理。
- bridge release 启动前已丢失的内存态写 PRE_BRIDGE_RUNTIME_UNOBSERVABLE，不得伪造空集合为完整迁移。
- bundle 文件以 0600 写临时文件，fsync 后原子 rename；final import 验证完成后删除内容，只保留摘要。

## 4. Snapshot

### 4.1 输入与输出

```text
db-snapshot
  --workspace-root <explicit absolute path>
  --staging-root <explicit empty path>
  --runtime-bundle <sealed file>
  --format json
```

输出目录：

```text
snapshot-<digest>/
  source-manifest.json
  snapshot-manifest.json
  transforms.json
  runtime-bundle.json
  settings.redacted.json
  payload/
  SEALED
```

staging-root 必须为空且不在 workspace-root 内；不接受 symlink 根。

### 4.2 manifest item

```json
{
  "storageKey": "projects/p1/project.json",
  "type": "file",
  "bytes": 123,
  "sha256": "sha256:..."
}
```

storageKey 使用正斜杠、相对路径；拒绝绝对路径、反斜杠、空段、.、..、NUL、symlink、socket/device。目录项不进入 digest，空目录无需保存。

### 4.3 两次源扫描

固定顺序：

1. coordinator 已 closed，生成 pre source manifest。
2. 复制允许文件；settings 只在内存生成 redacted 版本，不复制原文。
3. 对复制内容执行 redactor/normalizer 并写 transforms。
4. 生成 snapshot manifest。
5. 再扫活动源生成 post source manifest。
6. pre/post 逐字不同则删除未封口 staging，返回 SNAPSHOT_SOURCE_CHANGED。
7. 相同后写 SEALED；SEALED 内容绑定两个 manifest digest、runtime bundle digest 和 transform digest。

mtime 只用于诊断，不参与 digest；工具不得修改源文件内容或 mtime。

### 4.4 source 与 snapshot digest

- sourceManifestDigest：pre/post 原始源条目 canonical 排序后的摘要。
- snapshotManifestDigest：真正交给 importer 的脱敏字节摘要。
- transforms 逐项解释 omitted/redacted/normalized；不能只给总数。
- MigrationRun 同时保存 sourceManifestDigest 与 snapshotManifestDigest。

## 5. 稳定错误

| code | 含义 |
| --- | --- |
| MAINTENANCE_MODE | 新 mutation 被拒绝 |
| MAINTENANCE_DRAIN_TIMEOUT | 活动请求未在期限内归零 |
| MAINTENANCE_PARTICIPANT_BUSY | participant 仍 active/queued |
| MAINTENANCE_TOKEN_INVALID | 非 loopback 或 token 错误 |
| RUNTIME_BUNDLE_NOT_CLOSED | 未封口前请求 bundle |
| SNAPSHOT_ARGS_INVALID | 路径/参数不安全 |
| SNAPSHOT_PATH_UNSAFE | 越界、symlink 或特殊文件 |
| SNAPSHOT_SOURCE_CHANGED | pre/post manifest 不一致 |
| SNAPSHOT_SECRET_DETECTED | 无法安全脱敏的秘密命中 |

错误只输出 code、计数和 digest，不输出物理根、用户正文或秘密预览。

## 6. 测试与退出标准

G3-M0 已实现维护协调器、五类 participant、loopback/token 管理 controller 与 `maintenance` CLI。M0 只生成内存返回或 CLI 写出的 closed bundle skeleton；snapshot、redaction、importer、backup、activate 仍未实现。

```text
MNT-01 open mutation 正常、计数 finally 归零
MNT-02 draining 后新写 503，已进入写完成
MNT-03 dialogue stream/task worker/tool callback 都被纳入
MNT-04 participant 非零时 close 失败
MNT-05 非 loopback/错误 token 拒绝
MNT-06 closed bundle 稳定且无 fake secret
SNP-01 pre/post 相同后 sealed
SNP-02 中途改源失败且无 sealed 目录
SNP-03 symlink/../绝对路径拒绝
SNP-04 settings 与旧 payload fake key 不进入 snapshot
SNP-05 两个绝对根同内容产生相同 manifests
SNP-06 audit 前后源 hash/mtime 不变
```

M0/M1 completed 需上述测试全绿、临时根故障注入通过，并有脱敏 runtime-bundle/source-manifest/snapshot-manifest 样例。
