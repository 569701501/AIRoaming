# G0 七阶段行为刻画与 E2E 测试骨架方案

## 1. 结论

G0 不是再做一套七阶段，也不是证明当前项目已经完成最终漫画交付。G0 的职责是给后续能力切片建一张可靠的安全网：当前开发波次为 G1–G5，G6/G7 用例只保留为后置长期索引。

1. 用现有 Vitest 继续覆盖纯函数和 Nest Service 集成行为。
2. 新增独立的 Playwright Test，覆盖真实 HTTP、Vue 页面、路由和用户点击。
3. 自动化环境只使用临时 workspace、本地假 OpenCode/图片供应商和原创 fixture，禁止读取真实项目与真实密钥。
4. 只把当前正确且未来仍成立的行为写成绿色回归测试。
5. 当前已知错误只登记为未来验收用例；到对应 G1/G2/G3/G4/G5/G6 切片开始时，才逐条写 red 测试并实现到 green。
6. 排版与素材包当前分别是“一镜一页复制源图”和“目录包”，因此 G0 只锁它们的前置门禁和步骤投影，不锁当前错误的成功产物。

测试分层最终确定为：

```text
Vitest 纯函数
  -> Vitest Nest Service characterization
    -> Playwright API smoke
      -> Playwright Chromium 用户路径
        -> G7 完整三镜、返修、重启与真实供应商验收
```

G0 本轮只完成本文档和用例矩阵。整套开发文档完善、且用户另行明确授权开发前，不安装 Playwright、不新增测试、不改业务代码。

## 2. G0 要证明什么

### 2.1 本阶段证明

- 七阶段键、顺序、状态投影和基础门禁没有在 D7 迁移中被无意改坏。
- 剧本完成、结构确认、分镜确认、preflight 确认、候选锁定等现有正确动作可以通过公开接口重复执行。
- pending 与 confirmed 的边界可验证；未确认内容不能推进正式阶段。
- 服务关闭后重新创建 application context，已经正式保存的语义事实仍能读取。
- 项目库能打开测试项目；工作区能展示七阶段；waiting 步骤不能由流程栏直接点击。
- 浏览器测试不会启动真实 OpenCode、不会访问真实图片供应商、不会污染默认 `workspace/`。
- 失败时能留下 API/控制台/截图/trace 等可定位证据。

### 2.2 本阶段不证明

- D1 漫画版式必选与不可修改已经实现。
- 上游修改后的 revision/freshness 已修复。
- D3 `CandidateLockRevision` 已实现。
- D7 SQLite DB-only、持久任务、重启恢复和 SecretStore 已实现。
- D4/D5 多格、文字、气泡和确定性渲染已实现。
- 素材包已经是可下载 ZIP，manifest V2 已通过摘要审计。
- 真实文本模型或图片供应商质量稳定。
- `draft -> exported` 最终成品链路已经通过；该结论只能在 G7 给出。

| 项目 | 当前事实 | G0 处理 |

| 单元/集成框架 | shared/server 使用 Vitest，共 79 项测试 | 保留，不更换 |
| Web 测试 | 无测试脚本、无组件测试、无 E2E | 新增独立 Playwright 最小骨架 |

## 4. 测试用例的四类状态

为避免“错误也被测试保护”，G0 统一使用四类用例状态：

| 状态 | 含义 | 是否进入默认 CI |
| --- | --- | --- |
| `green_now` | 当前正确且未来仍必须成立的公开行为 | 是 |
| `migration_witness` | D7 前用于证明旧数据可读取/重启保持的临时迁移证据 | 是；G1 必须用 DB 等价测试替换后才能删除 |
| `record_only` | 已知错误或错误骨架，只保留证据和未来期望，不断言当前错误结果 | 否 |
| `red_on_slice` | 目标行为尚未实现；在所属 G1–G6 切片开始时写成第一个失败测试 | 现在否；所属切片开始后是 |

禁止以下做法：

- 为保持 CI 绿色，把未来失败用例长期写成 `skip/todo` 后无人维护。
- 断言“一镜一页”“复制源图”“素材包是目录”等已知错误。
- 用 snapshot 固化完整随机 ID、时间戳、绝对路径或 Vue DOM 结构。
- 先批量写完 G1–G6 全部 red 测试，再让主分支长期失败。

```text
└────────────────────────┘   └──────┬───────────┬───────┘

  -> 同一 fixture 语义
  -> 临时 workspace
  -> adapter 边界 fake，不启动 Web
```

### 5.1 为什么不只做浏览器 E2E

- 七阶段大多数关键规则在 Service 层，浏览器失败时很难快速定位是 UI、HTTP、状态机还是文件问题。
- Service characterization 运行更快，适合 D7 大规模迁移时频繁回归。
- 浏览器层只保留用户可见的关键路径，不重复所有组合。

### 5.2 为什么 G0 不先搭 Vue 组件测试

- 当前最高风险是跨页面、API、workspace 和任务的链路，而不是单个按钮渲染。
- Vitest Browser 自身仍需要 Playwright/Webdriver provider；在 G0 同时搭组件浏览器栈会增加配置和维护面。
- D4/D5 开发时应优先测试纯编辑命令、文档模型、渲染器和少量关键组件，不应靠大量 DOM snapshot 证明画布正确。

## 6. Web E2E 工具选型

### 6.1 结论：独立 Playwright Test

Playwright 官方支持：

- 通过 `webServer` 启动一个或多个本地服务，并分别设置环境变量、就绪 URL 和关闭信号。
- 使用隔离的 browser context、page 和 request fixture。
- 使用 project dependencies 建立 setup/teardown 项目。
- 保存 trace、DOM snapshot、网络请求和失败截图。
- 用 Chromium 起步，后续按风险增加 Firefox/WebKit 或移动设备 profile。

这些能力直接对应 AI漫游的“Vite + Nest + fake provider + 临时 workspace”场景。

### 6.2 暂不选择 Vitest Browser 作为完整 E2E

Vitest Browser 适合在真实浏览器中挂载 Vue 组件，也推荐 Playwright provider；但 G0 的目标是启动完整应用、跨两个服务、走真实路由和 HTTP。独立 Playwright Test 的 server 生命周期、API request、trace 和下载能力更直接。

后续若 D4/D5 编辑器需要大量组件级交互测试，可以单独评估 Vitest Browser，不影响本次选型。

### 6.3 官方依据

- [Playwright Web server](https://playwright.dev/docs/test-webserver)
- [Playwright fixtures](https://playwright.dev/docs/test-fixtures)
- [Playwright setup/teardown project dependencies](https://playwright.dev/docs/test-global-setup-teardown)
- [Playwright best practices 与 trace](https://playwright.dev/docs/best-practices)

## 7. 自动化环境隔离契约

### 7.1 强制环境变量

| 变量 | 示例 | 规则 |
| --- | --- | --- |
| `AIROAMING_E2E_RUN_ID` | `g0-28431` | 每次运行唯一；用于项目名、路径和证据 |
| `AIROAMING_E2E_SERVER_PORT` | `4311` | 默认与开发端口不同，可覆盖 |
| `AIROAMING_E2E_WEB_PORT` | `5174` | 默认与开发端口不同，可覆盖 |
| `AIROAMING_E2E_PROVIDER_PORT` | `4397` | fake provider，仅绑定 `127.0.0.1` |
| `AIROAMING_WORKSPACE_ROOT` | `/tmp/airoaming-e2e-g0-28431` | 必须是本次运行专用目录 |
| `OPENCODE_AUTO_START` | `false` | 禁止测试启动本机真实 OpenCode |
| `OPENCODE_BASE_URL` | `http://127.0.0.1:4397/opencode` | 只指向 fake provider |
| `OPENAI_IMAGE_BASE_URL` | `http://127.0.0.1:4397/image/v1` | 只指向 fake provider |
| `OPENAI_IMAGE_API_KEY` | `e2e-fake-key` | 固定假值，不使用真实 key |
| `VITE_API_BASE_URL` | `http://127.0.0.1:4311/api` | Web 直连测试 Server |

### 7.2 workspace 防误删

E2E server 包装器在启动前必须：

1. `path.resolve` 规范化根目录。
2. 拒绝默认仓库 `workspace/`、用户 home 和文件系统根目录。
3. 要求目录名包含 `airoaming-e2e-<runId>`。
4. 创建 `.airoaming-e2e-root` marker，写入 runId 和创建时间。
5. 只有 marker 与当前 runId 一致时，关闭 Server 后才允许清理该目录。

任何保护条件不满足时，测试必须直接失败，不能降级到默认 workspace。

### 7.3 端口与并行

- G0 首版 `workers=1`、`fullyParallel=false`，因为当前项目索引、任务和部分 pending 仍在内存，跨测试并行会制造非业务竞态。
- 测试数据仍使用唯一项目名和项目 ID，单用例结束后通过公开删除 API 清理。
- 同一台机器并行启动两次 E2E 时，调用方必须提供不同的 runId 和三个端口。
- `reuseExistingServer=false`。即使本机已有开发服务，也不能复用，因为它可能连接真实 workspace 和真实设置。
- G1 完成事务、DB-only 和持久 worker 后，再评估按 worker 独立项目并行；不在 G0 提前承诺。

## 8. fake provider 边界

fake provider 是测试基础设施，不进入 Nest 业务代码，也不通过 `AIROAMING_E2E=true` 在生产 Service 内写分支。

### 8.1 fake OpenCode

最低支持：

- `GET /opencode/session`：ready 探针。
- `GET /opencode/config`：返回固定 provider/model 列表。
- `POST /opencode/session`：返回固定格式 session ID。
- 消息接口在后续 AI 对话 E2E 使用时返回确定性文本/结构；G0 浏览器 smoke 不发送真实对话。

### 8.2 fake Image API

最低支持：

- `POST /image/v1/images/generations`。
- `POST /image/v1/images/edits`，兼容 JSON 和 multipart。
- 返回固定合法 PNG/WebP 的 `b64_json`。
- 可通过 fake server 自己的测试控制接口切换 `success/delay/429/500/late_success`；控制接口不能出现在 AI漫游正式 API。

### 8.3 网络封闭

- fake provider 只监听 loopback。
- 浏览器 fixture 记录所有请求；出现非当前 Web、Server 或 fake provider host 时失败。
- Server 启动环境不继承任何真实图片 key；显式覆盖为固定假值。
- 日志只记录请求类型、测试 case ID 和摘要，不打印 Authorization、完整 prompt 或表单图片字节。

## 9. fixture 设计

### 9.1 原创故事

继续使用完整验收基线中的原创故事“雨夜末班车”，但拆为两个 profile：

| Profile | 用途 | 内容 |
| --- | --- | --- |
| `rain_smoke` | G0 快速行为刻画 | 1 项目、1 章、1 镜头、每镜 1 候选；不验证最终成稿质量 |
| `rain_full` | G7 完整验收 | 1 项目、1 章、3 镜头、每镜 2 候选、A→B 返修、多格、文字、气泡和 ZIP |

G0 不另造一套业务故事；`rain_smoke` 是 `rain_full` 的最小子集。

### 9.2 fixture 建立原则

- Service 测试通过 `ProjectsService/TasksService` 公开方法逐步建立状态。
- Playwright setup 项目通过 HTTP API 建立测试项目。
- 不把现有用户 workspace 复制成 fixture。
- 不直接修改业务 Service 的私有 Map。
- 只有测试 adapter 自身可以注入固定图片响应。
- 随机 ID 和时间戳只断言关系，不做整对象 snapshot。
- 重新启动 application context 后，用公开 snapshot 读取相同语义，不直接断言 Repository 私有缓存。

### 9.3 标准 checkpoint

```text
draft
  -> script_done
  -> structured
  -> storyboard_pending（不推进）
  -> storyboard_done + preflight blocked
  -> storyboard_done + preflight confirmed
  -> candidates partially locked
  -> images_done
```

`layout_done/exported` 在 G0 只由纯 workflow 映射用例覆盖，不通过当前错误导出动作制造 fixture。

## 10. 测试层级与公开接口

### 10.1 纯函数层

继续使用现有 Vitest：

- `resolveWorkflowCurrentStepKey`。
- workflow step status。
- 任务章节作用域、生成规格、格式规范化等纯规则。

不重复写同一映射测试；G0 只补缺失的行为链。

### 10.2 Nest Service characterization

使用：

```text
NestFactory.createApplicationContext(ProjectsModule)
AIROAMING_WORKSPACE_ROOT=<temp>
ProjectsService / TasksService 公开方法
ImageProviderService adapter fake
```

主要断言：

- 每次用户确认前后 `WorkbenchSnapshot.workflow` 的变化。
- pending 不推进、confirmed 才推进。
- 门禁错误码与正式事实数量不变。
- 全锁前不能完成图片阶段，全锁后进入 `images_done`。
- 关闭并重建 application context 后，正式语义仍存在。

不断言：

- 私有 Map 内容。
- 某个内部方法被调用几次。
- 完整 `project.json` 字符串或写文件顺序。

### 10.3 Playwright API smoke

使用 Playwright `request` fixture 对运行中的真实 Nest App 验证：

- `/api/health`。
- `/api/workspace` 指向测试虚拟根，而不是泄露物理路径。
- 创建带显式 `comicFormat=vertical_scroll` 的项目。
- `/api/projects/:id/workbench` 返回七阶段和默认章节。
- 非法前置动作返回非 2xx 与稳定业务错误。
- setup/teardown 通过公开 API 建立和删除 fixture。

G0 不新增 `supertest`，避免同一 HTTP 层维护两套启动栈。

### 10.4 Playwright Chromium

首版只覆盖最小用户路径：

1. 打开项目库。
2. 看见 setup 创建的原创测试项目。
3. 点击项目卡进入剧本工作区。
4. 看见七个阶段且顺序正确。
5. draft 项目只有“剧本”为 active；后续步骤 disabled。
6. 返回项目库成功。

定位优先级：

```text
getByRole / getByLabel / getByText
  -> 业务稳定 aria-label
    -> 必要时 data-testid（只表达业务身份，不表达 CSS 结构）
```

不使用 `.stage-step:nth-child(4)`、深层 CSS class 或像素坐标作为核心定位。

## 11. 为什么 G0 不跑当前排版与素材包成功路径

这是本方案最重要的边界之一。

### 11.1 排版

当前动作会：

- 每镜创建一页。
- 每页只有一个 placement。
- 导出时只读取 `placements[0]`。
- 直接复制候选源图。

如果 G0 断言“生成 N 个一镜一页文件并进入 layout_done”，就会把 ADR-0011 明确要删除的行为变成回归契约。

G0 只验证：

- 未完成候选图时不能 build/export layout。
- `images_done` 的 workflow 当前步骤是 `layout_export`。
- 排版成功目标由 G5 的多格/文字/气泡/确定性渲染 red 测试定义。

### 11.2 素材包

当前动作会：

- 创建目录而非 ZIP。
- 允许必需文件缺失后继续。
- 把目录登记为 archive Asset。

G0 只验证：

- `layout_done` 前不能导出素材包。
- `layout_done` 的 workflow 当前步骤是 `asset_package`。
- ZIP、下载、manifest V2、摘要和失败原子性由 G6 首个 red 测试定义。

## 13. Playwright 配置边界

建议配置：

| 配置 | G0 值 | 原因 |
| --- | --- | --- |
| browser | Chromium | 先锁主桌面路径 |
| workers | 1 | 当前内存状态与共享测试 workspace 不适合并行变更 |
| retries | 本地 0；CI 1 | 本地直接暴露失败；CI 首次重试用于 trace |
| trace | 本地 `retain-on-failure`；CI `on-first-retry` | 保存定位信息，避免所有成功用例长期保留重 trace |
| screenshot | `only-on-failure` | 失败证据 |
| video | `off` | 首版 trace 已包含主要证据，降低体积 |
| reuseExistingServer | `false` | 禁止误连用户开发服务和真实 workspace |
| outputDir | `test-results/e2e` | 临时测试产物，gitignore |
| reporter | line + html | 命令行与可视报告 |

若安装时所选 Playwright 版本支持 `failOnFlakyTests`，CI 应开启，避免“第一次失败、重试通过”被当作完全通过。

## 14. 命令契约

G0 实现后预计提供：

```text

```

安装步骤只在用户另行授权开始开发后执行：

```text

```

具体版本由实施当日 lockfile 固定，不在方案文档里写漂移版本号。

## 15. 垂直实施切片

每次只完成一个可运行切片，不一次性堆满测试文件。

### G0-1：环境守卫 + 第一个 Service characterization

行为：显式选择 `vertical_scroll` 创建项目后，返回默认章节与七阶段，只有剧本 active。

退出：

- 临时 workspace 建立与清理可证。
- 当前 79 项测试不回归。
- 新用例通过，不触碰真实 workspace。

### G0-2：剧本 → 结构 → 分镜确认边界

行为：

- 完成剧本后进入结构。
- 确认结构后进入分镜。
- 保存 pending storyboard 不推进。
- 确认 storyboard 后进入 preflight。

### G0-3：preflight 与候选门禁

- blocked preflight 不写 confirmed record。

候选生成细节继续由现有 contract integration 测试负责，G0 只断言阶段关系。

### G0-4：排版/素材包前置门禁

行为：

- `images_done` 前 layout build/export 被拒绝。
- `layout_done` 前 package export 被拒绝。

不调用并锁定当前错误成功产物。

### G0-5：Playwright 最小骨架

行为：

- fake provider、临时 Server、Web 都能由测试启动并关闭。

- 浏览器打开项目库和工作区，检查七阶段与禁用状态。
- teardown 删除项目，server wrapper 清理临时根。

### G0-6：稳定性与证据复核

验证：

```text

corepack pnpm test:e2e
```

`repeat-each=3` 是实现验收，不必成为每次普通 CI 的固定成本。

| 后续阶段 | 第一个 red 测试 |

## 17. 证据与留痕

### 17.1 临时证据

默认忽略：

```text
test-results/
playwright-report/
blob-report/
tests/.runtime/
```

失败时至少保留：

- Playwright trace。
- 失败截图。
- 浏览器 console error。
- 失败请求 URL、status 和业务 error code。
- Server/fake provider stderr。
- runId、端口、Node/pnpm/浏览器版本和临时 workspace marker。

禁止写入真实 key、Authorization 或完整图片字节。

### 17.2 正式证据

G0 实现完成后在任务记录和完成记录中登记：

- 新增测试文件与用例数量。
- 全量命令和结果。
- 一次重复运行结果。
- trace/report 的受控路径或摘要。
- Scrutiny Review 与 Runtime/User Review。

不把体积大的 trace、浏览器二进制或临时 workspace 提交到 `文档/`。

## 18. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 测试误启动真实 OpenCode | fake URL + `OPENCODE_AUTO_START=false` + 非 loopback 请求失败 |
| 测试读取真实图片 key | 显式覆盖所有相关 env，临时 settings 根，固定假 key |
| 误删用户 workspace | runId 路径 + marker + 默认 workspace 拒绝 + 关闭后清理 |
| fixture 与实现细节耦合 | 通过公开 Service/API 建立，私有 Repository 只作现有迁移证据且有到期点 |
| 大型 E2E 慢或 flaky | Service 层承担组合测试，浏览器首版只留关键路径，workers=1 |
| 把错误骨架固化 | `record_only/red_on_slice` 分类；G0 不测试错误成功结果 |
| D7 后旧文件测试阻碍迁移 | `migration_witness` 必须由等价 DB 测试接替后删除，不直接删证据 |
| 重试掩盖 flaky | CI retry-pass 视为不稳定；支持时开启 `failOnFlakyTests` |

## 19. G0 实现完成标准

只有同时满足以下条件，G0 才能标记完成：

1. 本文关联的 `green_now` 用例已实现并通过。
2. `migration_witness` 明确标识，且 G1 接替条件写入测试注释和任务计划。
3. `record_only/red_on_slice` 没有被错误地写成当前绿色契约。
4. `corepack pnpm test`、现有三包 typecheck、E2E typecheck 和 `test:e2e` 全部通过。
5. E2E 连续重复 3 次无随机失败。
6. 自动化只访问 loopback，没有真实 provider 请求。
7. 默认 `workspace/`、真实设置和真实项目文件 hash/mtime 不变。
8. Playwright 进程结束后 Server、Web 和 fake provider 均关闭，临时 workspace 被安全清理。
9. Scrutiny Review 通过。
10. Runtime/User Review 能从报告或实际命令确认项目库、工作区和流程栏路径可用。

满足 G0 只代表“安全网建立”，不代表七阶段最终链路完成。
