## 1. 状态

已采纳。

## 2. 背景

AI漫游的 AI 对话(OpenCode runtime)原先只有纯文本聊天能力,所有"AI 生成"动作(生成剧本、剧情结构、分镜、角色图、场景图)都是**伪工具调用**:后端 `dialogue.service.ts` 用 intent 或正则识别用户意图,直接调 ProjectsService 方法,再包装成 `DialogueToolResult` 展示。AI 全程不知道自己"调了工具",它只是在聊天。

这导致:
- AI 不能自主调用工具(不能自己决定生成什么)。
- 用户必须逐步点按钮或对话触发,每一步都依赖用户。
- 将来想做"Agent 自主跑流水线"(给目标,AI 自己跑完全流程),伪工具调用做不到。
- 所有技能逻辑硬编码在 dialogue.service.ts(几千行),不可配置化、不可独立打磨。

项目愿景是让 AI 成为**能自主调用工具的 Agent**,参考 AuroraPlatformWeb 的真工具调用架构。

## 3. 决策

### 3.1 从伪工具调用切换到真工具调用

接通 OpenCode 的工具插件机制(`@opencode-ai/plugin`),让 AI 通过真正的 function calling 自主调用工具(AI 输出 tool_call → 插件 execute 执行 → 结果返回 AI → AI 继续对话)。

### 3.2 OpenCode 升级到 1.17.8

从 1.4.0 升级到 1.17.8。1.17.8 支持插件自动发现(放 `~/.config/opencode/plugin/*.js` 或项目 `.opencode/plugins/`),无需手动注册。验证:echo 插件被 `opencode debug config` 发现,AI 真调 echo 返回结果。

### 3.3 三层架构(参考 Aurora,适配本地非沙盒)

```text
插件工具层(opencodeAI/plugin/airoaming-tools.js)
  每个 tool() 定义:description + args + execute
  execute 保持瘦:参数校验 + HTTP 回调后端 + 结果格式化
    ↓ fetch POST /api/tool-callback/<tool_name>
后端工具网关(src/tool-callback/)
  ToolCallbackController:按工具名路由,token 鉴权
  ToolCallbackService:委托 ProjectsService 业务方法
    ↓ 委托
业务 Service 层(ProjectsService)
  真正干活:调豆包出图、写文件、存 asset、生成任务
```

### 3.4 工具分类与迁移策略

工具分两类,迁移策略不同:

**类型 1(简单触发型)→ 迁移为真工具**:工具参数简单(几个 id/名字),execute 回调后端一个方法即可。已完成:
- `generate_character_image`:生成角色预览图(委托 queueCharacterReference)
- `generate_character_final`:生成角色三视图(委托 queueCharacterReference)
- `generate_scene_image`:生成场景背景图(委托 queueSceneReference)
- `extract_characters`:提取项目角色(委托 extractProjectCharacters)
- `get_project_status`:查询项目状态(委托 getWorkbenchSnapshot,为 Agent 自主编排预留口子)

**类型 2(多轮交互型)→ 保持伪工具调用**:生成内容类(剧情结构/分镜/剧本),AI 要生成大量 JSON 内容。这类天然适合"对话输出 → dialogue 解析 → 存 pending → 用户确认",不适合"作为工具参数搬运"(AI 要先输出一大段 JSON 再作为参数传入,双重负担且可能超模型输出限制)。现有伪工具调用工作良好,强行工具化无收益。

最终格局:**类型 1 走真工具(AI 自主调),类型 2 走伪工具(对话流程 + 用户确认),两套并存各管所长。**

### 3.5 工具与调用方解耦(为 Agent 预留口子)

工具只在 tool-callback 网关注册业务,不关心谁调的:
- 用户点 UI 按钮 → 直接调 ProjectsService(controller 快速路径)
- 用户对话说 → AI 真工具调用(插件 execute 回调 tool-callback)
- [将来] Agent 自主编排 → AI 连续调工具(看状态 → 决策 → 调工具 → 看结果 → 下一步)

三种调用方都最终走到 ProjectsService,工具只是 AI 的调用通道。`get_project_status` 工具是 Agent 自主决策的基础——AI 能看到"哪些角色没图、哪些场景没图",从而自主决定下一步调什么工具。

### 3.6 Nest ESM 下的依赖注入

Nest 在 ESM 模式下,构造函数隐式注入(DI)不工作(service 是 undefined)。必须用 `@Inject(Token)` 显式注入(和 ProjectsController 一致)。

### 3.7 spawn 环境变量注入

OpenCode 是 server spawn 的子进程,默认继承不到 server 的自定义环境变量。改 `opencode-runtime.service.ts` 的 spawn,注入 `AIROAMING_TOOL_CALLBACK_BASE_URL`(指向 server 的 API 地址,用 `process.env.PORT` 即 server 端口,**不是** `this.port` 即 OpenCode 端口)。

## 4. 被否决的备选

### 4.1 否决:工具放前端

前端不能直接调豆包/写文件,技能放前端只是 HTTP 调用包装,真正的执行逻辑还是在后端散落。技能在后端独立成层(tool-callback)更合理,且将来 Agent(在后端跑)能直接调同层技能。

### 4.2 否决:类型 2 迁移为真工具

生成内容类(剧情结构/分镜/剧本)不适合工具化。AI 要在对话里先生成完整 JSON,再作为工具参数搬运,双重负担且可能超模型输出限制。伪工具调用(对话解析 → 存 pending → 用户确认)更适合这类场景。

### 4.3 否决:工具用 Aurora 老版散落文件方式

Aurora 用 OpenCode 1.2.22,散落 .js 文件放 tools/ 目录自动发现。AIRoaming 升级到 1.17.8 后,工具注册方式改为 plugin 函数格式(export default async 返回 {tool:{}}),放 plugin/ 目录。核心思路一致(散落文件、自动发现),只是打包格式适配新版本。

## 5. 影响范围

### 5.1 新增模块

- `apps/server/src/tool-callback/`(controller + service + module):工具回调网关。
- `apps/server/opencodeAI/plugin/airoaming-tools.js`:AIRoaming 工具插件(5 个工具)。
- `~/.config/opencode/plugin/airoaming-tools.js`:全局发现目录的副本(开发期;长期迁项目级 `.opencode/plugins/`)。

### 5.2 修改

- `apps/server/src/ai-runtime/opencode-runtime.service.ts`:spawn 注入工具回调环境变量。
- `apps/server/src/app.module.ts`:注册 ToolCallbackModule。
- OpenCode 全局版本:1.4.0 → 1.17.8(`npm install -g opencode-ai@latest`)。

### 5.3 环境要求

- 全局 `opencode-ai >= 1.17.8`。
- `AIROAMING_TOOL_CALLBACK_BASE_URL`(可选,默认 `http://127.0.0.1:{PORT}/api`)。
- `AIROAMING_TOOL_CALLBACK_TOKEN`(可选,不配则不校验 token)。
