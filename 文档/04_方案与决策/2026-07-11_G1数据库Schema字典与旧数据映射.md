# G1 数据库 Schema 字典与旧数据映射

## 1. 文档定位

本文是 G1 的 M0 数据契约，不是已经落地的 `schema.prisma`。它回答四个问题：

1. DB-only 切换前必须有哪些关系表、版本文档、投影、当前指针和运维记录。
2. 当前 workspace、内存 Map 和旧 Prisma 六模型分别迁到哪里。
3. 哪些稳定关系在 G1 建表，哪些业务能力仍由 G2–G6 实现。
4. 哪些规则必须由数据库约束、事务、文档 codec 和验收共同保证。

本文确认后才可据此编写 Prisma schema 和 migration SQL；确认本文不等于授权修改 schema、数据库、业务代码或真实 workspace。

## 2. 结论

G1 采用以下边界：

- SQLite 是唯一业务事实源，workspace 只保存 Asset 字节、临时文件、显式导出和只读迁移证据。
- 身份、外键、当前指针、任务执行权、历史关系和可查询来源进入关系表。
- 剧情结构、分镜、预检、布局、任务载荷和 manifest 使用带 `schemaVersion + digest` 的 Prisma `Json`。
- Story/Storyboard 的 Scene、Beat、Shot 和来源绑定是确定性投影，只能由文档服务与权威文档同事务写入。
- `ProjectWorkflow` 和项目制作进度不单独保存为另一套可写事实；由章节里程碑、current 指针和 freshness 派生。
- G1 建立 D1/D3/D4-D5 所需的稳定关系，但不实现 G3 创建入口、G4 返修交互或 G5 画布对象能力。
- 不建立通用 `DocumentRecord` 或通用多态业务表来压缩表数量；关键领域继续有明确表名和所有者。

## 3. G1 与后续阶段的边界

| 能力 | G1 处理 | 后续所有者 |
| --- | --- | --- |
| `comicFormat` | 数据库存规范值；导入 `page_horizontal -> paged_comic`；`four_panel/缺失/非法` 阻塞并要求迁移决议 | G3 完成创建弹窗必选、共享枚举收口、普通更新不可修改和用户可见错误 |
| Script/Story/Storyboard 来源链 | 建表、迁移 current/pending、保存 digest 和来源 ID | G2 已采纳方案明确：Script 使用 Chapter working fields，Story/Storyboard 复用 pending version 做 copy-on-write，不新增 Working Copy/Freshness 表；完成显式发布、来源快照和派生 freshness |
| Candidate 定稿 | 建 `CandidateLockRevision` 和 current 指针；只把旧 `lockedCandidateId` 的直接证据导入为 `origin=legacy_import` 的首条修订 | G4 完成收藏/定稿、更换、clear、影响预览和乐观锁 |
| Layout | 建 Working Copy、不可变 Revision 和来源绑定表；旧 `ChapterLayout` 以 `legacy_chapter_layout_v1` 文档导入 | G5 完成 LayoutDocument V1、编辑命令、富文本、气泡和正式渲染 |
| Export | 建不可变 ExportRevision/Artifact；旧来源不足的记录标记 `legacy_unresolved` | G5/G6 完成 PNG/PDF/ZIP、ExportProfile 和素材包 V2 |
| Task | G1 完整实现持久任务、attempt、claim/lease、取消、恢复和 legacy 隔离 | G4/G5/G6 为各自任务补充更精确的来源绑定和幂等规则 |

G1 不允许为了“以后可能用到”提前拆出文字 run、气泡节点、画格顶点、视频时间轴、权限、团队和计费表。

## 4. 全局建模约定

### 4.1 标识、时间和命名

| 项目 | 规则 |
| --- | --- |
| 主键 | `String`；新实体使用 UUID v4。旧 ID 只有在全局唯一且不冲突时保留；`chapter_001/shot_001/script_outline_current` 等作用域 ID 必须按 `projectId + entityType + legacyId-or-relative-key` 稳定重键，原 ID/路径/摘要写入 `ImportedEntitySource`，不得随机或按导入顺序重键 |
| 时间 | `DateTime`，应用层统一输出 UTC ISO 8601；未知旧业务时间保持 `null`，不得用文件 mtime 伪造任务开始或完成时间 |
| 数据库名 | Prisma 模型使用 PascalCase；表和列通过 `@@map/@map` 固定为 snake_case |
| 相对路径 | 统一命名 `storageKey`，使用 `/` 分隔、相对 workspace；数据库不保存本机绝对路径 |
| 摘要 | `sha256:<64个小写十六进制字符>`；同一字段不能混用裸 hex、base64 和带前缀格式 |
| 可变行 | 增加 `rowVersion Int @default(0)`；更新使用 `id + rowVersion` 条件并原子递增 |
| 顺序 | 业务顺序从 1 开始；迁移与 schema CHECK 拒绝 0 和负数 |

### 4.2 Json 文档摘要

文档摘要采用 RFC 8785 JCS 规范化后执行 SHA-256：

- 对象属性递归确定排序。
- 数组元素顺序保持不变。
- 不输出多余空白。
- 拒绝重复键、`NaN`、`Infinity`、`undefined` 和非 I-JSON 值。
- 输出 UTF-8。

参考：[RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html)。

每类复杂 Json 必须由唯一 `DocumentCodec<T>` 负责：

```text
parse/validate
  -> normalize
  -> canonicalize
  -> digest
  -> buildProjection
```

页面、Controller、导入器和普通 Repository 不得绕过 codec 直接写 Json 或投影。

### 4.3 关系删除规则

| 关系类型 | `onDelete` 原则 | 说明 |
| --- | --- | --- |
| 私有值对象/投影 | `Cascade` | 例如 StoryVersion -> StoryBeatProjection；父版本删除时没有独立存在价值 |
| current/pending 指针 | `SetNull` | 删除被指对象前先显式切换指针；避免循环级联 |
| 历史来源 | `Restrict` | Candidate -> Asset/Task、LayoutSourceBinding -> LockRevision 等不得被普通删除破坏 |
| 项目最终清理 | 显式删除顺序 | 先完成文件删除 Outbox，再按引用顺序删除历史行，最后删除 Project；不依赖一次裸 cascade 假装文件和数据库原子 |
| 通用来源索引 | 仅真实父表外键 | `GenerationTaskSource` 的 `sourceType/sourceId` 是多类型索引，无法用单一 FK；由 codec/事务校验并有一致性扫描 |

所有稳定 ID 和 owner scope FK 精确 `onUpdate=NoAction`；不用 `Cascade` 暗示可以改写历史身份。

### 4.4 同作用域约束

以下关系不能只验证“ID 存在”，还必须验证属于同一项目/章节：

- Project.currentChapter -> 同一 Project 的 Chapter。
- Chapter 的所有 current/pending 指针 -> 同一 Chapter 的版本。
- Candidate -> 同一 project/chapter 的 Shot、Asset 和 Task。
- CandidateLockRevision -> 同一 Shot 的 Candidate。
- Layout/Export 来源 -> 同一 project/chapter。

实现优先使用复合唯一键与复合外键；Prisma 无法清晰表达的关系使用定制 migration SQL 或短事务校验，并必须有跨作用域负例测试。

## 6. 持久化、迁移与 Outbox

### 6.1 `PersistenceState`

| 字段组 | 字段 |
| --- | --- |
| 单例 | `id="primary"`, `storageContractVersion` |
| 激活 | `activationState=shadow/ready_for_activation/db_only/recovery_required`, `cutoverRunId`, `sourceManifestDigest`, `effectiveSchemaManifestDigest` |
| 回滚边界 | `activatedAt`, `firstBusinessWriteAt` |
| 健康 | `lastVerifiedAt`, `createdAt`, `updatedAt` |

约束：

- 表中只能有 `id=primary` 一行。
- 首行只能以 shadow/空激活身份创建且永不允许 DELETE；不能删后重插伪造切换历史。
- id/storageContractVersion/createdAt 永久不可由业务 UPDATE；版本升级只能走显式 migration。
- Server 以 `AIROAMING_PERSISTENCE_MODE=db` 启动时，必须确认状态是 `db_only` 或显式维护态；不匹配即启动失败。
- `sourceManifestDigest` 绑定迁移输入/工作区身份，必须与 `MigrationRun.sourceManifestDigest` 相等；`effectiveSchemaManifestDigest` 绑定当前实际发布的 Schema 身份，必须与 final run `verificationJson.effectiveSchemaManifestDigest` 及当前发布包相等，两者不得混用。
- shadow 身份的 cutover/source/effective/activated/firstWrite 全为 null；ready/db_only 的 cutover/source/effective 全非空。从 `ready_for_activation→db_only` 时必须同时复核 run/source/effective，激活后三者均不可改。
- `activatedAt` 只能在 `ready_for_activation→db_only` 同一 UPDATE 首次写入；pre-activation recovery 的 activatedAt/firstBusinessWriteAt 必须都为空。
- 正式激活后的第一个非迁移业务写事务单独填充 `firstBusinessWriteAt`；它只能在已激活 db_only 首写，非空后禁止退回 file-only。

### 6.2 `MigrationRun`

字段：`id/kind/status/importerVersion/sourceManifestDigest/snapshotManifestDigest/decisionsDigest/reportDigest/countsJson/countsSchemaVersion/verificationJson/verificationSchemaVersion/errorCode/startedAt/finishedAt/createdAt`。

枚举：

- `kind=audit/shadow/final/rollback_restore`
- `status=running/blocked/succeeded/failed`

规则：INSERT 只能 running；只允许一次 running→blocked/succeeded/failed 终结。final succeeded 必须有完整 snapshot/decisions/report/counts/verification、integrity ok/FK 0/manifest match，且没有未解决 blocker；run 的输入摘要、报告摘要和状态不可在完成后覆盖或删除，重新演练创建新 run。

### 6.3 `ImportedEntitySource`

字段：`id/sourceKey/entityType/entityId/sourceStorageKey/sourceDigest/payloadDigest/provenanceStatus/firstRunId/lastRunId/createdAt/updatedAt`。

索引与约束：

- `sourceKey` 全局唯一。
- 索引 `(entityType, entityId)` 和 `lastRunId`。
- 同一 sourceKey 再次出现时，digest 相同为幂等 no-op；digest 不同进入 `SOURCE_MUTATED_AFTER_IMPORT`，不得静默覆盖已导入不可变实体。
- `provenanceStatus` 只能 `reference_only -> partial -> complete` 单向提升。
- source/entity/storage/digest/firstRun identity 创建后不可改；更强证据只可补齐原 null payloadDigest、推进 lastRun/provenance，已有摘要不得覆盖。

### 6.4 `MigrationIssue`

字段：`id/runId/issueKey/severity/code/sourceKey/entityType/entityId/storageKey/detailJson/detailSchemaVersion/resolutionStatus/resolutionJson/resolvedAt/createdAt`。

约束：`(runId, issueKey)` 唯一。`severity=blocker/warning/info`；只有未解决 blocker 数为 0 才能进入正式切换。Issue 只可在父 run=running 时新增/解决，run terminal 后禁止 I/U，Issue 永不删除。

### 6.5 `OutboxEvent`

字段：

```text
id, eventType, aggregateType, aggregateId,
payloadJson, payloadSchemaVersion, payloadDigest,
status, attempt, maxAttempts, availableAt,
leaseOwnerId, leaseToken, leaseExpiresAt,
lastErrorJson, createdAt, updatedAt, processedAt,
idempotencyKey
```

约束与索引：

- `idempotencyKey` 唯一；当前非空 leaseToken 也唯一（多个 null 合法）。terminal 清 token 后 DB 不保存 token 历史，Service 必须每次 claim 生成新 UUID v4并由测试防复用。
- maxAttempts 在 G1 固定为 3，不由调用方扩大。
- claim 索引 `(status, availableAt, createdAt)`；恢复索引 `(status, leaseExpiresAt)`。
- 首版事件：`asset.promote`, `asset.delete`, `project.delete_files`, `secret.delete_old_ref`, `legacy_metadata.archive`。
- 文件、SecretStore 和压缩等外部动作必须在数据库事务外执行；Outbox 只持久化意图和可重放状态。
- INSERT 只能 pending/attempt=0；每次 pending→processing 恰好 attempt+1，processing→retry/terminal 不增 attempt，到 maxAttempts 不得再回 pending。processed/failed 不可重开，禁止直接插 processed 伪造 purge 证据。
- processing heartbeat 不得换 owner/token，只能单调延长 expiry；过期接管必须先 CAS 回 pending 清 lease，再以新 attempt/唯一 token claim。
- OutboxEvent 在 G1 不允许普通 DELETE；pending/processing 重放意图和 processed purge/secret 证据都必须保留，retention 后置显式 maintenance overlay。
- 五类 event 的 strict payload、idempotency、claim/fencing、外部 postcondition、retry/replay 与 terminal 行为以 `2026-07-11_G1任务与Outbox实施注册表.md` 的 `OutboxHandlerRegistryV1` 为唯一实施表；未知或 registry 不完整的 event 可作为 legacy 证据保留，但 runtime 不得 claim。

## 7. 全局设置与凭据元数据

### 7.1 `AppPreference`

单例字段：`id="primary"/theme/activeImageProviderId/defaultTextProviderId/defaultTextModelId/rowVersion/updatedAt`。

`theme=system/dark/light`。这里没有任何 key、token、密码或 key preview。

### 7.2 `ProviderConfig`

字段：`id/providerId/runtimeKind/displayName/modelId/baseUrl/enabled/rowVersion/createdAt/updatedAt`。

- `providerId` 唯一。
- `runtimeKind=text/image`。
- `baseUrl` 是非秘密配置，但写入前仍执行 URL allow/deny 和日志脱敏。

### 7.3 `CredentialMetadata`

字段：`id/providerConfigId/owner/status/secretRef/fingerprint/configured/rotatedAt/createdAt/updatedAt`。

- `providerConfigId` 唯一。
- `owner=opencode/image_secret_store/environment`；text 固定 opencode，image 才可 image_secret_store 或无桌面部署下的 environment。
- `status=unconfigured/configured/rotating/clearing/error`。
- 任何 configured metadata 必须有完整 fingerprint；图片 secret-store 配置还必须有唯一不透明 `secretRef`，数据库无法解析明文。
- 文本模型 owner 固定为 `opencode`，不复制 OpenCode auth 内容。
- 非空 secretRef 全局唯一。image ref 旋转前同事务建立旧 ref 删除 Outbox；clear 先保留旧 ref 进入 clearing，匹配 Outbox processed 后才清 ref/变 unconfigured，当前 ref 非空时禁止删 metadata。
- 表中没有 `apiKey/token/password/keyPreview/ciphertext/masterKey` 列。
- `ProviderConfig.providerId` 是不可变逻辑身份。普通编辑只更新 displayName/modelId/baseUrl/enabled；从 provider A 改到 provider B 必须新建 ProviderConfig/credential、切 AppPreference 指针，再按 clearing + `secret.delete_old_ref` 清旧配置，不能原地 UPDATE providerId。

## 8. 项目、章节和剧本

### 8.1 `Project`

字段：

```text
id, name, type, lifecycleStatus,
storyTitle, genreTags, comicFormat, artStyle, description,
currentChapterId, currentScriptOutlineId,
rowVersion, createdAt, updatedAt, deletingAt
```

规则：

- `lifecycleStatus=active/deleting`；制作进度不保存在这里，由章节事实派生。
- `genreTags` 是受控字符串数组，是 Project 行的一部分，不作为独立版本文档。
- 数据库只保存 `comicFormat=vertical_scroll/paged_comic`。
- `page_horizontal` 在导入时映射为 `paged_comic`；`four_panel/空/非法` 必须先有迁移决议。
- G1 可保留旧 DTO 的临时读别名，但不得把旧别名写回数据库；G3 删除兼容层并完成不可变入口。
- 索引 `(lifecycleStatus, updatedAt)`。

### 8.2 `ProjectScriptOutline`

字段：`id/projectId/version/status/title/sourceText/sourceDigest/createdAt/updatedAt/confirmedAt`。

- `(projectId, version)` 唯一。
- `status=draft/confirmed/archived`。
- 旧单份 `script-outline.md/json` 导入为 version 1；`sourcePath` 只进入迁移证据，不进入运行时领域表。
- 状态只允许 draft→confirmed→archived；confirmed/archived 不得退回 draft。正式后的正文、摘要、版本、归属和 confirmedAt 永久不可改；重新生成新建版本。

### 8.3 `Chapter`

字段：

```text
id, projectId, slug, order, title, milestoneStatus,
scriptWorkingText, scriptWorkingDigest, scriptWorkingState,
summary, completedAt,
currentScriptVersionId,
currentStoryVersionId, pendingStoryVersionId,
currentStoryboardVersionId, pendingStoryboardVersionId,
currentPreflightRevisionId,
currentLayoutRevisionId, currentExportRevisionId,
lastScriptRevisionId,
rowVersion, createdAt, updatedAt
```

唯一约束与索引：

- `(projectId, slug)` 唯一。
- `(projectId, order)` 唯一。
- 索引 `(projectId, milestoneStatus)`。
- current/pending 指针必须属于同一 Chapter；同一 Story/Storyboard 版本不能同时是 current 和 pending。
- current Story/Storyboard 必须 confirmed 且 source/基础 projection 完整，pending 指针必须指 pending_confirmation；current Preflight 必须 confirmed+ready+source 完整，current Layout 必须 sealed+source complete（legacy unresolved 不得 current）。这些目标状态属于 G1 base，G2 只叠加 active pending、CAS/freshness/NewWorkGate。

`milestoneStatus` 继续表示单调完成里程碑；G2 的 stale/needs_update 不通过倒退该字段表达。

### 8.4 `ChapterScriptVersion`

字段：`id/chapterId/version/sourceText/sourceDigest/origin/createdAt/completedAt`。

- `(chapterId, version)` 唯一。
- `origin=user/import/ai_confirmed`。
- 创建后正文、摘要和版本号不可更新。

### 8.5 `ChapterScriptPending`

字段：`id/chapterId/sourceText/sourceDigest/operation/threadId/messageId/toolCallId/rowVersion/createdAt/updatedAt`。

- `chapterId` 唯一；每章最多一份当前 pending。
- 新生成按现有产品语义替换当前 pending；被替换/采用/丢弃的动作仍在 DialogueToolResult 和 ScriptRevision 留痕。
- 采用 pending 只更新 Working Text；是否发布新 ScriptVersion 由 G2 的完成动作决定。

### 8.6 `ChapterScriptRevision`

字段：`id/chapterId/source/threadId/messageId/toolCallId/operation/summary/targetWorkingDigest/createdAt`。

- `(threadId, toolCallId)` 在非空时唯一。
- 当前 `script.revisions/latest.json` 导入一条记录；不虚构更早历史。

## 9. 剧情结构、分镜和预检

### 9.1 `StoryVersion`

字段：

```text
id, projectId, chapterId, version, status,
sourceScriptVersionId, sourcePolicyVersion, sourceDigest,
documentJson, schemaVersion, documentDigest,
origin, rowVersion,
createdAt, updatedAt, confirmedAt, archivedAt
```

- `(chapterId, version)` 唯一。
- `status=pending_confirmation/confirmed/archived`。
- 生命周期只允许 `pending_confirmation→confirmed` 或 `pending_confirmation→archived`；`confirmed` 永远不转 `archived`，`archived` 只表示尚未确认的 pending 被替换或主动放弃。
- pending 可由统一 codec 更新；确认事务必须在 parent 仍为 pending 时先生成并校验投影，再切 confirmed，最后切 current 指针；confirmed 后文档不可原地更新。
- G2 已采纳契约选择直接复用 pending StoryVersion 作为 Working Copy，不新增独立表；pending 更新必须递增 `rowVersion`，confirmed/archived 后不可修改 source/document/version/origin。
- `origin=user_edit/ai_generate/import/legacy_import`；`archivedAt` 只在 pending 被替换或放弃时写入。
- runtime/非 `legacy_import` 的 `sourceScriptVersionId/sourcePolicyVersion/sourceDigest` 必须全部非空。legacy 无法证明的字段可保持 null；缺任一项时派生 unresolved，不得用空串或当前 policy 伪造历史，也不得静默设为 Chapter current。

### 9.2 `StorySceneProjection`

字段：`id/storyVersionId/chapterSceneId/sceneKey/order/name/semanticDigest`。

- `(storyVersionId, sceneKey)` 和 `(storyVersionId, order)` 唯一。
- 只保存查询和关联所需的稳定片段；完整描述仍在 StoryVersion.documentJson。

### 9.3 `StoryBeatProjection`

字段：`id/storyVersionId/beatKey/order/chapterSceneId/summary/semanticDigest`。

- `(storyVersionId, beatKey)` 和 `(storyVersionId, order)` 唯一。
- 不能由页面直接编辑；损坏时从 StoryVersion 重建。

### 9.4 `ChapterScene` 与 `SceneVisual`

`ChapterScene` 字段：`id/projectId/chapterId/sceneKey/currentVisualId/createdAt/updatedAt`；`(chapterId, sceneKey)` 唯一。

`SceneVisual` 字段：`id/chapterSceneId/assetId/sourceTaskId/version/createdAt`；`(chapterSceneId, version)` 和 `assetId` 唯一。

这样场景语义版本与场景参考图分离：补一张场景图不会原地改写已确认 StoryVersion，也不会仅因 `updatedAt` 变化让所有分镜失效。

ChapterScene 设置 currentVisualId 时必须反查 SceneVisual 对应 Asset.status=ready；staged/missing 不能切 current。

### 9.5 `StoryboardVersion`

字段与 StoryVersion 同构，来源改为 `sourceStoryVersionId/sourcePolicyVersion/sourceDigest`，文档使用 `StoryboardDocumentCodec`；同样包含 `origin/rowVersion/archivedAt`。

- `(chapterId, version)` 唯一。
- `status=pending_confirmation/confirmed/archived`。
- 生命周期与 StoryVersion 完全同构：只允许 `pending_confirmation→confirmed` 或 `pending_confirmation→archived`；离开 current 的 confirmed 历史仍保持 confirmed，不通过 archived “解冻”。
- 确认时先在 parent 仍为 pending 时维护 Shot、ShotProjection、ShotCharacterProjection，通过 formalize guard 后再切 confirmed/current，全部位于同一事务。
- G2 已采纳契约复用 pending StoryboardVersion 作为 Working Copy；被确认版本不允许原地编辑，删除/重排镜头也不能清空 Candidate/Layout/Export 历史。
- Storyboard 的 source 三元组与 Story 同样：非 legacy 必填，legacy 可按直接证据保留部分/null，任一缺失即 unresolved 且不得静默 current。

### 9.6 `Shot`

字段：`id/projectId/chapterId/lifecycleStatus/currentCandidateLockRevisionId/createdAt/updatedAt/retiredAt`。

- Shot 是跨 StoryboardVersion 保持的稳定身份；具体镜头内容属于版本文档和投影。

### 9.7 `StoryboardShotProjection`

- `(storyboardVersionId, shotId)` 和 `(storyboardVersionId, order)` 唯一。
- 完整 comic/motion/prompt 内容留在 StoryboardVersion.documentJson。

### 9.8 `StoryboardShotCharacter`

字段：`id/storyboardShotProjectionId/order/sourceToken/characterId`。

- `(storyboardShotProjectionId, order)` 唯一。
- 已解析角色写 `characterId`；G1 runtime/legacy V1 的结构角色 token 可保留 `sourceToken` 且 `characterId=null`，由 preflight 明确解析或阻塞；G2 V2 未解析 token 直接拒绝，不伪造角色。

### 9.9 `PreflightRevision`

字段：

```text
id, projectId, chapterId, version, status,
sourceStoryboardVersionId, sourcePolicyVersion, sourceDigest,
documentJson, schemaVersion, documentDigest, ready,
createdAt, confirmedAt
```

- `(chapterId, version)` 唯一。
- `status=confirmed/archived`；confirmed 内容不可原地改写。是否 historical 由 `Chapter.currentPreflightRevisionId` 派生，不把 freshness 写回 status。
- `ready` 是与同一 document/digest 一起生成的查询投影，客户端不能直接写。
- Preflight 的 `sourceStoryboardVersionId/sourcePolicyVersion/sourceDigest` 始终非空。旧 preflight 无法完整证明时不插入伪 `PreflightRevision`，只创建 blocker `PREFLIGHT_SOURCE_UNRESOLVED`。final run 不能带 open blocker 激活；切换前用户必须显式选择 `drop_current_preflight_and_reconfirm_after_cutover`，Importer 将 issue 标 resolved、把 canonical resolution 纳入 decisionsDigest、保持 currentPreflightRevisionId=null。DB-only 后 NewWorkGate 以 `PREFLIGHT_RECONFIRMATION_REQUIRED_AFTER_MIGRATION` 阻止新候选任务，直到用户基于 current Storyboard/Visual/comicFormat 新建并确认 PreflightRevision。本规则不代表当前已取得真实数据决议。

## 11. Layout 与 Export

### 11.1 `LayoutWorkingCopy`

字段：`id/projectId/chapterId/documentKind/documentJson/schemaVersion/documentDigest/sourceLockSetDigest/basedOnRevisionId/rowVersion/createdAt/updatedAt`。

- `chapterId` 唯一，每章一份当前 Working Copy。
- `documentKind=legacy_chapter_layout_v1/layout_document_v1`。
- legacy 文档由 importer 包成固定 envelope：`{schemaVersion:1,kind:'legacy_chapter_layout_v1',sourceResolution:'complete'|'unresolved',legacyDocument,sourceBindings}`；raw JSON 只放在 legacyDocument，可证明来源放 sourceBindings，不能让 SQL trigger 猜旧路径；unresolved 不得设 current。
- G1 只保证旧布局 DB-only 可读写；G5 才允许创建正式 V1 高自由对象。

### 11.2 `LayoutRevision`

字段：`id/projectId/chapterId/revision/previousRevisionId/contentBasedOnRevisionId/documentJson/schemaVersion/documentDigest/sourceLockSetDigest/origin/saveReason/bindingSetSealedAt/createdAt`。

- `(chapterId, revision)` 唯一。
- `origin=runtime/legacy_import`；`saveReason=user_checkpoint/export_checkpoint/history_restore/legacy_import`；不可变。
- G5 runtime 使用 `previousRevisionId` 建立 current 线性时间线并支持精确重放；`contentBasedOnRevisionId` 单独记录历史恢复的内容来源，不能把两者混成一个字段。
- 只有来源可确定且通过 codec 的文档才能成为正式 revision；无法回填 lock revision 的旧布局进入 Working Copy 或 `legacy_unresolved`，不伪装为 current。
- 创建顺序固定为“插入 unsealed LayoutRevision → 插入 LayoutSourceBinding → 单向写 `bindingSetSealedAt` → 切 current”，整体位于同一事务；INSERT 禁止预填 seal。合法空 canvas/纯文字文档可以有 0 条 Binding，但只要文档含 source-backed 元素，Binding 必须与 codec 投影精确一致。seal 后 Binding 禁止晚插入/改写/删除。

### 11.3 `LayoutSourceBinding`

字段：`id/layoutRevisionId/elementId/role/order/shotId/candidateId/candidateLockRevisionId/assetId/sourceDigest`。

- `(layoutRevisionId, elementId, role)` 与 `(layoutRevisionId, role, order)` 唯一。
- `candidateLockRevisionId` 对正式新修订必填；旧不可解析来源允许为空并派生 `unresolved`。
- 来源新鲜度由 binding 与 Shot.currentCandidateLockRevisionId 比较得到，不存独立可写 stale 标志。
- Binding 永久 append-only：seal 前只能继续 INSERT，任何 UPDATE 拒绝；DELETE 仅协调 purge，seal 后连 INSERT 也禁止。

### 11.4 `ExportRevision`

字段：

```text
id, projectId, chapterId, scopeKey, revision, kind, status,

profileJson, profileSchemaVersion, profileDigest,
preflightDigest, rendererVersion,
manifestJson, manifestSchemaVersion, manifestDigest,
completionApplicability, origin, createdAt, readyAt, failedAt, cancelledAt
```

- `scopeKey=project` 或 `chapter:<chapterId>`；`(projectId, scopeKey, kind, revision)` 唯一，不依赖 nullable chapter 的唯一语义。
- G5 accepted（尚未实现）将 runtime `kind` 收口为 `layout_publication/asset_package/video`；一个 layout_publication 通过 ExportArtifact 同时表达必需 PNG 与可选 PDF/long PNG，避免单一 current 指针在 PNG/PDF 间竞争。

- `completionApplicability=current/historical/legacy_unresolved`；按 G4 细化，它表示完成登记时的不可变适用性，当前 source freshness 另行查询派生。

- `(exportRevisionId, role, order)` 和 `assetId` 唯一。

## 13. 持久任务

### 13.1 `GenerationTask`

字段：

```text
id, projectId, chapterId, type,
recordKind, provenanceStatus, status,
phase, progressPercent, targetType, targetId,
inputJson, inputSchemaVersion, inputDigest,
outputJson, outputSchemaVersion, outputDigest,
errorJson, errorSchemaVersion,
sourceDigest, sourceSetSealedAt, idempotencyKey, concurrencyKey, priority,
attempt, maxAttempts, nextRunAt,
leaseOwnerId, leaseToken, leaseExpiresAt, heartbeatAt,
cancelRequestedAt, retryDisabled, needsReview, applicability,
importSource, importedAt, observedEvidenceJson, evidenceSchemaVersion,
createdAt, updatedAt, startedAt, finishedAt
```

索引：

- claim：`(recordKind, status, nextRunAt, priority, createdAt)`。
- recovery：`(status, leaseExpiresAt)`。
- 查询：`(projectId, status, updatedAt)`、`(chapterId, type, createdAt)`、`(targetType, targetId)`。
- `idempotencyKey` 可空且唯一；runtime 必填，legacy 为空。

`inputJson` 保存创建时已经规范化的完整执行文档：业务 input、options、非秘密 provider/model 选择、trace 和 `sourceProjection: TaskSourceProjectionV1`；`targetType/targetId/chapterId` 与 `GenerationTaskSource` 是同事务关系投影。sourceProjection 与 TaskSource 逐项/计数完全一致后才可 seal，sourceType 使用 G1 registry 的 snake_case token。任何 credential 明文都不属于执行文档。

Shared 10 类 task 的完整 input/output codec、target、source builder、idempotency、slot、attempt/backoff、lease replay、Artifact、cancel 与 terminal policy 以 `2026-07-11_G1任务与Outbox实施注册表.md` 的 `TaskPolicyRegistryV1` 为唯一实施表；未启用或缺任一字段的 policy 不得创建 runtime Task。

数据库 CHECK：

1. runtime：`status` 必须是正常状态、`retryDisabled=false`、`maxAttempts>=1`、`idempotencyKey` 非空。
2. legacy_imported：只读，`retryDisabled=true/maxAttempts=0`；status 只能为空或有直接证据的终态。
3. legacy_stub：`status=null/retryDisabled=true/maxAttempts=0`，不得有 lease、nextRunAt 或 current attempt。
4. progress 为 null 或 0–100；attempt 不得大于 maxAttempts。
5. 任何 legacy 行不得进入 queued/running/retrying。
6. runtime 只能以 queued/attempt=0/无 lease 创建；queued/retrying 只可 claim→running 或取消，running 只可由当前 Attempt 终结触发 terminal/retrying，terminal 不可重开。
7. runtime Task 在 claim 前必须已写 `sourceSetSealedAt`；INSERT 禁止预填 seal，创建顺序是“unsealed Task → GenerationTaskSource[] → 单向 seal”，同一事务完成。

legacy 永不升级为 runtime；发现更强原始证据时只允许 `legacy_stub→legacy_imported` 和 provenance 单向提升，原为 null 的证据字段可首次补齐，已有非空字段不可覆盖。legacy TaskSource 只可在未 seal/证据未 complete 时 append，不能 UPDATE/DELETE。

claim 通过唯一的 Task 条件 UPDATE 入口触发数据库 materialize：同一 statement/事务内切 running、插入当次 TaskAttempt、占用最低空闲 slot，子动作失败则全部回滚；未到 nextRunAt 或已有 cancel 请求不得 claim。heartbeat 先用 OLD Task/Slot/Attempt fencing，再由 AFTER trigger 原子同步 Task 与 Slot expiry；终结以当前 TaskAttempt 的一次性 finish UPDATE 为唯一入口，同 statement 映射 Task 状态并释放匹配 slot。finalize/recovery 全程核对 claimToken，避免即时 trigger 之间出现“谁先存在”的循环漏洞。

### 13.2 `TaskAttempt`

字段：`id/taskId/attemptNo/workerId/claimToken/outcome/errorJson/errorSchemaVersion/artifactRefsJson/artifactSchemaVersion/startedAt/finishedAt/createdAt`。

- `(taskId, attemptNo)` 和 `claimToken` 唯一。
- outcome 为 `succeeded/failed/cancelled/interrupted` 或 null。
- finished 后不可再次修改；旧 attempt 永不覆盖。
- legacy task 禁止建立 attempt。

### 13.3 `TaskConcurrencySlot`

字段：`id/concurrencyKey/slotNo/taskId/leaseOwnerId/claimToken/leaseExpiresAt/updatedAt`。

- `(concurrencyKey, slotNo)` 唯一，`taskId` 可空且唯一。
- V1 初始化 `image-provider:1` 一个槽；不使用 Prisma 6.19 尚不支持表达的 partial unique index模拟并发 1。
- claim、task lease 和 slot 占用在同一短事务提交。

### 13.4 `GenerationTaskSource`

字段：`id/taskId/role/order/sourceType/sourceId/sourceDigest`。

- `(taskId, role, order)` 唯一。
- 索引 `(sourceType, sourceId)`，用于 D3/G4 影响分析。
- 它是 inputJson 的确定性关系投影，不能独立编辑；每次创建任务与 input 同事务生成。
- sourceType 采用 `TaskSourceRegistryV1` 的 snake_case token；首版 owner lookup/digest policy 见 G1 实施契约 10.4.1，未知 token 只能留在 legacy/unsealed 证据，不能让 runtime seal/claim。
- Source 永久 append-only：任何 UPDATE 拒绝、DELETE 仅协调 purge；父 Task seal 后连 INSERT 也禁止。未 seal Task 不进入 claim 查询。

## 17. 冲突与阻塞规则

### 17.1 必须阻塞切换

- project 目录 ID 与 `project.json.id` 冲突。
- 重复 Project/Chapter/Shot/Candidate/Asset ID 指向不同内容。
- `four_panel`、缺失或非法 comicFormat 没有迁移决议。
- JSON 无法解析或 codec 校验失败，且该文件是 current/pending 权威输入。
- current 指针指向另一项目/章节或不存在实体。
- Asset 记录引用的物理文件缺失、越界或摘要在同一快照中变化。
- Candidate 指向不存在的 Shot/Asset；缺 Task 不阻塞，必须创建 stub。
- 图片 key 未成功进入后端 SecretStore，或明文仍可在活动 settings/DB/report/log 中检出。
- 旧 task artifact、Asset meta、runtime bundle 或 provider error 检出凭据原文；旧历史也不得带秘密进入 snapshot/DB/档案。
- 最终停写时仍有 queued/running/retrying 旧任务或活动对话流。
- `PRAGMA integrity_check` 非 `ok` 或 `PRAGMA foreign_key_check` 返回任意行。

### 17.2 可以带 warning 进入切换

- `chapter.json.sourceText` 与 `script.md` 不同，但现有加载规则明确以非空 `script.md` 为准，且两个摘要都进入证据。
- `workflow.json` 与从正式实体重建的 workflow 不同；DB 使用重建结果。
- 文件时间缺失，业务时间保持 null 或使用实体直接字段，不用 mtime 推断。
- 物理孤儿文件没有任何业务引用；报告后保留，不自动删除，也不注册为成功资产。
- 旧 layout/export 无法回填修订来源；保留为 `legacy_unresolved`，不能成为新的正式导出来源。

## 18. Prisma 与 migration SQL 约束

当前仓库实际使用 Prisma 6.19.3。G1 不同时升级 Prisma major，原因是数据库切换本身已经高风险。

### 18.1 Prisma schema 表达

- 使用 SQLite `Json`、`String`、外键、唯一约束和普通索引。G1 closed/controlled-open/free-text 标量在 Prisma 层统一为 `String`；Shared union/codec 管理应用类型，SQLite CHECK 管理闭合值域。本实施裁决覆盖早期“使用 Prisma enum”的通用表述，避免 enum 与独立 CHECK/manifest 形成两份可漂移值域。
- 44 模型的 556 计数只统计 scalar fields（含 FK scalar）。Prisma relation navigation fields 单独进入 machine manifest，必须显式 relationName/fields/references/onDelete/onUpdate 且不计入 556；不得依赖自动 relationName 掩盖多关系歧义。
- 当前 Prisma 6.19.3 不采用后来版本才提供的 partial index schema 预览能力；需要“唯一活动项”的场景使用 current 指针、非空 scopeKey 或显式 slot 表。

参考：[Prisma SQLite connector](https://www.prisma.io/docs/orm/v6/overview/databases/sqlite)、[Prisma database features](https://www.prisma.io/docs/orm/reference/database-features)。

### 18.2 定制 migration SQL

Prisma Migrate 生成草稿后必须人工补充并审查：

- enum、数值区间和跨字段 CHECK。
- confirmed/version/attempt 的不可变 update trigger。
- legacy task 不可执行约束。
- 必要的同作用域复合外键或 trigger。
- `PersistenceState` 单例约束。
- Boolean/Int/digest/storageKey/Json 的精确 SQLite 表达式，不只提交约束名。
- formal projection、sealed TaskSource/LayoutSourceBinding、ready Asset/ExportArtifact 的 I/U/D 保护。

另提交一份不从 schema/migration/SQLite 反向生成的独立 machine manifest，其中 CHECK 含完整 normalized expression，trigger 含 timing/event/columns/WHEN/body，index 含列顺序/方向，FK 含双方列和精确 action。契约版本采用 G1 base + G2～G5 overlay，后续已声明 overlay 不误报为 drift。

迁移 SQL 可以定制，且 migration history 必须提交版本控制；正式环境使用 `migrate deploy`，不能用 `db push` 替代。参考：[Prisma Migrate](https://www.prisma.io/docs/orm/prisma-migrate)、[Customizing migrations](https://www.prisma.io/docs/orm/prisma-migrate/workflows/customizing-migrations)、[migrate deploy](https://www.prisma.io/docs/cli/migrate/deploy)。

### 18.3 migration 序列

建议按以下可复核顺序建立历史，而不是一个不可审阅的超大 init：

```text
0001_persistence_and_migration
0002_project_chapter_script
0003_story_storyboard_preflight
0004_character_asset_candidate
0005_dialogue_settings_secret_metadata
0006_generation_task_worker
0007_layout_export_outbox
0008_sqlite_checks_triggers_indexes
```

在 M3 前，必须从空数据库完整重放全部 migration，并把 `sqlite_master` 中的完整规范化 SQL 与独立 effective manifest 逐项比较。`0008` 使用 Prisma 6.19.3 E0 已证明的“事务外 FK OFF guard → BEGIN IMMEDIATE → rebuild/事务内 FK guard → COMMIT → FK ON”序列；独立 verifier 新连接自行启用 FK 并检查 integrity/FK/checksum/failed-ledger。

## 20. M0 Schema 实施退出标准

本文档的 `accepted` 只代表用户接受 Schema 方案作为开发基线。未来实际 M0 Schema 实施只有同时满足以下条件，才可标记为实现完成并进入迁移阶段：

1. 44 个模型均有唯一 owner、字段、索引、Json codec、删除策略和测试责任。
2. 所有 current/pending 指针的同作用域规则明确。
3. Task runtime/legacy 跨字段 CHECK 可由真实 SQLite 测试证明。
4. 旧文件、旧内存状态和秘密均有唯一迁移去向。
5. G1 与 G2–G6 的边界没有把后续功能提前塞进本阶段。
6. 从空库重放 migration 后 `integrity_check=ok`、`foreign_key_check=0`。
7. 真实 workspace 只读 audit 的 blocker 为 0，或每个 blocker 都有用户签署的迁移决议。
8. G1 base manifest 与当前阶段 overlay 组成的 effective manifest 已独立审查，同名 `CHECK(1)`/`WHEN 0` 空壳不可能只靠名称过关。
