## 1. 背景与问题

剧本页已经进入章节工作流：用户在项目内选择当前章节，右侧编辑 `chapters/{chapterSlug}/script.md`，左侧使用公共对话框和 AI 讨论剧本。

上一版方案把左侧对话定位为“只给建议和可应用草案”，右侧文档必须由用户通过插入、追加或替换动作显式改动。新的产品判断是：剧本阶段本身就是创作和整理阶段，AI 不应只是旁边的建议者，而应在受控工具下成为剧本文档协作者。

剧本阶段需要支持两类真实用户：

| 类型 | 用户状态 | AI 角色 | 目标 |
| --- | --- | --- | --- |
| 已有固定剧本 | 用户已经有完整或半完整剧本文件或文本 | 剧本整理员、格式规范员、章节拆分助手 | 通过对话框附件上传或粘贴后整理成统一格式，写入项目章节，从第 1 章开始展示 |
| 没有灵感 | 用户没有明确故事，只想先看方向 | 灵感共创者、漫画编剧 | 生成灵感种子，用户选中后先生成项目级剧本大纲，确认大纲后只生成当前一章 |

本方案解决的问题：

- 明确剧本阶段左侧对话和右侧编辑器的职责。
- 把“用户提供剧本整理”和“无灵感生成剧本”纳入同一剧本阶段。
- 定义 AI 可读取和编辑剧本文档的工具边界。
- 重新拆分下一步实现阶段，移除“插入/追加/替换按钮是核心闭环”的旧前提。

本次确认的核心方向：

```text
剧本阶段有两个起步来源：用户提供剧本、从灵感生成剧本
右侧章节文档仍是当前剧本事实源
左侧对话可以通过受控工具读取和编辑章节剧本
AI 不直接操作本地物理路径，所有读写必须走 AI漫游后端工具/API
保存草稿、完成本章、版本记录仍由章节契约负责
```

### 2.3 当前真实用户体验

用户现在可以：

1. 在右侧写当前章节剧本。
2. 在左侧询问 AI，AI 会看到已保存的当前章节正文。
3. 看到 assistant 流式回复。
4. 通过附件或粘贴长文本整理已有剧本。
5. 不上传剧本时，让 AI 先给灵感种子，选方向后生成项目级剧本大纲，用户确认大纲后再生成第 1 章草稿。
6. 在某章中要求 AI 改写当前章节，AI 会通过后端受控工具更新右侧编辑器草稿。

用户现在不能：

- 停止正在生成的回复。
- 在服务重启后保留对话历史。
- 查看完整 AI 写入历史并一键回退任意版本。

刷新页面或离开页面导致的流式连接中断不等同于正式“停止生成”功能，但必须做状态收敛：当前实现会 abort 对应 OpenCode 请求，并把不再活跃的旧 `running` assistant 消息标记为失败，避免用户重新进入后看到永久转圈。

## 3. 设计目标

### 3.1 目标

- 剧本阶段同时服务“用户提供剧本整理”和“无灵感生成剧本”。
- AI 可以读取当前章节、项目级设定和用户上传文本。
- AI 可以通过 AI漫游受控工具创建章节、更新章节草稿、整理剧本格式。
- 右侧编辑器始终展示当前章节最新剧本，用户可以继续手动编辑。
- 剧本步骤对话应按 `projectId + stepKey + chapterId` 隔离；导入或灵感生成这种项目前置对话可以按 `projectId + stepKey` 隔离。
- 所有 AI 写入都必须有可追溯记录，至少能知道是哪个对话消息或工具调用造成的修改。
- 保存草稿、完成本章、版本归档继续使用章节 API 和章节文件契约。

### 3.2 非目标

- 不让 OpenCode 直接拿本地物理路径写 `workspace/projects/...`。
- 不把 OpenCode 原始 session tree 作为 AI漫游业务事实源。
- 不在本轮要求复杂多人协作。
- 不要求第一版实现精细 diff 合并和逐行冲突解决。
- 不把没有写入章节、没有保存为项目事实的普通聊天内容自动带入后续步骤。

### 3.3 AuroraPlatformWeb 可参考点与取舍

AuroraPlatformWeb 的灵感文档和对话框设计可作为方法参考，但不能整体照搬。AI漫游的主对象是章节漫画创作，当前应保持章节级事实源、项目级共享事实和受控写入工具。

| 参考点 | 处理 | AI漫游落点 |
| --- | --- | --- |
| workflow 驱动对话语境 | 采用 | 对话框根据 `ProjectWorkflow.currentStepKey` 调整开场文案、placeholder、快捷建议和后端 prompt |
| 左侧对话推动，右侧文档承载事实 | 采用 | 右侧 `script.md`、后续 `structure.json/storyboard.json` 是事实源；聊天不是事实源 |
| 附件作为上下文 | 提前采用 | 剧本阶段复用对话框附件入口上传固定剧本；用户也可以直接在输入框粘贴剧本文本 |
| show/open file 工具 | 有限采用 | 先做剧本阶段专用的读取当前章节、读取章节列表，不做通用文件浏览器 |
| agent 写正式文档 | 有条件采用 | AI 可以通过 AI漫游受控工具写章节草稿；不允许直接写本地物理路径 |
| 动态多标签工作台和复杂工具链 | 不采用 | 当前工作台按章节和 6 步主流程收敛，不迁移 Aurora 的 Docker/sandbox/Phaser 专用闭环 |

## 4. 核心设计

### 4.1 剧本阶段双来源

剧本阶段进入后，左侧对话框应能引导用户选择两种起步方式。

#### 4.1.1 用户提供剧本整理

用户路径：

```text
用户创建或打开项目
  -> 进入剧本阶段
  -> 通过对话框附件上传剧本文件，或在输入框粘贴长文本
  -> AI 读取文本并整理为统一剧本格式
  -> AI 按章节拆分或生成章节列表
  -> 后端写入 chapters/chapter-001/script.md 等章节文件
  -> 右侧从第 1 章开始展示
  -> 用户切换章节继续编辑
```

导入能力重点：

- 接受已有剧本文件或粘贴文本，不强迫用户重新讲故事。
- AI 的第一职责是整理、规范格式、拆章节，而不是重写用户核心内容。
- 如果原文没有明确章节，AI 可以提出拆分方案并直接生成章节草稿。
- 导入完成后，章节列表成为主导航。

#### 4.1.2 无灵感生成剧本

用户路径：

```text
用户创建或打开项目
  -> 进入剧本阶段
  -> 选择“帮我找灵感”
  -> AI 生成多个灵感种子
  -> 用户选择一个方向
  -> AI 扩展为剧本大纲，包含故事梗概、角色、冲突和章节规划
  -> 用户确认、调整或要求重生成剧本大纲
  -> 用户确认大纲后，AI 只生成当前一章的章节剧本草稿
  -> 后端写入当前章节文件
  -> 右侧从第 1 章开始展示
```

灵感能力重点：

- AI 先给用户可判断的方向，而不是直接生成一大段不可控正文。
- 每次生成 3 个灵感种子；用户不喜欢时，可以重新调用灵感技能再生成 3 个。
- 用户确认灵感种子后，AI 先生成可保存、可确认的「剧本大纲」，不直接写章节正文。
- 「剧本大纲」是项目级/篇章级规划，固定承载基础信息、主要角色和情节概要。
- 用户确认剧本大纲后，AI 再生成当前章节的「章节剧本」；第一版只生成当前一章，不按大纲一次性创建或生成多章。
- 生成后的章节剧本仍落到章节，而不是停留在聊天消息里。
- 大纲必须作为稳定项目事实保存，不能只留在聊天消息中，否则后续逐章生成和漫剧转化会丢失依据。
- 大纲内容必须在对话中展示并询问用户是否确认；用户说“不行”或提出修改要求时，应基于要求重新生成大纲，直到用户明确确认为止。

「剧本大纲」固定格式：

```md
# 剧本大纲

## 一、基础信息
剧集名称：
题材风格：
剧集篇幅：
剧集章数：
剧情简介：

## 二、主要角色
角色名（定位）：

## 三、情节概要
第 1 - 2 集：
```

其中 `剧集章数` 用来说明每集或每组集数对应多少漫画章节；`情节概要` 面向后续漫剧按集规划，但不会在当前阶段直接替代 `Chapter`。用户给出的示例只表示格式，不得代入示例人名、题材和剧情。

#### 4.1.3 剧本阶段最终输出格式

无论来源是用户上传/粘贴剧本，还是用户选择某个灵感种子后生成，剧本阶段最终写入右侧编辑器的用户可见产物都统一为「章节剧本」。

「章节剧本」固定包含：

| 模块 | 作用 |
| --- | --- |
| 章节标题 | 表示当前章节名；保存后同步为章节列表和顶部章节选择器显示名 |
| 基础方向 | 说明类型、主题、风格、漫画形式和目标篇幅 |
| 本章方向 | 说明一句话梗概、本章目标、核心冲突、情绪走向和结尾钩子 |
| 剧本亮点 | 提炼开场吸引点、情绪冲击点和剧情钩子 |
| 视觉基调 | 给后续分镜和候选图提供画面氛围、色调方向和视觉记忆点，但不是图片 Prompt |
| 剧本正文 | 保存本章真正的剧情描写、人物动作、对白、旁白和场景结束点 |
| 本章结尾 | 说明结尾事件、悬念和下一章引子 |

最终「章节剧本」不要输出：

- 主体列表。
- 正式场景列表。
- 剧情节拍。
- 分镜剧本。
- 镜头编号。
- 图片 Prompt。
- JSON。

`剧本名称/剧集名称` 是项目级作品名，来自已确认剧本大纲并同步到 `Project.storyTitle`，显示在章节下拉框右侧，不写进章节正文。这些后续阶段产物后置到「剧情结构」「分镜工作台」和「候选图」阶段。剧本正文里可以出现“场景、人物、对白”，但它们只是正文内容，不是正式角色卡、场景卡或剧情节拍。

### 4.2 进入章节后的共同模式

无论剧本来自上传整理还是灵感生成，进入章节后都进入同一工作模式：

```text
左侧：剧本协作对话
中间/右侧：当前章节剧本文档编辑器
章节列表：切换第 1 章、第 2 章...
顶部：workflow 和章节状态
```

共同规则：

- 右侧编辑器显示当前章节最新草稿。
- 用户可以手动编辑右侧文本。
- AI 可以读取当前章节文本。
- AI 可以根据用户要求直接更新当前章节草稿。
- AI 修改后，右侧编辑器应按章节级局部更新显示新正文，不应因为写入结果重新打开整个工作台。
- 用户仍可点击 `保存草稿` 或 `完成本章，进入下一章`。

### 4.3 AI 工具分层

剧本阶段建议暴露的是业务工具，不是通用文件工具。

| 工具 | 类型 | 作用 | 写入范围 |
| --- | --- | --- | --- |
| `read_current_chapter` | 读取 | 读取当前章节标题、状态、正文和最近版本 | 无 |
| `read_chapter_list` | 读取 | 读取项目章节顺序、标题和状态 | 无 |
| `read_project_context` | 读取 | 读取项目级已确认角色、世界观、通用场景和共享素材摘要 | 无 |
| `analyze_script_import` | 分析 | 判断上传/粘贴内容是否像剧本、章节边界是否可信、是否需要用户确认 | 无 |
| `import_script_to_chapters` | 写入 | 将上传或粘贴的完整剧本整理并写入多个章节 | `chapters/*/script.md` |
| `update_chapter_draft` | 写入 | 更新当前章节草稿全文 | 当前 `chapterId` 的 `script.md` |
| `generate_inspiration_seeds` | 生成 | 生成灵感种子供用户选择 | 无 |
| `generate_script_outline_from_seed` | 生成/记录 | 根据用户选中的灵感种子生成可确认的剧本大纲 | 项目级剧本大纲 |
| `generate_script_from_outline` | 写入 | 根据用户确认的剧本大纲生成当前一章的章节剧本 | 当前 `chapterId` 的 `script.md` |
| `record_script_revision` | 记录 | 记录 AI 写入前后的摘要、来源消息和可回退点 | 章节版本或修订日志 |

权限规则：

- AI 不直接写本地物理路径。
- AI 不执行 shell 命令。
- AI 不直接编辑数据库。
- AI 写章节必须通过后端工具/API，由后端校验 `projectId`、`chapterId`、workflow step 和目标路径。
- AI 写入时必须绑定来源：`threadId`、`messageId`、`toolCallId` 或等价追溯字段。

### 4.4 文档编辑权限边界

新的原则不是“AI 永远不能改文档”，而是：

```text
AI 可以改剧本阶段的章节草稿；
AI 只能通过 AI漫游定义的章节编辑工具改；
AI 不能绕过章节 API 直接写 workspace。
```

建议将剧本写入分为两种：

| 写入类型 | 触发 | 行为 | 是否推进章节 |
| --- | --- | --- | --- |
| 草稿更新 | AI 整理、改写、续写、生成 | 更新当前章节 `script.md` 或生成新章节草稿 | 否 |
| 完成本章 | 用户点击 `完成本章，进入下一章` | 归档版本，标记章节状态，创建或进入下一章 | 是 |

第一版不需要再围绕 `insert_at_cursor`、`append_to_chapter`、`replace_selection` 设计主要闭环。右侧编辑器仍可保留手动编辑能力，但 AI 的主要编辑动作是“更新当前章节草稿”或“生成/整理章节草稿”。

### 4.5 Workflow 驱动对话语境

`ProjectWorkflow` 是对话框判断当前创作语境的主输入。对话框按 workflow 步骤生成提示，但 workflow 本身不等于文件权限。

| workflow step | 对话框重点 | 典型工具 |
| --- | --- | --- |
| `project_story` | 剧本导入、灵感种子、剧本大纲生成、章节剧本生成、章节剧本编辑 | `analyze_script_import`, `import_script_to_chapters`, `generate_inspiration_seeds`, `generate_script_outline_from_seed`, `generate_script_from_outline`, `update_chapter_draft` |
| `story_structure` | 当前章节摘要、角色、场景、剧情节拍 | 后续结构化任务 |
| `storyboard` | 当前章节分镜、画面节奏、镜头表达 | 后续分镜任务 |
| `image_candidates` | 分镜图像提示词、候选比较、重生成理由 | 后续图片任务 |
| `layout_export` | 页面排版、阅读节奏、导出检查 | 后续排版任务 |
| `asset_package` | 素材归档、manifest、复用素材说明 | 后续素材工具 |

规则：

- 前端对话框读取 `WorkbenchSnapshot.workflow` 生成 UI 文案和快捷建议。
- 后端 prompt 注入当前 `workflow.currentStepKey`、当前 step summary、completion criteria 和 evidence。
- 只有剧本阶段先开放受控文档编辑工具；后续步骤是否开放写工具，需要按结构化剧情、分镜、候选图、排版各自契约单独设计。

### 4.6 对话作用域

推荐规则：

| 场景 | 对话作用域 |
| --- | --- |
| 剧本导入前、灵感种子选择前 | `projectId + stepKey` |
| 当前章节剧本编辑 | `projectId + stepKey + chapterId` |
| 剧情结构 | `projectId + stepKey + chapterId` |
| 分镜 | `projectId + stepKey + chapterId` |
| 候选图 | `projectId + stepKey + chapterId` |
| 排版导出 | `projectId + stepKey + chapterId` |
| 素材包 | `projectId + stepKey`，可选 `chapterIds` |

当前代码已支持 `projectId + stepKey + chapterId`。前端进入剧本页时先读取 workbench 获取当前章节，再加载当前章节线程；导入和灵感生成这种项目前置对话可以保留项目级剧本线程，但章节内普通聊天和改写默认落在当前章节线程。

### 4.7 剧本阶段 Agent 与 Skill

剧本阶段需要独立 agent/skill，不应只靠普通聊天 prompt。

源码位置：

```text
apps/server/opencodeAI/
  agents/airoaming__script-collaboration-agent.md
  skills/script-import-normalize/SKILL.md
  tools/
```

推荐 agent：

```text
airoaming__script-collaboration-agent
```

角色定义：

- 你是漫画剧本协作者。
- 用户可能已有固定剧本，也可能完全没有灵感。
- 当用户已有剧本时，优先尊重原文，做整理、拆章、格式规范和必要补全。
- 当用户没有灵感时，先生成灵感种子，等用户选择后再扩展为剧本。
- 进入章节后，你可以通过受控工具读取和编辑当前章节草稿。
- 不要声称自己直接操作本地文件；只说明已通过系统工具更新章节草稿。

推荐 skill：

| skill | 使用时机 | 职责 |
| --- | --- | --- |
| `script-import-normalize` | 用户上传或粘贴已有剧本 | 先识别内容类型和章节边界可信度；通过后再清洗格式、拆章节、保留原意、写入章节草稿 |
| `script-inspiration-seeding` | 用户没有故事方向 | 生成 3 个灵感种子，等待用户选择 |
| `script-outline-drafting` | 用户选择灵感种子或要求调整大纲 | 生成固定格式项目级「剧本大纲」，保存到项目下，等待用户确认 |
| `script-chapter-drafting` | 用户确认项目级剧本大纲后要求生成当前章 | 生成固定格式「章节剧本」，写入当前章节 |
| `script-chapter-editing` | 用户要求改写、补台词、调节奏 | 读取当前章节并返回完整固定格式「章节剧本」 |
| `script-consistency-check` | 用户要求检查逻辑 | 输出问题清单，可选择后续改写 |

`script-import-normalize` 第一版必须遵守：

- 不允许只因为文本里有 `1`、`2`、`3` 或 Markdown 标题就直接拆章写入。
- 先判断内容是剧本、故事正文、大纲、世界观设定、灵感笔记还是无效文本。
- 只有内容像可导入剧本且章节边界可信时，才允许调用 `import_script_to_chapters`。
- 内容不适合导入时，只在对话框说明原因和修正建议，不写 `chapters/*/script.md`。
- 如果已有章节非空且会被覆盖，必须先让用户确认影响范围。

### 4.8 剧本阶段统一边界契约

剧本阶段的边界不做成一个普通可选 skill，而是所有剧本对话默认生效的底层契约。普通聊天、导入、灵感、起草和改写都必须先遵守本契约；各具体 skill 只补充任务细则，不能放宽写入、确认和事实源边界。

#### 4.8.1 事实源

| 事实源 | 规则 |
| --- | --- |
| 当前章节正文 | 以工作台注入的 `currentChapter.sourceText` 或本轮 `context.sourceText` 为准 |
| 附件、粘贴文本、普通聊天 | 只是临时上下文，不是项目事实 |
| 章节草稿、保存、完成本章、用户确认 | 可以成为后续步骤可依赖事实 |
| 聊天回复 | 不是正式产物，正式产物必须落到章节草稿、章节版本、项目事实或后续受控任务 |

#### 4.8.2 行为分级

| 级别 | 触发情况 | 允许动作 |
| --- | --- | --- |
| 只能回答，不能写入 | 用户询问建议、评价、分析、解释、讨论方向；用户要求“看看怎么样”“有什么问题”“给我建议”；用户提供世界观、角色设定、灵感笔记、提纲或零散资料但未要求写成章节；问题属于剧情结构、分镜、图片、排版或素材包阶段且当前没有对应受控工具 | 给建议、分析、问题清单或候选方案，不更新章节 |
| 可以生成候选，但不能直接写章节 | 用户没有灵感、想看几个方向；用户选择灵感种子后需要先生成项目级剧本大纲；用户提供多个方向要求帮忙挑选；内容可用但章节边界不清晰；写入会覆盖非空章节、替换整本剧本或造成后续产物失效 | 生成候选方向、剧本大纲、拆章方案或确认问题，等待用户明确选择或确认 |
| 可以通过受控工具写入章节 | 用户明确要求导入、整理成章节、写入章节；用户已确认项目级剧本大纲并要求生成当前章；用户在当前章节中明确要求改写、润色、扩写、压缩、调整节奏、补对白或加强冲突；后端有对应受控工具且能校验 `projectId`、`chapterId`、当前步骤和写入范围 | 通过 AI漫游后端受控工具/API 写入章节草稿 |

#### 4.8.3 写入前确认规则

以下情况必须先说明影响范围并等待用户确认：

1. 覆盖已有非空章节。
2. 替换整本剧本或清空旧章节集合。
3. 根据不清晰章节边界拆章。
4. 把小说正文、提纲、设定资料转换成章节剧本。
5. 修改可能导致后续剧情结构、分镜、候选图或排版需要重新生成。

确认语义必须明确，例如“确认导入”“确认覆盖”“按这个方案写入”。

#### 4.8.4 禁止事项与回复口径

禁止：

- 直接操作本地物理路径、数据库、shell 或 workspace 文件。
- 绕过 AI漫游受控工具/API 写入章节。
- 把未确认聊天内容自动当作项目事实。
- 在剧本阶段擅自生成分镜、图片、排版或素材包产物。
- 把普通建议包装成已经完成的写入。
- 在用户已有固定剧本时擅自换题材、换主角或推翻核心设定。
- 只因为文本里有 `1`、`2`、`# 1` 这类低可信编号就拆成章节。

回复口径：

- 如果只是建议，明确说“我建议”，不要说“我已更新”。
- 如果调用了受控工具，说“已通过系统工具更新章节草稿”，并说明影响章节和摘要。
- 如果不能写入，说明原因，并给用户下一步选择。
- 如果需要确认，列出将影响哪些章节、是否覆盖旧内容、继续需要用户回复什么。

### 4.9 UI 布局建议

剧本页左侧对话框不再以“生成建议，然后点插入”为核心，而是以“选择入口 + 驱动文档变化”为核心。

建议空剧本状态：

```text
左侧对话框
  附件按钮：上传剧本文件
  输入框：粘贴剧本文本，或输入“帮我找灵感”

右侧编辑器
  当前章节为空或等待 AI 生成
```

建议已有章节状态：

```text
左侧对话框
  当前章节协作对话
  快捷动作：整理格式 / 续写本章 / 润色对白 / 检查逻辑 / 重写本场

章节列表
  第 1 章 / 第 2 章 / ...

右侧编辑器
  当前章节正文
  保存草稿 / 完成本章，进入下一章
```

当 AI 更新章节后，UI 至少应提示：

```text
AI 已更新当前章节草稿
来源：某条对话 / 某次导入 / 某次灵感生成
可操作：查看最新正文、继续编辑、保存草稿、完成本章
```

## 5. 数据与协议影响

### 5.1 对话发送上下文

当前后端 prompt 只读取已保存的 `WorkbenchSnapshot.currentChapter.sourceText`。后续仍需要请求携带编辑器当前草稿，避免 AI 读到旧文本。

建议 `SendDialogueMessageRequest` 支持：

```json
{
  "content": "帮我把这一场写得更紧张一点",
  "stepKey": "project_story",
  "chapterId": "chapter_001",
  "intent": "script_chapter_edit",
  "context": {
    "sourceText": "右侧编辑器当前未保存正文",
    "selectionText": "用户当前选中的片段"
  }
}
```

规则：

- `context.sourceText` 可作为 AI 编辑当前章节的输入。
- 如果 AI 调用 `update_chapter_draft`，后端应以工具结果作为新的章节草稿。
- 如果没有传 `context.sourceText`，后端继续使用已保存章节脚本。

### 5.2 AI 写入记录

建议新增或预留 AI 写入记录概念：

```json
{
  "id": "script_revision_001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "source": "ai_tool",
  "threadId": "thread_001",
  "messageId": "msg_assistant_001",
  "toolCallId": "tool_call_001",
  "operation": "update_chapter_draft",
  "summary": "润色第 1 场对白并补充冲突",
  "createdAt": "2026-05-27T00:00:00.000Z"
}
```

第一版可以先落在 workspace 修订日志中，后续接 SQLite 后再进入正式表。

### 5.3 章节文件写入

AI 写入仍复用章节目录：

```text
workspace/projects/{projectId}/chapters/chapter-001/script.md
workspace/projects/{projectId}/chapters/chapter-001/chapter.json
workspace/projects/{projectId}/chapters/chapter-001/script.versions/
```

导入多章节时，后端负责创建连续章节目录；灵感链路确认大纲后第一版只生成当前一章，不自动创建连续章节。

当导入、生成或维护动作会替换整本项目剧本时，后端必须先删除旧 `chapters/` 目录，再写入新的章节集合或空白 `chapter-001`。不能只覆盖部分章节文件，否则旧章节目录会在服务重启后的 workspace 扫描中重新进入项目索引。

编辑器里的用户可见“清空”动作只清空当前打开章节正文，不替换整本项目剧本，也不删除其他章节。清空当前章节后，该章节应退回草稿状态，并把从正文派生出的章节标题重置为默认 `第 N 章`；项目级剧本名不变，项目级重置只作为整本替换或错误导入维护能力保留。

## 7. 风险与取舍

| 风险 | 处理 |
| --- | --- |
| AI 改坏用户固定剧本 | 导入 skill 默认尊重原文；AI 写入记录来源和摘要；后续补回退 |
| AI 直接越权写 workspace | 不暴露本地物理路径；只开放 AI漫游后端工具/API |
| 导入长剧本拆章不准 | 允许用户继续编辑章节；后续提供章节拆分调整能力 |
| 灵感生成太发散 | 先生成种子让用户选，再生成可确认大纲，确认后只生成当前一章 |
| 章节对话混淆 | 章节内编辑线程按 `chapterId` 隔离 |
| 未保存文本和已保存文本不一致 | 请求携带编辑器当前草稿作为临时上下文 |
| 复杂 diff 成本高 | 第一版使用全文更新当前章节草稿，后续再做精细 diff |
| 对话历史丢失 | M5 持久化 |

## 8. 推荐下一步

推荐先做 M1 文档与契约收口，然后进入 M2 用户提供剧本整理。

建议实现顺序：

1. 先补剧本阶段工具/skill 文档和共享 DTO。
2. 再接入对话框附件上传，并支持输入框粘贴长文本。
3. `analyze_script_import` 导入前分析已接入，非剧本或格式不可信内容不会写入章节。
4. 分析通过后调用 `import_script_to_chapters` 后端写入已接入。
5. `generate_inspiration_seeds` + `generate_script_outline_from_seed` + `generate_script_from_outline` 已接入，灵感链路先保存项目级大纲，确认后只生成当前一章。
6. 章节内 `update_chapter_draft` 和最近一次 AI 写入追溯已接入；后续补完整版本回退和对话持久化。

这个顺序能先满足“用户有固定剧本”的刚性场景，再补“用户没有灵感”的创作场景。
