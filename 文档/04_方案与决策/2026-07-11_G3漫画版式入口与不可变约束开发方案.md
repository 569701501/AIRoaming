# G3 漫画版式入口与不可变约束开发方案

## 1. 结论

G3 不新增“创建项目”入口，也不新建页面、向导或中间确认页。项目库已经存在创建按钮、`CreateProjectModal.vue`、创建请求和成功后进入第 1 步“剧本”的完整路径；本阶段只扩展这条现有路径：

```text
现有项目库
  -> 现有“创建项目”按钮
    -> 现有 CreateProjectModal
      -> 项目名称（已有）
      -> 漫画版式（G3 新增字段，默认空、必选）
        -> 现有 POST /api/projects
          -> 同一事务创建 Project + 默认 Chapter
            -> 现有项目工作台 / 第 1 步剧本
```

用户可见增量只有一个字段和少量只读标签；真正需要严密建设的是后面的契约：

1. 项目级 `ComicFormat` 只有 `vertical_scroll/paged_comic`。
2. 新建请求必须显式传入，不存在默认值。
3. 创建后，前端无编辑控件、更新 DTO 无字段、服务拒绝旧客户端、SQLite trigger 拒绝底层误写。
4. `page_horizontal/four_panel/缺失/非法` 只由 G1 maintenance importer 处理，正式运行时不提供兼容别名或静默回退。
5. `paged_comic` 表示固定分页，不表示横屏；页面横竖、尺寸、跨页和四格由 G5 的 PageProfile/LayoutPreset 表达。

本方案于 2026-07-11 获用户确认并进入 `accepted`，细化已采纳的 ADR-0009。确认方案不等于授权开发；G0–G3 及后续文档全部完成且用户明确授权后，实际实现仍从 G0 开始。

## 2. 用户澄清与范围修正

用户于 2026-07-11 明确指出：当前项目已经有创建项目入口，只是弹窗里没有漫画版式。

因此后续文档统一使用以下准确措辞：

- “扩展现有创建项目弹窗”。
- “在现有项目名称下方补漫画版式字段”。
- “沿用现有创建成功跳转”。

不再使用可能让人误解为重建流程的表述：

- 新增创建入口。
- 新建 onboarding。
- 新建项目类型选择页。
- 新建两步向导。

## 3. 当前代码事实

### 3.1 已经存在且必须复用

| 能力 | 当前实现 | G3 动作 |
| --- | --- | --- |
| 项目库创建按钮 | `ProjectCommandPanel -> ProjectLibraryView` | 不改入口层级 |
| 创建弹窗 | `apps/web/src/components/projects/CreateProjectModal.vue` | 在同一表单增加字段 |
| 创建调用 | `workbench.createProject -> api.createProject` | payload 增加 canonical `comicFormat` |
| 创建 API | `POST /api/projects` | 增加严格运行时解析 |
| 创建成功导航 | `router.push(projectRoute(project.id))` | 保持不变 |
| 默认工作台步骤 | `project_story` | 保持不变 |

### 3.2 当前必须修复的冲突

| 层 | 当前事实 | 风险 |
| --- | --- | --- |
| Shared | `COMIC_FORMATS` 仍是 `vertical_scroll/page_horizontal/four_panel` | 阅读容器与布局模板混为一层 |
| Create DTO | `comicFormat?` 可选 | 编译期允许省略 |
| Update DTO | 仍含 `comicFormat?` | 普通项目 PATCH 暴露写入口 |
| Server | `normalizeComicFormat` 对缺失或非法值回退 `vertical_scroll` | 用户没有选择也会被永久锁定 |
| Controller | `@Body()` 只标 TypeScript interface | 运行时额外字段不会自动剔除 |
| Repository | 旧 metadata/preflight 读取会静默回退 | 迁移歧义被掩盖 |
| Web | 创建弹窗只有项目名称 | 无法作出明确选择 |
| Dead UI | 未被引用的 `ProjectStoryPanel.vue` 仍有三值可编辑下拉框 | 未来误接回时恢复错误写入口 |
| Display | 项目卡、TopBar 未展示版式 | 用户创建后难以核对选择 |
| Candidate | 项目版式直接决定默认请求尺寸 | `paged_comic` 容易被误解为横幅 |
| Layout | 旧 `LayoutPage.format` 仍是 `vertical_comic/page_horizontal/four_panel` | 不能机械等同于 Project 枚举 |

### 3.3 G1/G2 已冻结的前置契约

- G1 目标数据库只保存 `vertical_scroll/paged_comic`，`Project.comicFormat` 非空且无默认值。
- G1 `MigrationIssue` 已有 `resolutionStatus/resolutionJson/resolvedAt`，可承载版式人工决议，不新增第 45 个模型。
- G2 Preflight SourceSnapshot 包含 `comicFormat`；项目创建后不可变，避免原地切换导致既有任务和产物来源失真。
- G2 的 dirty/pending、freshness 和历史保留不因 G3 改变；G3 只是提供稳定的项目级来源事实。

## 4. 目标与非目标

### 4.1 目标

1. 用户在现有弹窗内明确选择竖向条漫或分页漫画。
2. 未选择、空值、旧别名或非法值都不能创建任何 Project/Chapter 行。
3. 成功创建后，所有正式读取只返回 canonical 值。
4. 创建后任何普通更新都不能改变版式，即使传入与原值相同也要暴露旧客户端问题。
5. 旧数据迁移不猜测、不污染活动 workspace、可审计且幂等。
6. 项目卡和工作台头部能核对版式；现有剧本文档保持只编辑正文，不恢复元信息表单。
7. 下游旧枚举通过显式适配器隔离，不能继续叫作领域真值。

### 4.2 非目标

- 不实现“复制为另一版式”；只保留未来能力边界。
- 不在创建时选择四格、三格、页面尺寸、横竖方向、平台或导出格式。
- 不实现 G5 的 LayoutDocument、PageProfile、LayoutPreset 或 ExportProfile。
- 不实现镜头/画格级 `targetAspectRatio`；仅把现有默认尺寸标成版本化临时策略。
- 不让 G3 修复当前一镜一页、复制源图等已知排版骨架问题。
- 不在 G3 新建通用 Project Create 幂等协议；只防止弹窗 loading 期间重复提交，响应丢失等通用创建幂等问题另行统一处理。
- 不读取或修改真实 workspace、真实数据库或密钥。

## 5. 领域契约

### 5.1 canonical enum

```ts
export const COMIC_FORMATS = ["vertical_scroll", "paged_comic"] as const;
export type ComicFormat = (typeof COMIC_FORMATS)[number];
```

用户可见定义：

| 值 | 标签 | 说明 |
| --- | --- | --- |
| `vertical_scroll` | 竖向条漫 | 用于手机连续滚动阅读；后续排版使用条漫画布和切片规则 |
| `paged_comic` | 分页漫画 | 用于固定页面阅读；页面横竖、尺寸和跨页在排版阶段设置 |

禁止出现：

- 默认或推荐值。
- `page_horizontal` 作为运行时别名。
- `four_panel` 作为项目版式。
- `custom` 绕过容器契约。

### 5.2 单一展示目录

Shared 提供唯一的 `COMIC_FORMAT_DEFINITIONS` 和 `isComicFormat`，前端选项、项目卡、TopBar、preflight 用户标签从同一目录读取，不在 Vue 组件里复制 `Record<ComicFormat, string>`。

Prompt 使用的英文/模型提示是另一种消费语义，由 Server 的 `getComicFormatPromptHint` 生成；它不能反向成为 UI 标签或输入 parser。

### 5.3 严格解析与迁移映射分离

必须存在两个不同命名、不同调用面的函数：

```text
parseRequiredComicFormat(raw)
  仅用于新建/正式运行时
  只接受 vertical_scroll/paged_comic
  不默认、不映射旧别名

mapLegacyComicFormat(raw)
  仅用于 G1 maintenance importer
  可识别旧值并返回 mapped/decision_required
  不允许被 Controller/Service 调用
```

禁止继续保留含糊的 `normalizeComicFormat`。如果一个函数既能处理请求又能处理旧文件，它最终一定会把迁移容错带回正式业务。

## 6. 现有弹窗的最小增量

### 6.1 表单结构

```text
创建项目

项目名称
[ 例如：迷雾之城                         ]

漫画版式
[ 请选择漫画版式                     ▼ ]
  选择后显示对应的一句用途说明
  创建后不可直接修改；选错需新建项目

取消                               创建项目
```

实现约束：

- 字段位于现有项目名称下方。
- `form.comicFormat` 类型是 `"" | ComicFormat`。
- 每次弹窗从关闭变为打开时重置为 `""`，不记住上次选择。
- 第一项是 `disabled value=""` 的“请选择漫画版式”。
- 只显示两个 canonical 选项，不带“推荐”。
- `canSubmit = name.trim().length > 0 && isComicFormat(form.comicFormat)`。
- loading 时名称、版式、取消和关闭行为按现有弹窗规则锁定。
- 提交失败不清空用户已经输入的名称和版式。
- 关闭再打开必须恢复默认空，避免无意识复用上一次项目身份。

### 6.2 提示文案

固定提示：

```text
创建后不可直接修改；选错时需要新建项目。
```

选择后说明：

```text
竖向条漫：用于手机连续滚动阅读；后续排版将使用条漫画布。
分页漫画：用于固定页面阅读；页面方向和尺寸在排版阶段设置。
```

文案不得把尚未实现的长图、PDF 或复制转换写成当前可用功能。

### 6.3 无障碍与错误

- `<label>` 可通过可见文字或 `for/id` 绑定 select。
- select 设置 `required`、`aria-describedby`；错误时设置 `aria-invalid=true`。
- 字段错误使用 `role=alert`，不能只在弹窗背后的项目库显示原始错误码。
- 已知错误映射为中文；未知错误保留“创建失败，请重试”和可诊断日志，不泄露数据库细节。
- 键盘 Tab 顺序保持“项目名称 -> 漫画版式 -> 取消 -> 创建”。

### 6.4 创建失败状态归属

当前 store 只有通用 `error`。G3 推荐增加创建动作专用的 `createProjectErrorCode`，打开弹窗时清空，失败时保留，成功或关闭后清空。它只负责当前弹窗，不能把项目列表加载错误误显示为版式字段错误。

## 7. 创建后的只读展示

| 位置 | G3 目标 | 说明 |
| --- | --- | --- |
| 项目卡 | 名称/摘要附近显示“竖向条漫”或“分页漫画”小标签 | 便于进入前核对 |
| 工作台 TopBar | 返回按钮旁显示项目名和锁定版式 | `TopBar.vue` 已接收但未使用 `projectName` |
| 第 1 步剧本 | 不恢复项目元信息表单 | 顶部标签已经在该步骤可见；右侧继续只编辑章节正文 |
| 出图准备 | 读取共享标签目录 | 删除组件内旧三值 label map |
| 候选图 | 展示“默认候选画幅”，不把分页漫画叫横版 | 尺寸是临时策略，不是容器定义 |

`ProjectStoryPanel.vue` 当前未被任何页面引用，且仍包含旧版可编辑下拉框。G3 实现时建议删除该死组件，而不是把它重新接入工作台；项目名称等未来元信息编辑应使用独立、明确的设置入口，并继续排除 `comicFormat`。

## 8. HTTP 与服务契约

### 8.1 创建请求

```ts
export interface CreateProjectRequest {
  name: string;
  type: ProjectType;
  comicFormat: ComicFormat;
  storyTitle?: string;
  genreTags?: string[];
  artStyle?: ArtStyle;
  description?: string;
  sourceText?: string;
}
```

`type` 继续沿用当前固定 `comic` 的前端输入；D6 后置，本阶段不改 ProjectType。

服务端不能信任 TypeScript interface。Controller/command parser 必须对 `unknown` body 做显式检查，并只把允许字段构造成内部 command。

### 8.2 创建校验顺序

```text
body 必须是 object
  -> name 必须是非空字符串
    -> comicFormat 必须存在且非空
      -> comicFormat 必须是 canonical enum
        -> 规范化其余允许字段
          -> 一个事务插入 Project + 默认 Chapter/current 指针
```

任何一步失败：

- 不插入 Project。
- 不插入默认 Chapter。
- 不创建 Asset 目录或 metadata。
- 不产生 Outbox 副作用。
- 不消耗一个可见项目 ID。

### 8.3 普通更新

目标 DTO：

```ts
export interface UpdateProjectDraftRequest {
  name?: string;
  storyTitle?: string;
  genreTags?: string[];
  artStyle?: ArtStyle;
  description?: string;
  sourceText?: string;
}
```

运行时规则比 DTO 更严格：只要原始 JSON body 自有属性中出现 `comicFormat`，无论值与当前项目相同、不同、空或非法，都返回 `409 COMIC_FORMAT_IMMUTABLE`。

选择“同值也拒绝”的原因：

1. 让旧客户端尽快暴露，而不是悄悄保持过期协议。
2. 防止未来开发者误以为该字段仍属于普通 PATCH。
3. 保持服务层 allowlist 清晰，不需要比较当前值后再决定是否写。

拒绝时 `updatedAt/rowVersion` 不变化，也不触发任何 G2 freshness 计算。

### 8.4 错误码

| HTTP | code/message | 条件 | 用户文案 |
| --- | --- | --- | --- |
| 400 | `PROJECT_NAME_REQUIRED` | 名称空 | 请输入项目名称 |
| 400 | `COMIC_FORMAT_REQUIRED` | 字段缺失、null、空或纯空格 | 请选择漫画版式 |
| 400 | `COMIC_FORMAT_INVALID` | 非字符串、旧别名或非法值 | 漫画版式无效，请重新选择 |
| 409 | `COMIC_FORMAT_IMMUTABLE` | 普通更新 body 出现字段或底层 trigger 拒绝 | 漫画版式创建后不可直接修改 |
| 500/maintenance | `COMIC_FORMAT_DATA_CORRUPT` | 读取到违反 DB 契约的数据 | 项目数据需要修复，禁止静默默认 |

当前 Nest 默认错误响应以 `message` 承载稳定 code；G3 不借机重做全站错误 envelope。前端只对上述稳定 code 做本地化。

## 9. SQLite 硬约束

### 9.1 Project 字段

```text
comic_format TEXT NOT NULL
CHECK (comic_format IN ('vertical_scroll', 'paged_comic'))
DEFAULT: 无
```

G1 已拥有该 canonical 字段和 CHECK；G3 增加并验证不可变 trigger。若实际实现时 G1 尚未合并，仍应保持独立 migration 历史，不能把 G3 责任悄悄揉进一个不可审阅的 init。

### 9.2 不可变 trigger

目标 SQL 语义：

```sql
CREATE TRIGGER project_comic_format_immutable
BEFORE UPDATE OF comic_format ON projects
FOR EACH ROW
WHEN NEW.comic_format IS NOT OLD.comic_format
BEGIN
  SELECT RAISE(ABORT, 'COMIC_FORMAT_IMMUTABLE');
END;
```

约束含义：

- 直接 SQL、Prisma、维护脚本或未来 repository 都不能原地改变值。
- 同值底层 no-op 可以通过；普通 HTTP 服务仍拒绝 body 出现该字段。
- restore/import 通过 INSERT 写入已经决议的 canonical 值，不依赖 UPDATE 绕过 trigger。
- 若未来实现“复制为另一版式”，它创建新 Project ID，不需要关闭 trigger。

### 9.3 数据库错误映射

Repository 只能识别明确的 trigger 消息并映射为 `COMIC_FORMAT_IMMUTABLE`。其他 Prisma/SQLite 错误继续走通用内部错误，不把 SQL、文件路径或数据库堆栈返回前端。

## 10. 旧数据迁移

### 10.1 映射矩阵

| 旧值 | importer 结果 | 是否需要用户决议 | Project 新值 | 附加证据 |
| --- | --- | --- | --- | --- |
| `vertical_scroll` | `canonical` | 否 | `vertical_scroll` | 原值/摘要 |
| `paged_comic` | `canonical` | 否 | `paged_comic` | 支持重复演练 |
| `page_horizontal` | `auto_mapped` | 否 | `paged_comic` | `mappedFrom=page_horizontal` |
| `four_panel` | `decision_required` | 是 | 用户选两者之一 | `layoutPresetIntent=four_panel` |
| 缺失/null/空 | `decision_required` | 是 | 用户选两者之一 | issue code + 原始证据 |
| 其他非法值 | `decision_required` | 是 | 用户选两者之一 | 原始值的安全表示/摘要 |

`page_horizontal` 可以自动映射，因为“分页”是其上位语义；但自动映射绝不表示未来页面固定为横向。

### 10.2 决议载体

不新增业务表。G1 的 `MigrationIssue` 使用：

```text
severity=blocker
code=COMIC_FORMAT_CONFIRMATION_REQUIRED
resolutionStatus=open/resolved
resolutionJson={ chosenComicFormat, layoutPresetIntent, decisionSchemaVersion }
```

迁移流程必须在插入 Project 前完成决议。已完成的 audit/blocked run 及其 issue 不原地改写；用户决议形成独立、可摘要的 decision artifact，下一次 shadow/final run 在启动时把 `decisionsDigest` 固定下来，并在该新 run 中记录 resolved issue：

```text
只读 audit run 生成 open MigrationIssue
  -> 用户在 maintenance 决议文件/工具中选择
    -> 新 shadow/final run 校验 sourceDigest + decisionsDigest
      -> 新 run 记录 resolved MigrationIssue
        -> final import 直接 INSERT canonical Project
```

禁止先插入一个默认值，再通过特权 UPDATE 修改；这既掩盖歧义，也会绕开不可变设计。

### 10.3 四格意图

`four_panel` 的项目容器由用户选择；其“四格”意图保存在不可变迁移决议证据中：

```json
{
  "decisionSchemaVersion": 1,
  "chosenComicFormat": "paged_comic",
  "layoutPresetIntent": "four_panel"
}
```

G3 不创建 LayoutPreset。G5 建立首个正式 LayoutDocument 时可以一次性消费该迁移意图；消费前后都不能把 Project.comicFormat 改回 `four_panel`。

### 10.4 嵌套历史与任务证据

- 旧 Preflight 文档中的 `page_horizontal/four_panel` 由 migration codec 单独解析，保留 source alias；来源证据不足时按 G2 规则标为 stale/unresolved，用户重新确认后才成为 current。
- 旧 LayoutPage 的 `format=page_horizontal/four_panel` 是历史布局文档值，可以原样保留；它不重新进入 Project ComicFormat。
- 旧 `legacy_imported/legacy_stub` 任务 payload 和摘要不机械改写。新 runtime 任务只能写 canonical 值。
- 旧 Asset 字节不受版式枚举迁移影响。

### 10.5 幂等与阻塞

- 同一 source manifest + decisionsDigest 重跑，Project 值和 issue 结果必须一致。
- 更改决议必须创建新的 MigrationRun；不能覆盖已完成 run 的 resolution/report。
- 任一 blocker 未决议，final import 和 DB-only activate 失败。
- 迁移只读 source snapshot；不得把 canonical 值反写活动 workspace 的 `project.json`。

## 11. 下游兼容边界

### 11.1 G2 SourceSnapshot

新 Preflight/任务只写 canonical `comicFormat`。它是 Project 身份事实且不可变，因此不会通过普通编辑产生新的 sourceDigest。若发现不同值，视为数据损坏或另一个复制项目，而不是 freshness 更新。

### 11.2 Prompt 与用户标签

- 用户界面：`竖向条漫/分页漫画`。
- 模型提示：由 Server 明确映射为连续滚动或分页阅读语义。
- 禁止把 raw enum 直接当中文用户文案。
- 禁止给 `paged_comic` 输出“横版页漫”标签。

### 11.3 候选图默认尺寸

当前 `getCandidateRequestedSize(comicFormat)` 把项目版式直接等同为单张候选图比例。G3 不扩大范围去实现镜头级比例，但必须改名并版本化为临时兼容策略，例如：

```text
legacy_generation_default_v1
vertical_scroll -> 1024 x 1536
paged_comic     -> 1536 x 1024（只为保持 page_horizontal 旧行为）
```

强制说明：

- 这只是没有 shot/frame override 时的暂时默认，不是“分页漫画只能横版”。
- UI 显示“默认候选画幅”，不显示“分页漫画=横版”。
- 任务 input 保存 policyVersion、width、height，保证旧任务可复现。
- G5 或独立镜头比例切片引入 `targetAspectRatio/frameSpec` 后，优先使用镜头值并升级 policyVersion。

### 11.4 旧 LayoutPage 适配

G3 不能把 Project enum 直接赋给旧 `LayoutPage.format`。应建立名字明确的 `toLegacyLayoutPageFormat`：

```text
vertical_scroll -> vertical_comic
paged_comic     -> page_horizontal
```

该映射只让当前错误骨架在 G5 前保持可编译、可读取，不是最终产品契约：

- 不出现在创建选项和项目标签中。
- 不作为“分页漫画只做横版”的验收断言。
- 旧 layout 标记 `documentKind=legacy_chapter_layout_v1`。
- G5 用 PageProfile/LayoutDocument 替换并删除该 adapter；页面方向届时独立可选。

### 11.5 四格

- `four_panel` 可以暂时保留在 legacy `LayoutPage.format` union 和迁移 codec 中。
- 它必须从 Project `ComicFormat`、创建 DTO、preflight runtime 和候选 runtime 分支中消失。
- G5 才定义正式 `LayoutPreset.four_panel`。

## 13. 实施切片

### G3-A：canonical 契约与 red 测试

1. 将 G0 中 G3 用例转为 red 测试。
2. 建共享定义目录、strict predicate 和 migration-only mapper 测试。
3. 一次性更新所有旧三值 exhaustive 分支，避免主分支长期无法 typecheck。
4. 添加临时候选尺寸和 legacy layout adapter，并明确 deprecated 删除点。

退出标准：shared/server/web typecheck 通过；不存在运行时 `normalizeComicFormat`。

### G3-B：数据库与服务硬锁

1. 增加/验证 NOT NULL、无 default、canonical CHECK。
2. 增加不可变 trigger 和 sqlite_master 合同测试。
3. 创建 parser/allowlist；Create 必填，PATCH body 出现字段即 409。
4. Project + 默认 Chapter 仍同事务创建。

退出标准：直接 SQL、Prisma、HTTP 三条写路径的非法操作均被拒绝且没有部分写。

### G3-C：现有弹窗增量与只读展示

1. 在现有弹窗增加默认空 select、说明、错误和 loading 状态。
2. payload 显式携带 comicFormat；成功后沿用现有路由。
3. 项目卡、TopBar、排版页显示共享 label。
4. 删除未引用的旧 `ProjectStoryPanel.vue`，不恢复元信息表单。

退出标准：两个版式都能从同一弹窗创建；关闭重开为空；创建后无编辑控件。

### G3-D：迁移与历史隔离

1. 完成旧值映射/决议 codec 和 MigrationIssue 报告。
2. 验证 `page_horizontal` 自动映射、`four_panel/空/非法` 阻塞。
3. 验证 legacy preflight/layout/task 证据不被错误写成 runtime canonical 历史。
4. 在脱敏 snapshot 上重复演练，活动 workspace 保持只读。

退出标准：无未决 blocker；同输入和决议重跑摘要相同。

### G3-E：完整验收与留痕

1. Vitest、数据库合同、Playwright API/Chromium 全绿。
2. 分别创建两个项目，重启后值保持。
3. 直接 PATCH/SQL 修改都失败，旧值导入报告可审计。
4. 更新文档、完成记录、Handoff、Scrutiny Review 和 Runtime/User Review。

退出标准：满足 `G3漫画版式入口与锁定验收清单.md` 的全部 mandatory 项。

## 14. 回滚与兼容

### 14.1 未产生新 Project 前

可以回滚 Web/Server 版本并撤销尚未应用的 G3 migration；保留已采纳文档和设计证据。

### 14.2 已产生 canonical Project 后

不能回到只理解旧三值的应用版本：

- 旧应用不认识 `paged_comic`，可能静默回退为 `vertical_scroll`。
- trigger 和新 DTO 会与旧客户端冲突。

因此回滚只能使用兼容 `paged_comic` 的上一构建或协调恢复完整备份，不能把 DB 值批量改回 `page_horizontal`。

### 14.3 复制转换的未来边界

未来能力应是：

```text
POST /projects/{sourceProjectId}/copies
  + targetComicFormat
  -> 新 Project ID
  -> 显式转换任务与报告
```

本轮不预留可原地 UPDATE 的管理员后门。

## 15. 验收摘要

### 15.1 用户路径

- 点击现有“创建项目”打开同一个弹窗。
- “漫画版式”初始为空；不选无法提交。
- 两个版式均能创建并直接进入第 1 步剧本。
- 项目卡与工作台头部显示选定版式。
- 关闭重开仍为空；创建失败保留当前输入并在字段内显示错误。
- 创建后所有普通页面无可编辑版式控件。

### 15.2 API/数据库

- 缺失、空、非法、`page_horizontal`、`four_panel` 新建均失败。
- 合法两值均创建 Project + 默认 Chapter，无部分写。
- PATCH 同值或不同值均 409，rowVersion/updatedAt 不变。
- 数据库无 default，CHECK 和 trigger 均存在且有效。
- 重启读取保持 canonical 值，无静默 fallback。

### 15.3 迁移/下游

- `page_horizontal -> paged_comic` 可重复、可审计。
- `four_panel/缺失/非法` 未决时阻止 final import。
- 四格意图保留为迁移证据，不成为 Project enum。
- 新 preflight/task 使用 canonical 值；旧 task/layout 摘要不被重写。
- `paged_comic` 的用户标签从不出现“横版”；临时候选/布局适配有明确 policy/version 和 G5 删除点。

## 16. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 把“扩展弹窗”写成“新增入口” | 产品重复建设 | 文档和任务统一写明复用现有路径 |
| 只改 TypeScript DTO | 旧客户端仍能发额外字段 | 原始 body guard + service allowlist + DB trigger |
| 继续用 normalize fallback | 用户被无意识锁成条漫 | strict parser 与 migration mapper 分离 |
| 把分页漫画继续叫横版页漫 | 与 PageProfile 设计冲突 | 统一标签“分页漫画”；横向只存在 legacy adapter |
| 共享枚举翻转导致大量编译错误 | 切片难以合并 | G3-A 一次更新 exhaustive 分支并保留明确 adapter |
| 四格意图丢失 | 迁移后无法还原用户意图 | resolutionJson 保存 layoutPresetIntent，G5 一次性消费 |
| UI 禁用但数据库可改 | 后续脚本破坏历史来源 | NOT NULL/CHECK/trigger + sqlite_master 合同测试 |
| G3 提前实现 G5 | 范围失控 | 旧 LayoutPage 只兼容读取；PageProfile/LayoutPreset 仍归 G5 |

## 17. 最终推荐

1. 复用现有项目库、现有创建按钮、现有 `CreateProjectModal` 和现有成功跳转。
2. 只在项目名称下方补默认空、必选的“漫画版式”。
3. canonical enum 固定为 `vertical_scroll/paged_comic`，Shared 提供唯一展示目录。
4. 正式运行时 strict，旧数据只在 maintenance importer 中映射。
5. 普通 PATCH 只要出现 `comicFormat` 就返回 409；数据库 trigger 防止底层绕过。
6. 项目卡和工作台 TopBar 提供只读核对；不把旧元信息表单重新接回剧本文档。
7. `paged_comic` 永远不等于横屏；现有横幅候选/旧 LayoutPage 只作为带版本和删除点的临时兼容层。

本方案尚未实现。详细字段和迁移协议见 `文档/04_方案与决策/2026-07-11_G3漫画版式契约与旧值迁移字典.md`，测试与用户路径见 `文档/06_测试与验收/G3漫画版式入口与锁定验收清单.md`。
