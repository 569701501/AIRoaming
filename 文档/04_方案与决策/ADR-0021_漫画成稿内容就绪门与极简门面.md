# ADR-0021 漫画成稿内容就绪门与极简门面

## 1. 决策状态

已采纳，作为漫画成稿下一轮实施基线。

本文扩展 ADR-0019，不改变“一份 `LayoutDocumentV2` 贯穿自动成稿、人工编辑、版本和出版”的决定；本文收缩 ADR-0019 后续实现中暴露给普通用户的 mode、intent、Pending、双预览和四步出版流程。

ADR-0020 继续有效。`LayoutCompositionApplication` 仍是当前任务与应用分离架构中的 exactly-once 证据，本轮不合并、不删除。

## 2. 触发问题

指定真实 Working Copy 的技术渲染正常，11/11 张图片可加载且镜头顺序正确，但内容不是正确漫画：

- 正式 Storyboard 有 16 条 voice line 和 3 个旁白镜头；
- Working Copy 的 `automation.dialogueBindings=[]`；
- 唯一气泡没有 `sourceShotId`、`speakerCharacterId`，文字也不来自正式分镜；
- 多张素材存在 AI 乱码或与分镜关键动作不一致；
- 页面仍能以普通 Working Copy 只读预览展示。

这证明现有正确性门出现得太晚：V2 Revision/Publication 会阻止错误内容正式出版，但普通用户在打开、阅读和调整 Working Copy 时仍可能把错误稿当成成稿。

同时，当前工作台把底层安全步骤原样暴露为产品流程：

- `initial / full_reflow / scoped_reflow`；
- 选区、页/段、场景三类局部范围；
- 四类 intent；
- 缩略对比和完整视觉对比；
- 成稿预检、保存 Revision、出版预检、提交 Publication 四步；
- 来源返修、版本历史和出版历史常驻；
- Working Copy、Revision、Publication 等技术术语。

问题不是缺少能力，而是缺少一个把能力封装起来的深门面。

## 3. 决策

漫画成稿收敛为“一个工作台、一个内容就绪门、一个建议模型、一条发布链”。

普通用户的唯一主路径：

```text
打开章节
→ 自动生成或恢复成稿
→ 在同一画布直接修正
→ 预览并导出
→ 确认
→ 下载成品
```

底层继续保留异步任务、Pending、应用凭证、CAS、两次服务端预检、不可变 Revision、Publication 和确定性 renderer；Web 不再编排或解释这些内部概念。

### 3.1 一个内容就绪门

从现有 `runLayoutPreflightV2()` 提取纯派生能力：

```ts
evaluateLayoutContentReadiness(input): LayoutContentReadiness
```

建议只读结果：

```ts
interface LayoutContentReadiness {
  contentState: "readable" | "blocked";
  sourceState: "current" | "stale" | "unresolved";
  expected: number;
  placedOriginal: number;
  userModified: number;
  userSuppressed: number;
  invalid: number;
  unclassifiedNarrativeText: number;
  issues: LayoutContentIssue[];
}
```

闭合公式：

```text
expected = placedOriginal + userModified + userSuppressed
invalid = 0
unclassifiedNarrativeText = 0
```

判定规则：

| 状态 | 判定 |
| --- | --- |
| `placedOriginal` | binding、Shot、气泡类型、说话者和文字摘要均与正式来源一致 |
| `userModified` | binding 仍有效，文字不同，但存在 `reason=user_edit + scope=text` 保护 |
| `userSuppressed` | 由 `balloon.suppress_bound` 形成显式 disposition/tombstone |
| `invalid` | 缺失、重复、悬空、来源不符、无保护改文或非法 suppression |
| 自定义文字 | 符合下述显式所有权规则，不计入正式对白覆盖 |
| 未分类叙事文字 | 无 binding、也没有显式所有权证据的可见气泡或叙事文字，阻断 |

`invalid` 统计互斥的正式 dialogue item 数，不统计 issue 条数；同一个 item 即使同时存在来源、类型和说话者问题也只计一次。每个 item 按以下优先级只进入一个桶：

```text
binding/来源/类型/说话者/元素非法 → invalid
否则 disposition=user_suppressed → userSuppressed
否则文字等于正式来源 → placedOriginal
否则存在 user_edit:text 保护 → userModified
否则 → invalid
```

`contentState` 与 `sourceState` 正交，不能用单一枚举丢掉“内容错误且来源又 stale”的组合。普通页面状态优先级为：

```text
保存冲突
> content blocked
> source unresolved
> source stale
> readable/current
```

叙事文字分类固定为：

- 所有可见 `BalloonElement` 都属于叙事文字：要么有正式 binding，要么有显式自定义所有权；
- `TextElement.semantic=caption` 属于叙事文字，当前不能充当正式 dialogue binding，只能经显式确认作为自定义旁注；
- `TextElement.semantic=custom` 必须有显式自定义所有权；
- `title` 与 `sfx` 不计入正式对白账本，但仍执行非空、字体、溢出和可见性检查；
- 隐藏的正式 binding 必须走 `user_suppressed`，不能因为不可见就从账本消失。

不新增文档字段或 `LayoutDocumentV3`。显式自定义所有权使用现有 protection 表达，但规则必须严格：

- 用户通过 `element.add(actor=user)` 新建文字时，命令内核已建立包含 `existence + text` 的 `user_edit` 保护；
- 用户新建气泡时，必须有包含 `existence + text + source` 的 `user_edit` 保护；
- 旧对象或来源不明对象只有执行新的用户语义命令 `text.confirm_custom` / `balloon.confirm_custom` 后，才能补齐上述保护组合；
- 普通改字只产生 `text` 保护，不能把旧无来源气泡自动洗成自定义内容；
- `explicit_preserve` 只表示迁移保留，不是用户自定义证据。

不新增持久化的 `user_modified` 枚举。它由“文字摘要变化 + user text protection”无歧义派生，避免双状态漂移。

执行时点：

1. initial 结果写入 Working Copy 前；
2. Proposal/Pending 创建前与应用前；
3. Working Copy 保存后；
4. 工作台 `open` 返回时；
5. Working Copy 阅读预览前；
6. Revision 与 Publication 现有预检中。

旧的错误 Working Copy 不自动覆盖。它进入 `blocked` 修复态，保留原稿和人工修改，生成可预览、可放弃的修复 Proposal。普通只读预览不得把它标成正常成稿；内部诊断仍可显式查看“未完成草稿”。

### 3.2 可执行的内容修复 Proposal

现有 full/scoped reflow 只改布局、裁切、样式和尾巴，不能修复 `dialogueBindings=[]`。因此内容门启用前必须先增加一个受限的 V2 语义命令：

```text
content.reconcile_from_storyboard
```

该命令由 Server 根据冻结 Storyboard、dialogue ledger、当前来源和 base Working Copy 构建，客户端不能提交任意 binding。payload 至少密封：

- base document digest；
- StoryboardVersion 与 dialogue ledger digest；
- 完整的规范化 dialogue ledger snapshot；Shared 重算其 digest 后，才能独立核对文字、类型、说话者和 item identity；
- source lock-set digest；
- 要新增或替换的正式 binding；
- 与每个 binding 配对的气泡、canvas 和插入位置；
- 更新后的 composition evidence；
- 仍需用户处理的未分类元素 ID。

Shared 应用规则：

1. base、Storyboard、ledger 和来源任一变化即拒绝；payload 中的规范化 ledger 必须能重算出声明摘要，并在应用时仍与当前权威 ledger 一致；
2. 新气泡的文字、类型、Shot 和说话者必须与 ledger 精确一致；
3. 每个正式 item 最多一个 binding，禁止模糊匹配和静默改写；
4. 默认只补缺失项或替换非法 binding，不删除现有未绑定元素；
5. 所有人工 protection 和 lock 保留；需要碰受保护对象时转为问题，不越权；
6. 单个语义命令使用现有 snapshot inverse，应用后形成一个 Undo history entry；
7. `dialogueBindings=[]` 的测试稿应能补齐全部正式项，但原无来源气泡仍需用户“保留为自定义”或删除。

Proposal 创建/应用使用 `proposalIntegrity`，不得错误要求所有旧问题已经清零：

```text
schema/source/base/command/protection 有效
且任何原本合法的 dialogue item 都不得退化或换桶
且本次声明修复的 item 必须变为合法
且未声明修复的 invalid item 不得被替换成另一种未解释错误
```

initial 创建仍必须 `contentState=readable`。普通重排必须保持原有内容闭合；内容修复 Proposal 可以在减少问题后仍保持 `blocked`，直到用户处理剩余未分类文字。Revision 和 Publication 始终要求最终 `readable`。

### 3.3 一个深门面，最多三个入口

新增兼容门面，不替换底层事实：

```ts
interface MangaFinalizationFacade {
  open(scope: ChapterScope): Promise<LayoutWorkspaceView>;
  change(scope: ChapterScope, request: LayoutChangeRequest): Promise<LayoutOperationView>;
  release(scope: ChapterScope, request: LayoutReleaseRequest): Promise<LayoutReleaseView>;
}
```

`open` 返回 opaque `draftToken`/ETag。它封装 Working Copy ID、rowVersion、文档摘要和当前来源身份；Web 只原样回传，不能解析或自行拼装。

#### `open`

- 聚合 Working Copy、内容就绪、来源 freshness、当前 Proposal、版本/出版摘要；
- 无 Working Copy 且来源完整时零配置启动 initial 并原子应用；
- 有稿时直接恢复；
- 同时返回正交的 `contentState` 与 `sourceState`；
- 不向 Web 分字段暴露 task、digest、rowVersion 或 application evidence，只返回 opaque `draftToken`。

#### `change`

统一承载：

- `save_draft`：autosave 当前 V2 文档，携带 `draftToken`，成功后返回下一枚 token；
- `resolve_conflict`：重载服务端或显式保留本地恢复稿；
- 当前上下文智能整理；
- 整章换版；
- 内容修复与“保留为自定义”确认；
- 来源更新；
- 历史版本恢复；
- Proposal 应用或放弃。

所有改变 Working Copy 的分支都必须携带 `draftToken` 并走 CAS。冲突响应返回服务端快照身份和可下载的本地恢复信息，不允许最后写入者静默获胜。

范围由当前 selection/canvas/shot 自动推断，服务端继续按连续对白和叙事组扩展。`initial/full_reflow/scoped_reflow` 不再是普通 Web 状态。

“对白可读”是硬约束，不再是用户可关闭的 intent。紧凑、舒展或强调重点作为具体上下文动作或“更多”偏好保留，不展示底层枚举。

#### `release`

统一承载：

- 手动检查点；
- 预览并导出。

主路径内部执行：

```text
等待自动保存
→ Working Copy 内容与来源检查
→ 创建或复用不可变 Revision
→ 对 Revision 运行出版检查
→ 创建 Publication
→ 返回进度与产物
```

用户只看到一份去重后的问题清单并确认一次。服务端仍在 Revision seal 和 Publication 创建时分别重验，不能把一次旧 preflight 跨阶段当成永远有效；并发产生新 warning 时重新返回 `needs_attention`，不得静默绕过。

`release` 同样只接收 opaque `draftToken`，Server 内部展开并复核 rowVersion、完整/可见摘要和来源身份。

字体、图片和产物下载等 GET/data-plane 接口不计为新的业务命令入口；“最多三个入口”约束的是会改变漫画状态的工作流门面。

### 3.4 一个建议模型

普通界面统一称“调整预览”，内部继续使用 `PendingEditorCommandSet` 和 `LayoutCompositionApplication`。

只保留一个权威视觉面：

- 删除结构缩略图作为决策依据；
- 当前稿和建议稿都使用同一 RenderScene 语义；
- 全章换版需完整渲染并浏览全部受影响内容；
- 局部调整只需验证并浏览受影响范围；
- 图片或字体未就绪时不能应用；
- 应用仍生成一个可撤销批次；
- 刷新后仍可恢复待决策建议。

### 3.5 一个页面主路径

顶部常驻：

- 章节；
- 自动保存状态；
- 撤销 / 重做；
- 上下文“整理成稿”；
- `预览并导出`；
- `更多`。

三栏布局继续保留：

```text
结构与异常 | 唯一正式画布 | 当前对象常用属性
```

界面原则：

- 左栏正常时只显示页/段和镜头顺序；未放置、来源更新或内容错误时才展开异常素材。
- 中央在编辑、调整预览、阅读预览三种状态间互斥切换，同屏只有一个权威视觉面。
- 右栏首层只显示当前对象 3～5 个常用属性和具体动作。
- 精确坐标、详细裁切、气泡内边距/尾巴数值、图层、历史、来源和导出设置进入不超过两层的“更多”。
- 自定义画格、自由图片、文字和气泡继续保留，但合并为一个 `+` 入口。

### 3.6 异常状态

| 状态 | 页面动作 |
| --- | --- |
| 正常 | 直接编辑或“预览并导出” |
| 来源更新 | 一条横幅和“更新到最新定稿”；默认保留归一化裁切 |
| 内容错误 | 显示缺失/未分类数量，“修复内容”；禁止版本和出版 |
| 保存冲突 | 暂停自动保存，提供查看差异、重载和恢复副本 |
| 发布中 | 非阻塞进度；继续编辑的内容不进入已冻结版本 |

图片像素内 AI 乱码、人物或动作与分镜不符，不属于排版编辑器的对白门。它们作为候选图/视觉素材质量问题返回上游处理；漫画成稿只消费并展示上游质量结论，不新增滤镜、OCR 修图或第二套图片编辑器。

## 4. 删除、合并与内收

### 4.1 从普通路径删除

| 当前内容 | 处理 |
| --- | --- |
| AI Drawer | 删除 |
| `initial/full/scoped` 可见模式 | 删除，由状态与 selection 推导 |
| 选区/页段/场景三选一 | 删除模式选择，改为上下文 |
| `standard/dialogue_readability` 用户选项 | 删除；分别是默认和硬约束 |
| 四按钮 intent 面板 | 删除；紧凑/舒展/重点改为具体动作或更多偏好 |
| MiniPreview | 删除，只保留权威视觉预览 |
| 独立手机预览按钮 | 合并到阅读预览的视口切换 |
| “立即保存” | 删除；正常时自动保存，失败时显示重试 |
| M6 四步控制中心 | 删除 |
| 两张 preflight 卡和两套 warning 勾选 | 合并为一次发布问题页 |
| 常驻来源状态与来源返修卡 | 正常隐藏，stale 时出现单一入口 |
| 常驻完整 Shot tray | 正常隐藏，只显示未放置或异常镜头 |
| 选择/平移/裁切常驻模式按钮 | 改为单击、空白拖动/快捷键、双击裁切 |
| 画格/图片/文字/气泡四个添加按钮 | 合并为 `+` |
| 常驻属性/图层双标签 | 图层移入按需抽屉 |
| 常驻精确坐标、画布尺寸和模板 | 移入更多属性 |
| raw digest、rowVersion、task、Pending、Revision、Publication | 普通 UI 全部隐藏 |

### 4.2 必须保留但内收

- `LayoutDocumentV2.automation`；
- 正式对白账本、稳定 dialogue item ID 和 binding；
- Working Copy、全文档摘要、rowVersion CAS、autosave、Undo/Redo；
- 字段级 protection、显式 lock、suppress/restore；
- Storyboard、CandidateLockSet、Asset/font 与 source projection seal；
- 持久 `layout_compose` 任务和视觉分析安全 fallback；
- Pending 的刷新恢复、过期、应用和放弃语义；
- `LayoutCompositionApplication` 不可变 exactly-once 凭证；
- Revision、双摘要、来源绑定、Publication、RenderPlan、manifest 和 Artifact；
- V1 历史读取与 V2→V1 只读投影。

### 4.3 本轮明确不做的破坏性删除

- 不合并 Pending 与 Application；
- 不从 Working Copy 直接出版；
- 不只运行一次 preflight；
- 不删除不可变 Revision；
- 不删除 V1 历史读取；
- 不新增 `LayoutDocumentV3`；
- 不引入 Comical-JS、TUI Image Editor 或 Manga Editor Desu 代码；
- Konva 继续只作为交互 adapter，不成为业务事实源。

如果未来把 composition worker 改成在同一终态事务中直接创建 Working Copy/Proposal，并用不可变 `originTaskId` 唯一约束完整替代应用证据，才可另立 ADR 评估移除 `LayoutCompositionApplication`；本轮不得提前删除。

## 5. 依赖与模块边界

```text
Web Manga Workspace
  -> HTTP Adapter（open / change / release）
      -> MangaFinalizationFacade
          -> Shared 纯逻辑
          -> Working Copy / Pending / Application / Revision / Publication repositories
          -> Persistent Task Scheduler
          -> VisualEvidenceProvider
          -> Renderer / Publication Worker
```

- Shared 纯逻辑只接收冻结事实，负责规划、命令、保护、内容就绪、preflight 和 RenderScene；不读 DB、HTTP、时间或环境变量。
- Server/DB adapter 负责事务、唯一约束、CAS、不可变 seal 和 exactly-once。
- 远端视觉分析只提供增强证据；失败时回退安全规则，不得决定 Storyboard 文字。
- Web 只理解 `workspace / readiness / proposal / release`，不再导入 mode、Pending、双 preflight 或 Prisma 概念。
- Konva、DOM 富文本和 viewport 仍是本地交互 adapter，不能进入文档或数据库。

## 6. 实施顺序

### P0 内容就绪前置

1. 从 V2 preflight 提取 `evaluateLayoutContentReadiness`，先补纯函数测试；issue 规则与现有 preflight 等价，覆盖计数按本文互斥优先级修正，不能机械复制现有可能重复计数的 summary。
2. 以独立 feature gate `layout_content_readiness_v1` 的 `off → shadow → on` 切换；shadow 先在 open/save/Proposal/preflight 记录差异，不改变用户可读行为。
3. 实现 `content.reconcile_from_storyboard`、`text.confirm_custom` 和 `balloon.confirm_custom` 语义命令及 Proposal 回归，先证明旧错误稿有可执行修复路径。
4. shadow 无未解释漂移后，按 initial 创建 → 普通 Proposal create/apply → Working Copy save/open → 只读预览的顺序逐入口 fail-closed；每个入口均可单独回滚，不能只依赖 Facade 总开关。
5. 对旧错误稿只返回 `blocked` 和修复 Proposal，不静默覆盖。
6. 用本次真实测试章固定回归：应显示 16 条正式对白缺失和未分类气泡；补齐正式项后仍要求用户处理无来源气泡，不得显示为正常成稿。

### P1 兼容 Facade

1. 新增 `open/change/release` 聚合服务，内部继续调用现有服务。
2. `open` 返回 opaque `draftToken`；`change.save_draft`、Proposal 决策、来源更新、恢复和冲突处理都使用同一 token CAS。
3. 不修改数据库；先 shadow 比较 Facade view 与旧接口聚合结果。
4. 新 Web session 只消费 Facade 视图。

### P2 页面删除

1. 删除 AI Drawer、MiniPreview、mode/intent 选择和 M6 四步控制中心。
2. 中央视图统一编辑/建议/阅读预览。
3. 来源、问题、历史、图层和高级属性改为按需出现。
4. 保留现有手调能力、命令、保护和 Undo/Redo。

### P3 一条发布链

1. `预览并导出` 编排 autosave、两次内部校验、Revision 和 Publication。
2. 合并普通用户 warning 显示和确认状态。
3. 保留并发重验、任务取消、历史产物和恢复入口。

### P4 物理清理

1. Facade 路径完成等价 E2E 后，删除 Web 对旧编排 API 的直接调用。
2. 删除无人使用的组件、状态、文案和 CSS。
3. 旧 Server 接口先降为内部兼容，不在同一阶段做破坏性数据库清理。
4. 超过回滚窗口后，再单独评估停止 V1 新写；历史读取不随意删除。

## 7. 验收标准

| 指标 | 标准 |
| --- | --- |
| 首次成稿 | 来源完整后 0 配置、0 点击 |
| 已有稿恢复 | 0 弹窗、0 点击 |
| 正常发布 | “预览并导出”+确认，正常情况共 2 次点击 |
| 局部调整 | 选中、动作、应用共不超过 3 次点击 |
| 同屏权威预览 | 1 个 |
| 顶部常驻动作 | 不超过 6 个 |
| 普通界面工程术语 | 0 个 |
| 高级能力入口 | 不超过 2 层 |
| 镜头覆盖 | 100% |
| 正式对白/旁白闭合 | 100%，无遗漏、重复、悬空和静默改写 |
| 未分类叙事文字 | 0 |

## 8. 风险与回滚

| 风险 | 控制 | 回滚 |
| --- | --- | --- |
| Facade 隐藏了必要异常 | `needs_attention` 保留结构化问题和定位；高级抽屉可查看详情 | 关闭 Facade feature gate，恢复旧 Web |
| 一条发布链误用旧检查 | Revision 与 Publication 内部继续各自重验 | 阻止提交，不创建新 publication |
| readiness 与正式 preflight 漂移 | 从同一纯 evaluator 派生并 shadow 对比 | 只展示正式 preflight 结果 |
| readiness 提前阻断旧稿且无修复路 | 先实现修复语义命令，再按入口打开独立 gate | 关闭对应入口 gate，不关闭正式出版 preflight |
| 旧错误稿被自动覆盖 | 只生成 Proposal，不直接应用 | 放弃 Proposal，原稿保持不变 |
| UI 删除后高级功能不可达 | 每项保留可达性合同与两层入口门槛 | 恢复对应抽屉入口 |

本方案首轮不改数据库和持久化 `LayoutDocument` wire shape，因此回滚不需要数据迁移。任何回滚都不得把 V2 可见投影写回为 V1。
