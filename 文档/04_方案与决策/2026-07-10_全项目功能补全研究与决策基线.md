# 全项目功能补全研究与决策基线

## 1. 文档定位

本文不是开发排期，也不授权开始开发。它回答三个前置问题：

1. AI漫游当前真实做到哪一步，而不是页面或类型定义看起来做到哪一步。
2. 市面能力中哪些值得吸收、哪些需要改造后吸收、哪些应暂缓或明确不做。
3. 哪些产品分叉必须由用户逐项确认，确认后才能写详细开发文档。

配套决策页：`2026-07-10_全项目功能补全决策版.html`。

## 2. 核心结论

AI漫游当前不是“七步都没做完”，而是形成了三个明显不同的成熟层级：

1. **前半段已可工作**：项目、剧本、剧情结构、分镜、角色、出图准备已经有真实页面和业务服务。
2. **候选图已进入真实闭环，但质量门槛尚未闭合**：真实生图、批次、候选记录、服务端生成规格和锁定均已存在；真实 Grok 样例仍暴露场景参考图污染、伪文字和无关人物继承。
3. **成稿与交付仍是骨架**：当前排版近似“一镜一页”，导出只是复制候选图；素材包是目录和 manifest，不是用户可下载的 ZIP，也没有真正的多格合成、文字气泡和渠道成品。

因此，下一阶段不应追求竞品功能并集，而应同时管理三条轨道：

| 轨道 | 目标 | 当前建议 |
| --- | --- | --- |
| A. 静态漫画发布闭环 | 从锁定候选图得到真正可发布的漫画成品 | 作为近期主线 |
| B. 生产可靠性底座 | 任务可恢复、状态一致、版本可追溯、回归可验证 | 与主线并行补齐必要部分 |
| C. AI 质量系统 | 用版本、样例、评分和供应商能力配置替代“凭感觉改 prompt” | 立即建立最小闭环 |
| D. 轻漫剧扩展 | 从分镜资产延伸到关键帧、视频、音频与 MP4 | 静态主线后续；可先做低成本架构验证 |

## 3. 核验方法

每项能力分四层核验，避免把“有字段”误判为“用户可用”：

| 证据层 | 判定问题 |
| --- | --- |
| 文档目标 | 项目是否正式声明要做，边界和验收是否明确 |
| 代码存在 | 是否有真实路由、服务、协议和持久化，而非占位类型 |
| 自动验证 | 是否有对应测试、类型检查或契约验证 |
| 用户路径 | 是否能从真实输入走到可检查、可下载、可继续使用的结果 |

成熟度枚举：

- `usable`：主路径可用且有基本验证。
- `partial`：存在真实实现，但关键操作、异常路径或质量门未闭合。
- `skeleton`：有页面/模型/服务骨架，输出不等于正式成品。
- `missing`：尚无真实业务实现。
- `deferred`：有意后置，不视为当前缺陷。

## 4. 当前能力成熟度

| 能力域 | 成熟度 | 真实现状 | 主要缺口 |
| --- | --- | --- | --- |
| 项目与章节 | `partial` | 项目、章节和工作台入口存在，真实样例可跨步骤推进 | 手动新建/改名/删除/排序章节不足；项目状态与章节/工作流状态可能漂移 |
| AI 剧本协作 | `partial` | OpenCode 对话、流式输出和步骤工具可工作 | 对话持久化、停止生成、修订历史和回滚不足 |
| 角色资产 | `partial` | 项目级角色库、角色图和引用已存在 | creature/group/voice 等实体类型仍有降级行为；上传、版本和全局复用不足 |
| 场景与风格资产 | `partial` | 章节场景和背景图存在，项目有风格枚举 | 缺少项目级场景库、纯环境图资格、版本、风格板和可执行风格约束 |
| 剧情结构与分镜 | `usable` | 生成、编辑、确认和步骤流转均有真实实现 | 上游修改后的依赖失效、差异对比和可靠回滚仍需加强 |
| 出图准备 | `partial` | 预检、确认和问题记录存在 | 文档契约仍有矛盾；参考素材合格性没有成为硬门禁 |
| 候选图工作台 | `partial` | 真实生成、批次、候选持久化、服务端生成规格和旧模型唯一锁定存在 | 收藏/废弃、定稿修订、影响预览、prompt 覆盖与版本、失败归因、真实重试/取消、成本记录不足 |
| 排版与成稿 | `skeleton` | Layout 数据与页面存在 | 当前接近一镜一页；无结构化多格画布、文字层、气泡层和真正合成渲染器 |
| 导出与素材包 | `skeleton` | 可建目录与 manifest | 无真实长图/分段图/PDF 渲染，无 ZIP 下载和发布前检查 |
| 任务与持久化 | `partial` | 图像任务有状态与进度；业务数据主要落工作区 JSON | 通用任务驻留内存，重启丢失；取消不能终止运行中请求；无可靠恢复与重试；Prisma 尚未接管主数据 |
| 轻漫剧/视频 | `missing` | 只有路线图和部分供应商方向 | VideoDraft、关键帧/视频片段、音频、字幕、时间线和 MP4 均未实现 |

### 4.1 当前真实样例暴露的状态问题

`workspace/projects/3c91668b...` 的项目元数据仍是 `draft`，但章节已经到 `storyboard_done`，15 个镜头全部是 `image_generated`，工作流停在候选图阶段。这说明“项目状态、章节状态、镜头状态、工作流步骤”尚未形成单一派生规则。

这不是展示文案问题：后续批量任务、恢复、导出门禁和统计都会依赖它，必须在继续扩大异步流程前修正。

## 5. 现有两份 HTML 的复核结论

### 5.1 全功能竞品对照复核版

仍然有效的判断：

- AI漫游的差异化应建立在正式步骤、确认、锁定、任务和素材追溯，而不是“一次生成整页”。
- 多格成稿、文字气泡、局部修图和真实渠道导出是后半段核心缺口。
- 旧报告推荐结构化轻画布；用户现已选择高自由画布方向，后续必须在 D4/D5 重新定义“成品形态有边界、画布工具高自由”的首版范围，旧建议不再作为当前最终决策。

需要更新的部分：

- 候选图生成、批次、锁定和服务端 prompt 规格已比旧盘点更完整，不能继续按“未实现”排序。
- 新出现的真正 P0 是“参考素材资格与真实质量门”，不是再增加一套前端 prompt 拼接。
- 2026 年的开源短剧/漫剧工作台已经把实体资产、准备态、持久任务、失败恢复和视频链路做成一体化生产系统，竞品范围需要加入 Jellyfish、LocalMiniDrama、LumenX 等架构邻居。

### 5.2 提示词外部借鉴优先级

旧报告中 P25/P26 指向“后端供应商 prompt 与前端预览不一致”。当前代码已改为服务端权威 `CandidateGenerationSpec`，旧优先级不再成立。

新的问题不是“再收集热门 prompt”，而是：

1. 是否能用固定样例复现成功与失败。
2. 是否知道某个输出由哪个模板版本、模型版本、参考素材和参数产生。
3. 是否按供应商能力生成不同规格，而不是给所有模型套同一套 negative prompt。
4. 是否能在 prompt 或模型升级时比较质量、成本和耗时，并阻止明显回退。

## 6. 外部资料带来的新判断

以下资料均于 2026-07-10 核验。对“公开展示或官方仓库声明了某能力”的置信度为高；对其内部实现、稳定性和商业效果不作推断。

### 6.1 直接漫画产品：成稿编辑与发布预览已成为基线

- [Dashtoon Studio 2024-08 Release](https://insiders.dashtoon.com/dashtoon-studio-august-2024-release/) 将 story mode、逐格 screenplay、预设画框、inpainting 与带尾巴/连接的气泡放在同一创作工作台。
- [LlamaGen 2026-06 Release](https://llamagen.ai/releases) 继续强化 storyboard 叙事、发布前预览、分辨率与气泡素材，说明“生成后可编排、可预览、可发布”仍是直接漫画产品的竞争焦点。
- [Anifusion Features](https://anifusion.ai/all-features/) 同时提供页面模板、气泡文字、画布、素材管理和视频，但无限画布服务于自由探索，不等于 AI漫游必须复制其交互范式。

结论：AI漫游应吸收“结构化成稿能力”，不应在 P0 复制无限自由画布。

### 6.2 邻近生产系统：准备态、资产实体和持久任务比“一键按钮”更关键

- [Jellyfish](https://github.com/Forget-C/Jellyfish) 把 script breakdown、shot preparation、candidate confirmation、entity reuse、image/video generation 和统一异步任务中心连成生产链，并把 prepared 与 generating 分离。
- [LocalMiniDrama](https://github.com/xuanyustudio/LocalMiniDrama) 提供角色/场景/道具、逐镜图像与视频、失败重试、工程 ZIP 导入导出、列表与画布同源等能力。
- [LumenX](https://github.com/alibaba/lumenx) 走小说到剧本、角色、分镜和视频合成的完整短漫剧链路。

结论：如果以后进入轻漫剧，优先吸收“关键帧准备 + 可恢复任务 + 实体资产”的架构，而不是先做一个把静态图机械转视频的按钮。

### 6.3 模型 prompt 不存在通用最佳模板

- [OpenAI Image Generation Guide](https://developers.openai.com/api/docs/guides/image-generation) 明确支持生成、编辑和高保真参考输入，但也明确列出精确文字、跨次一致性和布局控制仍有限制。
- [Runway Gen-4 Image Prompting Guide](https://help.runwayml.com/hc/en-us/articles/35694045317139-Gen-4-Image-Prompting-Guide) 推荐描述性完整句，并明确 Gen-4 Image 不支持 negative prompt。
- [Promptfoo](https://www.promptfoo.dev/docs/intro/) 的重要启发是测试样例、矩阵对比、结构化评分和持续反馈，而不是把某条流行 prompt 当成永久答案。

结论：AI漫游需要 `provider profile + capability registry + eval cases`，而不是单一全局 prompt 模板。

## 7. 缺口优先级与吸收方式

### 7.1 G0：先完成正在进行的真实质量阻塞

| 能力 | 建议 | 原因 | 退出标准方向 |
| --- | --- | --- | --- |
| 场景参考图资格与纯环境图版本 | 立即完成 | 当前 Grok 多图编辑会继承参考图中的人物和文字，直接污染候选底图 | 使用合格场景图后，不再出现参考图中的无关人物、气泡、页框或可读伪文字；结果可追溯到素材版本 |
| 干净候选图真实供应商验收 | 立即完成 | 契约与单测通过不等于真实结果通过 | 至少覆盖人物、双人、纯场景和复杂场景代表镜头，并记录人工评分与失败类型 |

G0 是现有任务收口，不是新增功能包。未收口前继续堆局部修图或视频，会掩盖输入素材和生成规格问题。

### 7.2 P0：静态漫画发布闭环

| 垂直切片 | 必要能力 | 依赖 | 建议 |
| --- | --- | --- | --- |
| 候选图可决策 | 收藏/废弃、定稿修订与影响预览、批次比较、失败原因、prompt/模型/参考素材版本展示 | G0、状态契约、ADR-0010 | 吸收 |
| 有边界的高自由成稿画布 | 按漫画成品形态建立页面/长条容器；首期支持最基础、最主要的自由摆放、缩放、裁切、文字、气泡和图层能力 | D1、D4、D5 | 改造后吸收 |
| 真正合成器 | 按布局裁切/缩放/合成候选图，渲染文字和气泡，不再复制单张源图充当页面 | 画布数据契约 | 吸收 |
| 发布导出 | 首发渠道要求的长图/分段图或固定页图片；真实 ZIP；PDF 是否进入 P0 由格式决定 | 合成器、首发格式 | 吸收 |
| 导出前检查 | 未锁定镜头、溢出文字、缺字体、低清图、空画格、素材丢失、版本过期阻断 | 完整版本图 | 吸收 |
| 黄金用户路径 | 从新项目到可打开的成品和素材包，保留截图、产物与 manifest 证据 | 上述全部 | 吸收 |

### 7.3 P0 底座：不做全量重写，只补会阻断主线的可靠性

| 能力 | 建议 | 边界 |
| --- | --- | --- |
| 项目/章节/工作流状态派生规则 | P0 | 建立单一状态来源和迁移检查，不继续容忍四套状态漂移 |
| 持久任务账本与启动恢复 | P0 | 图像任务先落持久存储；视频前必须扩展为通用任务底座 |
| 真实取消、有限重试与幂等 | P0 | 取消要传递到供应商请求或在回写前硬拦截；重试必须保留 attempt 和错误 |
| 版本与下游失效图 | P0 | 上游变更必须明确哪些结构、分镜、候选、布局和导出物过期 |
| 章节新建/改名/删除/排序 | P0 | 这是连续生产多个章节的基本操作，不扩展到团队权限 |
| 对话持久化与停止生成 | P0/P1 | 停止生成优先；复杂分支对话和全文版本浏览可后置 |
| 全量 Prisma 接管 | 暂缓决策 | 任务持久化是必要结果，但不等于 P0 必须立刻完成所有 JSON 到数据库迁移 |

### 7.4 P1：质量与效率扩展

- 项目级场景库、场景图资格、场景版本和跨章节复用。
- 风格板、色板、禁用项、参考图与风格版本，不再只有风格枚举。
- 用户上传/替换角色、场景、候选和字体素材，并保留来源与版本。
- 单图 mask 局部重绘，保留父候选、mask、prompt、模型和结果谱系。
- 全局素材库与跨项目复用。
- 供应商用量、估算成本、实际成本与耗时对比。
- 候选质量辅助检查：伪文字、人物数、构图、清晰度和身份一致性提示；人工仍作最终判断。

### 7.5 P0.5：轻漫剧架构验证，是否进入正式开发待用户决定

如果用户确认轻漫剧是下一条主线，先验证以下最小链路：

`锁定分镜图 → 视频片段规格 → 图生视频任务 → 片段确认 → 字幕/对白 → 顺序合成 → MP4`

正式路线至少需要：

- `VideoDraft`、`VideoSegment`、关键帧和视频 prompt 版本。
- 图生视频供应商适配、能力协商、长任务持久化、取消、重试和恢复。
- TTS、字幕、BGM/音效、音量和时长对齐。
- 时间线或受控片段列表，以及 FFmpeg 合成和发布预检。

不建议先做：复杂节点画布、自由关键帧曲线、专业级剪辑器或“一键全自动成片”承诺。

### 7.6 明确暂缓或不做

| 能力 | 当前判断 | 重新评估条件 |
| --- | --- | --- |
| 无限画布/节点工作流作为默认 UI | 暂缓 | 受控画布无法承载真实用户任务，且有可复现证据 |
| Photoshop 级图像编辑器 | 不做 | 产品定位改变为通用设计工具 |
| ComfyUI 节点直接暴露给普通用户 | 不做 | 仅可吸收可追溯工作流和隐藏复杂度的 App Mode 思路 |
| 实时多人协作、审批权限、评论 | deferred | 明确进入团队/SaaS 场景 |
| 社区、市场、商业化发布平台 | deferred | 明确从生产工具转为内容平台 |
| 同时支持所有漫画发布格式 | 不做 | 先用一个真实渠道走通，再以导出 profile 扩展 |

## 8. 提示词与 AI 质量优先级重排

### 8.1 新优先级

| 顺序 | 能力 | 产物 | 价值 |
| --- | --- | --- | --- |
| Q0 | 代表样例与失败样例集 | 固定项目/镜头、期望、失败标签、人工评分表 | 让改动可比较 |
| Q1 | 生成规格与输入素材审计 | prompt/template/model/reference/parameters/digest 全链路 | 让结果可追溯 |
| Q2 | 供应商能力注册与 profile | 尺寸、多参考图、mask、negative prompt、最大参考数、输出格式 | 避免错误套用通用模板 |
| Q3 | 回归评测与质量门 | schema 校验、规则评分、人工视觉复核、成本/耗时对比 | 阻止质量倒退 |
| Q4 | 剧本/结构/分镜 prompt 去重 | 每类 agent 目标、工具边界、输出 schema 与测试样例 | 提高文本链路稳定性 |
| Q5 | 外部热门 prompt 例库 | 只作案例与失败模式参考 | 价值最低，不能直接进入生产模板 |

### 8.2 必须分开的四类资产

1. **Agent/System 指令**：角色、权限、工具调用与安全边界。
2. **Skill/Workflow**：多阶段执行方法、记录与复核流程。
3. **结构化输出契约**：剧情结构、分镜、生成规格等 schema。
4. **模型生成 prompt**：图像、视频、TTS 等供应商相关描述。

这四类资产可以共享术语与事实，但不能共享同一套评测标准或拼接器。

## 9. 推荐路线草案

路线根据 2026-07-10 用户决策更新，仍保持 `proposed`，逐项形成详细方案后再进入开发：

```text
G0 真实底图质量收口
  ↓
R1 候选可决策 + 版本/失效规则 + 状态一致性
  ↓
R2 成品形态约束内的高自由画布 + 基础核心编辑
  ↓
R3 真正合成器 + 发布预检 + 渠道导出 + ZIP
  ↓
R4 黄金用户路径、真实样例、回归评测与文档同步
```

R5 暂不考虑，只保留历史记录，不进入近期方案和排期。

并行底座包括全量数据库迁移、持久任务、取消/重试、状态派生和版本谱系。Prompt 重排不再只是并行小项，已独立登记为“AI 质量与提示词工程”大功能。

## 10. 需要逐项确认的产品决策

### 10.1 D3 解释与最终决策

假设镜头 7 生成了 A、B、C 三张候选图：

- `selected` 表示“我目前更喜欢 B，先把它作为草选”。用户仍可随时改选 C，不触发画布、导出或下游版本失效。
- `locked` 表示“B 已正式批准给下游使用”。画布 placement、合成器和导出 manifest 都绑定 B 的候选 ID 和版本。
- 如果已锁定 B 后要改成 C，系统必须明确提示哪些布局和导出物会过期，并生成新的正式版本关系。

若合并成一个状态，会出现两个坏结果之一：用户只是点一下候选就导致大量下游失效；或者下游悄悄引用一个尚未正式确认、仍会变化的草选。

用户进一步提出了关键反例：如果 A 已经被后续排版或导出使用，用户返回候选阶段换成 B，会不会造成下游错误。答案是：**会，若系统只替换当前指针而没有版本和失效机制，就一定会出问题。**

当前代码的实际行为也证明这个风险存在：

- UI 只有“锁定此图”，没有真实 `selected` 业务动作；`selected` 目前只是枚举和展示文案。
- 在章节仍为 `images_done` 时，锁定 B 会直接把 A 从 `locked` 改回 `generated`，并把 `Shot.lockedCandidateId` 改为 B。
- 如果此时已经建立排版草稿，`PanelPlacement.candidateId` 仍可能指向 A，当前锁定值和排版来源会分叉，系统没有自动失效或影响提示。
- 导出后章节变为 `layout_done`，当前锁定接口反而会拒绝继续换图；这虽然避免了静默覆盖，但也没有提供正式返修路径。

因此问题不应只写成“selected 和 locked 是否区分”，而应拆成两个层次：

1. **草选是否需要持久化**：当前推荐不把 `selected` 作为下游工作流状态；用户可以预览、收藏或标记偏好，但下游绝不读取草选。
2. **正式定稿能否替换**：允许替换，但必须生成新的定稿修订，计算并展示下游影响，保留旧布局和旧导出，不做静默原地覆盖。

推荐返修规则：

| 下游状态 | A 改为 B 时的行为 |
| --- | --- |
| 尚未建立排版 | 直接建立新的定稿修订，A 保留历史，B 成为当前定稿 |
| 已有排版草稿 | 建立新定稿修订；使用 A 的 placement 标记为 `stale`，画布提示用户逐项替换或继续保留旧快照 |
| 已有正式导出 | 旧导出保持不可变；基于 B 生成新的布局/导出修订，旧导出标记为被后续版本替代但仍可追溯 |
| 有运行中的下游任务 | 不让旧任务回写成当前结果；任务产物仍归入旧修订，新修订另行生成 |

用户已确认采用修订式返修方案。UI 不强调 `selected/locked` 两个英文状态，而使用“收藏（不影响下游）”“当前定稿”“更换定稿图（先做影响检查）”“来源已更新”和“历史导出”。正式数据、接口、任务隔离、迁移和验收方案见：

- `文档/04_方案与决策/2026-07-10_D3候选定稿修订与下游返修方案.md`
- `文档/04_方案与决策/ADR-0010_候选定稿修订与下游返修.md`

## 13. 证据边界

- 竞品页面能证明公开展示的能力，不能证明其内部实现、实际稳定性或商业效果。
- GitHub README 能证明开源项目声明与可检查结构，不能直接证明其适合复制到 AI漫游。
- 本文对 AI漫游的成熟度以 2026-07-10 仓库、测试和本地样例为准；后续代码变化必须重新核验。
- 标记为 `accepted` 并有 ADR 的条目是用户已确认决策；其余“推荐”仍只是基于当前产品主线和最短可发布闭环的方案判断。
