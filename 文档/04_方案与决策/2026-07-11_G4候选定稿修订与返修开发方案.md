# G4 候选定稿修订与返修开发方案

## 1. 结论

G4 不改变“候选图工作台”在七阶段中的位置，也不重做一套人工工作台。它只把当前“锁定此图”升级为一条可返修、可并发、可追溯的正式决策链：

```text
生成候选图
  -> 收藏/废弃只帮助挑选，不影响下游
    -> “定稿此图”建立 CandidateLockRevision v1
      -> 排版只读取当前定稿修订
        -> 返回候选页更换/取消时先预览影响
          -> 确认后新增 v2/v3，旧布局、旧导出、旧任务结果不改写
            -> 画布派生“来源已更新”，由 G5 解决 stale
```

G4 的核心不是多一个表或多一个弹窗，而是四个稳定边界：

1. `Candidate` 是生成结果，`favorite/rejected` 是挑选辅助，`CandidateLockRevision` 才是下游权威。
2. 当前决策是不可变线性修订 + Shot 当前指针，不是 Candidate 状态互相改写。
3. 更换/取消是“预览影响 -> 带 expected revision + digest 提交”的两阶段命令。
4. 更换只改当前定稿指针；Layout/Export/Task 是否过期由来源关系派生，不做批量回滚。

本文于 2026-07-11 获用户确认并进入 `accepted`。确认文档不等于授权开发；开发仍须等全部规划完成和用户明确开始。

## 2. 继承与细化关系

### 2.1 不重新决策的内容

| 已有事实源 | G4 直接继承 |
| --- | --- |
| ADR-0010 | lock/replace/clear 不可变修订、影响预览、旧产物保留、任务来源隔离 |
| G1 | DB-only、Candidate/Shot/Revision/Layout/Export/TaskSource 表和当前指针 |
| G2 | 上游 current 门禁、`ArtifactFreshness`、`milestoneStatus` 单调、历史任务结果隔离 |
| ADR-0011 / G5 边界 | ImageElement 绑定定稿修订；画布逐格/批量换图、裁切保护和 LayoutDocument 由 G5 实现 |

### 2.2 G4 对 D3 的开发级细化

- D3 中的 `PanelPlacement.sourceCandidateLockRevisionId` 在 G1 关系模型中落为 `LayoutSourceBinding.candidateLockRevisionId`；G5 `ImageElement` JSON 仍保留可读的 `sourceCandidateLockRevisionId`。
- `LayoutWorkingCopy` 不新增第 45 张“WorkingCopyBinding”表；影响分析时通过 document codec 投影临时 binding。
- D3 中的 `affectedPlacementIds` 细化为 Working Copy 的 `elementId` 和正式 LayoutRevision 的 `(layoutRevisionId, elementId)`。
- `current/stale/unresolved` 是单个布局来源 binding 的解析状态；G2 `ArtifactFreshness` 仍保持 `current/stale/historical/pending`，不混用两个枚举。
- 影响 digest 补充 schema/policy version、作用域和 Working Copy 影响，不再依赖“格子恰好有独立数据库 ID”的假设。
- 幂等不额外增加 request log 表；使用 `expectedCurrentRevisionId + previousRevisionId + 目标状态` 识别丢响应重放。

## 3. 现有代码事实

### 3.1 候选与定稿

| 位置 | 当前事实 | 问题 |
| --- | --- | --- |
| `packages/shared/src/dto.ts` | `CandidateStatus` 包含 `selected/locked`；`WorkbenchShot` 含 `lockedCandidateId` | 生成结果、收藏和正式决策混在一起 |
| `apps/server/src/projects/image-candidate.service.ts` | lock 原地改 Candidate.status 和 Storyboard JSON | 没有修订历史，且污染已确认分镜文档 |
| `projects.controller.ts` | `POST .../candidates/:candidateId/lock` | 没有 preview、expected revision、digest 或 clear |
| `ImageCandidatesWorkspace.vue` | 按 Candidate.status 显示“锁定此图/已锁定” | 没有收藏、废弃、影响确认、当前定稿派生标记 |
| `workbench-store.ts` | 调旧 lock API 后在客户端拼装 snapshot | 缺少服务端权威的 revision/workflow/freshness 响应 |

### 3.2 返修链路

- Server 只允许 `storyboard_done/images_done` 锁定，进入 `layout_done/exported` 后没有正式返修入口。
- Web 在 `images_done/layout_done/exported` 后禁止再生成候选；用户无法在已导出章节中继续尝试新图。
- `completeChapterImages` 仅检查 `lockedCandidateId`，然后把章节设为 `images_done`，无法表达“曾完成但现在 clear 了一镜”。

### 3.3 布局、导出与素材包

- `LayoutExportService` 从 `lockedCandidateId` 构建一镜一页布局，原地覆盖 layout JSON，没有 LayoutRevision/SourceBinding/freshness。
- `AssetPackageService` 通过 `Candidate.status=locked` 寻找图片，没有绑定 ExportRevision 或 source digest。
- 现有 Prisma schema 仍只有 `Shot.lockedCandidateId`；G1 已规划目标表，G4 必须建在 G1 完成后，不能在旧 JSON/Prisma 模型上再做临时双写。

## 4. 目标与非目标

### 4.1 目标

1. 支持首次定稿、更换定稿、取消定稿和取消后重新定稿。
2. A→B→clear→A 产生 v1→v2→v3→v4，每次决策可追溯。
3. 收藏/废弃不驱动下游，当前定稿不再是 Candidate.status。
4. 更换/取消前精确显示 Working Copy、正式布局、导出和活动任务影响。
5. 预览后决策、布局、导出或活动任务变化时，提交显式 409，不静默使用旧预览。
6. 丢失成功响应后重试可安全返回已创建修订，不重复插入。
7. 旧 LayoutRevision、ExportRevision、Asset 和任务结果保持不可变。
8. 完整 lock set 和布局来源有单一规范化 digest，G5/G6 可直接消费。
9. 用户在已完成甚至已导出的章节中仍能生成新候选；只有正式更换定稿才让下游 stale。

### 4.2 非目标

- 不自动把新图覆盖到画布格子。
- 不在 G4 实现 LayoutDocument 编辑命令、裁切转换、批量换图或布局历史 UI；这些属于 G5。
- 不在 G4 实现正式 PNG/PDF/ZIP 渲染器；属于 G5/G6。
- 不用回退 `Chapter.milestoneStatus` 表达返修。
- 不通过删除候选、布局或导出“解决” stale。
- 不让活动任务取消代替完成时的来源校验。
- 不为 Working Copy 新增一张关系投影表。

## 5. 领域契约

### 5.1 Candidate 的三层语义

| 层 | 权威对象 | 可变性 | 会否让下游 stale |
| --- | --- | --- | --- |
| 生成内容 | Candidate + Asset + GenerationTask sources | 内容和来源不可覆盖 | 否 |
| 挑选辅助 | `favoriteAt`、`status=generated/rejected/superseded` | 允许收藏、废弃/恢复 | 否 |
| 正式决策 | CandidateLockRevision + Shot current pointer | 仅新增修订并切指针 | 是 |

规则：

- `selected/locked` 从 Candidate runtime enum 删除。
- `isCurrentFinal` 是查询投影，不存入 Candidate。
- 收藏幂等，可收藏多张，不创建修订。
- 废弃非当前定稿时，将 `status` 改为 `rejected` 并清空 `favoriteAt`；恢复后为 `generated`，不自动恢复收藏。
- 当前定稿候选不能废弃；先更换或 clear。
- `superseded` 是系统/迁移状态，V1 不提供用户恢复入口。
- Candidate 不提供单条硬删除；只随用户明确删除整个项目走 G1 Outbox 流程。

### 5.2 当前决策的派生

```text
Shot.currentCandidateLockRevisionId = null
  -> decisionState=unset
  -> currentCandidateId=null

指向 action=lock/replace 的修订
  -> decisionState=finalized
  -> currentCandidateId=revision.candidateId

指向 action=clear 的修订
  -> decisionState=cleared
  -> currentCandidateId=null
```

`currentCandidateId` 和旧 `lockedCandidateId` 都是投影，不得再反向写回 StoryboardDocument。

### 5.3 修订状态机

| 当前决策 | 请求 | 结果 |
| --- | --- | --- |
| unset | `lock(candidate=A)` | 新建 v1(A) |
| unset | `clear` / `replace` | `CANDIDATE_LOCK_ACTION_INVALID` |
| finalized(A) | `replace(candidate=B)` | 新建 next(B) |
| finalized(A) | `replace(candidate=A)` | no-op，不新建 |
| finalized(A) | `clear` | 新建 next(clear) |
| finalized(A) | `lock(...)` | 非重放请求时 action invalid |
| cleared | `lock(candidate=A)` | 新建 next(A) |
| cleared | `clear` | no-op，不新建 |
| cleared | `replace` | action invalid |

这里的 `lock` 表示“当前没有定稿图时建立定稿”，因此 clear 后重新定稿仍是 `lock`，而不是 `replace`。

修订号从当前修订的 `revision + 1` 获取，不通过无锁 `MAX(revision)+1` 分配。`previousRevisionId` 在非空时全表唯一，确保一条修订不能分叉出两个 next。

### 5.4 候选可定稿条件

目标 Candidate 必须同时满足：

1. 属于 URL 中同一 Project/Chapter/Shot。
2. Shot 是当前 confirmed StoryboardVersion 中的 active Shot。
3. `status=generated`，不是 rejected/superseded。
4. Asset 存在且 `status=ready`，不得用 staged/missing/corrupt 文件。
5. Candidate 的 GenerationTask/SourceSnapshot 对当前 Preflight 是 current；无法证明来源的 legacy Candidate 可保留历史当前指针，但不能被重新定为新 current，除非已有明确迁移决议。
6. G2 `NewWorkGate` 表明 Script/Story/Storyboard/Preflight 无 dirty、pending、stale 或 integrity blocker。

预览可以读取历史影响，但正式提交必须再次执行全部条件，不相信前端预览时的结果。

### 5.5 完整 lock set

一章“需要定稿的 Shot”精确定义为：该章当前 confirmed StoryboardVersion 中 `lifecycleStatus=active` 的 Shot。V1 没有“不需要出图”的镜头开关，因此所有 active Shot 都必须有可用的 finalized 修订；retired Shot 不阻塞。

Lock set resolver 把“结构是否完整”与“候选来源是否仍适用”分开返回。结构状态：

```text
complete   所有 active Shot 都有关系完整的非 clear 当前修订
incomplete 存在 unset 或 clear Shot
unresolved 存在断链指针、作用域错误、候选/Asset 缺失等完整性问题
```

来源适用性沿用 G2 `TaskApplicability=current/historical/legacy_unresolved`，由每个当前 Candidate 的生成来源聚合。仅 `complete` 可生成 `sourceLockSetDigest`；`incomplete/unresolved` 时 digest 为 `null`，不用包含 null 的假 digest 绕过门禁。新正式排版同时要求 `state=complete` 且 `sourceApplicability=current`。上游更新后，旧定稿可以仍结构 complete，但 sourceApplicability 会转 historical，不会被误当成新排版来源。

### 5.6 “完成本章候选图”

- 首次所有 Shot 定稿后，仍保留现有用户确认动作，将 `milestoneStatus` 单调推进到至少 `images_done`。
- 已经达到该里程碑后，replace 不要求用户再点一次“完成”；它是新的明确定稿决策。
- 已达里程碑后 clear 使候选步骤派生为 `needs_update`，但 `milestoneStatus` 不回退。
- clear 后重新 lock 使 lock set 再次 complete；因为里程碑已经达到，候选步骤自动恢复 done，不再要求重复确认。
- `complete` API 对已达里程碑且 lock set complete 的章节幂等返回当前投影。

## 6. 模块边界

G4 不把全部逻辑堆进 `ImageCandidateService`，而是建立以下深模块：

| 模块 | 唯一职责 | 不负责 |
| --- | --- | --- |
| `CandidateDecisionService` | preview/commit、状态机、候选可用性、修订事务 | 解析 LayoutDocument 细节 |
| `CandidateLockRepository` | 读当前修订、插入 next、条件切 Shot 指针、历史分页 | UI 文案和影响规则 |
| `CandidateLockSetResolver` | active Shot 集、完整性、规范化 lock set digest | 修改任何业务状态 |
| `CandidateLockImpactAnalyzer` | 从 Working Copy、LayoutRevision、ExportRevision、TaskSource 计算影响快照 | 提交修订或取消任务 |
| `LayoutWorkingCopyDependencyProjector` | 根据 `documentKind` codec 从 JSON 投影 element binding | 建第二份可写来源真值 |
| `LayoutSourceFreshnessResolver` | binding/lock set/layout/export 查询时派生新鲜度 | 批量 UPDATE stale |
| `CandidatePreferenceService` | favorite/reject/restore 与当前定稿保护 | 建立正式定稿 |

Controller 只解析 unknown body、调用服务并映射 HTTP；Web store 不自行猜 revision 或影响集。

## 7. 两阶段影响检查

### 7.1 第一阶段：preview

```text
POST /api/projects/{projectId}/chapters/{chapterId}/shots/{shotId}/candidate-lock/preview
```

Server 读取当前决策、验证 action/target，再生成完整影响快照。preview 不写数据库，返回的 `expectedCurrentRevisionId` 是下一步必填值；首次 lock 为显式 `null`，不是省略字段。

preview 本身必须在一个一致读事务中完成，避免将不同时刻的 current revision、Working Copy、Export 和 active Task 拼成一份从未真实存在过的影响快照。它不阻塞预览之后的新写入，因此 commit 仍必须重算。

如果只是 G2 上游 dirty/pending/stale，preview 仍可返回影响供用户理解，但必须返回 `commitAllowed=false` 和阻塞原因；正式 commit 继续由 NewWorkGate 强制拒绝。Candidate 跨作用域、已废弃、Asset 不 ready 或来源 historical/unresolved 属于目标本身非法，preview 直接返回稳定错误。

### 7.2 影响集口径

对 replace/clear，“本次会新变旧”的直接定义是：当前来源正在引用 `expectedCurrentRevisionId`，提交后将不再等于 Shot 新当前修订。

| 类别 | 权威查询 |
| --- | --- |
| Working Copy 元素 | codec 投影中 `shotId` 匹配且 `sourceCandidateLockRevisionId=expectedCurrentRevisionId` |
| 正式 Layout binding | `LayoutSourceBinding.shotId` 匹配且 `candidateLockRevisionId=expectedCurrentRevisionId` |
| LayoutRevision | 至少有一个上述受影响 binding |
| ExportRevision | `layoutRevisionId` 指向受影响 LayoutRevision |
| 活动任务 | queued/running/retrying，且 GenerationTaskSource 直接或递归引用当前 lock revision、lock set digest、受影响 layout/export |

已经引用更旧 lock revision 的格子在预览前就 stale，不冒充“本次将导致”；响应可额外给出 `alreadyStaleCount/unresolvedCount` 作提示，但不把它们计入 newly affected 数量。

首次 lock 通常没有可证明的下游引用，影响集为空。clear 后重新 lock 时，旧布局在 lock 前已 stale，也不冒充新影响。

### 7.3 Working Copy 的处理

`LayoutWorkingCopy` 只有 JSON 和 digest，没有正式 `LayoutSourceBinding` 行。`LayoutWorkingCopyDependencyProjector` 必须：

1. 根据 `documentKind` 选择 `legacy_chapter_layout_v1` 或 `layout_document_v1` codec。
2. 安全解码，不在影响请求中自动修复 JSON。
3. 投影 `{workingCopyId, elementId, shotId, candidateId, sourceCandidateLockRevisionId}`。
4. legacy placement 没有 element ID 时，仅用 codec 的稳定规则生成 `legacy:{pageId}:{order}`，同一 document digest 必须产生同一 ID。
5. 无法证明 source revision 时标为 unresolved，不猜测当前修订。

### 7.4 `impactDigest`

`impactDigest` 使用 RFC 8785 JCS + SHA-256，格式 `sha256:<64位小写十六进制>`。哈希输入含：

```text
schemaVersion, policyVersion,
projectId, chapterId, shotId,
action, targetCandidateId, expectedCurrentRevisionId,
affectedWorkingCopyElements[],
affectedLayoutBindings[],
affectedLayoutRevisionIds[],
affectedExportRevisionIds[],
activeTaskIds[]
```

- 所有 ID 去重，简单数组按字典序。
- 复合项按其 ID 元组字典序。
- 中文文案、数量、时间、本地路径、数据库行顺序不参与。
- `policyVersion` 固定为 `candidate_lock_impact_v1`；改变影响口径必须升版。
- 客户端不重新计算 digest，只原样回传；Server 在事务内重算。

### 7.5 弹窗规则

- 首次定稿：仍调 preview；影响为 0 时可直接提交，不弹大型返修对话框。
- replace：总是显示确认，即使影响为 0，因为它会建立新正式决策。
- clear：总是显示确认，并说明该镜头将重新阻塞新排版/导出。
- 弹窗用用户语言：“画布格子来源已更新”、“上次导出仍保留”、“运行任务将尝试取消”，不显示 stale/digest/revision 细节。

## 8. 提交、并发与幂等

### 8.1 第二阶段：commit

```text
PUT /api/projects/{projectId}/chapters/{chapterId}/shots/{shotId}/candidate-lock
```

请求必须显式带：

```text
action
expectedCurrentRevisionId | null
impactDigest
reason | null
```

`lock/replace` 必须显式带非空 `candidateId`；`clear` 必须省略 `candidateId`，即使显式传 null 也拒绝。Server 仅在内部规范化和 digest 中把 clear 的 `targetCandidateId` 表示为 null。`reason` 可省略。

`reason` 只是审计辅助，trim 后最多 500 字符，空字符存 null，不参与 lock set/impact digest。

### 8.2 校验顺序

1. 严格解析 body，区分“字段缺失”和“显式 null”。
2. 读 Project/Chapter/active Shot 和当前修订。
3. 先识别丢响应重放，再判定 expected revision 冲突。
4. expected 匹配后校验状态机和 no-op。
5. 执行 G2 NewWorkGate 和 Candidate/Asset/source 可用性检查。
6. 在同一事务视图内重算影响快照/digest。
7. digest 不匹配则 409，不自动使用新影响集继续。
8. 插入 next revision，条件更新 Shot current pointer。
9. 返回 Server 重新投影的当前决策、lock set、workflow 和影响摘要。

### 8.3 丢响应重放

不新增 `idempotencyKey` 表。当且仅当以下条件同时成立，当前修订可视为本请求已经成功的重放结果：

```text
current.previousRevisionId == request.expectedCurrentRevisionId
current.action == request.action
current.candidateId == normalized request.candidateId
```

首次 lock 的 expected 与 previous 都为 null，因此也可识别。返回 `replayed=true`，不新增修订，不要求原 digest 仍匹配当前影响集。

如果当前已经经历后续决策，`previousRevisionId` 不再等于旧 expected，旧请求必须 409，不会错把“后来又选回同一候选”当成重放。

### 8.4 SQLite 事务算法

```text
BEGIN write transaction
  read Shot + current revision
  if exact replay: return existing revision
  assert current.id == expectedCurrentRevisionId (null-safe)
  validate state transition and target
  recompute impact snapshot/digest
  assert digest == request.impactDigest
  nextRevision = current ? current.revision + 1 : 1
  insert immutable CandidateLockRevision(previous=current.id)
  update Shot
    where id=shotId
      and currentCandidateLockRevisionId IS expectedCurrentRevisionId
    set currentCandidateLockRevisionId=new.id
  assert affectedRows == 1
COMMIT
```

数据库还必须有：

- `(shotId, revision)` 唯一。
- `previousRevisionId` 非空全表唯一。
- previous/current/candidate 必须属于同一 Project/Chapter/Shot。
- action/candidate nullability CHECK。
- 修订 UPDATE/DELETE 禁止 trigger。
- Shot current pointer 与 Candidate 当前废弃/硬删除的完整性保护。

两个 SQLite writer 如在同一 expected 上竞争，唯一约束、条件 pointer update 或 `SQLITE_BUSY` 会使其中一个事务失败。Repository 在事务外重读一次：符合精确重放则返回成功，否则统一映射 `CANDIDATE_LOCK_REVISION_CONFLICT`，不盲目重试新决策。

### 8.5 事务内不做的事

不更新：

- 旧 CandidateLockRevision。
- LayoutWorkingCopy JSON。
- LayoutRevision / LayoutSourceBinding。
- ExportRevision / ExportArtifact。
- 旧 Asset 或导出文件。
- `Chapter.currentLayoutRevisionId/currentExportRevisionId`。
- `Chapter.milestoneStatus`。

事务提交后，对 preview 中的活动下游任务发出 best-effort 协作取消请求。取消失败不回滚定稿；任务完成时的 applicability guard 仍是最终防线。

## 9. 下游来源与 Freshness

### 9.1 Binding 级解析

```text
current
  binding.candidateLockRevisionId 有效
  且 == Shot.currentCandidateLockRevisionId
  且当前修订非 clear

stale
  binding 可完整解析
  但与 Shot 当前修订不同
  或 Shot 当前 unset/clear

unresolved
  source revision 缺失
  或作用域/候选/Asset 关系断裂
  或 legacy 数据无法证明来源
```

聚合优先级：`unresolved > stale > current`。任一必需 binding unresolved，整个布局不得生成新正式导出。

### 9.2 不混用“是哪一版”和“来源是否新”

Layout/Export 查询同时返回两个轴：

```text
revisionPosition = working_copy | current | historical
sourceResolution = current | stale | unresolved
```

映射到 G2 `ArtifactFreshness`：

| position | sourceResolution | ArtifactFreshness / attention |
| --- | --- | --- |
| current | current | `current / none` |
| current | stale | `stale / source_updated` |
| current | unresolved | `null / integrity_blocked` |
| historical | 任意 | `historical`，详情仍显示 sourceResolution |
| working_copy | 任意 | 不冒充正式 ArtifactFreshness |

这样一个仍由 `Chapter.currentLayoutRevisionId` 指向的布局，在换图后可以精确表达为“当前选中版，但来源 stale”，无需清空指针或改写历史行。

### 9.3 Lock set digest

`CandidateLockSetResolver` 对 complete lock set 产生：

```json
[
  { "shotId": "shot_001", "candidateLockRevisionId": "lockrev_001" },
  { "shotId": "shot_002", "candidateLockRevisionId": "lockrev_009" }
]
```

数组按 `shotId` 字典序，对 JCS 结果做 SHA-256。Candidate ID、时间、Storyboard order 和本地路径不参与。

`LayoutRevision.sourceLockSetDigest` 必须与其 `LayoutSourceBinding` 重建出的 digest 相同；两者不同是 integrity blocker，不是普通 stale。

### 9.4 ExportRevision 的不可变性

G1 中 `ExportRevision.applicability` 在 G4 细化为“任务完成登记时的 applicability”，实现时字段建议明确命名为 `completionApplicability`：

```text
current            完成时来源仍 current，可切 currentExportRevisionId
historical         完成时来源已变，只登记历史产物
legacy_unresolved  迁移时无法证明来源
```

该字段随 ready ExportRevision 不可变。之后换定稿时不把它从 current 批量 UPDATE 为 historical；“现在是否仍新”由 `currentExportRevisionId + sourceResolution` 查询派生。

### 9.5 任务隔离

- `image_generate` 来源是 Preflight，生成新 Candidate 本身不依赖当前 lock，不属于更换定稿的受影响任务。
- `layout_export/asset_package_export` 及后续合成任务必须通过 GenerationTaskSource 绑定 LayoutRevision/ExportRevision 和 lock set digest。
- 任务成功不等于可切 current。完成时重算来源；已变更则登记 historical，不切 Chapter current pointer。
- 取消只减少无意义计算；任务忽略取消或在边界时完成，仍会被 applicability guard 隔离。

## 10. 工作流投影

| 条件 | 候选图步骤 | 排版导出步骤 | 素材包步骤 |
| --- | --- | --- | --- |
| 未达 images 里程碑，lock set incomplete | active | waiting | waiting |
| 未达里程碑，lock set complete | active，可点完成 | waiting | waiting |
| 已达里程碑，lock set complete，无 layout | done | active | waiting |
| replace 后 lock set complete，current layout stale | done | needs_update/source_updated | waiting |
| clear 后 lock set incomplete | needs_update/source_updated | blocked/waiting | waiting |
| current layout unresolved | done 或 needs_update | blocked/integrity_blocked | waiting |
| layout current，current export stale/missing | done | needs_update 或 active | waiting |
| current export current | done | done | active/done 按 package 状态 |

`Chapter.milestoneStatus` 全程保持最远里程碑，不因 replace/clear 回退。

只要 G2 上游仍 current，在 `images_done/layout_done/exported` 后仍可为 active Shot 启动新 `image_generate`。生成完成后只新增 Candidate/Asset，不自动定稿，所以不影响当前 Layout/Export。

## 11. HTTP 与查询面

### 11.1 正式接口

```text
POST   .../shots/{shotId}/candidate-lock/preview
PUT    .../shots/{shotId}/candidate-lock
GET    .../shots/{shotId}/candidate-lock/revisions?cursor=&limit=

PUT    .../candidates/{candidateId}/favorite
DELETE .../candidates/{candidateId}/favorite
PUT    .../candidates/{candidateId}/rejection
DELETE .../candidates/{candidateId}/rejection
```

收藏/废弃响应返回 Server 最新 Candidate 投影，不返回伪造的本地乐观状态。历史修订只读分页，不提供“把旧 revision 设回 current”；想选回旧 Candidate 仍建立新 revision。

### 11.2 旧接口处置

`POST .../candidates/{candidateId}/lock` 在新 Web 同一个 G4 切片中迁移完成后删除。不保留一个绕过 preview/digest 的兼容 shim；旧本地客户端应明确失败并升级，而不是继续写旧权威字段。

### 11.3 Workbench 投影

Shot 返回：

```text
currentCandidateDecision:
  | { state: unset, revisionId: null, revision: null, action: null, candidateId: null, ... }
  | { state: finalized, revisionId, revision, action: lock | replace, candidateId, ... }
  | { state: cleared, revisionId, revision, action: clear, candidateId: null, ... }
```

该字段始终存在，不用整个 null/省略表示 unset。

Candidate 返回：

```text
status: generated | rejected | superseded
favoriteAt: string | null
isCurrentFinal: boolean
sourceApplicability: current | historical | legacy_unresolved
```

Snapshot 返回 chapter lock set summary 和服务端 workflow。新 Web 不再用 `Candidate.status=locked` 或 `shot.lockedCandidateId` 判定完成状态。

## 12. Web 交互

### 12.1 候选卡

| 状态 | 主动作 | 辅助动作 |
| --- | --- | --- |
| 没有当前定稿 | `定稿此图` | 收藏、废弃 |
| 本卡是当前定稿 | `当前定稿`（disabled 标记） | 收藏、取消定稿；不允许废弃 |
| 同 Shot 另一张可用候选 | `更换为定稿图` | 收藏、废弃 |
| rejected | `恢复候选` | 可查看，不可定稿 |
| superseded / source historical | 无正式定稿按钮 | 历史查看，必要时收藏仅作比较 |

候选预览大图使用同一动作和权限函数，不在缩略卡和大图里分别实现状态机。

### 12.2 冲突处理

- `REVISION_CONFLICT`：刷新该 Shot 候选与当前定稿，显示“定稿已在其他操作中更新，请重新确认”。
- `IMPACT_CHANGED`：自动重新 preview，展示新数量，但不自动提交。
- Candidate 已废弃/失效：刷新候选卡并保留用户当前 Shot 位置。
- 请求成功返回 `replayed=true`：按普通成功处理，不对用户显示内部重放术语。

### 12.3 返回排版页

G4 只要求排版页能显示“有 N 个图片来源已更新”、查看旧产物且禁止新正式导出。“替换当前格”、“批量替换”、裁切保留选项和新 LayoutRevision 创建由 G5 完成。G4 因此是 G5 的前置切片，不单独作为全部返修体验的可发布终点。

## 13. 旧数据迁移

### 13.1 权威证据顺序

1. `Shot.lockedCandidateId` 是可创建 legacy v1 的直接证据。
2. Candidate `status=locked` 只能作为佐证，不能单独猜测当前定稿。
3. Candidate `status=selected` 只迁移为 favorite，绝不创建 lock revision。
4. layout candidateId 只能在与有证据的 v1 一致时回填 source revision。
5. export 只能绑定可证明的 layout；否则 `legacy_unresolved`。

### 13.2 映射

| 旧状态 | 目标 |
| --- | --- |
| Shot.lockedCandidateId 指向同 Shot 有效 Candidate/ready Asset | 创建 `revision=1, action=lock, origin=legacy_import`，设 Shot current |
| lockedCandidateId 不存在/跨 Shot/Asset 缺失 | 不猜，记 MigrationIssue blocker |
| Candidate.status=locked | 转 `generated`；当前性仅由上述 v1 派生 |
| Candidate.status=selected | `favoriteAt=candidate.updatedAt`；无合法时间时用 recordedAt 并记 warning |
| 多个 status=locked 但无 Shot 指针 | 全部保留 generated，记 conflict，不选最新一张 |
| layout candidateId 与 v1 一致 | 建可证明 LayoutSourceBinding |
| layout candidateId 与 v1 不同/无 v1 | unresolved，保留 JSON/Asset，阻止新导出 |

legacy `decidedAt` 只在旧数据有明确决策时间字段时回填；不用 Candidate.updatedAt 冒充正式决策时间。`recordedAt` 始终是导入登记时间。

### 13.3 迁移后不得存在的 runtime 读路径

- 从 Storyboard JSON `lockedCandidateId/status` 决定当前候选。
- 从 Candidate `status=locked` 决定排版或素材包输入。
- 对旧 layout 缺失 source revision 时自动绑当前 lock。
- 为了保持旧 UI 而双写 JSON 和 DB。

## 14. 实施拆分

### G4-A：Shared + Schema overlay 约束

- 新 DTO/枚举/错误码，删除 Candidate `selected/locked` runtime 语义。
- G1 base 已拥有 CandidateLockRevision 的 action nullability、scope、不可变历史和 `revision DESC` 查询索引；G4 overlay 只叠加 non-null previous 唯一、previous=current、revision+1、action transition、replay 与 current CAS，不重复 ADD COLUMN 或重复声明基础 immutable。
- 完成 legacy mapping 的 importer contract test。

### G4-B：纯规则与 Resolver

- 状态机、lock set digest、replay 识别、binding freshness 表驱动单测。
- Working Copy projector 与 formal binding 影响分析。
- Export/task 递归影响查询和规范化 digest。

### G4-C：事务命令与 API

- preview、commit、history、favorite、reject/restore、complete 幂等。
- SQLite 并发、条件 pointer update、唯一冲突重分类。
- 去掉旧 lock API 和旧 JSON 双写。

### G4-D：工作流与下游门禁

- Workbench/ProductionState 加 candidate lock set 和 layout/export source summary。
- stale/unresolved 禁止新正式 layout export/package。
- 旧任务完成只能登记 historical。
- 允许后续阶段中生成新 Candidate，但不自动更换定稿。

### G4-E：Web 候选返修交互

- 收藏、定稿、更换、clear、废弃/恢复、修订历史。
- preview 影响弹窗和 409 重新确认。
- 排版页只读 stale 摘要与导出门禁；实际解决命令留给 G5。

### G4-F：迁移与端到端验收

- 直接证据/冲突/unresolved 迁移演练。
- A→B→clear→A、布局后更换、导出后更换、任务运行中更换、丢响应重试、真并发。
- 重启/备份恢复/数据库完整性/旧文件无权威回归。

## 15. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 影响分析扫全部历史导致慢 | binding/foreign key 索引；只查引用 expected revision 的新变 stale 集，不扫 Asset 文件 |
| 预览后活动任务快速变化经常 409 | 这是真实影响变化；UI 自动重新 preview，但不自动确认 |
| 取消任务来不及 | completion applicability guard 仍隔离结果 |
| 为兼容旧 UI 继续双写 lockedCandidateId | G4 同切片删旧 API/读路径，DB current revision 唯一权威 |
| 把 historical 和 stale 混为一个字段 | 强制 `revisionPosition + sourceResolution`两轴 |
| legacy 来源不足却被当成 current | unresolved + MigrationIssue，阻止新正式导出 |
| G4 提前侵入 G5 画布命令 | G4 只投影/标记/门禁，G5 才修改 Working Copy 并建 LayoutRevision |

## 16. G4 退出闸门

G4 实施只有在以下条件全部满足时才可交给 G5：

1. Candidate runtime 无 `selected/locked` 权威读写，StoryboardDocument 无 lock/status 污染。
2. A→B→clear→A 得到四条线性修订，所有旧行不可变。
3. preview/commit 对 revision 冲突、impact 变化、丢响应重放和 SQLite writer 竞争有测试。
4. 收藏/废弃不改变 lock set/layout/export/workflow freshness。
5. replace/clear 不修改旧 Layout/Export/Asset，但查询可稳定派生 stale/unresolved。
6. 布局来源 stale/unresolved 时新正式导出被 Server 门禁拒绝，不只依赖按钮 disabled。
7. 运行中的旧导出任务结束后只能 historical，不切 current pointer。
8. 已导出章节可生成新 Candidate，未定稿前不影响任何下游。
9. 旧数据迁移可幂等重跑，冲突不猜测，真实 workspace 不被反写。
10. G4 验收清单有实际命令、退出码、数据库证据和 Playwright/API 证据；未运行不得写 passed。
