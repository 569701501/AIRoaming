# 多角色与场景一致性平台调研

## 1. 调研问题

当一个候选图镜头同时包含 3 个已定稿角色和 1 个已定稿场景时，系统如何在不丢失任何必需视觉条件的前提下，适配不同图片模型的参考图数量和编辑能力。

本文选择有公开官方资料的代表性主流平台和模型，不声称是严格市场份额排名。

## 2. 结论摘要

1. 用户的质疑成立：“Grok 三人镜头保留 3 张角色图、场景改用文字”只是丢失场景视觉条件的止损降级，不是双重一致性的正确解法。
2. 用户提出的“把多个角色合成一张参考图”能确定解决图片槽位不足，是 Grok 三人及以上镜头的重要兼容手段；但它不应成为所有 Provider、所有人数的一刀切默认。1～2 人且独立角色图和场景图本来就能完整传入时，独立参考通常能保留更多单人身份细节，也更少引入设定表/拼贴先验。
3. 更完整的问题不是“把 N 张图塞进上限”，而是同时约束三个通道：`identity`（谁）、`environment`（在哪里）、`composition`（谁站哪里、做什么）。静态多人角色板只解决第一个通道；当前项目的构图仍主要依赖文字，正是多人动作主客体和站位可能漂移的原因。
4. 推荐架构是 Provider 无关的 `ShotVisualRequirementSet` 加自适应 `ReferencePlan`：容量足够时直传独立角色和场景；容量不足时使用多人身份板、场景/构图合并板或分层编辑；任何必需条件都必须有覆盖证据，不能静默裁掉。
5. 对三人及以上的高要求镜头，最佳质量路径不是无限扩大一张角色板，而是“先得到可用整体镜头，再用 mask 逐个修正失败角色”。没有任何官方资料承诺多角色和场景能 100% 一次保真，全部入图只是必要条件，不是充分条件。

## 3. 模型和 API 能力对比

| 模型 / 服务 | 官方公开能力 | 三角色 + 场景的直接适配 | 边界 |
| --- | --- | --- | --- |
| OpenAI GPT Image 2 | Image Edits 支持一张或多张参考图，官方给出 4 张输入组合为新图的示例；所有输入图默认高保真处理；另支持 mask 区域编辑 | 可直接输入 3 张单人角色图 + 1 张场景图 | 官方仍明确提示跨多次生成的长期一致性可能失败；高保真多图会增加输入成本 |
| Seedream 4.0 / 4.5 | 官方支持多图输入和复合编辑；公开 API 资料写明最多 10 张输入图；建议在 Prompt 明确“图一/图二/图三”的职责，并支持箭头、线框、涂鸦等视觉位置信号 | 可直接输入 3 张角色图 + 1 张场景图，还可增加构图/位置图 | 多图数量增加延迟；需要清楚指定每张图的对象和操作 |
| xAI Grok Imagine | 官方 Multi-Image Editing 单次最多 3 张源图，支持按输入顺序组合多主体，并支持 multi-turn editing | 不能在单次请求中把 4 个独立资产全部作为独立图片输入 | 必须使用合成参考板、多步编辑或路由到其他 provider；不能把第 4 个必需视觉条件静默丢弃 |

OpenAI 当前官方页面没有在调研可见段落中声明“最大 16 张”；当前项目代码中的 16 是本地 adapter 上限，不应当成官方能力承诺。对当前需求，官方 4 图示例已足以证明 OpenAI 可直接接收三角色+场景。

## 4. 主流创作平台的工作流

| 产品 | 用户看到的工作方式 | 官方公开的技术策略 | 对 AI漫游的启示 |
| --- | --- | --- | --- |
| Boords | 先创建、上传或选择可复用角色；一个 frame 可选择一个或多个角色，再描述互动 | 没有公开其内部如何适配不同模型的图片槽位 | 产品界面只让用户选择镜头实体，provider 打包细节应由系统隐藏 |
| LTX Studio | 用 Elements 管理 Characters、Objects、Locations，并在 Storyboard/Flow 中按名称复用 | Brand Kit/Elements 的 `@mention` 会自动解析进工作流，节点结果可缓存；没有公开每个底层模型的实际图片封装 | 一致性首先是资产、版本和工作流结构问题，不是每次手写 Prompt |
| Runway Gen-4 References | 保存并命名角色/场景 Reference，在 Prompt 用 `@名称` 引用，另可画 Sketch 控制站位 | 单次最多 3 张 Reference；复杂变更建议每次迭代一个元素，并沿角色路径和场景路径生成中间结果后合并 | 容量足够时独立命名参考质量更好；超限或复杂镜头走多步合并 |
| Vidu Reference to Video | 在 My References 保存角色、道具和场景，用 `@角色/@场景` 组合 | 官方公开支持 1～7 个参考，可把 character、scene、composition 等作为独立参考 | 原生多实体模型适合“每个实体独立引用”，但这种能力不能假定所有 provider 都有 |
| Midjourney | 只选一张 Omni Reference，再用文字描述多人及关系 | Omni Reference 只能一张；官方明确建议多人时使用一张已经包含多个人物的参考图 | 多人角色板是有官方产品先例的槽位压缩方案，尤其适合 Grok 这类小上限接口 |
| Adobe Photoshop / Firefly | 先选中角色区域，再选择 Object/Whole Image Reference，放入或替换选区 | 选区保护未编辑背景；合作模型当前可传 Flux 最多 3 张或 Gemini 最多 8 张参考 | 当某一个角色失败时，只修该区域，不重新生成整个场景 |
| Ideogram | 保存 Character Reference；已有画面可 Remix，单个角色可用 Magic Fill + mask 替换 | Character Reference 与 Remix/Canvas/Mask 联动，以区域为单位保留背景和构图 | “先生成整体、再定向修人”是正式产品路径，不应只依赖一次生成成功 |
| Scenario | 可把多个独立角色图在 Edit with Prompts 中合成，也可训练各角色模型并合并成 Multi-LoRA，最后在 Canvas 分角色 mask 修复 | 官方明确提示不同角色特征仍可能互相污染；修复时把另一个角色模型影响降为 0 | 对大量长期复用角色，训练/合并模型是高阶路线；局部 mask 仍是最终保险 |
| Freepik Custom Character | 上传多张角色图片训练可复用 Custom Character | 使用角色 LoRA；官方建议约 8～25 张、不同角度和表情的高质量训练图 | 适合长期核心 IP，不适合当前只有少量参考、希望立即出图的所有章节角色 |
| Leonardo | 分别选择 Character、Style、Content Reference 及 Pose/Depth/Edge 控制 | 不同参考职责有独立强度通道 | 角色身份、场景内容、构图/姿态应分开表达，不应混在一个无语义图片数组里 |

### 4.1 市场共识与未公开部分

市面产品并没有统一使用“一张多人板”。官方资料能确认的是四种互补路线：

1. **资产化**：Boords、LTX、Vidu 让角色、场景、道具成为可命名、可复用实体。
2. **原生多参考**：Runway、Vidu、OpenAI、Seedream 在模型容量内分别传角色和场景。
3. **参考打包**：Midjourney 在只有一个 Omni Reference 时，官方建议把多个人放进同一张参考图。
4. **多步修复或训练**：Adobe、Ideogram、Scenario 使用 Canvas/Mask；Scenario、Freepik 对长期角色进一步使用 LoRA/Multi-LoRA。

Boords、LTX 等完整产品没有公开其底层究竟是拼图、embedding、模型训练还是按 provider 动态选择，因此不能把“产品支持多角色”反推成“它内部一定使用多人参考板”。可以借鉴的是它们把技术限制藏在资产与工作流编译层之后。

## 5. 行业共同方法

### 5.1 可复用实体先于生成请求

角色、地点、道具、画风和构图是项目资产；模型请求只是这些资产在某个镜头上的一次编译。

### 5.2 参考职责分开

成熟系统区分：

- identity：角色/道具身份。
- environment：场景地标、空间和光线。
- composition：站位、前后层次、姿态和视线。
- style：线稿、配色、材质和渲染方式。

这些职责可以来自不同图，也可以在上游确定性合成为更少的参考板。

### 5.3 多角色打包是容量策略，不是固定人数规则

AI漫游已有角色视觉资产，不需要重新生成角色。引用编译应按“完整条件能否在当前 Provider 容量与输入像素预算内保持可读”决定是否打包：

1. 零角色：直接使用场景参考；不能因为只有一张参考就退化为纯文字。
2. 一个角色：角色单人身份锚点 + 场景图。
3. 两个角色：容量允许时优先两个单人身份锚点 + 场景图；Grok 恰好占满 3 个槽位，不需要为了统一而降低身份分辨率。
4. 三个及以上角色：容量不足时，把全部角色或次要角色确定性合成多人身份板；场景仍保留为视觉输入。
5. 如果合成后单个角色低于当前 Provider 经 A/B 验证的最小可读尺寸，不能继续往一张板里塞，应切换独立多参考、分层编辑、Provider 或拆分镜头。

多人身份板必须由当前已锁定角色资产机械拼接，不能调用模型重新画；它只改变封装，不改变来源事实。它确定节省图片槽位；只有在合成后总输入像素实际下降时，才可能同步降低图像输入 token/成本，不能对所有 Provider 承诺“必然省 token”。

### 5.4 三类约束需要独立覆盖

| 约束通道 | 回答的问题 | 当前来源 | 更稳的视觉载体 |
| --- | --- | --- | --- |
| `identity` | 画面里是谁 | 角色文字档案、`preview_front`、`final_reference` | 独立单人参考或多人身份板 |
| `environment` | 发生在哪里 | 场景卡、无人场景参考 | 原始场景锚点 |
| `composition` | 谁站哪里、谁对谁做什么 | `coreAction`、`comic.composition` | 结构化站位计划、场景构图板或已选镜头母版 |

静态多人身份板不应同时假装承担最终构图：角色在板上的排列容易让模型复制成排队、拼贴或设定表。Provider 还有槽位且镜头调度复杂时，应把第三槽用于构图/站位，而不是重复输入同一身份信息。

### 5.5 高一致性需要区域编辑

一次全画面生成很难同时锁定多张脸、多套服饰、一个场景空间和复杂互动。高保真路径应先选出场景和构图正确的整体镜头，再只 mask 失败角色所在区域，输入该角色的单人身份锚点进行修正；已经正确的场景和其他角色不得重新全图生成。

## 6. AI漫游推荐方案

### 6.1 Provider 无关的镜头视觉需求

候选图任务应先冻结完整需求，而不是先按 provider 裁图：

```json
{
  "characters": [
    { "characterId": "A", "visualId": "A-v3", "screenRegion": "left", "depth": "foreground", "importance": "focal", "actionRole": "initiator", "required": true },
    { "characterId": "B", "visualId": "B-v2", "screenRegion": "center", "depth": "midground", "importance": "support", "actionRole": "recipient", "required": true },
    { "characterId": "C", "visualId": "C-v5", "screenRegion": "right", "depth": "background", "importance": "support", "actionRole": "observer", "required": true }
  ],
  "scene": { "visualId": "scene-v4", "required": true },
  "composition": {
    "sourceText": "A 在左前景，B 位于中景，C 在右后景观察",
    "mappingConfidence": "high",
    "layoutGuideAssetId": null
  },
  "style": { "styleAssetId": null }
}
```

当前 `Shot` 只有自由文本 `comic.composition`。第一阶段可以保留文字并把无法可靠解析的站位标成 `mappingConfidence=low`；不能凭空伪造结构化位置。后续要稳定生成构图板，应在分镜或候选准备层增加可校对的轻量 `ShotStagingPlan`，至少保存逐角色画面区域、前后层次、大小、朝向和动作职责。

### 6.2 镜头参考包不是一张固定大拼图

推荐把完整 `ShotReferenceBundle` 拆成可独立编译的语义载体：

| 载体 | 职责 | 物理来源 |
| --- | --- | --- |
| `direct_identity` | 单个重点角色的最高身份清晰度 | 当前锁定单人身份锚点 |
| `cast_identity_board` | 在有限槽位中覆盖多个角色身份 | 多个单人锚点的确定性合成 |
| `scene_anchor` | 场景地标、空间、材质和光向 | 当前无人场景参考 |
| `scene_layout_guide` | 把场景和角色站位/景深绑定 | 场景锚点加可忽略的站位草图；仅在结构化站位可用时生成 |
| `shot_master` | 已经正确的整体构图与场景，供后续局部修正 | 用户选中的候选图 |

前三类用于首轮生成；`shot_master` 用于第二阶段修复。Provider 编译器根据容量选择其中一部分，而不是要求每家都接收完全相同的图片数组。

不建议在 Grok 仍有 3 个槽位时，把“全部角色 + 场景 + 构图”再压成一张巨型拼图：这会混淆每个区域的职责，进一步压低单人和场景有效像素，并增加模型复制拼贴排版的概率。除非某个 Provider 只有一个图片入口，否则至少保持“身份”和“场景/构图”两张物理参考分离。

### 6.3 自适应编译规则

| 镜头主体 | Grok（当前最多 3 张） | OpenAI / Seedream（容量足够时） |
| --- | --- | --- |
| 0 个角色 | 直接传场景；修复当前“单参考被省略”策略 | 直接传场景 |
| 1 个角色 | 单人角色 + 场景；复杂站位可用第 3 槽 | 单人角色 + 场景 + 可选构图板 |
| 2 个角色 | A 单人 + B 单人 + 场景；不默认合板 | A 单人 + B 单人 + 场景 + 可选构图板 |
| 3 个及以上、角色同等重要 | 全员身份板 + 场景 + 可选构图板 | 容量和输入预算允许时独立直传；否则全员身份板 + 场景 + 构图板 |
| 3 个及以上、有明确焦点 | 焦点角色单图 + 其余角色身份板 + 场景构图板 | 焦点角色单图 + 其余角色独立图或身份板 + 场景/构图 |
| 单板已无法保持逐人可读 | 切分层编辑、换 Provider 或阻止一次生成 | 切分层编辑或拆分镜头；不继续压缩 |

“单板已无法逐人可读”不应写成一个跨模型固定人数。编译器需要按身份板成图尺寸、角色单元最小像素、景别和角色重要度判断；阈值必须来自真实 A/B。背景群众应使用一个 `group` 视觉主体，不把每个无名路人当成必须锁定的独立角色。

### 6.4 多人身份板合同

多人身份板不是项目级新角色资产，而是可缓存的任务级派生产物：

- 来源：本镜头锁定角色的单人 `preview_front`。`final_reference` 用于出图准备批准与服装/多角度事实，不直接进入候选编辑；新 final 优先使用其 `sourceVisualId` 指向的精确 preview。旧空来源资产仅在同角色存在唯一一张版本更早且仍可用的 preview 时兼容，零张或多张都失败。现有资产既有横向四格也有 2×2 四格，不能靠固定格位或当前指针猜测。
- 选择：只有编译器判定独立参考超出槽位或输入预算时才打包；1～2 人不为“统一形式”强制合板。
- 布局：每个角色只出现一次，统一单元比例、视觉高度和中性背景；使用 `contain` 保留完整来源，不放姓名、编号、格线、水印或剧情场景。
- 绑定：板内顺序和 Prompt 中的角色绑定使用同一个 `characterBindings`；板内排列不是最终镜头站位，Provider 指引必须明确忽略身份板排版。
- 清晰度门禁：每个角色单元必须达到经 Provider A/B 验证的最小可读尺寸；达不到时返回 `requires_layered_workflow`，不能继续缩小。
- 追溯：记录来源 CharacterVisual/Asset、顺序、缩放/留白、背景处理、布局版本、输出尺寸和 `packDigest`。任一来源变化后旧板失效。

### 6.5 场景构图板合同

`scene_layout_guide` 是比“角色板 + 纯文字构图”更强的一层，但不能在当前自由文本无法可靠解析时伪造：

- 使用真实 `scene_anchor` 作为底图，叠加低干扰的站位区域、大小和前后层次，不生成新场景。
- 只在 `ShotStagingPlan` 已由系统可靠生成并允许用户校对时使用；人物身份仍来自独立参考或身份板。
- 不写人物姓名、编号和可复制文字；标记样式、透明度和颜色必须版本化并做污染 A/B。
- Provider 指引明确“保留场景与空间关系，站位标记只用于布局，不得出现在成图”。

如果构图板会被模型复制成色块、轮廓或拼贴，应退回原始场景 + 文字构图，或进入分层编辑；不能为形式完整牺牲成图质量。

同一地点需要跨很多镜头、反打或大幅改变机位时，一张中性远景也不足以证明完整空间。后续可把单张场景资产升级为版本化 `SceneVisualSet`（中性远景、反向/侧向视图、关键地标或简化平面关系），按当前机位选择最相关视图；在此之前不能把“传了一个场景图”夸大成任意机位下的绝对场景一致。

### 6.6 高保真分层路径

对关键三人/多人镜头，推荐的质量优先流程是：

```text
完整视觉需求
  -> 首轮生成多个整体候选
  -> 用户选择场景和构图最正确的一张作为 shot_master
  -> 对失败角色建立局部 mask
  -> 使用 shot_master + 该角色单人身份锚点局部编辑
  -> 必要时逐角色重复，保留每一步来源
```

这种方式比连续全图重生成更能保护已经正确的场景、光线和其他角色。区域编辑尚未在当前候选工作台实现，因此属于后续能力；不能把它写成当前已可用。

### 6.7 Provider 编译后的覆盖证据

`ReferencePlan` 应显式证明每个必需条件由哪个物理输入覆盖：

```json
{
  "strategy": "hybrid_pack_v1",
  "slots": [
    { "order": 1, "role": "direct_identity", "covers": ["character:A"] },
    { "order": 2, "role": "cast_identity_board", "covers": ["character:B", "character:C"] },
    { "order": 3, "role": "scene_layout_guide", "covers": ["scene:scene-v4", "composition:shot-001"] }
  ],
  "omittedRequired": []
}
```

`omittedRequired` 非空时不得创建正式图片任务。Provider 切换后必须重新编译引用计划；不能沿用另一家 Provider 的物理槽位方案。

### 6.8 产品档位

| 档位 | 系统行为 | 用户需要理解的内容 |
| --- | --- | --- |
| 自动（默认） | 按人数、焦点、构图复杂度和 Provider 能力选择直传、身份板或混合方案 | 只显示“3 个角色、场景、站位均已锁定/哪项有风险” |
| 质量优先 | 尽量保留独立关键角色参考，必要时进入分层修复 | 成本和时间更高 |
| 修复角色 | 基于已选候选只修改指定角色区域 | 选择要修的角色和区域 |
| 核心 IP | 真实失败率证明值得后，再评估 LoRA/Multi-LoRA/ID Adapter | 训练数据和 Provider 绑定更重 |

技术上的图片槽位、角色板和 Provider 上限不应暴露成普通用户必须手工处理的工作。

### 6.9 生成前和生成后门禁

生成前：

- 每个 `required=true` 的角色和场景都必须出现在 provider 引用计划的来源证据中。
- 参考压缩只能改变封装形态，不能删除必需条件。
- 场景参考资产存在时不能退回纯文字；不存在时必须明确显示“场景未视觉锁定”，不能声称场景一致。
- 页面展示“角色 A/B/C + 场景 + 站位：已直接引用/已打包引用/仅文字约束/需分层处理”。

生成后：

- 记录所有原始条件资产 ID、打包资产 ID、provider 实际输入顺序和编译模式。
- 对三个角色分别做“存在/身份/服装/站位”检查，对场景做“地标/空间/光向”检查。
- 校验不通过时进入定向区域修复或让用户选择其他候选，不自动将失败图定稿。

## 7. 2026-07-19 P0 实施状态与剩余缺口

已完成：

1. 删除 Grok 超限固定保留“两个角色 + 场景”的裁剪策略；成功计划不再允许必需角色或场景省略。
2. Grok 单参考已按官方 JSON `image` 走单图编辑；单图比例跟随输入的限制写入 warning，不再以丢图换比例。
3. 新增 `candidate_reference_plan_v1` 与逐槽覆盖证据；文件兼容候选元数据和 DB-only Candidate Asset metadata v2 均保存原始来源、物理顺序、派生摘要和 `omittedRequired=[]`。
4. 新增 PNG/JPEG/WebP 真实解码、损坏图片门禁和确定性 `cast_identity_board_v1`；DB-only 候选任务在 `final_reference` 预检证据之外冻结 ready 的 `preview_front` 单人锚点，新 final 记录并优先沿 `sourceVisualId` 使用精确来源，不从布局不稳定的四视图裁图；容量足够时仍独立直传，容量不足时只合并角色、场景保持独立。
5. 当前无结构化构图时明确记录 `compositionCoverage=prompt_only`，未伪造场景构图板或站位已视觉锁定。

仍未完成：

1. 当前“进入任务规格的引用全部必需”是 P0 隐式合同，还没有独立、可被 UI 检查的 `ShotVisualRequirementSet`，也没有焦点角色、逐角色站位、动作职责和背景群体等结构化条件。
2. P0 身份板使用固定 640×896 单元和最多 12 人的技术打包门；它只避免继续缩小，不是经过真实模型 A/B 得出的质量人数上限。焦点角色单图 + 其余角色板也因缺少可靠焦点字段暂未启用。
3. `comic.composition` 仍是自由文本，不能可靠生成逐角色视觉站位图；需要先定义可校对的 `ShotStagingPlan`。
4. 候选工作台还没有展示实际 `ReferencePlan`，用户看不到“独立引用/身份板/仅文字构图”的真实状态。
5. 当前没有基于已选图的局部 mask 修复，因此关键多人镜头的高保真分层路径尚未落地。
6. 新策略尚未运行固定语料的真实 Provider A/B，不能把“全部条件已送达”写成“角色和场景一定一致”。
