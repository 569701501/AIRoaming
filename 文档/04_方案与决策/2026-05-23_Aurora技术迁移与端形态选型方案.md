## 1. 结论摘要

AI漫游第一阶段建议采用 **Web 工作台核心 + 本地 NestJS 服务 + 本地 workspace 文件系统**，暂不做纯桌面端优先，也不直接复制 AuroraPlatformWeb 的完整云端沙盒体系。

后续如果需要桌面端，应以现有 Web 核心为主体，再包装 Electron 或 Tauri 桌面壳，而不是重写一套桌面原生 UI。

## 3. 可直接采用的技术与模式

| 技术/模式 | 采用方式 | 原因 |
| --- | --- | --- |
| pnpm workspace | `apps/web`、`apps/server`、`packages/shared` | 支持前后端契约共享，适合 AI 可读工程结构 |
| Vue 3 + Vite + Pinia | 作为 Web 工作台前端 | 分镜、素材候选、排版、任务中心都适合响应式 UI |
| Tailwind + reka/shadcn 风格组件 | 作为基础 UI 体系 | 组件可组合，适合构建密集型生产工具 |
| NestJS 模块化后端 | 作为 API 与任务编排层 | 便于拆分 Project、Story、Shot、Asset、Task、Export 模块 |
| Prisma | 作为数据模型事实源 | 便于 AI 阅读 schema，并支持 SQLite 到 PostgreSQL 的迁移 |
| shared package | 放 DTO、枚举、任务协议、路径类型 | 避免前后端字段漂移 |
| 统一 workspace 路径 | 使用 `/workspace/...` 虚拟路径 | 防止前端感知物理路径，方便未来桌面壳或对象存储 |
| MaterialTask 模式 | 改名或泛化为 `GenerationTask` | 支撑故事、分镜、图片、音频、导出等异步任务 |
| SSE 任务事件流 | 用于任务进度、完成、失败、取消 | 比 WebSocket 更轻，适合 MVP |
| 图片 provider adapter | `ImageProvider` 接口隔离具体服务 | 后续可接云端 API、本地模型或 mock provider |
| 任务中心 UI | 展示队列、进度、失败、完成跳转 | AI漫游生成链路长，用户需要稳定反馈 |
| 素材库/候选图面板 | 管理候选图、锁定、废弃、重生成 | 直接对应 AI漫游“分镜到漫画图候选”主链路 |
| 深思熟虑文档流 | 保持任务三件套、Handoff、复核和完成记录 | 已迁入 AI漫游，应成为复杂功能默认工作方式 |

## 4. 改造后采用的技术

| Aurora 技术 | AI漫游处理 | 触发条件 |
| --- | --- | --- |
| PostgreSQL | MVP 先 SQLite，schema 保持可迁移 | 多人协作、云端部署或数据量变大时切换 |
| BullMQ + Redis | MVP 先本地任务表 + 进程内 worker | 任务并发、重试、崩溃恢复要求变高时引入 |
| ProviderCredential/BYOK | 先用本地配置或环境变量 | 多用户、团队、成本归属出现后再产品化 |
| Sharp 图像处理 | 可用于尺寸、格式、透明裁剪 | 图片候选管理和导出开始后引入 |
| FFmpeg | 用于基础轻漫剧导出 | M4 或视频导出进入实现时引入 |
| 预览运行时 | 只保留导出预览和视觉验收思想 | 需要可交互预览或自动截图回归时引入 |
| Docker 沙盒 | 暂不引入 | 只有需要不可信代码执行或隔离 agent runtime 时再评估 |
| OpenCode 对话运行时 | 迁移最小闭环 | 用户已决定第一阶段采用 OpenCode 支撑项目对话框；只迁移 headless 对话、流式事件、模型选择和 provider 配置经验 |
| OpenCode tool bridge | 后置，只保留“工具回调与任务协议”思想 | 当 AI 代理需要直接触发生成任务时再实现 |

## 5. 暂不采用的内容

| 内容 | 暂缓原因 |
| --- | --- |
| 完整 Docker sandbox + browser node + preview runtime | AI漫游 MVP 不需要运行用户代码，过早引入会增加部署和调试成本 |
| 账务、积分、计费 ledger | 当前是内部工具，不应让商业化模型污染核心创作链路 |
| 团队、邀请、权限、多人面板 | 第一阶段目标是单人创作闭环 |
| 微信控制、远程运行控制 | 与故事到漫画主链路无关 |
| OpenCode 代理完整执行系统 | 不迁移完整体系；仅迁移对话运行时最小闭环 |
| Aurora 的游戏/Phaser 专用预览逻辑 | AI漫游是漫画与轻漫剧工作台，预览对象不同 |

## 6. 端形态选型对比

| 方案 | 优点 | 缺点 | 适配度 |
| --- | --- | --- | --- |
| 纯 Web/SaaS | 迭代快、协作和部署简单、复用 Aurora 最多 | 大素材、本地 FFmpeg、本地模型、隐私和文件权限较麻烦 | 中 |
| 纯桌面端优先 | 本地文件、离线、FFmpeg、本地模型体验好 | UI/打包/更新/签名/跨平台成本高，难复用 Aurora Web 工作台 | 中 |
| Web 核心 + 本地后端 + 未来桌面壳 | 复用 Aurora 技术，同时保留本地文件和桌面扩展空间 | 后续仍要处理桌面打包和后端进程管理 | 高 |

## 7. 推荐路线

### 7.1 MVP 形态

```text
浏览器 Web 工作台
  -> 本地 NestJS API
  -> Prisma SQLite
  -> 本地 workspace
  -> 本地任务 worker
  -> 云端或本地 AI provider adapter
```

### 7.2 桌面端策略

MVP 不先选 Electron 或 Tauri。先把 Web 核心写成“可被桌面壳包装”的结构：

- 前端不直接操作本地物理路径。
- 所有文件读写走后端 API。
- 所有生成任务走 `GenerationTask` 协议。
- 所有 provider key 不进入前端运行时。
- workspace 根目录可配置。
- 导出和 FFmpeg 通过后端服务执行。

当出现以下任一条件，再进入桌面壳选型：

| 触发条件 | 倾向 |
| --- | --- |
| 需要把 Node/NestJS/FFmpeg 一起打包，追求实现速度 | Electron 优先评估 |
| 需要更小体积、更强原生权限控制，能接受 Rust sidecar 工作 | Tauri 优先评估 |
| 需要多人在线协作和远程访问 | Web/SaaS 优先评估 |

## 8. MVP 工程骨架建议

```text
apps/
  web/                 # Vue 工作台
  server/              # NestJS API + worker
packages/
  shared/              # DTO、枚举、任务协议、路径工具类型
workspace/
  projects/{projectId}/
    source/
    story/
    shots/
    assets/
    exports/
```

## 9. 第一批应实现的技术底座

| 顺序 | 底座 | 产出 |
| --- | --- | --- |
| 1 | monorepo scaffold | web/server/shared 可启动 |
| 2 | Prisma SQLite schema | Project、StoryVersion、Shot、Asset、GenerationTask |
| 3 | workspace path helper | `/workspace` 虚拟路径与物理路径映射 |
| 4 | GenerationTask service | 创建、执行、取消、重试、记录错误 |
| 5 | SSE task stream | 前端可实时看到任务状态 |
| 6 | mock provider | 先跑通故事/分镜/图片任务闭环 |
| 7 | 图片 provider adapter | 接入真实图片生成 |
| 8 | 素材库与候选图面板 | 支持候选查看、锁定、废弃 |

## 10. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| Web-first 后续桌面化困难 | 从第一天开始禁止前端直连物理文件和 provider key |
| 本地任务 worker 崩溃导致任务状态不一致 | 任务表保留 `phase/status/error/attempt`，启动时扫描可恢复任务 |
| SQLite 后续迁移成本 | Prisma schema 避免 SQLite 专有能力，JSON 字段保持清晰契约 |
| AI provider 频繁变化 | provider adapter 与任务输入输出隔离 |
| 过早复制 Aurora 复杂模块 | 每个迁移点必须能服务 M1-M3 主链路 |

## 11. 验收标准

- 新功能实现时能在 `文档/02_架构与契约/生成任务协议.md` 找到任务类型。
- 前端不直接依赖物理文件路径。
- 生成任务均能被记录、查询、取消，并产生完成或失败事件。
- 所有素材可追溯到项目、业务对象和生成任务。
- 桌面端包装决策有明确触发条件，而不是在 MVP 前反复摇摆。
