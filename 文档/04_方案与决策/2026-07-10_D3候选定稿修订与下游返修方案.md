# D3 候选定稿修订与下游返修方案

## 1. 目标

允许用户在候选图已经进入排版或导出后返回更换图片，同时保证：

1. 不静默改变旧布局和旧导出。
2. 用户在确认更换前能看到准确的下游影响。
3. 每次定稿选择、布局和导出都能追溯到对应版本。
4. 运行中的旧任务不能回写覆盖新决定。
5. 普通用户不需要理解 `selected/locked/stale/digest` 等内部术语。

## 2. 当前实现的问题

当前真实路径：

```text
候选 A 已锁定
  -> LayoutPage.placements[].candidateId = A
  -> 用户返回候选图锁定 B
  -> Shot.lockedCandidateId = B
  -> A.status 从 locked 变回 generated
  -> 既有 placement 仍引用 A
```

结果是“镜头当前锁定 B，排版仍使用 A”，没有警告、失效标记或修订关系。

导出后章节进入 `layout_done`，当前锁定接口不接受该状态，用户又无法走正式返修路径。因此现状同时存在“导出前可能静默分叉”和“导出后完全不能返修”两个问题。

## 3. 正式术语

| 用户术语 | 领域术语 | 是否影响下游 | 说明 |
| --- | --- | --- | --- |
| 收藏 | Candidate preference | 否 | 可收藏多张，只帮助比较 |
| 当前定稿 | Current Candidate Lock Revision | 是 | 当前 Shot 给下游使用的正式候选修订 |
| 定稿此图 | Create lock revision | 是 | 第一次把候选定为正式图 |
| 更换定稿图 | Replace lock revision | 是 | 建立新修订，不覆盖旧修订 |
| 来源已更新 | Derived freshness = stale | 是 | 画布格子仍引用旧定稿修订 |
| 历史导出 | Export revision | 否（只读） | 文件仍有效，但不代表当前最新定稿 |

不在普通 UI 暴露 `selected`。如果保留内部 `favoriteAt`，它只表达收藏，不是工作流状态。

## 4. 数据模型

### 4.1 Candidate 是不可变生成结果

Candidate 记录某次任务生成的一张图片。图片、来源任务、prompt digest、模型和参考素材不能被原地覆盖。

推荐内容状态：

```text
generated | rejected | superseded
```

- `selected` 从正式工作流状态移除。
- `locked` 不再作为 Candidate 自身生命周期；是否当前定稿由 Shot 的定稿修订决定。
- `favoriteAt` 或等价偏好字段独立存在，可收藏多张。

### 4.2 CandidateLockRevision

每次定稿或更换定稿都创建不可变修订：

```json
{
  "id": "lockrev_shot007_002",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "shotId": "shot_007",
  "revision": 2,
  "action": "replace",
  "candidateId": "candidate_B",
  "previousRevisionId": "lockrev_shot007_001",
  "reason": "用户更换定稿图",
  "createdAt": "2026-07-10T00:00:00.000Z"
}
```

| 字段 | 规则 |
| --- | --- |
| `action` | `lock/replace/clear`；第一次定稿、更换和取消都留下明确事件 |
| `candidateId` | `lock/replace` 时必填；`clear` 时为空 |
| `revision` | 同一 Shot 从 1 开始单调递增，任何动作都不复用旧 revision |

Shot 保存：

```text
currentCandidateLockRevisionId
```

`lockedCandidateId` 仅在迁移期作为兼容派生字段，完成切换后不再是唯一事实源。`currentCandidateLockRevisionId` 指向最近一次正式决定；如果该修订 `action=clear`，则当前没有可供下游使用的候选，但取消事件本身仍可追溯。

同一 Shot 从 A 改为 B、再改回 A 时，产生 v1(A) → v2(B) → v3(A)，不能重新激活 v1。这样每次用户决定都有明确时间和下游影响。

### 4.3 布局依赖

每个 `PanelPlacement` 至少记录：

```text
candidateId
sourceCandidateLockRevisionId
```

布局修订记录 `sourceLockSetDigest`，代表创建或保存该布局时所有相关镜头的定稿修订集合。计算规则固定为：

```text
sha256(canonicalJson(sortByShotId([
  { shotId, candidateLockRevisionId }
])))
```

`canonicalJson` 使用 UTF-8、固定字段顺序、无多余空白；数组按 `shotId` 升序。不得把更新时间、数据库行顺序或本地路径放入 digest。

格子新鲜度不以批量 UPDATE 作为事实源，而是派生：

```text
current     sourceCandidateLockRevisionId == Shot.currentCandidateLockRevisionId
stale       两者不同
unresolved  旧数据无法映射到定稿修订
```

### 4.4 导出修订

每次正式导出创建新的 `ExportRevision`，绑定：

- `layoutRevisionId`
- `sourceLockSetDigest`
- 导出文件 Asset IDs
- manifest
- 创建时间

导出修订和文件不可修改。新定稿只会让旧导出相对当前项目显示为“历史版本”，不会删除或改写旧文件。

## 5. 用户路径

### 5.1 第一次定稿

```text
打开候选图
  -> 可收藏任意候选
  -> 点击“定稿此图”
  -> 创建 CandidateLockRevision v1
  -> 当前镜头满足进入排版的条件
```

### 5.2 尚未排版时更换

```text
A 是当前定稿
  -> 点击 B 的“更换为定稿图”
  -> 影响检查结果：无下游产物
  -> 创建 v2(B)
  -> A 与 v1 保留历史
```

### 5.3 已有排版草稿时更换

更换前弹窗展示：

- 将建立新的定稿修订，不删除 A。
- 有多少个当前画布格子仍引用 A。
- 哪些布局草稿会显示“来源已更新”。
- 是否存在运行中的布局/导出任务。

确认后：

1. 创建 v2(B)。
2. 旧 layout revision 不修改。
3. 相关 placement 派生为 `stale`。
4. 排版步骤显示“有 N 个格子来源已更新”。
5. 用户在画布逐格或批量执行“替换为当前定稿图”；该动作创建新的 layout revision。

旧布局允许查看和比较，但在未解决 stale 前不能生成新的正式导出。

### 5.4 已有正式导出时更换

确认后：

- 旧 ExportRevision 和文件继续可下载、可追溯。
- 当前项目显示“定稿已更新，最新导出待重新生成”。
- 画布基于新定稿解决 stale 后生成新的 LayoutRevision 和 ExportRevision。
- 素材包可以同时包含历史导出索引，但默认只把最新有效导出标为 current。

### 5.5 取消定稿

V1 允许取消定稿，但使用与更换相同的影响检查：

- 无下游时创建新的 `action=clear` 修订，并让当前指针指向该修订；不能静默把指针置空而不留事件。
- 有布局或导出时，旧产物保留并标记为历史；候选步骤重新阻塞该镜头进入新排版。
- 当前定稿图在替换或取消前不能直接废弃或删除。

## 6. 影响检查与并发控制

### 6.1 影响预览

推荐接口：

```text
POST /api/projects/{projectId}/chapters/{chapterId}/shots/{shotId}/candidate-lock/preview
```

请求：

```json
{
  "action": "replace",
  "candidateId": "candidate_B"
}
```

首次定稿使用 `action=lock`，已有定稿时换图使用 `action=replace`，取消使用 `action=clear` 且不传 `candidateId`。

返回至少包含：

```json
{
  "currentRevisionId": "lockrev_shot007_001",
  "targetCandidateId": "candidate_B",
  "affectedPlacementCount": 1,
  "affectedPlacementIds": ["placement_001"],
  "affectedLayoutRevisionIds": ["layoutrev_001"],
  "historicalExportCount": 1,
  "historicalExportRevisionIds": ["exportrev_001"],
  "activeTaskIds": [],
  "impactDigest": "sha256:..."
}
```

`impactDigest` 固定为以下字段的规范 JSON 哈希：`shotId/currentRevisionId/targetCandidateId/action/affectedPlacementIds/affectedLayoutRevisionIds/historicalExportRevisionIds/activeTaskIds`。所有 ID 数组先去重并按字典序排序，计数字段和展示文案不参与计算。

### 6.2 提交更换

推荐接口：

```text
PUT /api/projects/{projectId}/chapters/{chapterId}/shots/{shotId}/candidate-lock
```

请求：

```json
{
  "action": "replace",
  "candidateId": "candidate_B",
  "expectedCurrentRevisionId": "lockrev_shot007_001",
  "impactDigest": "sha256:..."
}
```

规则：

- 当前修订已变化：`409 CANDIDATE_LOCK_REVISION_CONFLICT`
- 影响集合变化：`409 CANDIDATE_LOCK_IMPACT_CHANGED`
- 目标候选已废弃：`400 CANDIDATE_REJECTED`
- 目标候选不属于该 Shot：`400 CANDIDATE_SHOT_MISMATCH`
- action 与当前状态不匹配：`400 CANDIDATE_LOCK_ACTION_INVALID`
- 目标已是当前定稿：幂等返回当前结果，不新建重复修订。

### 6.3 取消定稿提交

取消使用同一 PUT 接口，提交：

```json
{
  "action": "clear",
  "expectedCurrentRevisionId": "lockrev_shot007_002",
  "impactDigest": "sha256:..."
}
```

`clear` 时不接受 `candidateId`。若当前本来就是 clear，幂等返回当前修订，不重复新增。

### 6.4 事务边界

提交接口必须在同一数据库事务中：

1. 重新读取并锁定 Shot 当前修订指针。
2. 重新计算影响集合和 digest。
3. 校验目标候选与当前状态。
4. 插入下一条 CandidateLockRevision。
5. 更新 `Shot.currentCandidateLockRevisionId`。

事务内不批量改写旧 LayoutRevision、PanelPlacement 或 ExportRevision；它们的新鲜度在事务提交后按来源关系派生。

### 6.5 运行中任务隔离

所有布局、合成、导出和素材包任务 input 必须保存：

```text
sourceLayoutRevisionId
sourceLockSetDigest
```

任务完成时：

- 产物永远登记到任务启动时的来源修订。
- 如果当前 lock set 已变化，任务可以成功，但结果标为 historical/outdated，不能自动成为当前导出。
- 取消是用户体验优化，修订校验才是防止旧任务污染新状态的最终防线。

## 7. 工作流与状态

改变定稿图不应粗暴地把章节状态从 `layout_done` 回退成 `images_done`。单一单调 `Chapter.status` 无法表达“候选仍完整，但布局来源已过期”。

正式新增派生新鲜度：

| 步骤 | 条件 |
| --- | --- |
| 候选图 | 所有需要排版的 Shot 都有当前定稿修订 |
| 排版导出 | 当前 layout revision 的所有 placement 均为 current |
| 素材包 | 引用最新有效 export revision |

换图后：

- 候选图步骤仍为完成。
- 排版导出步骤变为 `needs_update`。
- 素材包等待最新导出。
- 历史布局、导出和素材包仍可查看，不重新定义为失败。

## 8. 数据库目标模型

D7 已确认全量数据库化。D3 至少需要：

| 表/字段 | 作用 |
| --- | --- |
| `Candidate.favoriteAt` | 非权威收藏状态 |
| `CandidateLockRevision` | 不可变定稿、更换与取消历史；`action=clear` 时 candidateId 为空 |
| `Shot.currentCandidateLockRevisionId` | 当前定稿修订指针 |
| `LayoutRevision` | 不可变或可追溯的画布保存修订 |
| `PanelPlacement.sourceCandidateLockRevisionId` | 格子来源修订 |
| `ExportRevision` | 不可变导出快照 |
| `GenerationTask.sourceLockSetDigest` | 长任务输入快照 |

正式约束：

- `CandidateLockRevision(shotId, revision)` 唯一。
- Shot 当前指针必须指向同一 Shot 的修订。
- 当前定稿候选不能被硬删除。
- ExportRevision 只新增，不更新来源修订。

## 9. 旧数据迁移

| 旧数据 | 迁移规则 |
| --- | --- |
| `Shot.lockedCandidateId` 非空 | 为该 Shot 创建 `CandidateLockRevision v1` 并设为当前 |
| Candidate `status=locked` | 迁移为普通生成结果；“当前定稿”由 v1 关系派生 |
| Candidate `status=selected` | 迁移为 `favoriteAt`；不赋予下游权威 |
| Layout placement 的 candidateId 与当前 v1 一致 | 回填 `sourceCandidateLockRevisionId=v1` |
| placement 无法匹配修订 | 标记 `unresolved`，阻止新导出并进入迁移报告 |
| 旧导出 Asset | 建立 imported ExportRevision，绑定可识别的 layout；无法识别时保留历史文件并标记 unresolved |

迁移必须幂等，并输出每个 Shot、placement 和 export 的处理状态。

## 10. UI 方案

候选卡动作：

- `收藏` / `取消收藏`
- `定稿此图`
- 当前候选显示 `当前定稿`
- 其他候选显示 `更换为定稿图`
- 当前定稿不可直接废弃，先更换或取消定稿

影响弹窗不使用内部状态名，使用用户结果语言：

```text
更换后不会删除旧图片和旧导出。
1 个画布格子仍使用旧图，需要回到排版更新。
已有 1 个历史导出将继续保留。
```

排版页：

- 格子显示“来源已更新”。
- 支持“替换当前格”和“替换本章全部过期格子”。
- 批量替换前再次显示数量；不能静默改变用户手工裁切。
- 替换后保留旧 LayoutRevision，并创建新修订。

## 11. 明确不做

- 不自动把 B 填进所有使用 A 的格子并覆盖旧布局。
- 不删除旧导出文件。
- 不禁止用户在导出后返修。
- 不让收藏/草选驱动排版或导出。
- 不只依赖取消任务防止旧结果回写。
- 不用简单回退 `Chapter.status` 代替依赖新鲜度。

## 12. 分阶段实施建议

### D3-A：数据与迁移
- 建立 CandidateLockRevision、当前指针和旧数据迁移。
- 将 `selected/locked` 从 Candidate 内在状态迁出。

### D3-B：定稿与更换 API
- 收藏、第一次定稿、影响预览、更换/取消定稿。
- 乐观锁和 impact digest。

### D3-C：布局依赖与 stale
- placement 绑定来源定稿修订。
- 派生 freshness，阻止未解决 stale 的新导出。

### D3-D：导出修订与任务隔离
- ExportRevision、sourceLockSetDigest、旧任务结果隔离。

### D3-E：前端返修体验
- 候选卡文案、影响弹窗、画布 stale 提示、逐格/批量替换和历史版本入口。

### D3-F：端到端验证
- 覆盖 A→排版→B、A→导出→B、任务运行中换 B、B→A 等真实路径。

## 13. 验收标准

1. 收藏任意候选不会改变排版或导出。
2. 第一次定稿会产生 v1，第二次更换会产生 v2，取消会继续产生 clear 修订，旧修订不被改写。
3. 已有排版草稿时换图，旧 placement 不被静默替换并明确显示 stale。
4. stale 未解决前不能生成新的正式导出。
5. 旧导出文件仍可查看、下载并追溯到旧布局和旧定稿修订。
6. 运行中的旧任务完成后不能成为当前结果。
7. 并发更换使用乐观锁，过期 impact preview 被拒绝。
8. 当前定稿候选不能直接废弃或硬删除。
9. 工作流显示候选已完成、排版需更新，而不是粗暴回退整章状态。
10. 数据迁移可重复执行，异常进入报告，不静默丢失历史。
