# 生成任务协议

## 1. 协议目标

生成任务协议定义所有 AI 和导出任务的统一输入、输出、状态和错误格式。无论后续接云端 API、本地模型还是 FFmpeg，都必须通过任务协议与业务系统交互。

## 2. 统一任务信封

```json
{
  "taskId": "task_001",
  "projectId": "project_001",
  "type": "image_generate",
  "target": {
    "type": "shot",
    "id": "shot_001",
    "chapterId": "chapter_001"
  },
  "input": {},
  "options": {
    "candidateCount": 4,
    "provider": "default"
  },
  "trace": {
    "requestedBy": "user_001",
    "source": "web"
  }
}
```

`target.type` 必须使用 Shared `GENERATION_TASK_TARGET_TYPES` 的 8 个值之一：`project`、`character`、`chapter`、`story`、`shot`、`asset`、`export`、`scene`。凡是处理章节内产物的任务，都必须携带 `chapterId`，避免后续生成结果只挂到项目级而无法追溯到具体章节。

`target.type` 与 `GenerationTaskSource.sourceType` 是两套不同枚举：前者描述任务的 polymorphic routing/owner 目标，后者描述不可变来源；输出真正允许写入哪里由 TaskPolicy 的独立 `writeTargetBinding` 冻结。`story_parse/shot_generate` 的 routing target 都是 Chapter，写目标分别是 Chapter active pending StoryVersion/StoryboardVersion，两个 ID 不得强行相等。`layout_export` 的 routing 与写目标恰好都是 `target.type=export`、`target.id=ExportRevision.id`；`export_revision` 只能出现在 `GenerationTaskSource.sourceType`，不得写入 Shared target 枚举或 `GenerationTask.targetType`。2026-07-22 接受的 `layout_compose` routing target 是 Chapter，任务只写来源密封的规划输出，不能直接写 `LayoutWorkingCopy`、`LayoutRevision` 或 `ExportRevision`；apply 必须由 Layout application 在重新校验来源和 Working Copy CAS 后独立完成。

当前已强制 `chapterId` 的章节作用域任务：

```text
story_parse
shot_generate
shot_prompt_generate
image_generate
layout_compose
layout_export
```

`layout_compose` 已同步进入 Shared 枚举、章节作用域 allowlist、TaskPolicy、worker、恢复测试和 API；它的 routing target 是 Chapter，不能直接写 Layout Working Copy 或正式版本。

创建上述任务时，`target.chapterId` 必须存在。`input.chapterId` 建议同步传入；如果省略，服务端会按 `target.chapterId` 规范化写回任务输入；如果传入但与 `target.chapterId` 不一致，服务端必须拒绝创建任务。

`character_reference_generate` 是项目级任务，目标是 `Character`，不强制 `chapterId`。它可以记录来源章节或来源剧本大纲，但输出必须挂到项目级角色库和项目级 `Asset(reference image)`，不能挂到某个章节候选图目录。

`scene_reference_generate` 是章节场景参考图任务，目标类型必须是 `scene`，并携带场景所在的 `chapterId`。当前任务由章节场景专用 API 受控创建，不通过通用任务入口直接构造；输出挂到章节级场景卡和章节级 `Asset`，不能误挂为项目级共享场景。Shared 的 `CHAPTER_SCOPED_GENERATION_TASK_TYPES` 当前只约束通用任务入口的 6 类任务，因此不能据此省略场景任务自己的章节校验。

图片生成 provider 配置：

- 当前支持 `openai`、`doubao`、`grok`、`runware` 四类图片 provider，对应设置页 `openaiImageProvider`、`doubaoImageProvider`、`grokImageProvider`、`runwareImageProvider`，由 `activeImageProvider` 决定当前生效 provider。
- OpenAI 图片默认模型为 `gpt-image-2`；豆包图片默认模型为 `doubao-seedream-4-5-251128`；Grok 图片默认模型为 `grok-imagine-image-quality`；Runware 无参考草稿默认模型为 FLUX.1 Schnell `runware:100@1`。
- `baseUrl` 来自非秘密 provider 配置；图片 `apiKey` 由 NestJS 后端 `ImageCredentialStore/SecretStore` 在运行时读取，不复用 OpenCode 文本模型 key，也不返回前端。
- OpenAI、豆包、Grok 的 `baseUrl` 是最终 API 前缀；后端只移除末尾 `/`，再拼接 `/images/generations` 或 `/images/edits`，不自动追加 `/v1`。Runware 的 `baseUrl` 是完整任务入口，默认 `https://api.runware.ai/v1`。
- Grok 官方默认前缀为 `https://api.x.ai/v1`；如果用户使用 Grok 中转，设置页必须填写中转后的最终 API 前缀。
- Grok 文生图走 JSON `POST /images/generations`，使用 `aspect_ratio`、`resolution` 和 `response_format=b64_json`；Grok 图生图走 JSON `POST /images/edits`，参考图以 `data:<mime>;base64,...` 的 `image.url` 传入，不使用 OpenAI SDK 的 multipart `images.edit()`。
- Grok 文生图、单图编辑和多图编辑必须显式发送同一 `resolution`。运行配置 `GROK_IMAGE_RESOLUTION` 只允许 `1k|2k`，未配置时默认 `1k` 以控制日常制作与测试成本；非法值必须在联网前失败。该参数是 Grok Provider 成本档，不属于候选任务的 `requestedSize/sizePolicyVersion`，不得参与任务来源摘要或冒充 OpenAI/豆包的像素尺寸设置。
- Runware 使用 JSON 任务数组调用 `POST https://api.runware.ai/v1`，任务类型固定 `imageInference`，使用 Bearer 认证。Schnell/FLUX.1 Dev 尺寸规范化到 `128..2048` 且为 64 的倍数；FLUX.2 Dev 尺寸规范化到 `512..2048` 且为 16 的倍数；无效尺寸在联网前失败。
- Runware 无参考生成使用设置中的草稿模型，默认 Schnell `runware:100@1` 且 4 steps；单图 `editImage` 固定使用 FLUX.2 Dev `runware:400@1`，通过 `referenceImages` 传入挑中的草稿，并以 28 steps、`CFGScale=4` 做精修。
- Runware 候选图一旦存在角色或场景参考，固定升级为 FLUX.1 Dev `runware:101@1` + FLUX IP-Adapter `runware:56@1`。`candidate_reference_plan_v1` 编译出的每个物理槽位都必须进入 `guideImages`；不得为省成本静默丢弃必需来源。
- 当前 Runware 接入不包含 mask/inpainting、FLUX Fill、LoRA 训练/管理和 ControlNet 页面；这些能力需要后续独立的编辑器、素材与任务契约，不能伪装成现有单图/候选图设置。
- 文本模型 key 的权威存储是 OpenCode 本地 auth；图片模型 key 的权威存储是后端 SecretStore。图片 key 不得写入 SQLite、普通 workspace JSON、文档、Git、任务输入输出、artifact、导出或错误日志。
- file mode 当前仍使用两条本地进程内 Promise 串行队列：`ImageCandidateService.imageQueue` 生成候选图，`CharacterReferenceService.characterReferenceQueue` 生成角色/场景参考图；DB mode 已由 `PersistentTaskRepository` + `PersistentTaskRecoveryService` 持久化，四类 G2 任务均由 `PersistentTaskWorkerService` 执行。file-mode 兼容 worker 与 DB-mode worker 暂不合并为第二套事实源。

暂不强制单个 `chapterId` 的任务：

| 类型 | 原因 |
| --- | --- |
| `asset_package_export` | 可按项目导出，也可携带多个 `chapterIds` 导出章节子集 |
| `tts_generate` / `video_export` | 属于 P0.5 轻漫剧链路，等视频草稿模型接入后再决定是否强制章节作用域 |

### 2.1 下游任务来源快照（D3 接受目标）

凡是读取定稿候选、布局或导出结果的长任务，创建时必须把来源修订固化到 input，不能在任务完成时重新读取“当前指针”并把旧结果冒充为新结果。

```json
{
  "source": {
    "layoutRevisionId": "layoutrev_002",
    "lockSetDigest": "sha256:...",
    "candidateLockRevisionIds": [
      "lockrev_shot001_003",
      "lockrev_shot002_001"
    ]
  }
}
```

适用任务至少包括：布局合成、正式导出、素材包导出，以及以后所有以当前定稿图为输入的视频或音频合成任务。

任务回写规则：

1. 产物永远登记到启动时的来源修订。
2. 回写前重新计算当前来源 digest；若已变化，任务仍可成功，但结果标记为 `historical`，不得更新 current 指针。
3. `cancel` 只改善用户体验；供应商请求可能已经在运行，因此来源修订校验是防止旧结果污染当前状态的最终门禁。
4. 缺少来源快照的旧任务只能迁移为 `legacy_unresolved` 历史记录，不能把原记录重试为新任务；需要重新生成时必须创建新的 runtime task，并绑定当前有效来源。

DB-only runtime 的规范化 `inputJson` 根对象统一包含 `sourceProjection: TaskSourceProjectionV1`，sources 使用 `role/order/sourceType/sourceId/sourceDigest`；sourceType 是 snake_case registry token。该数组与 append-only `GenerationTaskSource` 在同一创建事务逐项投影并 seal，`GenerationTask.sourceDigest` 是 sourceProjection 的 JCS digest。canonical token/owner/digest 映射见 `文档/04_方案与决策/2026-07-11_G1数据库Schema实施契约.md` 10.4.1；旧 PascalCase model 名不作为持久 sourceType。

### 2.2 D75 持久执行信封（接受目标，F2～F4 已实现 G2 任务闭环）

`GenerationTask` 是任务排队、生命周期和当前执行权的唯一事实源。除第 2 节业务信封外，持久执行至少包含以下字段：

```json
{
  "status": "queued",
  "attempt": 0,
  "maxAttempts": 3,
  "nextRunAt": "2026-07-10T12:00:00.000Z",
  "leaseOwnerId": null,
  "leaseExpiresAt": null,
  "heartbeatAt": null,
  "cancelRequestedAt": null,
  "idempotencyKey": "image_generate:shot_001:sha256:...",
  "sourceDigest": "sha256:...",
  "concurrencyKey": "image-provider",
  "needsReview": false
}
```

`TaskAttempt` 每次 claim 新增一条记录；运行结束时只允许一次性写入 `finishedAt/outcome/error/artifactRefs`，终结后不可变：

```json
{
  "id": "attempt_001",
  "taskId": "task_001",
  "attemptNo": 1,
  "workerId": "worker_local_001",
  "startedAt": "2026-07-10T12:00:00.000Z",
  "finishedAt": null,
  "outcome": null,
  "error": null,
  "artifactRefs": []
}
```

正式规则：

1. 同一 NestJS 进程运行 worker；任务入库后主动唤醒，同时用数据库扫描兜底。进程内只可保存唤醒信号与当前 AbortController，不能保存权威队列。
2. worker 在短事务中原子 claim `queued/retrying` 任务并写 lease；provider 网络调用、文件写入、哈希和渲染在事务外完成。运行期间按约定刷新 `heartbeatAt/leaseExpiresAt`。
3. 执行语义为 at-least-once。每种任务必须定义稳定 `idempotencyKey`、来源 `sourceDigest`、已有产物检查和结果唯一约束；key 只能在创建事务中由已冻结 Task 字段/strict input 字段按注册表 placeholder binding 计算一次，replay 不得从可变 current/pending pointer 重算。重复执行不得产生第二份正式回写或覆盖新的 current 指针。
4. 服务启动或定时恢复扫描过期 `running` lease。只有明确可安全重放的任务才进入 `retrying`；无法确认外部副作用的任务进入 `failed`，错误码为 `WORKER_INTERRUPTED` 且 `needsReview=true`。
5. `queued/retrying` 任务可直接原子进入 `cancelled`。`running` 任务只先写 `cancelRequestedAt` 并触发协作 AbortSignal；worker 确认停止后才进入 `cancelled`，不能在外部调用仍继续时提前显示终态。
6. provider 无法真正取消或返回迟到结果时，worker 仍须检查 `cancelRequestedAt` 与 `sourceDigest`；迟到结果可以登记为诊断证据，但不能更新正式 current 关系。
7. V1 所有图片 provider 任务使用 `concurrencyKey=image-provider` 且并发上限为 1；本地轻量导出可定义独立通道，不能再由业务服务各自维护 Promise 队列。
8. 重试只适用于明确可重试错误，使用有限 `maxAttempts`、`nextRunAt` 与 backoff；每次尝试追加 `TaskAttempt`，终结后不得覆盖旧 attempt。

状态迁移：

| 当前状态 | 触发 | 下一状态 | 约束 |
| --- | --- | --- | --- |
| `queued` | claim 成功 | `running` | 同事务写 lease、attempt 与新 TaskAttempt |
| `retrying` | 到达 `nextRunAt` 且 claim 成功 | `running` | 必须未取消且未超过 maxAttempts |
| `running` | 当前 attempt 成功且来源仍匹配 | `succeeded` | 幂等登记结果并清除 lease |
| `running` | 可重试错误 | `retrying` | 结束当前 attempt，计算 backoff |
| `running` | 不可重试错误或不安全中断 | `failed` | 保留错误；不安全中断标记 needsReview |
| `queued/retrying` | 用户取消 | `cancelled` | 原子取消，不再被 claim |
| `running` | worker 确认协作中断 | `cancelled` | 必须先有 cancelRequestedAt |

首版不引入 Redis/BullMQ 或多进程 worker。多服务实例、远程 worker、持续任务积压或跨机器扩展出现时，再评估 PostgreSQL、BullMQ/Redis 与 Outbox；换队列也不取消本节的幂等和来源校验要求。

G2-F2～F4 已将 `claimToken` fencing、显式 `TaskConcurrencySlot`、Attempt、heartbeat、finish/retry/recovery 和 source projection seal 接到 DB runtime；四类 G2 provider 输出均在同一事务经 applicability 与目标约束后写入。当前 Prisma 6.19.3 不依赖 partial-index preview 来保证图片并发 1。图片结果采用 staged Asset→ready 与 Candidate 追溯，迟到结果不改 current lock；真实 provider smoke test、独立 Outbox consumer 和旧任务 importer 仍后置。详见 `文档/05_执行与记录/任务记录/2026-07-12_G2-F4-ImageTaskRuntime/`。

G2 已采纳目标进一步统一上游任务：`story_parse` 的 `GenerationTask.targetId=Chapter.id`，另按 `writeTargetBinding` 将 `input.expectedTargetId` 绑定 active pending StoryVersion；`shot_generate` 同样以 Chapter 做 routing target，另绑定 active pending StoryboardVersion。两者的幂等模板都使用创建时已冻结的 `{expectedTargetId}`，不使用也不动态读取 `pendingStoryVersionId/pendingStoryboardVersionId`。前者来源是 current ScriptVersion，后者来源是 current StoryVersion；Preflight/候选任务绑定 current Storyboard、角色/场景视觉和风格的聚合 SourceSnapshot。任务创建前执行 `NewWorkGate`，完成时执行 `TaskApplicabilityGuard`，同时比较 claimToken、active pending write target、write target/pending 行自身的 `expectedTargetRowVersion`、current 来源 ID 和 sourceDigest；Chapter.rowVersion 只用于 Chapter 命令 CAS，不能冒充 pending target rowVersion。dirty/pending Working Copy 会阻止新任务；迟到结果可以 `succeeded + applicability=historical`，但不能修改 active pending/current。精确字段见 `文档/04_方案与决策/2026-07-11_G2版本来源与Freshness契约字典.md`。

### 2.3 D76 旧任务历史信封（接受目标，未实现）

旧任务来源记录与 D75 可执行状态机分层：

| `recordKind` | `provenanceStatus` | 执行语义 |
| --- | --- | --- |
| `runtime` | `complete` | 新系统正常任务，可按 D75 状态机执行 |
| `legacy_imported` | `complete/partial` | 旧 artifact 能证明完整或部分历史，只读、不可执行 |
| `legacy_stub` | `reference_only/partial` | 只能证明原 taskId 被引用，只读、不可执行 |

`legacy_stub` 示例：

```json
{
  "id": "legacy_task_001",
  "recordKind": "legacy_stub",
  "provenanceStatus": "reference_only",
  "status": null,
  "retryDisabled": true,
  "maxAttempts": 0,
  "importSource": "workspace",
  "importedAt": "2026-07-10T12:00:00.000Z",
  "observedEvidence": {
    "schemaVersion": 1,
    "artifactStatus": "missing",
    "candidateIds": ["candidate_001"],
    "assetIds": ["asset_001"],
    "sourceFiles": [
      {
        "storageKey": "projects/project_001/chapters/chapter-001/candidates.json",
        "sha256": "sha256:..."
      }
    ]
  }
}
```

强制规则：

1. Candidate/Asset 保留原 taskId 外键；不得用散落的 `legacySourceTaskId` 字符串代替统一关系。
2. worker claim 查询必须显式限定 `recordKind=runtime`；`legacy_imported/legacy_stub` 禁止 claim、取消、重试和新增 TaskAttempt。
3. `legacy_stub.status=null`。未知 input/output/error/provider/attempt/startedAt/finishedAt 保持空；文件存在、Candidate 状态和文件时间不能推断任务终态。
4. 完整旧 artifact 只导入其能证明的字段；如果原终态没有直接证据，状态仍为空。
5. `observedEvidence` 是带 schemaVersion 的审计文档，不是可执行 input/output；其中的每条路径、摘要和引用都必须来自导入扫描。
6. 导入按原 taskId 幂等；`reference_only -> partial -> complete` 只能随更强原始证据单向提升。证据冲突进入 MigrationReport，不静默覆盖。
7. 用户要重新生成旧产物时，创建新的 runtime task，并在新任务 input 中记录来源 legacy taskId；不得“重试”历史记录。

## 3. 统一任务输出

```json
{
  "taskId": "task_001",
  "status": "succeeded",
  "applicability": "current",
  "outputs": [],
  "usage": {
    "provider": "default",
    "model": "unknown",
    "inputTokens": 0,
    "outputTokens": 0,
    "cost": null
  },
  "warnings": []
}
```

`applicability` 适用于有来源修订的任务：`current` 表示仍匹配当前依赖，`historical` 表示任务成功但来源已更新，`legacy_unresolved` 表示旧任务缺少足够来源信息。它不替代 runtime 任务自身的 `queued/running/succeeded/failed/cancelled` 生命周期；legacy stub 没有可执行生命周期。

## 5. 任务类型总表

| 类型 | 输入 | 输出 | MVP |
| --- | --- | --- | --- |
| `character_reference_generate` | 项目角色 + 角色层级 + 外貌/风格提示词 | 角色参考图 Asset | 是 |
| `scene_reference_generate` | 已确认章节剧情结构中的场景卡 + 可选提示词 | 场景背景图 Asset + 回写后的 `scene.referenceAssetId` | 是 |
| `story_parse` | 当前章节剧本 | 结构化剧情 JSON | 是 |
| `shot_generate` | 用户已确认的当前章节结构化剧情 | 分镜骨架 + 自动整理后的详细候选图单帧说明；整体写入待确认分镜 | 是 |
| `shot_prompt_generate` | 已确认分镜 + 已确认出图准备 + 当前可见三段草稿 + 角色/场景/风格 | 用户按需触发的单镜返修建议；兼容保留冻结图片提示词 | 是 |
| `image_generate` | 分镜提示词 + 已确认出图准备 + 参考图 | 候选图片 Asset | 是 |
| `layout_compose` | 当前 StoryboardVersion、完整 CandidateLockRevision/Asset 集、字体/样式策略、可选 Working Copy 与保护范围 | 初次 `LayoutDocumentV2` 或可预览 Editor Command Batch + 质量报告；不直接写正式版本 | 是（accepted target） |
| `layout_export` | 当前且来源完整的 LayoutRevision + 规范 PublicationProfile + preflight digest | 一个 `layout_publication` ExportRevision + 页漫 PNG/可选 PDF 或条漫 PNG 切片/条件长图 Asset | 是 |
| `tts_generate` | 文本 + 声音配置 | 音频 Asset | P0.5 |
| `video_export` | 图片序列 + 字幕 + 音频 | MP4 Asset | P0.5 |
| `asset_package_export` | 项目范围和导出选项 | ZIP/文件夹 Asset | 是 |

G2 目标下，“当前章节剧本/结构化剧情”必须解释为：current 正式版本来源链为 current，且更上游没有 dirty Working Copy 或 active pending；不能退化为读取 Chapter 当前文本字段或更新时间。

### 5.1 character_reference_generate

角色库和出图准备使用的角色参考图生成任务。它用于自动生成角色图，也用于基于当前角色图生成角色定稿图。

### 输入（DB API 客户端语义）

```json
{
  "characterId": "char_hero",
  "referenceKind": "final_reference",
  "sourceReferenceAssetId": "asset_char_preview_001",
  "model": "gpt-image-2",
  "prompt": "角色定稿图提示词",
  "image": {
    "size": "3072x1536",
    "quality": "high",
    "outputFormat": "webp"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `characterId` | string | 项目级 `Character` ID |
| `referenceKind` | enum | `preview_front/final_reference` |
| `sourceReferenceAssetId` | string | `final_reference` 必须使用已确认的 `preview_front` 资产作为图片参考输入 |
| `model` | string | 第一版固定使用 `gpt-image-2` |
| `prompt` | string | 后端根据项目类型、作品名、题材标签、漫画形式、美术风格、角色身份信息、用于 AI 生图的形象描述 / prompt 和用户要求生成的 provider prompt |
| `image.size` | string | `final_reference` 推荐 `3072x1536`；`preview_front` 推荐竖版尺寸 |
| `image.outputFormat` | enum | 推荐 `webp` |

`referenceKind` 规则：

- 所有角色进入项目角色库后，后端会为缺少预览图且没有运行中任务的角色补排 `preview_front`。
- 用户触发 `生成定稿` 时，系统内部自动使用当前可用的 `preview_front` 作为参考生成 `final_reference`；普通 UI 不要求用户先点击“确认预览”。
- 生成 `preview_front` 和 `final_reference` 时，prompt 必须明确这是漫画/条漫/漫剧制作项目，`dark_realistic`、`semi_realistic`、`japanese_realistic` 只能解释为漫画写实或半写实，禁止生成真人照片、真人演员定妆照、摄影棚肖像、电影剧照、cosplay 照片或 3D 渲染。
- 生成 `final_reference` 时，后端必须读取 `Character.previewReferenceAssetId` 对应的图片文件，并通过图片编辑/图片参考能力生成定稿图；禁止只用文字 prompt 重新文生图。
- DB-only 新 `final_reference` 的 `CharacterVisual.sourceVisualId` 必须记录本次实际使用的 preview Visual，不能只记录一个可能变化的 Character 当前指针。
- `chapter` 默认只生成 `preview_front`，不阻塞剧情结构；如果该角色在当前章多次出镜、有台词、近景或影响剧情，出图准备阶段应补 `final_reference` 或确认可用参考图；长期复用时可提升为常驻。
- `extra` 默认只生成 `preview_front`，不自动生成 `final_reference`。
- 已有同角色同 `referenceKind` 的 `queued/running/retrying` 任务时，后端返回既有任务，不重复排队。
- 角色图任务必须出现在全局任务队列入口中，用户能看到排队、运行、完成、失败和取消状态；顶部任务队列应独立刷新任务状态，不依赖项目角色库页面整体刷新。
- 普通 UI 中“重新生成”表现为直接替换当前角色图卡片展示图；底层可以创建新的 `Asset` 或视觉版本以保留追溯，但不得要求普通用户在多个图片版本之间选择。
- 角色图片生成弹窗不能修改角色名。角色名来自项目级 `Character`，弹窗只编辑用于 AI 生图的形象描述 / prompt。

### 输出

```json
{
  "characterId": "char_hero",
  "asset": {
    "type": "image",
    "mimeType": "image/webp",
    "path": "projects/project_001/assets/characters/char_hero/visual-v001/final-reference.webp",
    "referenceKind": "final_reference",
    "generationMode": "image_edit",
    "sourceReferenceAssetId": "asset_char_preview_001"
  },
  "providerMetadata": {
    "provider": "openai_image",
    "model": "gpt-image-2"
  }
}
```

### 验收

- 生成结果必须注册为 `Asset(reference image)`，并挂到项目级 `Character.referenceAssetIds`。
- 用户确认后才可写入 `Character.primaryReferenceAssetId` 并把角色推进到 `finalized`。
- 重新生成不得覆盖旧图，只能创建新的视觉版本目录。
- 一旦参考图被漫画候选图使用，旧图进入不可覆盖状态。

### 5.2 scene_reference_generate

章节剧情结构页使用的真实场景背景图生成任务。当前实现通过：

```text
POST /api/projects/{projectId}/chapters/{chapterId}/scenes/{sceneId}/reference
```

创建受控任务。API 路由中的 `sceneId` 是剧情结构里的稳定 `sceneKey`；DB 任务信封固定使用 `type = scene_reference_generate`、`target.type = scene`、`target.id = ChapterScene.id` 和目标章节 `chapterId`，不能把数据库行 ID 与 `sceneKey` 混为一个字段。

### 输入

```json
{
  "requestId": "2c8ad7d0-082e-4de7-9b53-b6c10c4a0efd",
  "sceneId": "chapter_scene_uuid",
  "sceneKey": "scene_001",
  "chapterId": "chapter_001",
  "prompt": "雨夜旧城区窄街，空镜环境底板，无人物无文字",
  "sourceProjection": {}
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `requestId` | string | 一次明确生成操作的唯一编号；同一编号可安全重放，不同编号表达用户再次生成 |
| `sceneId` | string | DB `ChapterScene.id`，必须与任务 `target.id` 一致 |
| `sceneKey` | string | 当前章节已确认 `StoryStructureSceneCard.id`，也是页面匹配任务状态的稳定键 |
| `chapterId` | string | 场景所在章节，必须与路由和 `target.chapterId` 一致 |
| `prompt` | string | 可选覆盖；为空时由后端根据场景卡构建场景环境提示词 |
| `sourceProjection` | object | 创建时冻结的 `ChapterScene` 来源投影，包含场景行摘要 |

HTTP 调用方只需提交 `requestId` 及可选 `prompt/size`；路由、服务端和来源投影负责补齐上表其余任务字段。Web 每次用户点击生成或重新生成时创建新的 `requestId`，网络重放必须复用原编号。

### 输出

```json
{
  "sceneId": "scene_001",
  "chapterId": "chapter_001",
  "assetId": "asset_scene_001"
}
```

DB-only 持久任务实际文件写入独立版本目录：

```text
projects/{projectId}/chapters/{chapterId}/scenes/{sceneKey}/visuals/{assetId}/background.webp
```

每次生成或重新生成都必须分配新的 `assetId` 和独立路径；失败清理只能删除本次新文件，不能覆盖或删除当前 `SceneVisual` 仍在使用的旧文件。file-mode 兼容实现仍可读取旧的 `scenes/{sceneId}/background.webp`，但不得作为 DB-only 新资产的路径合同。

对应章节级 Asset 必须记录 `chapterId`、`sourceTaskId`，并通过 `SceneVisual` 版本关联 `ChapterScene`。任务成功后，Workbench 只读投影把当前 `SceneVisual.assetId` 显示为场景卡的 `referenceAssetId`，不能回写不可变 `StoryVersion`。物理文件查询发现 `ENOENT` 时，Asset 从 `ready` 校正为 `missing` 并返回 `404 PROJECT_ASSET_FILE_NOT_FOUND`。

### 验收

- 项目、章节、已确认剧情结构和 `sceneId` 必须存在；缺任一项不得创建伪成功任务。
- 同一项目、同一章节、同一 `ChapterScene` 已有 `queued/running/retrying` 任务时返回既有任务，即使收到新的 `requestId` 也不重复产生付费任务。
- 同一个 `requestId` 重放时必须返回同一任务；旧任务进入 `failed/succeeded/cancelled` 后，用户再次点击所产生的新 `requestId` 必须创建新任务，不能把终态历史任务冒充“仍在队列中”。
- 任务必须使用 `target.type = scene` 并携带 `target.chapterId`。
- Web 的“生成中”判断必须用 `task.input.sceneKey` 对齐剧情结构 `scene.id`；`task.target.id` 只可作为旧 file-mode 兼容回退。
- 生成结果必须注册为章节级 Asset、写入本次 Asset 独有的 WebP 路径，并创建新的 `SceneVisual` 版本；只有来源仍为 current 时才切换 `ChapterScene.currentVisualId`。
- 重新生成失败时，旧 Asset、旧物理文件和当前 `SceneVisual` 指针必须保持可用。
- 成功输出至少包含 `sceneId/chapterId/assetId`；失败使用 `SCENE_REFERENCE_GENERATE_FAILED` 且保持可重试语义。
- 场景参考图当前由角色/场景共享串行队列执行；D75 实施后迁入持久任务图片并发通道，不改变本节业务输入输出。

DB-only 当前按 `projectId + chapterId + ChapterScene.id + active status` 去重，不会把另一章相同 `sceneKey` 的任务错误复用。file-mode 仅作为历史兼容，不再定义当前生产合同。

- 输出必须包含 `synopsis`、`direction`、`characters`、`scenes`、`beats` 和 `notes`。

- AI 不生成 `projectCharacterId`；后端在应用待确认结构的同一事务中按标准化角色名复用已有 `Character`，未匹配角色再受控创建，不能因为模型猜测 ID 而重复建角。

- `beats` 表示关键剧情事件，不和最终分镜或镜头一一对应；一个 beat 后续可拆成多个 shot。
- `beats.visualFocus` 只写轻量画面重点，不写镜头编号、景别、机位、构图或完整分镜稿。
- 不允许只输出自然语言总结。
- AI 生成后必须由用户确认，确认后的结构化剧情才能作为 `shot_generate` 输入。
- 待确认结构可以在右侧预览，但不能作为 `shot_generate` 输入。
- 用户确认结构后，当前章节状态推进到 `structured`，并绑定当前 `StoryVersion`。
- 对话生成与持久 `story_parse` 必须共用 `structure-story-parse` 的生产 Prompt、固定质量门和一次定向修复；第二次仍失败时不得把失败输出应用到 pending 文档。

- shot 顺序必须连续。
- shot 可追溯到 `beatId`，如果无法追溯要写 `sourceNote`。
- AI 生成结果先写入 `storyboard.pending.json` 作为待确认预览；用户确认后才写入正式 `storyboard.json`。
- `shot_prompt_generate`、候选图和排版只能读取已确认的正式分镜。
- `shot_prompt_generate` 和 `image_generate` 创建任务前必须通过章节级出图准备 guard：当前章节必须已有有效 `preflight.json`，且该确认记录与当前正式分镜的 `storyboardId/updatedAt` 匹配。

### 验收

- 任务必须调用 `shot-prompt-optimize` 文本 Skill，而不是只把既有 Provider Prompt 原样返回；首次 JSON 或单帧固定质量失败时最多修复一次。
- 优化结果是候选建议，只保存在 `GenerationTask.output`；worker 不写 `StoryboardVersion`、`PreflightRevision`、Candidate 或图片文件。
- 输出必须同时提供非空 `visualDescription/action/composition`、0～8 条 `mustShow`、固定 `visualIssues` 和只允许 `SOURCE_CONFLICT` 的 `optimizationWarnings`。

- `prompt/negativePrompt/image` 继续作为旧调用方可读的冻结生成规格；候选图工作台只在用户点击“采用返修结果”后，把三段建议复制到本地当次草稿。
- 候选图工作台只展示来源投影仍 current 且任务冻结的画面/动作/构图仍与当前草稿一致的建议；用户继续编辑后，旧建议不得覆盖新草稿。
- 任务 input 由 DB 创建门禁重建，必须含 `schemaVersion=2`、`shotId`、`promptSpec`、JCS `generationSpecDigest` 和 `sourceProjection`；source projection 至少包含 `storyboard_version`、`shot`、`preflight_revision`，未通过 `NewWorkGate` 不得创建。

## 9. image_generate

### 客户端语义输入

```json
{
  "chapterId": "chapter_001",
  "shotId": "shot_001",
  "candidateCount": 4
}
```

客户端不得成为候选图最终 Prompt、引用或尺寸的事实源。即使客户端提交旧的 `positivePrompt`、`negativePrompt`、`referenceAssetIds`、`preflightCharacterReferenceAssetIds` 或 `image`，任务 guard 也必须丢弃并由服务端正式项目、章节、分镜和出图准备事实重新生成。

客户端可选提交 `promptOverrides.visualDescription/action/composition`，表示候选图工作台中用户当前可见且确认用于本次生成的三段文字；每项非空且最多 1200 字。旧 `visualDescriptionOverride` 仅作为兼容别名读取。覆盖值不能删除系统禁止项、改变生成目的、引用、尺寸或 Provider；任务 input 与 digest 必须冻结覆盖后的服务端规格，正式 StoryboardVersion 不被修改。

批量入口必须先验证全部未锁定镜头的三段字段并读取全部服务端预览；任一规格含 `blocking` visual issue 时，本批不得创建任何 `image_generate`。全部预检通过后仍按既有队列逐任务创建，网络中断下的全批事务原子性不在首版保证范围内。

`shot_clean_plate` 内容契约：

- 一个任务目标只能是一个正式 storyboard shot；每张 Candidate 是一张单幅、全出血、静态画面。
- `visualDescription/action/composition` 先由服务端固定校验器检查；文字或数字生成要求、地点切换、多时刻、明确人数冲突、群体范围缺失属于 `blocking`，必须在任何图片 Provider 调用前以 `CANDIDATE_VISUAL_DESCRIPTION_BLOCKED` 拒绝。声音、气味、心理、时长、设定图语言和多人关系不清可作为 warning 明示，但不由 Provider Profile 暗中改剧情。
- 最终 Prompt 不得包含章节标题、对白、旁白、配音台词、动态运镜、时长、`vertical_scroll/paged_comic/four_panel/page_horizontal` 或对应中文标签等页面格式名。
- 禁止生成文字、字母、数字、Logo、水印、字幕、旁白框、对白/思考气泡、拟声词、分格、边框、沟槽、拼贴、角色设定表或整页布局。
- 只读取当前 shot 在出图准备中冻结的角色与场景视觉，不得注入本章全部角色；进入任务规格的每张引用都是必需来源，Asset 不存在、文件不可读或图片损坏时必须在调用 Provider 前失败。
- file mode 直接使用当前 shot 已确认的单人 `previewReferenceAssetId`。DB-only 的 `final_reference` 只证明角色已满足出图准备要求；创建候选任务时必须另外冻结单人 `preview_front` 及摘要到 `sourceProjection`。若 final 记录了 `sourceVisualId`，必须优先使用这张精确来源；旧 final 来源为空时，只允许自动关联同角色唯一一张“版本早于 final、Visual available、Asset ready 且摘要有效”的 preview，零张或多张都失败关闭。来源存在但跨角色、类型错误、缺失或非 ready 时同样失败。已有真实资产同时出现横向四格与 2×2 四格，禁止假定固定格位裁切完整角色设定表。
- 所有引用先由 `candidate_reference_plan_v1` 按当前 Provider 编译：本地能力表为 Grok 3 个、OpenAI 16 个、Doubao/Seedream 10 个物理图片槽位。容量足够时保持角色单图与场景图独立直传。
- 容量不足时只把本镜头全部角色编成一个 `cast_identity_board_v1`，场景仍为独立输入。身份板固定中性背景、每个角色一次、无姓名/编号/格线/水印/剧情背景；当前技术打包上限为 12 人，超过后或打包后仍超 Provider 容量时失败关闭，不按 `priority` 删除必需角色/场景。
- Grok 单参考必须走官方 JSON `image` 单图编辑，不得退回文生图；官方单图编辑输出比例跟随输入，因此写 `grok_single_reference_output_aspect_ratio_follows_input`，并继续执行实际成图比例校验。两张及以上使用 `images` 多图编辑并显式传目标比例。
- 成功计划必须满足 `omittedRequired=[]`，并记录原始来源、实际物理槽位、逐槽 `covers`、身份板布局版本/尺寸/摘要和 `compositionCoverage=prompt_only`。`priority` 只用于稳定排序和未来焦点策略，不再允许删除必需条件。
- 引用计划证明条件已被实际图片输入覆盖，但不等同于模型视觉质量通过；多人串脸、漏人、站位和动作职责仍需真实固定语料 A/B 与生成后验收。

### 验收

- 生成数量等于 `candidateCount` 或在 warnings 中说明原因。
- 每个候选必须注册为 `Asset` 和 `Candidate`。
- 新 Candidate 必须写 `generationPurpose/specVersion/specDigest`；缺少这些字段的旧候选读取为 `legacy_unspecified`，不删除、不迁移、不自动解锁。
- Asset meta 必须保存 provider、generationMode、requestedSize、actualSize、实际覆盖的原始 `referenceAssetIds`、完整 `referencePlan` 和 warnings。DB-only 新 Candidate Asset 使用 metadata schema v2；任务输出的每个 candidate 同步保存同一计划。
- `referenceAssetIds` 表示 Provider 实际物理输入覆盖的原始来源 Asset；身份板的 `derived:*` ID 只出现在 `referencePlan.slots[].providerReferenceId`，不能冒充项目资产。`final_reference` 若只作为预检批准证据而未进入 Provider，其 Visual 仍在任务 `sourceProjection` 中，但不能伪装成已物理覆盖的 `referenceAssetIds`。

- `tasks/{taskId}.input.json` 保存完整 task 与 CandidateGenerationSpec；成功写 `.output.json`，失败写 `.error.json`。
- 失败时保留 provider 错误和权威输入，不把 API Key、Authorization 或完整敏感响应写入任务证据。

## 9.5 layout_compose

### 定位

`layout_compose` 是章节作用域持久任务，用于普通首次进入的完整初稿，以及编辑后的 full/scoped 智能调整。它只生成建议结果，不创建 LayoutRevision 或 publication。

| 项 | 契约 |
| --- | --- |
| target | `type=chapter`、`id=chapterId`，并强制携带 `chapterId` |
| source | StoryboardVersion、CandidateLockRevision/Asset 集、相关角色 ID/名称目录、`fontPolicy`、精确 `typographyPreset`、样式策略、可选 Working Copy digest |
| concurrency | `layout-compose`，首版全局并发 1 |
| maxAttempts | 2；合同/覆盖失败不可重试，临时 Provider/IO 错误可重试 |
| idempotency | `chapterId + mode + sourceProjectionDigest + baseDocumentDigest + scopeDigest + policySetDigest` |
| write target | worker 仅写 GenerationTask output；apply 使用独立事务创建 WC/Pending，并写不可变应用凭证 |

### 输出与应用

输出必须二选一：初次成稿返回严格 `LayoutDocumentV2`，重排返回严格 `EditorCommandBatchV2`；同时返回 plan digest、分析模式、候选数、评分明细、Shot/对白覆盖和结构化问题。输出不得包含密钥、Authorization、绝对路径、图片字节或 Provider 原始自由文本。

`typographyPreset` 使用 `layout_typography_preset_v1`，为 `speech/thought/shout/caption` 分别冻结精确 `fontAssetId/fontWeight/fontStyle`，并进入 source projection、policy digest 和 Asset 可用性校验。旧任务缺少该字段时由旧 `fontPolicy` 生成兼容预设，上一版 policy digest 继续可读；新任务不得依赖浏览器或操作系统合成字体面。

运行时没有取得可验证视觉证据时必须显式输出 `analysisMode=rule_fallback` 与 `visual_protection_unverified`。该模式所有自动气泡主体必须完全位于画格外且尾巴关闭，不能以“未检测到人物”或“多数面积在画格内”通过主体保护。`vision` 模式只有在气泡完整位于同来源的 verified `textSafeRegion`，且不与脸、身体、焦点、其他画格或其他气泡相交时，才允许画内排版。

- 初次 apply：重验 source projection 且确认 Working Copy 仍不存在，再原子创建 V2 Working Copy。
- full/scoped reflow：重验 Working Copy rowVersion/documentDigest 与来源，转成现有 `PendingEditorCommandSet` 供用户预览、应用或放弃；不能直接更新 Working Copy。
- 同 task/同 base 重复 apply 根据不可变 `LayoutCompositionApplication` 返回 replay；目标或 base 已变化返回冲突，不能部分应用。该凭证只记录 task、实际目标和摘要，不保存第二份成稿；详见 ADR-0020。
- Shot、对白、来源、文字溢出、几何、字体或人工保护任一硬门失败时，不输出可应用的半成品。

完整 input/output、HTTP、状态机和错误码见 `文档/02_架构与契约/2026-07-22_智能成稿规划与编辑保护契约.md`。
