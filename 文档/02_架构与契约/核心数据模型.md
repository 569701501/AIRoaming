## 1. 建模原则

- 中间产物必须可追溯，不能只保存最终图片或视频。
- AI 任务的输入输出必须留存，便于复跑、调试和版本比较。
- 图片、音频、视频、PDF 都统一抽象为 `Asset`。
- 生成候选与分镜之间通过 `Candidate` 连接。
- 当前锁定结果与历史候选分离，避免覆盖历史。
- 依赖新鲜度与章节单调完成状态分离；上游返修通过来源修订和 digest 判断下游是否需要更新。
- 章节是项目内一等工作单元，后续剧本、结构化剧情、分镜、候选图、排版和导出优先挂到 `chapterId`。
- 项目级角色、世界观、通用场景和共享素材继续挂到 `projectId`，供多个章节复用。
- 对话框组件可以公共复用，但原始对话记录必须按项目步骤隔离。
- 跨步骤 AI 上下文只共享用户已确认的事实、保存文档和锁定产物，不共享未确认聊天假设。

## 3. Project

项目容器，承载一个作品的全部故事、分镜、素材和导出物。

```json
{
  "id": "project_001",
  "name": "月下旅人",
  "type": "comic",
  "status": "draft",
  "storyTitle": "月下旅人：第一话",
  "genreTags": ["悬疑", "都市"],
  "comicFormat": "vertical_scroll",
  "artStyle": "dark_realistic",
  "currentChapterId": "chapter_001",
  "currentStoryVersionId": "story_v001",
  "createdAt": "2026-05-23T00:00:00.000Z",
  "updatedAt": "2026-05-23T00:00:00.000Z"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 项目 ID |
| `name` | string | 项目名称 |
| `type` | enum | `comic/light_motion/mixed` |
| `status` | enum | `draft/story_ready/characters_ready/structure_ready/shots_ready/images_ready/layout_ready/exported`；`characters_ready` 仅作旧兼容或项目核心角色参考完成状态，不再作为剧情结构门槛；章节级出图准备由 `chapters/{chapterSlug}/preflight.json` 确认记录表达 |
| `storyTitle` | string | 故事标题，用于项目内创作和故事版本默认标题；在第 1 步“剧本”保存 |
| `genreTags` | string[] | 题材标签或类型标签；在第 1 步“剧本”保存，项目库卡片当前不展示 |
| `comicFormat` | enum | G3 目标为 `vertical_scroll/paged_comic`，创建时必填且创建后不可直接修改；当前 DB Schema 已两值，Shared/file runtime 仍含 `page_horizontal/four_panel`，待按五份施工资料收口 |
| `artStyle` | enum | `dark_realistic/semi_realistic/japanese_realistic/comic_style/cyberpunk/custom` |
| `currentChapterId` | string/null | 当前活跃章节 |
| `currentStoryVersionId` | string | 当前故事版本 |

当前处于受限双模式过渡期。默认或 `AIROAMING_PERSISTENCE_MODE=file` 时，后端仍维护进程内 `Project` 索引，并将项目创建、草稿保存和章节完成写入本地 workspace；启动或首次访问时从 `workspace/projects/*` 恢复。显式 `AIROAMING_PERSISTENCE_MODE=db` 时，Project/Chapter/Script 最小切片已改从 SQLite 读写，只放行创建项目、保存草稿和完成章节，不写 workspace 项目树；其他写入 fail-closed。DB 模式连接后、加载项目之前必须精确核验正式 0001～0010 migration artifact 与 `_prisma_migrations` ledger，缺失、额外、漂移、failed 或无 ledger 均拒绝启动。完整领域接管和生产切换仍未完成。

删除项目是用户二次确认后的破坏性操作，必须按项目容器全量清理：删除 `Project` 运行时索引、本地 `workspace/projects/{projectId}` 目录、该项目 `GenerationTask` 记录和项目级对话运行态缓存。已删除项目的异步生成请求即使稍后返回，也不能重新写入或重建该项目目录。全局设置、其他项目目录和其他项目任务不能受影响。

创建项目只建立项目记录。现有创建项目按钮、弹窗、API 调用和成功跳转全部复用，前端只在现有弹窗增加第二个必填字段 `漫画版式`。`comicFormat` 表单默认空，不允许服务端静默回退；用户必须选择 `vertical_scroll/paged_comic`，创建后普通更新接口不可修改。数据库字段无默认值且已有两值 CHECK，G3 再通过 0010 immutable trigger 阻止底层原地更新。HTTP/DB parser、file legacy read adapter 和 maintenance importer mapper 是三个独立边界：file page alias 可只读投影并保留原文件，歧义 fail-closed；最终改写只归 importer。`type` 使用默认漫画项目类型；`storyTitle`、`genreTags`、`artStyle` 和章节剧本在第 1 步“剧本”或后续专门入口保存。四格属于 `LayoutPreset`，不再属于项目版式。正式决策见 ADR-0009，施工入口见 `文档/04_方案与决策/2026-07-12_G3施工包_依赖边界与阶段门禁.md`。

```text
workspace/projects/{projectId}/project.json
workspace/projects/{projectId}/workflow.json
workspace/projects/{projectId}/chapters/chapter-001/chapter.json
workspace/projects/{projectId}/chapters/chapter-001/script.md
```

当前后端创建项目时已默认创建 `chapter-001` 并写入章节目录。过渡期旧剧本保存接口仍提交 `sourceText`，但后端只同步写入当前章节 `script.md`；`story/story_draft.source.txt` 旧兼容路径已废弃，新项目不再创建、读取或写入。

当维护动作清空项目剧本，或整本剧本导入需要替换章节集合时，后端必须先删除旧 `chapters/` 目录，再按最新章节列表重建目标章节目录。不能只覆盖新章节数量内的文件，否则服务重启后旧章节目录会被 workspace 扫描恢复，造成已经清掉的章节重新出现。

剧本编辑器里的用户可见“清空”动作只作用于当前打开章节，不删除项目下其他章节。项目级清空只作为整本替换、错误导入修复或维护能力保留，不应作为普通编辑器按钮触发。

旧项目草稿保存接口：

```text
PATCH /api/projects/{projectId}
```

请求字段：

```json
{
  "name": "迷雾之城",
  "storyTitle": "迷雾之城：第一话",
  "genreTags": ["悬疑", "都市"],
  "comicFormat": "vertical_scroll",
  "artStyle": "dark_realistic",
  "description": "迷雾之城：第一话",
  "sourceText": "故事原文"
}
```

响应返回更新后的 `ProjectListItem` 和 `WorkbenchSnapshot`。

该接口为过渡兼容入口。上例中的 `comicFormat` 只描述当前旧客户端行为；按 ADR-0009 实施后，普通更新 DTO 必须移除该字段，旧客户端提交不同值时返回 `409 COMIC_FORMAT_IMMUTABLE`。剧本页当前章节保存应优先使用章节草稿保存接口。

`WorkbenchSnapshot` 中章节字段为剧本页读取当前内容的主契约：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `chapters` | `ChapterListItem[]` | 当前项目章节列表，用于后续章节列表和章节切换器 |
| `currentChapter` | `ChapterDetail/null` | 当前活跃章节详情；剧本编辑器和剧本步骤对话上下文应优先读取这里的 `sourceText`、`title` 和 `id`；剧本页不再常驻展示基于该字段解析的当前章节信息面板 |
| `workflow` | `ProjectWorkflow` | 当前项目工作流状态，聚合当前章节的下一步、7 步状态、完成标准和证据路径；项目角色库作为常驻资产入口由 workflow 读取但不再作为线性主流程步骤 |
| `stages` | `WorkbenchStage[]` | `workflow.steps` 的前端兼容镜像；新增消费者优先读取 `workflow` |
| `pendingStoryboard` | `ChapterStoryboard/null` | 当前章节待确认分镜预览；来源为 `storyboard.pending.json`，只能用于右侧预览和编辑，不能作为候选图输入 |
| `story` | `WorkbenchStory` | 过渡镜像，用于尚未迁移的旧消费者兜底；新增消费点不应把它当作章节事实源 |

`ChapterListItem.storyboardStatus` 是章节下拉和章节列表展示分镜进度的主字段：`pending_confirmation` 表示该章存在 `storyboard.pending.json` 待确认预览，`storyboard_done` 表示该章存在正式 `storyboard.json`，`null` 表示尚无分镜产物。UI 不应只用当前章节的 `WorkbenchSnapshot.pendingStoryboard` 判断其他章节是否待确认。

## 4. ProjectWorkflow

`ProjectWorkflow` 是项目级流程事实视图，用于把“当前章节状态、项目资产准备状态”和“7 步主流程”合并成 UI、对话和任务都能消费的统一状态。

当前 MVP 中，工作流状态由当前章节 `Chapter.status` 推导，并写入本地：

```text
workspace/projects/{projectId}/workflow.json
```

示例：

```json
{
  "schemaVersion": 1,
  "projectId": "project_001",
  "currentChapterId": "chapter_001",
  "currentStepKey": "story_structure",
  "steps": [
    {
      "key": "project_story",
      "label": "剧本",
      "status": "done",
      "scope": "chapter",
      "summary": "章节剧本已完成并写入版本快照。",
      "evidence": "/workspace/projects/project_001/chapters/chapter-001/script.md",
      "completionCriteria": ["当前章节 `script.md` 已保存", "用户点击完成本章并写入章节剧本版本"]
    }
  ],
  "updatedAt": "2026-05-27T00:00:00.000Z"
}
```

工作流步骤：

| key | 页面 | scope | 下一步依据 |
| --- | --- | --- | --- |
| `project_story` | 剧本 | chapter | `Chapter.status = draft` |
| `story_structure` | 剧情结构 | chapter | `Chapter.status = script_done` |
| `storyboard` | 分镜工作台 | chapter | `Chapter.status = structured` |
| `image_preflight` | 出图准备 | chapter | `Chapter.status = storyboard_done` 且存在正式 `storyboard.json` |
| `image_candidates` | 候选图工作台 | chapter | 当前章节出图准备已确认 |
| `layout_export` | 漫画成稿 | chapter | 所需 active Shot 均有 current CandidateLockRevision 后可进入；当前 LayoutRevision 与 current `layout_publication` 决定完成态，并允许在 `layout_done/exported` 后返回返修 |
| `asset_package` | 素材包 | project | 存在来源为 current 的 ExportRevision；历史导出不自动满足当前素材包门槛 |

`project_characters` 不再作为顶部主流程步骤，只保留为 `/characters` 项目级资产入口；角色视觉定稿主要由 `image_preflight` 在候选图生成前检查。

`ProjectWorkflowStep.status`：

| 状态 | 含义 |
| --- | --- |
| `done` | 当前章节已越过该步骤，可回看 |
| `active` | 当前章节下一步应推进的步骤 |
| `waiting` | 前置步骤未完成，默认不开放点击 |
| `blocked` | 存在阻塞；目标口径中主要用于出图准备未完成时阻塞 `image_candidates`，或上游章节产物缺失时阻塞后续步骤 |
| `needs_confirmation` | G2 已采纳目标：步骤存在 dirty Working Copy 或 active pending，旧正式结果仍可查看，但新下游任务被阻止 |
| `needs_update` | 步骤曾完成，但当前上游修订已变化；历史产物保留，用户需生成或确认新修订 |

设计约束：

- workflow 不替代 `Chapter`；章节产物仍以 `chapterId` 归属。
- `image_preflight` 是章节级步骤，但会读取项目角色库、场景/风格参考和当前章节分镜。
- 项目角色库不再由单一 `Chapter.status` 决定，也不再阻塞 `story_structure`；它作为项目级资产事实源被剧情结构、分镜、出图准备和候选图读取。
- 前端路由表达“用户正在看哪个页面”，workflow 表达“当前章节应该推进到哪一步”。
- `Chapter.status` 保持单调完成里程碑；候选定稿变化导致的布局过期由 workflow freshness 派生为 `needs_update`，不把章节粗暴回退到 `images_done`。
- G2 实施后，workflow 同时投影 `milestoneReached/currentArtifactId/freshness/attention/canStartTask/historyAvailable/reasonCodes`；`currentStepKey` 指向最早需要用户处理的步骤。服务端是权威推导入口，前端不再仅凭 `Chapter.status + updatedAt` 维护第二套状态机。
- 对话框后续应读取 workflow 生成阶段提示；剧本阶段允许 AI 通过受控工具写章节草稿，但不能因为 workflow active 就自动绕过工具/API 写文档。

## 5. Chapter

章节是项目内创作的基本推进单元。用户完成第 1 章后，可以创建或进入第 2 章继续创作。

```json
{
  "id": "chapter_001",
  "projectId": "project_001",
  "order": 1,
  "title": "第 1 章",
  "status": "draft",
  "currentScriptVersionId": "chapter_script_v001",
  "currentStoryVersionId": "story_v001",
  "sourceText": "当前章节剧本正文",
  "summary": "本章一句话主线",
  "lastScriptRevision": {
    "source": "ai_tool",
    "threadId": "thread_001",
    "messageId": "msg_assistant_001",
    "toolCallId": "tool_call_001",
    "operation": "update_chapter_draft",
    "summary": "强化当前章节紧张感和冲突推进。"
  },
  "createdAt": "2026-05-27T00:00:00.000Z",
  "updatedAt": "2026-05-27T00:00:00.000Z",
  "completedAt": null
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 章节 ID |
| `projectId` | string | 所属项目 |
| `order` | number | 章节顺序，不能只依赖文件夹名 |
| `title` | string | 章节标题，默认可为“第 1 章” |
| `status` | enum | 章节当前状态 |
| `currentScriptVersionId` | string/null | 当前剧本版本 |
| `currentStoryVersionId` | string/null | 当前结构化剧情版本 |
| `sourceText` | string | 当前章节剧本正文，MVP 可先冗余保存 |
| `summary` | string | 当前章节故事主线或一句话总结 |
| `lastScriptRevision` | `ScriptRevisionItem/null` | 最近一次 AI 通过受控工具写入本章节的来源追溯；第一版只保留最近一次 |
| `completedAt` | string/null | 当前章节剧本完成时间 |

章节状态建议：

| 状态 | 含义 |
| --- | --- |
| `draft` | 章节草稿中 |
| `script_done` | 当前章节剧本已完成；下一步进入剧情结构，角色库待处理项只提示不阻塞结构化 |
| `structured` | 当前章节已结构化 |
| `storyboard_done` | 当前章节分镜已完成 |
| `images_done` | 当前章节候选图或锁定图已完成 |
| `layout_done` | 当前章节排版已完成 |
| `exported` | 当前章节已导出 |

### 5.1 ChapterScriptVersion

章节剧本版本用于保存用户对章节剧本的大改和完成本章时的快照。

```json
{
  "id": "chapter_script_v001",
  "chapterId": "chapter_001",
  "projectId": "project_001",
  "version": 1,
  "sourceText": "当前章节剧本正文",
  "sourcePath": "projects/project_001/chapters/chapter-001/script.md",
  "status": "current",
  "createdAt": "2026-05-27T00:00:00.000Z"
}
```

保存草稿只更新当前章节 Working Copy。点击“完成本章”时，必须把当前 Working Copy 发布为不可变剧本版本，并把章节状态推进到 `script_done`。当前工作上下文保留在刚完成章节，方便进入本章剧情结构；只有已确认项目大纲存在下一张章节卡时，系统才增加下一章入口，但不生成下一章草稿、不自动切换。如发现角色库待处理项，应提示但不阻塞剧情结构。

G2 已采纳目标会把上述“草稿文件”明确为 `Chapter.scriptWorkingText`：保存和采用 AI pending 只修改 Working Copy；已完成章节必须再次点击“完成本章”才发布新的不可变 ScriptVersion。dirty Working Copy 不使旧导出消失，但阻止新 `story_parse/shot_generate/image_generate`，用户可发布或还原。

保存草稿和完成本章必须校验规范化后的章节正文：项目级“剧本名称/剧集名称”被剥离后若不再含章节正文，返回 `CHAPTER_SCRIPT_REQUIRED`，且不得修改 `script.md`、章节元数据或剧本版本。

`chapter.pendingSourceText` 是 AI 创作路线生成的章节正文待确认缓冲（见 ADR-0008），落在 `chapters/{slug}/script-pending.json`，**不覆盖 Working Copy 或正式剧本版本**。用户必须完整查看待确认正文：点击“采用草稿”后，`confirmChapterPendingSource` 把 pending 写入当前章节 Working Copy 并清空 pending；点击“丢弃”只删除 pending。一个章节同时最多存在一份 pending；已有 pending、非空 Working Copy 或正式剧本时，不允许静默生成新 pending 覆盖。AI 创作路线不提供批量生成整本，章节切换也不触发生成；只有用户在当前章节上下文中明确要求生成当前章，系统才按该章章节卡、相邻章节卡、完整已确认大纲和上一章正式正文生成一章 pending。

章节 API：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/projects/{projectId}/chapters` | 返回章节列表和当前章节 ID |
| `GET` | `/api/projects/{projectId}/chapters/{chapterId}` | 返回单个章节详情 |
| `PATCH` | `/api/projects/{projectId}/chapters/{chapterId}/draft` | 保存当前章节草稿，覆盖 `script.md` |
| `POST` | `/api/projects/{projectId}/chapters/{chapterId}/complete` | 完成本章，把 Working Copy 写入 `script.versions/script-vNNN.md`；若确认大纲存在下一张章节卡，仅创建下一章入口，不创建正文草稿、不切换当前章 |
| `POST` | `/api/projects/{projectId}/chapters/{chapterId}/script/clear` | 清空当前章节剧本正文，其他章节不受影响 |

保存章节草稿请求：

```json
{
  "sourceText": "当前章节剧本正文",
  "title": "第 1 章",
  "summary": "本章一句话主线"
}
```

完成本章请求：

```json
{
  "sourceText": "当前章节剧本正文",
  "title": "第 1 章",
  "summary": "本章一句话主线",
  "createNextChapter": true,
  "nextChapterTitle": "第 2 章"
}
```

完成本章响应必须返回：

| 字段 | 说明 |
| --- | --- |
| `completedChapter` | 已完成章节，状态为 `script_done` |
| `activeChapter` | 完章响应中仍为刚完成的章节；即使 `createNextChapter` 创建了下一章草稿，当前章节也不自动切换，以便用户继续进入已完章的剧情结构步骤 |
| `chapters` | 更新后的章节列表 |
| `scriptVersion` | 本次完成动作写入的章节剧本版本 |
| `createdNextChapter` | 本次是否创建了下一章 |

清空当前章节剧本请求无 body。响应 `ClearChapterScriptResponse`：

| 字段 | 说明 |
| --- | --- |
| `chapter` | 清空后的当前章节详情；保留章节 ID、顺序和章节目录，章节标题重置为默认 `第 N 章`，`sourceText` 为空 |
| `chapters` | 更新后的章节列表；其他章节保留 |

清空当前章节必须将该章节退回 `draft`，将 `title` 重置为默认 `第 N 章`，并清空 `sourceText`、`summary`、`currentScriptVersionId`、`currentStoryVersionId`、`completedAt` 和 `lastScriptRevision`。当前实现会移除该章节的 `script.versions/` 与 `script.revisions/`，避免服务重启后旧剧本版本重新被恢复为当前版本；后续如果接入完整回退功能，再重新设计可恢复历史。项目级 `storyTitle` 不随“清空本章”清空。

项目级 `POST /api/projects/{projectId}/script/reset` 已于 2026-07-21 退役并删除。DB-only 模式不提供物理删除整本章节历史的重置入口；用户只能逐章操作 Working Copy，或新建项目/章节承载新的正文。

## 6. StoryVersion

保存结构化剧情。章节模型接入后，`StoryVersion` 应归属于 `Chapter`，用于表示某个章节的一次结构化结果。

剧情结构必须按章节生成和确认。一个 `Chapter` 对应自己的 `StoryVersion` / `structure.json`；不要把整本剧本一次性生成成一个全局剧情结构。

产品语义上，「剧情结构」不是章节剧本，也不是最终分镜；它是给制作使用的结构表，用于把当前章节拆成摘要、角色、场景和剧情节拍，并作为分镜生成的上游输入。

`structureJson.characters` 和 `structureJson.scenes` 默认表示本章结构卡，只归属于当前 `StoryVersion`；它们不等同于正式项目级 `Character` 或 `SceneLocation`。剧情结构确认时必须优先读取项目角色库，主角、常驻角色和已存在角色应按角色名关联已有 `Character`，不能重复创建；本章新出现且未匹配到的角色自动创建为项目级 `Character(source=story_structure)`，并自动排队生成第一张角色图。普通用户路径以角色图列表呈现：生成图自动展示为图片卡片，卡片 hover 后显示编辑和删除图标；编辑弹窗是角色图片生成弹窗，不是角色档案编辑弹窗。角色名只读，不能在这里修改；用户只编辑用于 AI 生图的形象描述 / prompt，并重新生成或应用当前图。重新生成后直接替换当前卡片展示图，不在普通 UI 中展示多版本选择。删除图卡必须二次确认，且只删除当前图片版本，不删除角色本身。加入角色库、合并到已有角色、标记临时或忽略是底层处理能力，只在系统自动判断、疑似重复角色、无法归类或用户展开高级处理时出现。本章新出现的重要场景，当用户确认需要跨章节复用时，后续再提升为项目级资产。

`structureJson.characters[].projectCharacterId` 是结构卡到项目角色库 `Character.id` 的稳定外键。字段名 `projectCharacterId` 是现有文件协议的兼容命名；当前 Shared 文件态 DTO 类型仍叫 `ProjectCharacter`，但它与本模型的 `Character` 表达同一角色记录，不是第二个正式实体。AI 生成结构卡时不填该字段（为 null），由后端在受控应用待确认结构或用户确认结构的事务中按 name 匹配/新建角色后回填；纯对话 pending 预览不回填。因为当前产品不允许删除项目角色，回填后的 id 在现行规则下保持有效；name 仍是跨章节建立“同一个角色”关联的二级线索。详见 `文档/04_方案与决策/ADR-0006_剧情结构卡角色ID回填方案.md`。

DB Working Copy 页面适配和持久 `story_parse` 任务中，未绑定角色可在 Working Copy update / task apply 边界使用 `unresolved-story-character:<local-ref>` 临时引用。该值只允许存在于进入 `StoryVersionRepository` 事务前的待应用文档；后端必须在同一业务事务内按标准化角色名复用或创建 `Character`，将待保存 StoryDocument 重写为真实 `Character.id` 后再计算摘要并持久化，任何 `unresolved-story-character:` 值都不得进入持久 StoryVersion。确认完成后，缺少 `preview_front` 的结构角色应自动创建持久生成任务；任务排队失败不得回滚已确认的结构，但必须记录 warning 并保留角色卡手动重试入口。

剧情结构的用户可见主形态是可编辑结构表，底层持久化为当前章节的 `structure.json` / `StoryVersion.structureJson`，不以 Markdown 正文作为主事实源。

`StoryVersion.status = structured` 表示用户已经确认当前结构，可以作为 `shot_generate` 的输入。AI 刚生成但未确认的结构应视为待确认草稿，不应自动触发分镜生成。

剧情结构右侧 UI 以 `structureJson` 字段渲染元素化结构表。可编辑字段应支持字段级编辑：展示态为普通文本，右上角有小笔图标；编辑态为输入框或多行输入框，失焦后写回对应字段并恢复展示态。

AI 生成但未确认的结构可以在右侧显示为待确认预览。待确认预览必须和正式结构表在状态上区分：它可以用于用户检查和修改，但不能作为 `shot_generate` 输入；用户确认后才写为正式 `StoryVersion` / `structure.json`。

剧情结构步骤的章节下拉/切换器应基于 `Chapter` 列表展示每章结构状态。`Chapter.status = structured` 且 `currentStoryVersionId` 存在时，表示该章剧情结构已完成；未确认预览不应推进 `Chapter.status`。

章节下拉应展示所有章节，但生成权限按章节状态控制：`draft` 章节不能生成剧情结构；`script_done` 章节可以运行 `story_parse` 并生成待确认预览；`structured` 及后续状态章节可以查看和编辑已有结构，如重新生成必须先提示会影响后续分镜、候选图和排版。`需更新` 是 UI 派生状态，只应在当前结构的 `sourceScriptVersionId` 与章节 `currentScriptVersionId` 不一致时出现；不要用 `chapter.updatedAt` 判断，因为分镜、结构编辑或其他元数据变化也会更新章节时间。

```json
{
  "id": "story_v001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "version": 1,
  "sourceText": "当前章节剧本正文",
  "summary": "一句话摘要",
  "structureJson": {
    "characters": [],
    "scenes": [],
    "beats": []
  },
  "status": "structured"
}
```

| 状态 | 含义 |
| --- | --- |
| `draft` | 只有原文 |
| `structured` | 已结构化 |
| `shots_generated` | 已生成分镜 |
| `archived` | 历史版本 |

## 7. StoryBeat

剧情节拍，是分镜生成的上游语义单元。

`StoryBeat` 的粒度是关键剧情事件，不是最终分镜或镜头。一个 `StoryBeat` 后续可以生成多个 `Shot`，因此不应在剧情结构阶段提前写镜头编号或镜头级构图。

`StoryBeat` 可以包含轻量 `visualFocus`，表示该剧情事件的画面重点；但不得包含镜头编号、景别、机位、构图或完整分镜稿，这些属于 `Shot`。

```json
{
  "id": "beat_001",
  "storyVersionId": "story_v001",
  "chapterId": "chapter_001",
  "order": 1,
  "sceneId": "scene_001",
  "summary": "主角进入雨夜街道",
  "characters": ["林舟"],
  "emotionalTone": "lonely",
  "visualFocus": "雨水倒映主角孤立的身影",
  "dialogueHints": []
}
```

## 8. Character

角色模板，约束图片生成一致性。`Character` 是项目级角色库的核心实体，挂到 `projectId`，供多个章节复用；剧情结构里的本章角色卡不能替代项目级 `Character`。

剧本大纲确认后应自动创建第一批项目级角色草稿，并为主角、常驻角色和主要反派自动排队生成 `preview_front` 角色预览图。AI 自动判断角色层级和角色描述；自动生成不等于自动定稿。剧情结构和分镜阶段可继续发现本章新角色，并生成待处理角色项。角色名是项目内唯一身份标识，普通角色图片生成流程不允许改名；右侧角色库工作区应支持用户查看角色名、角色描述、层级和备注，并支持在定稿前编辑用于 AI 生图的形象描述 / prompt、重生成或替换角色预览图；左侧 AI 对话负责生成、解释、合并建议和批量调整，不能成为唯一修改入口。

分镜生成时 AI 必须只使用剧情结构已确认的角色名（`structure.characters` 的 `name`），不得自创新名字或别名，从源头消除未识别出镜。分镜 `Shot.characterIds` 若仍出现未匹配角色库的名称，出图准备只提示"回分镜修正或重新生成分镜"，不再就地处理。角色图生成与定稿（`preview_front` 预览图、`final_reference` 角色定稿组合图）在剧情结构页完成；出图准备定位为"出门检查单"——只检查本章出镜角色是否已绑定、是否已锁定可用参考图、场景和画风是否就绪，确认后写 `preflight.json` 放行候选图，不再承担角色图生成/定稿，也不再提供加入/合并/临时/忽略四种就地处理动作。

进入项目角色库后，系统可为角色自动异步生成 `preview_front` 预览图。`lead` 和 `recurring` 必须在出图准备阶段前完成 `final_reference` 定稿图；`chapter/minor/extra` 按本章实际出镜次数判断，出镜 ≥2 次才要求定稿，只出镜 1 次不强制。角色视觉定稿不再阻塞章节级剧情结构，主要阻塞候选图生成。`preview_front` 是角色视觉身份锚点，不只是灵感图；用户可以修改用于图片生成的形象描述 / prompt 并重新生成角色图，但不能在图片生成弹窗里修改角色名。生成 `final_reference` 时，系统内部自动读取当前可用的 `preview_front` 作为图片参考输入，不能只用文字 prompt 重新生成，也不要求普通用户先点击“确认预览”。

角色参考图状态规则：

- 重新生成角色参考图不会直接覆盖已有定稿图；新图作为候选资产进入 `referenceAssetIds`，用户确认后才替换 `primaryReferenceAssetId`。
- `final_reference` 必须记录其来源预览图，例如在素材 `meta.sourceReferenceAssetId` 中保存已确认的 `preview_front` 资产 ID。
- 角色层级提升为 `lead` / `recurring` 时，如果原 `primaryReferenceAssetId` 不是 `final_reference`，必须清空 primary 并重新生成角色定稿图后才能通过出图准备门槛。
- `status = in_use` 表示角色定稿图已被后续漫画候选图使用；后端必须阻止修改角色设定、重新生成或替换 primary reference，避免破坏旧候选图追溯。
- 项目角色名在同一项目内应保持唯一；重名应拒绝写入或要求用户合并。

```json
{
  "id": "char_hero",
  "projectId": "project_001",
  "name": "林舟",
  "role": "protagonist",
  "level": "lead",
  "status": "finalized",
  "appearance": "黑发，短外套，神情克制",
  "personality": "冷静，敏感",
  "referenceAssetIds": ["asset_char_preview_001", "asset_char_ref_001"],
  "previewReferenceAssetId": "asset_char_preview_001",
  "previewConfirmedAt": "2026-06-01T11:40:00.000Z",
  "primaryReferenceAssetId": "asset_char_ref_001",
  "primaryReferenceKind": "final_reference",
  "promptFragment": "young man, black hair, short jacket",
  "source": "script_outline"
}
```

角色层级（level，5 层；AI 生成剧情结构时显式输出，未输出则 inferCharacterLevel 关键词兜底，见任务 2026-06-21_角色分层双维度）：

| level | 含义 | 定稿要求 |
| --- | --- | --- |
| `lead` | 主角或核心视角人物 | 必须有角色图和角色定稿图；门槛在出图准备前检查 |
| `recurring` | 重要配角、主要反派、长期出现人物 | 必须有角色图和角色定稿图；门槛在出图准备前检查 |
| `chapter` | 本章关键角色，未确认长期出现 | 默认生成预览图；如果本章多次出镜、有台词、近景或影响剧情，出图准备阶段需补可用参考图 |
| `minor` | 小角色/功能角色，有功能但戏份少 | 默认生成预览图（与 chapter 同档），不强制角色定稿组合图 |
| `extra` | 背景路人、纯背景填充 | 默认生成预览图，只保留描述和预览 |

角色存在形态（entityType，4 类；与 level 正交，AI 显式输出，未输出默认 human）：

| entityType | 含义 | 生图能力（第一批） |
| --- | --- | --- |
| `human` | 人类角色（默认） | 正常走现有生图 |
| `creature` | 怪物/异常体/非人生物 | 第一批 fallback 到 human prompt，专属模板待第二批 |
| `group` | 群体角色（一群人） | 第一批 fallback 到 human prompt，群体构图待第二批 |
| `voice` | 纯声音角色（不露脸） | 第一批占位不出图，专属任务类型待第三批 |

`Character.level` + `Character.entityType` 是双维度正交：一个怪物可以是 lead（主角怪物），一群村民可以是 extra（背景群体）。重要性决定出图投入，存在形态决定生图方式。

角色参考图类型建议：

| kind | 含义 | 适用角色 |
| --- | --- | --- |
| `preview_front` | 正面半身预览图，用于确认角色长相和气质 | 所有角色 |
| `final_reference` | 基于当前可用 `preview_front` 生成的四要素角色定稿组合图：正面半身、正面全身、侧面全身、背面全身 | `lead`, `recurring`；`chapter` 可选 |
| `none` | 不生成角色图的兼容值，新项目默认不使用 | 特殊跳过场景 |

角色图是漫画制作资产，不是真人演员定妆照。生成 prompt 必须携带项目类型、作品名、题材标签、漫画形式和美术风格，并明确禁止 photorealistic portrait、live-action still、studio photography、cosplay photo 和 3D render。`dark_realistic` 等写实类风格只表示漫画写实氛围，不表示真人照片质感。

角色状态建议：

| status | 含义 |
| --- | --- |
| `draft` | 从剧本大纲或导入剧本提取出的角色草稿 |
| `needs_reference` | 角色信息已确认，但尚未确认定稿图 |
| `finalized` | 已确认主参考图，尚未被漫画候选图使用时仍可替换 |
| `in_use` | 主参考图已被至少一个 `Candidate` 使用，不允许覆盖旧图 |

角色定稿图锁定规则：

- 未被任何漫画候选图使用前，角色定稿图可以重新生成、替换或编辑。
- 一旦角色定稿图被用于生成 `Candidate`，旧参考图不能被覆盖或静默替换。
- 后续如果需要改变角色形象，应创建新的视觉版本或新的参考图，只用于后续新生成内容；旧漫画候选图继续追溯旧参考图。
- 剧情结构和分镜必须优先注入角色库中的文字档案和角色匹配信息；候选图和漫剧相关 prompt 必须优先注入已通过出图准备检查的角色主参考图。

## 10. Shot

分镜单元，是图片生成和排版的核心。

`Shot` 按章节保存。AI 刚生成但用户尚未确认的分镜应视为待确认预览，可以在右侧工作区展示、编辑、排序、新增和删除，但不能作为候选图生成输入。文件兼容模式的待确认预览写入当前章节 `storyboard.pending.json`；DB-only 模式使用 active pending StoryboardVersion。用户确认后才切换正式 `storyboard.json` / current StoryboardVersion，并将 `Chapter.status` 至少推进到 `storyboard_done`；已经达到 `images_done/layout_done/exported` 时不得倒退。

pending StoryboardVersion 在创建时冻结 `sourceStoryVersionId + sourceDigest`。确认请求必须原样回显 pending VersionSummary 的冻结来源，不得从 Workbench 展示 DTO、角色映射或其他可变投影重新编码 Story 文档并计算摘要。服务端仍须在同一事务中把冻结来源与 current StoryVersion 比较：一致才切换 current；ID 或 digest 真实变化时返回 `UPSTREAM_SOURCE_STALE`。确认新分镜不删除旧 Candidate、CandidateLockRevision、LayoutRevision 或 Export；这些产物通过来源关系成为 historical/stale，Preflight 派生“需更新”，而章节最远里程碑保持单调。

分镜阶段需要一次性生成漫画画格字段和基础漫剧镜头字段。两者共用同一个 `Shot` 核心，包括顺序、`beatId`、场景、角色、主要动作、景别和机位，但字段分层表达：`comic` 服务候选图和漫画排版，`motion` 服务后续图片序列、配音、字幕和基础视频合成。完整轻漫剧成片、TTS、字幕和视频导出不在分镜工作台直接执行。

`shotType`(景别) 和 `cameraAngle`(机位角度) 是共同核心层字段，comic 和 motion 共用一份——同一个镜头的景别和机位理应一致，不要在 comic/motion 各填各的。`comic.composition` / `motion.compositionDesign` 只保留构图说明（人物位置、视觉重心），不再塞景别和机位。详见 `文档/04_方案与决策/ADR-0007_分镜字段拆分与枚举升级.md`。

`comic.panelRhythm`、`motion.cameraMovement`、`motion.frameType` 均为受控枚举，AI 必须从固定值中选一个，不能自创值。`motion.durationMs` 是数字毫秒（给程序算时间线），`motion.durationHint` 是展示文本（给人看）。`motion.voiceLines` 是数组，支持一个镜头多人对话，替换了旧的 `voiceRole` + `line` 两个字段。

M1 正式采用一个 `Shot` 同时包含一个 `comic` 表达和一个 `motion` 表达，但契约不应把漫画画格和漫剧镜头永久绑定为一一对应。后续如果出现一个漫画画格拆成多个漫剧镜头，或多个画格合成一个漫剧片段，应通过 `motion` 的扩展结构或独立 `MotionShot` 映射实现。

候选图生成只能读取已确认的正式 `Shot[]`，并且必须先通过出图准备检查。如果章节剧本或剧情结构在分镜确认后被修改，UI 应派生“需更新”提示，提醒用户旧分镜可能已经和上游内容不一致。

### 枚举值速查（见 ADR-0007）

| 字段 | 层级 | 可选值 |
| --- | --- | --- |
| `shotType` | 共同核心 | establishing / wide / full / medium / close_up / extreme_close_up |

### 10.1 出图准备确认记录

出图准备是章节级检查点。页面会基于当前正式 `storyboard.json`、项目角色库和素材资产做派生检查；用户确认通过后，系统写入 `chapters/{chapterSlug}/preflight.json` 作为本章进入候选图前的确认记录。

当前实现的 `preflight.json` 记录 `storyboardId` 和 `storyboardUpdatedAt`，并在结构/分镜修改时清空。G2 已采纳目标改为不可变 PreflightRevision：保存 current StoryboardVersion、实际出镜角色生成输入、CharacterVisual/Asset 摘要、场景视觉、漫画形式和画风的聚合 SourceSnapshot。来源改变后旧 Preflight 保留并派生 stale，不再清空。

待处理出镜角色由 `POST /api/projects/:projectId/chapters/:chapterId/image-preflight/characters/resolve` 处理：

| action | 副作用 |
| --- | --- |
| `add_to_library` | 创建或复用同名 `chapter` 角色，`source = image_preflight`，并把正式分镜里的文本 token 替换为 `character.id` |
| `merge_existing` | 要求传入 `targetCharacterId`，把正式分镜里的文本 token 替换为已有 `character.id` |
| `mark_temporary` | 创建或复用同名 `extra` 角色，`source = image_preflight`，并把正式分镜里的文本 token 替换为 `character.id` |
| `ignore` | 从正式分镜 `Shot.characterIds` 中移除该文本 token |

上述表格描述当前实现。G2 实施后，出图准备不得原地改写 confirmed storyboard：角色 token 修复进入 pending Storyboard Working Copy，用户确认新 StoryboardVersion 后再重新确认 Preflight；旧 storyboard/preflight 保留历史。

出图准备至少检查：

| 检查项 | 规则 | 阻塞级别 |
| --- | --- | --- |
| 镜头角色绑定 | 每个 `Shot.characterIds` 应能匹配项目角色库中的 `Character`，或明确标记为临时/背景角色 | blocked |
| 本章新增角色 | 剧情结构或分镜发现的新角色应先形成角色图卡片；普通路径是看图、hover 编辑/删除、在弹窗内改用于 AI 生图的形象描述 / prompt 并重生成或应用；角色名只读；重生成直接替换当前卡片图；删除只删除当前图片版本，不删除角色条目；底层再自动落为项目角色、复用已有角色、临时角色或忽略 | blocked |
| 必需角色参考图 | `lead`、`recurring` 不论本章出镜几次都必须锁定定稿图（`primaryReferenceKind = final_reference`）；`chapter` / `minor` / `extra` 按本章实际出镜次数判断：出镜 ≥2 次（反复出现、需要稳定形象）才要求定稿，只出镜 1 次的路人不强制 | blocked |
| 临时/背景角色 | 只出镜 1 次的 `chapter` / `minor` / `extra` 角色当背景处理，默认只需 `preview_front` 预览图和文字描述，不阻塞出图 | 不阻塞 |
| 场景绑定 | 镜头 `Shot.sceneId` 必须非空且存在于本章剧情结构场景卡 | blocked |
| 场景参考图 | 本章被引用的场景如未生成参考图（`scene.referenceAssetId` 缺失），仅提示补充，不阻塞候选图生成 | warning |
| 画风上下文 | 当前章出图所需风格和漫画形式应可被候选图 prompt 读取；自定义画风可作为 warning | warning |

> 2026-07-19 起，角色素材要求在剧情结构确认时由共享策略 `level + entityType` 固定，不再读取 `appearanceCount`：`human + lead/recurring/chapter → final_reference`；`human + minor/extra → preview_front`；`creature/group → preview_front`；`voice → none`。`appearanceCount` 仅展示。`final_reference` 固定是一张包含“正面半身 + 正面全身 + 侧面全身 + 背面全身”的四要素组合图。DB 新预检写 `preflight-source-v2`；`v1` 可读取但在当前生产策略下视为 stale，必须重新预检确认。共享判断函数是 `packages/shared/src/character-visual-policy.ts`，前端、file 兼容逻辑和 DB SourceSnapshot builder 不得另写不同规则。详见 ADR-0018。

确认记录中应写入 `sceneChecks` 和 `styleCheck`：`sceneChecks` 来自正式分镜 `Shot.sceneId` 与当前章剧情结构 `scenes` 的匹配结果，并记录 `referenceAssetId` / `referenceReady` 表明场景是否已生成参考图；`styleCheck` 记录项目漫画形式、画风枚举和可读标签。镜头缺失场景或场景 ID 不在当前章结构场景卡中时，应作为 blocked issue 阻塞确认；场景缺参考图作为 warning issue 提示；自定义画风可作为 warning，后续通过风格板或项目级提示词片段补强。

出图准备确认后，`image_candidates` 才能创建 `shot_prompt_generate` / `image_generate` 任务。当前任务中心用 ID/时间 guard；G2 实施后统一使用 `NewWorkGate + GenerationTaskSource`，注入 PreflightRevision、完整 SourceSnapshot/sourceDigest 和任务实际引用的角色/场景视觉。任务完成时再次校验来源；旧任务迟到只能登记 historical，不能进入 current 候选集。

## 11. GenerationTask

所有 AI 和导出任务的统一记录。

```json
{
  "id": "task_001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "type": "image_generate",
  "status": "running",
  "targetType": "shot",
  "targetId": "shot_001",
  "inputJson": {},
  "outputJson": null,
  "errorJson": null,
  "attempt": 1,
  "createdAt": "2026-05-23T00:00:00.000Z",
  "startedAt": "2026-05-23T00:00:01.000Z",
  "finishedAt": null
}
```

任务类型见 `文档/02_架构与契约/生成任务协议.md`。

### 11.1 D75 已确认目标：持久任务与不可变尝试

`GenerationTask` 还必须承载数据库排队和当前执行权：

| 字段 | 说明 |
| --- | --- |
| `attempt/maxAttempts/nextRunAt` | 当前尝试序号、有限重试上限和下一次可运行时间 |
| `leaseOwnerId/leaseExpiresAt/heartbeatAt` | 单进程 worker 的原子 claim、租约和存活时间；网络与文件工作不在 claim 事务中执行 |
| `cancelRequestedAt` | 运行中任务的协作取消请求；worker 确认停止前状态仍为 `running` |
| `idempotencyKey/sourceDigest` | at-least-once 重复执行保护与启动来源快照 |
| `concurrencyKey` | 资源通道；V1 图片 provider 统一为 `image-provider` 且并发 1 |
| `needsReview` | 中断后无法判断外部副作用时为 true，不自动盲目重跑 |

每次 claim 新增 `TaskAttempt`：`id/taskId/attemptNo/workerId/startedAt/finishedAt/outcome/errorJson/artifactRefsJson`；结束时只允许一次终结写入，之后不可变。旧 attempt 不因重试或最终成功而覆盖；过期 lease 只有在任务类型可安全重放时才进入 `retrying`，否则 `GenerationTask` 进入 `failed` 并记录 `WORKER_INTERRUPTED/needsReview=true`。

G2-F2～F4 已按该模型实现 DB runtime 的持久 claim/lease/Attempt/恢复与 detail history，并为四类 G2 任务接入统一创建门禁、provider completion 和图片 Asset/Candidate 产物；file mode 仍保留 `TasksService` 内存 Map 和兼容 Promise worker，独立 Outbox consumer 与 legacy importer 仍后置。

### 11.2 D76 已确认目标：旧任务历史与 legacy stub

目标 `GenerationTask` 增加独立的记录来源和证据完整度：

| 字段 | 枚举/含义 |
| --- | --- |
| `recordKind` | `runtime/legacy_imported/legacy_stub`；只有 runtime 可进入 worker |
| `provenanceStatus` | `complete/partial/reference_only`；只允许随更强证据单向提升 |
| `retryDisabled` | legacy 记录固定为 true |
| `importSource/importedAt` | 导入来源和时间；runtime 为空 |
| `observedEvidenceJson` | 带 schemaVersion 的引用、来源路径、摘要和 artifact 存在性 |

约束：

- Candidate/Asset 的原 taskId 保持外键，不降级为字符串旁路。
- `legacy_stub.status=null/maxAttempts=0`，未知业务载荷、provider、时间和 attempt 保持空；不得从文件存在推断成功。
- `legacy_imported/legacy_stub` 不得获取 lease、创建新 TaskAttempt、取消或重试；重新生成创建新的 runtime task。
- 有完整 artifact 的旧记录可保存直接证明的历史字段，但仍是只读 `legacy_imported`。
- 导入按原 taskId 幂等；发现更强证据时可以提升 provenance 或把 stub 提升为 imported，证据冲突必须留在 MigrationReport。

正式数据库 migration 必须用约束和队列查询测试证明 legacy 记录无法进入 D75 状态机，不能只依赖服务层 if 判断。

## 12. Candidate

候选结果，通常关联一个分镜和一个图片 Asset。Candidate 是一次生成任务的不可变结果，不再同时承担“用户当前正式选择”的职责。

```json
{
  "id": "candidate_001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "shotId": "shot_001",
  "taskId": "task_001",
  "assetId": "asset_img_001",
  "index": 1,
  "status": "generated",
  "favoriteAt": null,
  "score": null,
  "notes": ""
}
```

| 字段/状态 | 含义 |
| --- | --- |
| `status=generated` | 已生成且仍可使用 |
| `status=rejected` | 用户明确废弃，不能新建定稿修订 |
| `status=superseded` | 被新的生成谱系替代，但历史引用仍保留 |
| `favoriteAt` | 非权威收藏时间；可收藏多张，不驱动排版或导出 |

`selected` 不再作为正式工作流状态；`locked` 不再是 Candidate 自身状态。普通 UI 使用“收藏/定稿此图/更换定稿图”，当前正式选择由 `CandidateLockRevision` 表达。当前代码仍保留旧枚举，待按 ADR-0010 迁移。

### 12.1 CandidateLockRevision

每次第一次定稿、替换定稿或重新定稿都创建不可变修订。

```json
{
  "id": "lockrev_shot001_002",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "shotId": "shot_001",
  "revision": 2,
  "action": "replace",
  "candidateId": "candidate_002",
  "previousRevisionId": "lockrev_shot001_001",
  "reason": "用户更换定稿图",
  "decidedAt": "2026-07-10T00:00:00.000Z",
  "recordedAt": "2026-07-10T00:00:00.000Z"
}
```

| 字段 | 说明 |
| --- | --- |
| `revision` | 同一 Shot 单调递增，从 1 开始 |
| `action` | `lock/replace/clear`；第一次定稿、更换和取消都必须留痕 |
| `candidateId` | `lock/replace` 时为本次正式选用的不可变候选；`clear` 时为空 |
| `previousRevisionId` | 上一个正式决定；首次定稿为空 |
| `reason` | 可选返修说明 |
| `decidedAt/recordedAt` | runtime 决策时间/数据库登记时间；legacy 无直接决策时间时 decidedAt 保持空 |

`Shot.currentCandidateLockRevisionId` 指向最近一次正式决定；该修订为 `clear` 时，当前没有可供下游使用的候选。旧 `lockedCandidateId` 只在迁移期由当前修订派生。A→B→取消→A 必须产生 v1(A)→v2(B)→v3(clear)→v4(A)，不能复用 v1。

更换定稿前必须计算格子、布局、导出和运行任务影响，并用 `expectedCurrentRevisionId + impactDigest` 做并发校验。

修订链必须线性：`(shotId, revision)` 唯一，非空 `previousRevisionId` 不得被两条 next 复用，next revision 从当前 revision + 1 得到。精确相同的丢响应重试可返回已存修订；已经发生后续决策时必须冲突，不能把“后来又选回同一图”认作重放。

候选 lock set 同时返回结构状态 `complete/incomplete/unresolved` 和来源适用性 `current/historical/legacy_unresolved`。两者正交：上游更新后可以仍然“每镜都有定稿”，但旧候选来源 historical，不能进新正式排版。

## 14. Layout 与 Export

漫画成稿模型。旧 `LayoutPage/PanelPlacement` 只保留归档迁移证据；G5-M2～M8 已用规范化 `LayoutDocumentV1`、DB-only `LayoutWorkingCopy`、不可变 `LayoutRevision` 与 `layout_publication` 接管编辑器、来源返修、正式保存和出版。每个格子必须追溯到它保存时使用的定稿修订。

```json
{
  "id": "layout_page_001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "pageNumber": 1,
  "format": "vertical_scroll",
  "width": 1440,
  "height": 2560,
  "placements": [
    {
      "shotId": "shot_001",
      "candidateId": "candidate_001",
      "sourceCandidateLockRevisionId": "lockrev_shot001_001",
      "x": 0,
      "y": 0,
      "w": 720,
      "h": 640
    }
  ]
}
```

正式“保存版本”必须形成 `LayoutRevision`，记录 `sourceLockSetDigest`；普通编辑/离开只自动保存 Working Copy。该 digest 是按 `shotId` 排序的 `{shotId,candidateLockRevisionId}` 数组之规范 JSON 的 SHA-256；固定字段顺序、UTF-8、无多余空白，不包含时间戳和本地路径。旧 `PanelPlacement` 或新 ImageElement/`LayoutSourceBinding` 的来源新鲜度由其 CandidateLockRevision 与对应 Shot 当前修订比较得到：

| freshness | 含义 |
| --- | --- |
| `current` | 格子使用当前定稿修订 |
| `stale` | Shot 已更换定稿，格子仍使用旧修订 |
| `unresolved` | 旧数据无法映射到定稿修订 |

旧 LayoutRevision 不原地改写。用户在 Working Copy 执行“替换当前格/替换全部过期格子”时只更新可撤销草稿，随后显式保存才创建新 LayoutRevision；任何 stale/unresolved 格子存在时不能创建新的当前正式版本或出版导出。

Layout/Export 查询使用两个轴：`revisionPosition=working_copy/current/historical` 表示用户当前选中或历史版本，`sourceResolution=current/stale/unresolved` 表示来源关系。更换定稿后保留 Chapter current layout/export 指针，但对应来源派生 stale；不清指针、不批量改历史行。

### 14.1 LayoutDocument V1 目标契约

`LayoutDocument` 是 Working Copy、不可变 `LayoutRevision`、浏览器预览和服务端正式渲染的共同事实源，不允许另存一套仅供前端拖拽的状态。首版核心结构为：

| 结构 | 目标边界 |
| --- | --- |
| `PageProfile/StripProfile` | Project.comicFormat 内部的页面宽高、页漫阅读方向、条漫宽度/段高；不修改项目版式 |
| `LayoutCanvas` | 页漫 page 或条漫 strip_section；数组顺序、尺寸、背景和显式画格阅读顺序 |
| `PanelFrame` | 矩形/圆角矩形裁切容器；与所属 ImageElement 形成受控复合对象，共同占一个顶层图层 |
| `ImageElement` | 画格所属或自由图像；非破坏 contain/cover/crop/offset/zoom/rotation/flip；保存完整 CandidateLockRevision 来源 |
| `TextElement` | `horizontal-tb/vertical-rl`；内容为 `RichTextDocument -> paragraphs[] -> runs[]` |
| `BalloonElement` | `speech/thought/shout/caption` 四类受控轮廓、最多一条可调尾巴，并内嵌同一富文本结构 |

- 模板只生成上述对象，不建立另一套模板数据模型。
- 一般多选只存在会话级 `SelectionSet`；批量命令将结果分别回写元素，V1 不定义通用 `GroupElement`。
- Working Copy 自动保存可变草稿；离开编辑器只 flush，不自动造版本。用户明确保存、历史恢复后确认或导出前保存才生成不可变 `LayoutRevision`。
- FontAsset 复用通用 `Asset(type=font, role=layout_font)`，记录 sha/cmap/weight/style/license/embedding/package/source；项目 provision 固定走 staged→`asset.promote` Outbox→ready，字体字节只在受控 storageKey。浏览器通过 verified Asset file API 加载 Asset-ID 隔离的 FontFace，不读取或回退客户端系统字体。
- AI 建议形成严格 `PendingEditorCommandSet`，保存来源/document/rowVersion digest、影响摘要、预览差异和待执行命令；来源或 Working Copy 变化后自动过期，只有用户 apply 才在 Server 原子执行并进入一次可撤销 Editor Command。
- G5-M2～M8 已实现 0.001 量化、JCS document digest、会话级命令历史、Working Copy rowVersion/CAS/recovery、线性 LayoutRevision/SourceBinding、current source catalog、PanelFrame/FreeImage/Shot tray、模板/crop/顺序、受控字体、横竖排富文本、IME/paste/overflow、四类气泡、profile resize、stale source preview/commit、稳定预检、warning acknowledgement、历史恢复、手机只读预览和 AI pending。source catalog 只读投影 Shot current CandidateLockRevision 与 ready Asset 尺寸/sha；来源替换和 profile resize 均可一次 Undo。0014 修正 source binding trigger，0016 关闭 legacy runtime 写入口；两者均为 forward-only。

### 14.2 LayoutDocument V2 智能成稿扩展

2026-07-22 已接受 `LayoutDocumentV2` 作为后续新写 Working Copy 的目标格式。M1～M6 完成 Shared strict codec、V1 WC 保守升级、V2→V1 纯投影、actor/protection reducer、对白/叙事/规则与视觉 composition、Server V2 Working Copy/Pending 和同一 Web 编辑器；2026-07-24 已完成 V2 LayoutRevision/Preflight/Publication、来源覆盖确认和桌面/手机正式路径。V2 不增加新的可见元素类型，只在 V1 根级增加 `automation`：

| 字段 | 作用 |
| --- | --- |
| `automation.policyVersion` | 固定人工保护与自动化状态解释版本，首版为 `layout_automation_v1` |
| `automation.composition` | 记录最近一次已应用初稿的 composition、Storyboard、lock set 与可选视觉分析摘要；不包含 taskId、时间戳、本地路径或 URL |
| `automation.dialogueBindings[]` | 把稳定对白项 ID 映射到气泡元素；用户删除/隐藏时保留 `user_suppressed` tombstone，避免后续智能重排把人工省略静默补回 |
| `automation.protections[]` | 以 `targetKind + targetId + scopes[]` 保护人工改动；scope 为 `existence/geometry/crop/text/style/tail/source/reading_order` |

V2 继续存入现有 `LayoutWorkingCopy.documentJson` 与 `LayoutRevision.documentJson`，由 `schemaVersion/kind` 选择 strict codec；不为 automation、保护项、对白或气泡新增关系表。已有 V1 Revision 保持不可变并可继续预览/导出；打开可编辑 V1 Working Copy 时以受控 `system` 命令升级为 V2，并为无法判定来源的既有可见对象生成 `explicit_preserve` 保护，不能默认视为“从未人工调整”。切换期提供 `V2 -> V1` 可见内容等价纯投影，但不得将其覆盖写回 V2 Working Copy/Revision。

正式版本和出版的摘要字段固定为：

| 存储/协议 | V1 | V2 |
| --- | --- | --- |
| `LayoutRevision.documentDigest` | 完整 V1 摘要 | 完整 V2 摘要，对外名 `revisionDocumentDigest` |
| `LayoutRevision.visibleDocumentDigest` | 新 runtime 行等于 `documentDigest`；历史行可为 null | 必填，等于严格 V2→V1 投影摘要 |
| `ExportRevision.revisionDocumentDigest` | 新 runtime 行保存 V1 摘要；历史在途 V1 可为 null 并按旧任务恢复 | 必填，复制不可变 Revision 完整摘要 |
| `ExportRevision.visibleDocumentDigest` | 新 runtime 行保存 V1 摘要；历史在途 V1 可为 null | 必填，复制并重算可见投影摘要 |

V2 `layout_render_plan_v2`、`layout_publication_manifest_v2` 和持久任务同时冻结两条摘要；Worker 从 Revision JSON 重新计算两者，并把 task `sourceProjection` 与封存的 `GenerationTaskSource` 行逐项重建核对。V1 wire/detail 与旧任务语义不增加 discriminator、不回填历史行。

V2 来源返修使用一个 `layout.replace_sources` user command batch。同一 Shot 的任一选中 appearance 会扩展为该 Shot 的全部 appearance；每个 panel image/free image 同时获得 `source/crop` 的 `user_edit` protection。原 composition provenance 保留，因此 preflight 对合法人工来源覆盖产生需确认的 `LAYOUT_COMPOSITION_SOURCE_OVERRIDE` warning，而不是伪造新的自动 composition。

M4 另按 ADR-0020 增加窄 `LayoutCompositionApplication`：每个成功应用的 `layout_compose` 任务至多一条不可变凭证，只记录初次 Working Copy 或重排 Pending command 的目标 ID、base/result digest 和目标行版本。它解决丢响应、重复 apply 与重启恢复，不保存文档内容，也不替代 GenerationTask、Working Copy、Revision 或 publication。

编辑命令增加 `actor=user|smart|system`：用户命令按修改字段写入保护；smart 命令应用前检查 protection 与元素 `locked`；system 只用于来源替换和格式升级等明确白名单。只有用户执行“允许智能调整”才能清除指定保护范围，模型、任务和自动修复均不得自行清除。

完整字段、命令映射和兼容规则见 `文档/02_架构与契约/2026-07-22_智能成稿规划与编辑保护契约.md`。

### 14.3 ExportRevision

正式导出是不可变快照，至少绑定：

- `layoutRevisionId`
- `revisionDocumentDigest`
- `visibleDocumentDigest`
- `sourceLockSetDigest`
- 导出 Asset IDs
- manifest
- `createdAt`

G5-M7 已创建多 Artifact 出版版本：页漫必需 `page_png[]`、可选 `document_pdf`；条漫必需 `strip_slice_png[]`、能力允许时可选 `long_png`。单一 `Chapter.currentExportRevisionId` 不会在 PNG/PDF 两条版本间竞争，未来 G6 只消费一个明确 current publication。正式任务绑定 `profileDigest/preflightDigest/rendererVersion/taskId`，manifest 不保存可变 current/stale 结论。

更换定稿不会删除旧导出。旧导出可查看和下载，但相对当前项目显示为历史版本；解决画布 stale 后生成新的 ExportRevision。

ExportRevision 保存 `completionApplicability=current/historical/legacy_unresolved`，它只表示任务完成登记时是否可切 current，ready 后不可变。之后的定稿变更只会使查询时 `sourceResolution` 变为 stale，不回写旧 completionApplicability。

## 16. 对话框与项目上下文模型

对话框属于项目工作区公共能力，但数据上不采用“整个项目共用一条完整对话记录”。

### 16.1 ConversationThread

按项目步骤隔离的对话线程。章节工作流下，剧本、剧情结构、分镜、出图准备、候选图、排版等章节内步骤应带 `chapterId`，避免不同章节的原始对话混在一起。

```json
{
  "id": "thread_001",
  "projectId": "project_001",
  "stepKey": "project_story",
  "chapterId": "chapter_001",
  "title": "剧本对话",
  "status": "active",
  "toolResults": [],
  "createdAt": "2026-05-25T00:00:00.000Z",
  "updatedAt": "2026-05-25T00:00:00.000Z"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 对话线程 ID |
| `projectId` | string | 所属项目 |
| `stepKey` | enum | `project_story/project_characters/story_structure/storyboard/image_preflight/image_candidates/layout_export/asset_package`；除辅助域 `project_characters` 外，其余七值与 `ProjectWorkflowStep.key` 共用 |
| `chapterId` | string? | 章节内步骤的章节 ID；素材包等项目级步骤可为空 |
| `title` | string | 线程显示名 |
| `status` | enum | `active/archived` |
| `toolResults` | `DialogueToolResult[]` | 当前线程内 AI 受控工具/技能调用结果；前端按 `messageId` 挂回对应 assistant 消息，作为过程卡片展示 |

唯一性建议：

```text
projectId + stepKey + chapterId?
```

当前代码仍是进程内线程。剧本前置阶段使用 `projectId + project_story`，用于用户提供剧本整理和灵感种子；章节内对话使用 `projectId + project_story + chapterId`，避免不同章节的原始对话混在一起。前端进入剧本页时必须先读取 workbench，解析当前 `currentChapter.id` 后再加载对话线程；如果路由没有显式 `chapterId`，默认加载当前章节线程，避免误读空的项目级线程。后续再扩展多线程、专题线程或持久化线程。

当前 `DialogueThread` DTO 会返回 `messages` 和 `toolResults`。普通 assistant 正文仍在 `ConversationMessage.content`，并作为面向用户的最终回复独立展示；工具/技能执行摘要、结构化灵感种子、导入分析、章节写入结果和修订来源进入 `toolResults`，作为过程卡片展示。前端必须让过程卡片和最终回复拥有不同视觉容器；最终回复正文自然展开，由外层对话消息区统一滚动，避免把过程日志直接堆进正文撑开页面，或让用户误以为技能输出后没有 AI 回复。

流式对话必须收敛 `ConversationMessage.status`：assistant 消息创建时为 `running`，正常完成后为 `completed`，运行时异常、浏览器刷新、页面离开或 SSE 连接中断后必须转为 `failed` 或完成态，不能长期停留在 `running`。当前实现会在 SSE 客户端断开时 abort OpenCode 请求；读取线程或新建同线程 turn 时，如果发现没有活跃流式请求的旧 `running` assistant 消息，会标记为 `failed`，错误码为 `DIALOGUE_STREAM_INTERRUPTED`。

### 16.2.1 ProjectScriptOutline

剧集章数：
剧情简介：

规则：

- `analyze_script_import` 是正式工具动作，但不写项目文件。
- 写入类工具结果应带 `chapters` 和 `currentChapter`；`currentChapterId` 保留为路由和旧消费者兜底。
- `import_script_to_chapters` 是后端/AI 工具动作，不是 UI 主按钮。
- 附件上传和输入框粘贴只是输入方式，单独选择附件不写章节。

- 只有分析结果确认“内容像可导入剧本且章节边界可信”时，后端才可以触发 `import_script_to_chapters`。
- 分析失败或需要用户确认时，不写 `chapters/*/script.md`，只返回对话提示或 `failed/needs_user_confirmation` 类工具结果。

- 低可信章节边界，例如单独成行的 `1`、`2`、`3` 或 Markdown 标题 `# 1`，不能绕过内容校验直接写入章节。

- 用户回复“选第 N 个方向”后触发 `generate_script_outline_from_seed`，生成固定格式项目级「剧本大纲」并保存到项目目录；此时不写章节正文。
- 用户确认剧本大纲后触发 `generate_script_from_outline`；章节正文由 AI / `script-chapter-drafting` 生成固定格式「章节剧本」。当用户明确说“生成第 N 章/下一章/当前章”时，后端解析目标已有章节并写入对应 `script.md`；其中 `第 X 章：章节标题` 作为目标章节显示名同步到 `Chapter.title`；剧本名称来自项目级大纲并显示在章节下拉框右侧，不写入章节正文。

- `import_script_to_chapters` 写入的章节正文也必须统一为固定格式「章节剧本」；最终章节剧本不输出主体列表、正式场景列表、剧情节拍、分镜剧本、镜头编号、图片 Prompt 或 JSON。

- 图片 provider metadata 关系化保存：`providerId/modelId/baseUrl/credentialRef/credentialSource/configured/keyFingerprint/updatedAt`。`credentialRef` 只能由后端解析。
- `GET /api/settings` 目标响应不再包含 `keyPreview`；只返回 `configured/source/keyFingerprint/updatedAt`。写入、替换和清除仍是单向操作。
- 图片 key 在调用 provider 时只能短暂存在于后端进程内并通过 HTTPS Authorization 使用；不得持久化到 `GenerationTask.input/output/error` 或诊断导出。
- 旧 `app-settings.json` 迁移时，文本 key 先验证 OpenCode 已接收再删除本地副本；图片 key 写入 SecretStore、校验 fingerprint 后再删除明文字段。含 key 的旧设置文件必须先脱敏，不能直接进入 D71 只读封存。

## 18. 最小数据库实现建议

下列列表是 ADR-0012 形成前后的领域最小概念，不是可直接实现的完整 M0 schema：

1. `Project`
2. `Chapter`
3. `ProjectWorkflow`
4. `StoryVersion`
5. `Character`
6. `SceneLocation`
7. `Shot`
8. `GenerationTask`
9. `TaskAttempt`
10. `Candidate`
11. `CandidateLockRevision`
12. `Asset`
13. `LayoutRevision`
14. `LayoutSourceBinding`
15. `ExportRevision`
16. `MigrationRun`
17. `OutboxEvent`

`ChapterScriptVersion`、`StoryBeat`、`VideoSegment` 的具体拆表时机仍由 D7 方案确定。`CandidateLockRevision`、`LayoutRevision`、`LayoutSourceBinding` 和 `ExportRevision` 因 D3/G5 需要事务、外键、历史查询和影响分析，应关系化；PanelFrame/Image/Text/Balloon 继续保存在版本化 LayoutDocument，不拆成大量关系表。

`ProjectWorkflow` 当前可由章节状态推导并写入 `workflow.json`；接数据库后可以作为项目级状态表或快照 JSON 保存，避免流程栏、对话框和任务入口各自推导。

D7 DB-only 切换前，用户需要恢复的对话与待确认事实也必须进入数据库，至少增加：

1. `ConversationThread`
2. `ConversationMessage`
3. `ProjectContextFact`
4. `DialogueRuntimeSession`

`MigrationRun` 保存导入来源、摘要、计数、证据冲突和校验结果；`OutboxEvent` 承载数据库提交后必须补做的文件操作或删除清理。两者都不能用普通日志文件代替。

2026-07-11 的 G1 代码/真实数据复核进一步确认：如果只建上面这些主实体，会漏掉 current/pending 指针、Scene/Shot 投影、角色视觉版本、对话工具结果、SecretStore metadata、TaskAttempt/并发槽、导入 source map 和 runtime bundle 的落点。因此目标 Schema 按八组展开为 44 个明确模型，同时坚持“关键关系表 + 复杂版本 Json”，不把画格、文字 run、气泡节点完全关系化。2026-07-12 已将该 Schema 写入 Prisma，并形成正式 `0001～0010` migration tree；Project/Chapter/Script 最小 DB 切片、G2 A0～F4 与 G3-M shadow importer 至 A11C 已接线，full importer、全量 Repository 与生产切换仍后置。正式字段、索引、CHECK/trigger、旧文件映射和 G2–G6 边界见 `文档/04_方案与决策/2026-07-11_G1数据库Schema字典与旧数据映射.md`。

2026-07-11 已采纳的 G2 细化不增加第 45 个模型：Script 复用 Chapter working fields，Story/Storyboard 复用 pending version 做 copy-on-write，Preflight 使用实时 preview + 不可变 revision；freshness 从 current/pending 指针、来源 ID 和 RFC 8785 摘要派生。Story 文档不再包含场景视觉 Asset，Storyboard 文档不再包含候选锁定或生成状态，防止错误摘要级联。2026-07-12 已完成 G2 A0～F4，包括 persistent task 和四类 worker；legacy importer、独立 Outbox consumer、capability switch 与真实 provider smoke 仍后置。
