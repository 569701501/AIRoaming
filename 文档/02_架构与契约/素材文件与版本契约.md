## 1. 目标

素材文件契约定义 workspace 中所有项目文件、生成素材、导出物和元数据的稳定位置。数据库保存关系，文件系统保存实体文件，两者必须能互相追溯。

## 2. Workspace 根路径

MVP 使用本地路径。当前阶段是内部使用，真实素材文件和项目元数据优先放在用户机器的本地 workspace 中；后端服务统一管理路径、写入文件和记录元数据，前端不能直接写本地物理路径。

```text
workspace/
  projects/
    {projectId}/
```

后端负责把逻辑路径解析为物理路径，前端不直接拼接本地绝对路径。后续如果需要团队共享、云同步或对象存储，只替换后端的 workspace / asset 适配层，不改变前端调用方式。

## 4. 文件路径规则

| 类型 | 路径 |
| --- | --- |
| 项目元数据 | `projects/{projectId}/project.json` |
| 项目工作流状态 | `projects/{projectId}/workflow.json` |
| 章节元数据 | `projects/{projectId}/chapters/{chapterSlug}/chapter.json` |
| 当前章节剧本 | `projects/{projectId}/chapters/{chapterSlug}/script.md` |
| 章节剧本版本 | `projects/{projectId}/chapters/{chapterSlug}/script.versions/{version}.md` |
| 结构化剧情 | `projects/{projectId}/chapters/{chapterSlug}/structure.json`，用户确认后写入；用户界面以可编辑结构表展示 |
| 待确认分镜预览 | `projects/{projectId}/chapters/{chapterSlug}/storyboard.pending.json`，AI 生成和用户确认前编辑时写入；确认后删除 |
| 分镜快照 | `projects/{projectId}/chapters/{chapterSlug}/storyboard.json` |
| 角色视觉版本 | `projects/{projectId}/assets/characters/{characterId}/visual-v{version}/preview.webp` 或 `final-reference.webp`；version 从 1 单调递增并以三位数落盘（如 `visual-v001`），两种文件名分别对应 `preview_front/final_reference` |
| 分镜候选图 | `projects/{projectId}/chapters/{chapterSlug}/candidates/{shotId}/{candidateId}.{ext}`；当前 `image_generate` 写 `.webp`，未来扩展格式时扩展名必须与 Asset.mimeType 一致 |
| 章节排版（DB-only） | `LayoutWorkingCopy/LayoutRevision.documentJson` 是关系事实源；现有 `layout.json/layout_page_{pageNumber}.json` 只作归档迁移输入，不再双写 runtime current |
| 章节出版导出（G5 已实现） | `projects/{projectId}/chapters/{chapterSlug}/exports/{exportRevisionId}/`；目录内按 profile 保存 page/strip PNG、可选 PDF/long PNG 与 canonical manifest，每个目录不可变 |
| 章节场景参考图 | DB-only 新资产：`projects/{projectId}/chapters/{chapterId}/scenes/{sceneKey}/visuals/{assetId}/background.webp`，每次重生成使用独立 Asset 目录；file-mode/历史数据可只读兼容 `projects/{projectId}/chapters/{chapterSlug}/scenes/{sceneId}/background.webp` |
| TTS 音频 | `projects/{projectId}/assets/audio/tts/{shotId}_{assetId}.mp3` |
| 漫画页面（旧兼容） | `projects/{projectId}/exports/pages/page_{pageNumber}.png`；G5 后不作为新 runtime 输出 |
| PDF 导出（旧兼容） | `projects/{projectId}/exports/pages/comic_{exportId}.pdf`；G5 后归入对应 ExportRevision 目录 |
| MP4 导出 | `projects/{projectId}/exports/video/{videoDraftId}.mp4` |
| 素材包 | `projects/{projectId}/exports/packages/{packageId}/` |
| 旧任务输入（迁移证据） | `projects/{projectId}/tasks/{taskId}.input.json` |
| 旧任务输出（迁移证据） | `projects/{projectId}/tasks/{taskId}.output.json` |
| 旧任务错误（迁移证据） | `projects/{projectId}/tasks/{taskId}.error.json` |

项目创建时只建立项目记录，至少写入：

```text
projects/{projectId}/project.json
projects/{projectId}/workflow.json
projects/{projectId}/chapters/chapter-001/chapter.json
projects/{projectId}/chapters/chapter-001/script.md
```

其中 `project.json` 在创建时至少保存项目名称、项目类型、不可变的 `comicFormat`、当前章节和项目级元数据；`comicFormat` 由创建弹窗“漫画版式”必选，不允许缺省为竖向条漫。`workflow.json` 保存当前章节对应的 7 步流程状态、下一步和证据路径。项目角色库是常驻资产入口，不是 workflow 线性门槛；进入候选图前的角色、场景和画风门槛由出图准备确认记录承载。故事标题、题材标签、画风方向和故事原文进入项目后，在第 1 步“剧本”保存。故事原文保存为独立文本文件，避免后续结构化、版本化和素材包导出时只能从内存或数据库反推。D1 正式规则见 ADR-0009。

G3 file compatibility 冻结如下：新 `project.json` 只写 `vertical_scroll/paged_comic`；旧 `page_horizontal` 在 repository 输入边界只读投影为 runtime `paged_comic`，但记录内部 provenance，保存章节等无关内容时仍序列化原 alias，不能借普通写入静默迁移。`four_panel/缺失/空/非法` 聚合为 `LEGACY_COMIC_FORMAT_DECISION_REQUIRED` 并使项目列表 fail-closed，不能默认 vertical 或把项目从列表静默跳过。只读 audit 必须显式传入 workspace 根，只读取 `projects/*/project.json`，不改内容/mtime、不连接 DB/网络。最终 canonical 导入、MigrationIssue 决议、备份恢复和 provenance 清除只归 G3-M/G1 maintenance importer。

在数据库持久化接入前，`project.json`、`workflow.json`、`chapters/{chapterSlug}/chapter.json` 和 `script.md` 同时承担本地恢复源职责。后端服务启动或首次访问项目接口时，应从 `workspace/projects/*` 恢复项目列表、当前章节、章节状态和当前章节剧本文本；`workflow.json` 可由章节状态重新推导并补写。

恢复时，非 `draft` 章节若 `script.md` 与 `chapter.json.sourceText` 均为空，但 `currentScriptVersionId` 指向的版本文件正文非空，应以该当前版本自愈正式正文并在后续项目写入时补回 `script.md`。`draft` 章节允许保持空白；明确“清空本章”必须同时清除当前版本标识和版本文件，不能被自愈逻辑恢复。

当前后端已在创建项目时写入默认章节目录。`projects/{projectId}/story/story_draft.source.txt` 旧路径已废弃，新项目不再创建、读取或写入；剧本文本只以章节目录下的 `script.md` 为事实源。

剧本草稿保存时，后端覆盖写入当前草稿文件：

```text
projects/{projectId}/project.json
projects/{projectId}/chapters/{chapterSlug}/chapter.json
projects/{projectId}/chapters/{chapterSlug}/script.md
```

`script.md` 是当前章节草稿入口。用户点击“完成本章”时，必须额外写入 `script.versions/{version}.md` 或等价版本记录，并把 `chapter.json` 中的状态推进到 `script_done`。

保存草稿或完成本章时，应先移除项目级“剧本名称/剧集名称”等非章节正文，再对规范化后的章节正文执行非空校验；规范化结果为空时必须拒绝写盘，也不能创建空版本。

章节目录命名建议使用稳定 slug：

```text
chapter-001
chapter-002
chapter-003
```

章节显示名可以是“第 1 章”或用户自定义标题，但系统排序不能只依赖显示名。

## 5. Asset 记录与文件对应

每个可被 UI 引用、导出、复用或追溯的文件都应有 `Asset` 记录。

路径字段统一使用 G1 正式名 `storageKey`，保存相对 workspace 根的规范路径，不带 `/workspace/` 前缀。文件态 `WorkbenchAsset.path/meta` 只是兼容展示投影，分别映射到 `storageKey/metadataJson`；数据库模型不得继续使用 `path/meta` 作为第二套字段。DB 模式读取 Asset 字节必须按同项目 Asset 行的 `storageKey` 定位，不能使用展示 path；生产路径只允许 `projects/{projectId}/...`，真实迁移素材还允许 `legacy-import/{projectId}/...`，其他前缀一律拒绝。

```json
{
  "id": "asset_img_001",
  "projectId": "project_001",
  "chapterId": "chapter_001",
  "type": "image",
  "role": "candidate_image",
  "mimeType": "image/webp",
  "storageKey": "projects/project_001/chapters/chapter-001/candidates/shot_001/candidate_001.webp",
  "status": "ready",
  "sha256": "sha256:...",
  "bytes": 245760,
  "width": 1024,
  "height": 1536,
  "durationMs": null,
  "sourceTaskId": "task_001",
  "metadataJson": {
    "shotId": "shot_001",
    "candidateId": "candidate_001"
  },
  "metadataSchemaVersion": 1,
  "metadataDigest": "sha256:...",
  "createdAt": "2026-07-11T00:00:00.000Z",
  "updatedAt": "2026-07-11T00:00:00.000Z",
  "readyAt": "2026-07-11T00:00:00.000Z",
  "failedAt": null,
  "deletingAt": null
}
```

## 6. 版本策略

### 6.1 章节剧本版本

每次用户对章节剧本做大改或点击“完成本章”时，应创建章节剧本版本。

```text
chapters/chapter-001/script.versions/20260527_001.md
chapters/chapter-001/script.versions/20260527_002.md
```

### 6.2 故事版本

每次用户对章节结构化剧情做大改，应创建新的 `StoryVersion`。

```text
story_v001
story_v002
story_v003
```

### 6.3 分镜版本

MVP 当前分镜以章节目录文件为事实源：AI 生成或用户编辑待确认预览时写出 `storyboard.pending.json`；用户确认后写入正式 `storyboard.json` 并清除 pending 文件。后续如果需要保留历史版本，可在关键操作后写出快照：

```text
shots_v001.json
shots_v002.json
```

触发快照的动作：

- 首次生成分镜。
- 批量编辑分镜。
- 进入图片生成前。
- 导出漫画页前。

### 6.4 候选版本

候选不覆盖旧文件。重生成会产生新的 `Candidate` 和 `Asset`。

```text
chapters/chapter-001/candidates/shot_001/
  candidate_001.webp
  candidate_002.webp
  candidate_003.webp
```

扩展名不是固定常量：当前 `image_generate` 写 WebP；未来新增格式时必须由 `Asset.mimeType` 与实际文件字节共同决定，不能重新引入另一套候选目录。

G5-M8 起，图片提供方声明的 MIME 只能作为输入提示；worker 必须按真实字节识别 PNG/JPEG/WebP，并据此确定 `Asset.mimeType` 和扩展名。正式 LayoutRevision 与 renderer 还会再次检查 EXIF orientation、色彩空间和动画标记：非规范 orientation、未受控 ICC/色彩空间、APNG/动画 WebP、未知字节或 MIME/字节不一致均 fail-closed，不允许不同 renderer 自行猜测。

### 6.5 候选定稿修订

Candidate 文件和生成来源不可变；第一次定稿、每次更换定稿和重新定稿都新增 `CandidateLockRevision`。`Shot.currentCandidateLockRevisionId` 只指向当前决定，不能通过改写 Candidate 状态伪造历史。

```text
lockrev_shot001_001 -> candidate_001
lockrev_shot001_002 -> candidate_002
lockrev_shot001_003 -> candidate_001
```

A→B→A 是三个正式决定，必须保留三个修订。

### 6.6 布局修订

编辑命令与自动保存只更新 `LayoutWorkingCopy`；用户明确“保存版本”、历史恢复后确认或导出前保存时才创建 `LayoutRevision`，避免每次拖动产生正式版本。每个候选图片元素投影 `LayoutSourceBinding`，同时记录 Candidate、CandidateLockRevision、Asset 和 sourceDigest；布局修订记录整套 `sourceLockSetDigest`。

```text
chapters/chapter-001/layout/revisions/layoutrev_001/layout.json
chapters/chapter-001/layout/revisions/layoutrev_002/layout.json
```

旧布局不可原地覆盖。若某格来源修订不是对应 Shot 的当前定稿修订，该格派生为 `stale`；无法回填来源时为 `unresolved`。这两种状态都阻止生成新的正式导出。

### 6.7 导出修订

每次正式出版产生新的 `ExportRevision(kind=layout_publication)` 和独立目录，并绑定 `layoutRevisionId/sourceLockSetDigest/profileDigest/preflightDigest/rendererVersion/taskId`。

```text
chapters/chapter-001/exports/exportrev_001/page-0001.png
chapters/chapter-001/exports/exportrev_001/manifest.json
chapters/chapter-001/exports/exportrev_002/comic.pdf
```

同一个 current publication：页漫必须含 `page_png[]` 并可选 `document_pdf`；条漫必须含 `strip_slice_png[]` 并可在能力允许时含 `long_png`。PNG/PDF 不再各自竞争 Chapter 的单一 currentExportRevisionId；G6 只消费一个明确 current publication。

旧导出文件不可修改或删除。上游更换定稿后，旧导出相对当前来源显示为历史/已过期；解决布局 stale 后再创建新的导出修订。这个变化由 current pointer 与 source freshness 查询派生，不批量改写旧 ExportRevision 或文件。

## 7. 锁定规则

- 一个 `Shot` 在同一时间最多指向一个当前 `CandidateLockRevision`，但所有历史修订都必须保留。
- Candidate 是不可变生成结果；`selected` 不作为正式工作流状态，收藏不驱动排版或导出。
- 更换当前定稿前必须预览下游影响，并使用 `expectedCurrentRevisionId + impactDigest` 防止并发状态漂移。
- 被当前或历史修订引用的候选与 Asset 不得硬删除；废弃只影响新建修订资格。
- 新布局默认读取当前定稿修订；已有布局不因更换定稿而被静默改写。
- 正式导出只接受图片 binding 均为 `current`、完整预检通过的 current LayoutRevision，并创建不可变 publication ExportRevision。
- 接受方案与迁移规则见 ADR-0010。

## 8. Manifest 格式

素材包必须包含 `manifest.json`。

```json
{
  "project": {
    "id": "project_001",
    "name": "月下旅人"
  },
  "export": {
    "id": "exportrev_002",
    "createdAt": "2026-05-23T00:00:00.000Z",
    "type": "asset_package",
    "layoutRevisionId": "layoutrev_002",
    "sourceLockSetDigest": "sha256:..."
  },
  "stories": [],
  "shots": [],
  "assets": [
    {
      "assetId": "asset_img_001",
      "storageKey": "projects/project_001/chapters/chapter-001/candidates/shot_001/candidate_001.webp",
      "packagePath": "chapters/chapter-001/candidates/shot_001/candidate_001.webp",
      "sourceTaskId": "task_001",
      "shotId": "shot_001",
      "candidateId": "candidate_001",
      "sourceCandidateLockRevisionId": "lockrev_shot001_003"
    }
  ]
}
```

`storageKey` 是源 Asset 的规范项目存储路径；`packagePath` 是未来 G6 ZIP 内的相对路径，两者用途不同，均不得退回旧的扁平 `assets/images/{shotId}` 目录。G6 已后置，ZIP 内最终目录仍可在 G6 方案中细化，但必须从同一 source Asset 显式投影并保留摘要。

D7 全量数据库化完成后，`CandidateLockRevision`、`LayoutRevision`、`ExportRevision` 及当前指针以数据库为关系事实源；文件目录和 manifest 继续承担不可变产物、离线检查与导出追溯证据，不再与数据库双向争夺“当前版本”定义。

D7 切换后，`tasks/{taskId}.input/output/error.json` 只作为旧数据导入证据或显式诊断导出，不再是新任务的权威状态。完整旧 artifact 导入为只读 `legacy_imported`；只有 Candidate/Asset 引用的旧 taskId 导入为 `legacy_stub`。导入器保留来源路径和 sha256，但不得根据文件缺失或已有产物推断任务终态；新任务的 input/output/error、attempt 和 lifecycle 只以数据库为事实源。

G3 不全局替换历史 Preflight/Layout/Task 中的 `page_horizontal/four_panel`，也不重算其 digest。新 task 必须保存 `sizePolicyVersion` 与最终 width/height；缺该字段的 V1 task 是只读历史，不能用当前代码补推后执行。

G1 切换时不能把 `workspace/projects/{projectId}` 整体 chmod 为只读：当前 Asset 图片、场景图和导出字节与 JSON/Markdown 元数据混在同一树中，DB-only 后仍需继续写 Asset。正式做法是把 project/chapter/workflow/script/structure/storyboard/preflight/candidates/layout/task artifact/shared index 等旧元数据移入 `{dataRoot}/legacy-metadata/{cutoverRunId}` 的独立只读档案，保持已登记 Asset 的 storageKey 不动；完整 workspace snapshot 只承担开放新写入前的回滚和观察期证据，不参与运行时读取。

2026-07-14 R2 已验证：修改 metadata archive 的副本不会改变原 archive、目标 DB 或 Workbench 运行态；目标库和 fresh restore 的 67/67 ready Asset 均能按 `storageKey` 读回并通过 bytes/MIME/sha256。archive/backup 的删除仍需独立用户授权，不能因观察通过自动清理。

## 9. 清理策略

MVP 不自动删除历史候选。项目删除属于用户显式确认后的破坏性操作，不归入自动清理。

| 清理类型 | 规则 |
| --- | --- |
| 项目删除 | 用户二次确认后删除 `workspace/projects/{projectId}`、项目记录和该项目关联任务记录 |
| 临时文件清理 | 删除失败任务的临时文件 |
| 废弃候选清理 | V1 不自动删除；仅当未被任何定稿修订、布局、导出、任务或 manifest 引用时，未来才可提供显式物理清理 |
| 历史导出清理 | 不单独删除旧 ExportRevision 文件；只随用户明确删除整个项目一起清理，后续若引入保留策略必须另做决策 |
| 孤儿文件扫描 | 文件存在但无 Asset 记录时报告 |

## 10. 禁止事项

- 前端直接写物理路径。
- 覆盖已有候选图片。
- 导出物不写 manifest。
- 数据库存在 Asset 但文件缺失且无错误记录。
- 文件存在但无法追溯到项目或任务。
