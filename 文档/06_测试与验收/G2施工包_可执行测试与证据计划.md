# G2 施工包：可执行测试、Fixture、Barrier 与证据计划

## 1. 目标

把原 G2 验收矩阵从“用例描述”落成明确的测试文件、fixture builder、barrier 协议、package script 和证据目录。本文定义施工目标；在对应文件真实实现之前，命令不得写入完成记录冒充已通过。

## 2. 测试层次

| 层 | 证明什么 | 不证明什么 |
| --- | --- | --- |
| Shared unit | strict codec、JCS、digest、Resolver、stable Shot ID | DB/事务 |
| SQLite contract | 0009 对象、trigger/index、失败原子性 | Service 语义 |
| Nest integration | 公开 Service/API、事务、CAS、重启读回 | 浏览器交互 |
| Persistent worker integration | claim/lease/barrier/applicability/recovery | 真实 provider |
| Playwright | 双页面冲突、用户语言、历史可看、旧产物不消失 | importer/底层 trigger 全覆盖 |
| Migration importer | snapshot→DB、unresolved、幂等 | 正常 runtime UI |

不得用更高层单个 happy path 代替低层合同测试。

## 4. G2 DB Fixture

`G2DbFixture` 必须：

1. 在系统临时目录创建唯一 marker 根。
2. 创建临时 workspace/data/db，不读取用户真实 HOME/key。
3. 用正式 Prisma Schema fresh deploy 0001～0009。
4. 显式设置 `AIROAMING_PERSISTENCE_MODE=db`。
5. 从 Nest application context 取得公开 `ProjectsService` 和 G2 services。
6. 支持 `reopen()`：关闭 Nest/Prisma、重新打开同一 DB，证明重启读回。
7. 清理前验证 marker/realpath，禁止删除未知路径。

业务 fixture 默认只通过公开 Service/API 建立。以下场景允许直接 SQL：

- trigger 负例。
- migration preflight 污染数据。
- 模拟无法由公开 API 构造的损坏状态。

直接 SQL 用例必须在标题包含 `[contract-corruption]`，不能被用户路径测试复用。

## 5. 固定 Fixture Catalog

| 名称 | 最低状态 | 用途 |
| --- | --- | --- |
| `g2_empty_chapter` | Chapter，无 current，Script empty | 首次编辑/发布 |

## 6. Fake Provider Barrier 协议

### 6.1 Barrier 名称

```text
before_provider
after_provider_before_stage
after_stage_before_db_commit
before_current_pointer_update
```

### 6.2 控制接口

只在 `NODE_ENV=test`、`AIROAMING_E2E_BARRIERS=1` 且 host 为 loopback 时启用：

```text
POST /__e2e__/barriers/{name}/arm
body: { "token": "<run-scoped uuid>" }

POST /__e2e__/barriers/{name}/reached
body: { "token": "...", "taskId": "...", "attempt": 1 }
# 该请求保持 pending，直到 release

GET /__e2e__/barriers/{name}?token=...
response: { "state": "idle|armed|reached|released", "taskId": "..." }

POST /__e2e__/barriers/{name}/release
body: { "token": "..." }
```

规则：

- token 必须包含当前 E2E runId 绑定；跨 run 拒绝。
- 同一 name/token 只允许一次 `armed -> reached -> released`。
- 默认无 barrier；生产 adapter 是同步 no-op，不访问网络。
- 测试等待单次最多 10 秒，超时输出 task/attempt/barrier 状态，不长时间 sleep。
- provider failure mode 与 task barrier 状态相互独立，可组合 429/500/late_success。

### 6.3 注入点

持久 worker 执行器只调用一个接口：

```ts
interface TaskExecutionBarrier {
  reach(name: G2BarrierName, context: { taskId: string; attempt: number }): Promise<void>;
}
```

生产 `NoopTaskExecutionBarrier`；integration 使用 `ControllableTaskBarrier`；E2E 使用 loopback adapter。业务 Service 不自行判断测试环境。

### 8.1 G2-A0

unknown field 全拒绝

Stable Shot ID 同输入一致、任一 scope/requestId 改变则不同

最低命令：`pnpm test:g2:unit` 中 Shared 部分 + shared typecheck。

### 8.2 G2-A1

```text
fresh 0001～0009 deploy
同库二次 deploy no pending
integrity_check=ok / foreign_key_check=0
0008 DB 启动 G2 capability fail-closed
2 index/14 trigger exact
migration preflight 六类污染数据全部失败且对象数不变
```

### 8.3 G2-B

至少：

- 首次 Script 发布。
- dirty 不让旧 Story 丢失。
- clear 有 current 时变 dirty 空稿，不删 history。
- revert 回 clean。
- AI pending suggestion 存在时 gate blocked；adopt 只写 Working Copy，discard 不建 ScriptVersion。
- 两客户端同 rowVersion 只有一个成功。
- publish 在 insert 后/指针前异常整事务回滚。
- 丢响应重放不产生第二版本/第二下一章。
- `reopen()` 后 working/current/history 一致。

### 8.4 G2-C1

- create pending clone/empty。
- 同目标 create 重放，不兼容 active pending 冲突。
- full replace strict codec + rowVersion。
- confirm projection 与 document逐项一致。
- confirm 后旧 Story historical、旧 Board stale 但仍存在。
- 丢弃不改 current。
- history copy 创建新 pending 并绑定当前 Script，不复活历史 ID/source。
- V1 pending 显式 re-encode，失败产生 unresolved。

### 8.5 G2-D1

- create Shot 同 requestId 同 ID。
- 未知客户端 Shot ID 拒绝。
- retired Shot 不复活。
- confirm 新增/保留/删除 Shot 的 active/retired 与 projection 一致。
- 旧 Candidate/Layout/Export 行和 ID 不变。
- Board confirm 并发只有一个成功。
- history copy 创建新 pending，retired Shot ID 不得因此复活。

### 8.6 G2-E

- 所有 current/stale/pending/missing/source unresolved truth table。
- Preflight preview 零写入。
- preview 后 Asset/source 变化，confirm 409 且零 revision。
- confirm 同事务插 revision+切 pointer。
- workflow 与 productionState 同查询一致。
- 前端不读取 updatedAt 推导 freshness。

### 8.7 G2-F worker/importer

只有依赖真实接线后执行：原 G2 `G2-TASK-01～12`、`G2-MIG-01～10` 全部映射到可执行测试 ID。依赖未接线时必须写 `integration_blocked`，不能 skip 后宣称 G2 完成。

## 9. 故障注入矩阵

| barrier | 中间动作 | 期望 |
| --- | --- | --- |
| before_provider | 编辑 pending | provider 可继续；finish historical，不写 target |
| after_provider_before_stage | 发布新上游 | 输出可保存诊断；target/current 不变 |
| after_stage_before_db_commit | 替换 active pending | staged 非权威；CAS=0；Task historical |
| before_current_pointer_update | 注入 DB 异常 | formal row、projection、pointer 全回滚 |
| 任一 running barrier | cancel | cancelRequestedAt 可见；迟到结果不写 current |
| provider late_success | lease 过期并由新 claim 接管 | OLD claimToken 更新 0；新 Attempt 唯一 |
| after_provider_before_stage | 杀进程并 reopen | recovery 按 policy retry/manual review；不混用 Chapter rowVersion |

## 10. Playwright 用户路径

### 路径 A：有未确认修改

1. 打开 exported fixture。
2. 修改 Script，不发布。
3. 验证旧 Story/Board/Candidate/Layout/Export 可查看。
4. 验证新下游任务按钮 disabled，显示“有未确认修改”。
5. 还原后恢复 current。

### 路径 B：来源已更新

1. 发布 Script v2。
2. 验证旧 Story 显示“来源已更新”，历史仍可打开。
3. 创建并确认 Story v2，再观察 Board/Preflight 逐层 stale。
4. 不出现里程碑倒退或历史删除。

### 路径 C：双页面冲突

1. A/B 打开同一 pending。
2. A 保存成功。
3. B 保存收到 409，自动拉新 state，但不覆盖 B 编辑内容。
4. 用户可复制 B 内容后手工合并。

### 路径 D：历史复制

1. 打开旧 Story/Board detail。
2. 确认页面只读。
3. copy-to-working-copy 创建新 pending，历史 ID 不改变。
