# G2 上游版本链与失效验收清单

## 1. 结论与边界

本清单是未来 G2 实施的强制验收，不是本轮已执行结果。G2 只有同时证明以下事实才可完成：

1. Working Copy 不会静默改变正式版本。
2. 新正式上游会让旧下游派生 stale，但不会删除历史。
3. 新任务只读取当前且已确认的来源。
4. 迟到任务和并发页面不能覆盖新 current 或用户工作稿。
5. workflow 能同时展示最远里程碑、待确认修改和来源已更新。

当前文档阶段的 Runtime/User Review 不适用；实施阶段必须执行第 13 节。

## 2. 前置条件

G2 开发和验收开始前必须：

- G0 自动化测试骨架已落地。
- 44 模型正式 migration tree 已通过 exact check、Prisma validate、fresh deploy、二次 no-pending、integrity/FK；C3 Project/Chapter/Script 最小 DB substrate 已通过公开 Service 写入与应用上下文重建读回。
- 所有测试使用临时 SQLite、临时 Asset/workspace 和 loopback fake providers。
- 禁止读取真实 key、复用本机开发服务、写真实项目或调用真实外部模型。
- G2 的每个发布/确认切片必须自行证明同事务 current 指针更新、expected rowVersion/CAS、并发冲突、失败回滚、迟到写隔离与重启读回；不能借用 C3 单进程结果冒充这些证据。

以上条件允许 G2 在临时数据库中开始正式开发和验收；它不授权真实数据迁移或生产切换。完整 G1 的 importer、SecretStore、持久任务、Asset/Outbox、协调备份和 `WIT-01` 仍须在各自集成/生产门禁前完成。

## 3. Fixture

### 3.1 `g2_chain_current`

```text
chapter milestone = exported
Script v1 current
Story v1 -> Script v1 current
Storyboard v1 -> Story v1 current
Preflight v1 -> Storyboard v1 + refs/style current
Candidate/Layout/Export 历史各至少一份
所有 Working Copy clean/absent
```

用途：验证返修不删除历史。

### 3.2 `g2_chain_dirty_script`

在 `g2_chain_current` 上修改 Script Working Copy，但不发布。

用途：验证旧正式链仍 current、所有新下游任务被阻止。

### 3.3 `g2_chain_stale_story`

在 `g2_chain_current` 上发布 Script v2，保持 current Story 指向 v1。

用途：验证 Story/Storyboard/Preflight 传递 stale 和里程碑不回退。

### 3.4 `g2_pending_conflicts`

包含 Story pending、Storyboard pending、两个客户端 rowVersion 和一个运行中的生成任务。

用途：验证乐观锁、pending 替换和迟到结果。

### 3.5 `g2_legacy_unresolved`

旧 structure/storyboard/preflight 均存在，但至少一层缺 source ID/digest；另含旧分镜编辑已删除候选目录的证据。

用途：验证迁移诚实报告，不伪造 current 或历史。

## 12. Worker、并发与故障注入

### 12.1 Barrier 场景

loopback fake provider 支持：

```text
before_provider
after_provider_before_stage
after_stage_before_db_commit
before_current_pointer_update
```

每个 barrier 可暂停任务，让测试在中间发布新上游、替换 pending、取消任务或重启进程。

### 12.2 用例

| ID | 故障 | 期望 |
| --- | --- | --- |
| G2-TASK-01 | story_parse provider 运行时发布 Script v2 | 任务可成功但 historical；不写 pending/current |
| G2-TASK-02 | shot_generate 运行时确认 Story v2 | 同上 |
| G2-TASK-03 | 任务 A 运行时用户创建 target B | A target archived/失效；A 不覆盖 B |
| G2-TASK-04 | 用户编辑 pending 后旧 task 完成 | rowVersion guard 拒绝写回 |
| G2-TASK-05 | worker lease 过期、旧 worker 迟到 | claimToken 条件更新为 0；无版本/指针副作用 |
| G2-TASK-06 | DB 在 confirmed 插入后、指针前失败 | 整个事务回滚；无孤立半确认 |
| G2-TASK-07 | source snapshot 构建后 Asset 被替换 | 事务内复核失败，Preflight 不确认 |
| G2-TASK-08 | 任务取消但 provider 仍返回 | 输出诊断可留；不能成为 current |
| G2-TASK-09 | 进程重启 | Chapter routing target、active pending write target、pending rowVersion/current/sourceDigest 分别恢复一致，不混用 Chapter.rowVersion |
| G2-TASK-10 | task A 创建后 active pending 从 A 切到 B，再以相同请求重放 | idempotencyKey 仍由冻结的 `input.expectedTargetId=A` 计算且与已保存 key 相同；不得按 mutable pointer B 重算，也不产生第二个正式 pending/current 写回 |
| G2-TASK-11 | story_parse/shot_generate targetId 写 pending ID | create 拒绝；targetType=chapter 时 targetId 必须等于 input.chapterId |
| G2-TASK-12 | expectedTargetId 与 active pending 不同或 expectedTargetRowVersion 过期 | 完成可记 historical，但不得写 pending/current |

## 13. Runtime/User Review

在临时/演练项目上由用户执行：

### 路径 A：剧本未确认修改

1. 打开已有候选或导出的章节。
2. 回到剧本修改一段文字并保存。
3. 确认页面显示“有未确认修改”。
4. 打开旧候选/旧导出，确认仍可查看。
5. 尝试生成新剧情结构，确认被明确提示先完成或还原剧本。

### 路径 B：逐级发布

1. 完成剧本，产生新 ScriptVersion。
2. 确认剧情结构显示“来源已更新”。
3. 编辑并确认新的 StoryVersion。
4. 确认分镜显示“来源已更新”，旧分镜/候选仍可回看。
5. 编辑并确认新 StoryboardVersion。
6. 确认出图准备要求重新检查。

### 路径 C：来源资产变化

1. 在 current Preflight 下更换一个出镜角色的正式参考图。
2. 确认 Story/Storyboard 不显示过期。
3. 确认出图准备显示角色来源已更新，候选新生成被阻止。
4. 重新确认后恢复候选生成入口。

### 路径 D：并发与历史

1. 两个浏览器标签打开同一 Story pending。
2. A 修改并确认。
3. B 使用旧页面确认，必须收到冲突并刷新。
4. 历史页能看到旧/新版本与各自来源，不出现覆盖。

用户验收记录至少包含截图、版本 ID、reason code、任务 ID 和旧导出可打开证据。
