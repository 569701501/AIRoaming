# G3 施工包：下游适配与可执行证据

## 1. 文档定位

本文是 G3-core 的第五份施工资料，回答三件事：canonical 两值翻转后哪些真实消费点必须同步、尺寸策略如何进入可重放任务、Luna 用哪些 fixture 与命令证明实现完成。

本文不把尚不存在的 G1 maintenance importer 当作可运行前置。测试和完成结论分为：

| 类别 | 含义 | 是否阻塞 G3-core |
| --- | --- | --- |
| `core_mandatory` | 当前代码可实现、可自动验证的核心路径 | 是 |
| `rollout_gate` | 只读旧 workspace inventory 与真实启用前检查 | 不阻塞临时环境开发，阻塞真实发布 |
| `importer_deferred` | 依赖 G1 importer、决议、备份恢复或 DB-only activate | 否；阻塞 production-ready |

优先级与阶段边界以 `2026-07-12_G3施工包_依赖边界与阶段门禁.md` 为准。

## 2. 冻结常量与版本词汇

### 2.1 canonical 版式

```ts
export const COMIC_FORMATS = ["vertical_scroll", "paged_comic"] as const;
export type ComicFormat = (typeof COMIC_FORMATS)[number];
```

新 Runtime、API、DB、Preflight、SourceSnapshot 和 Task 不允许出现 `page_horizontal/four_panel`。

### 2.2 尺寸策略

```ts
export const LEGACY_GENERATION_DEFAULT_SIZE_POLICY_VERSION =
  "legacy_generation_default_v1" as const;
```

字段名固定为 `sizePolicyVersion`。它描述“如何为候选图选择默认宽高”，不能与下列 G2 来源投影字段合并：

```ts
TaskSourceProjectionV1.policyVersion = "g2-task-source-v1";
```

### 2.3 版本边界

| 对象 | G3 新写版本 | 说明 |
| --- | --- | --- |
| `CandidateGenerationSpec` | `schemaVersion: 2` | 增加 `sizePolicyVersion`，digest 覆盖策略与宽高 |
| file `CandidateGenerationTaskInput` | `generationSpecVersion: 2` | `candidateGenerationSpec.schemaVersion` 同为 2 |
| DB `input.promptSpec` | `schemaVersion: 2` | `image` 增加 `sizePolicyVersion` |
| G2 persistent task 外层 input | 保持 `schemaVersion: 2` | 这是 G2 命令协议版本，不因内部 prompt spec 升级而改名或盲目加一 |
| `TaskSourceProjectionV1` | 保持 `schemaVersion: 1` | `policyVersion` 继续为 `g2-task-source-v1` |

旧 Candidate/Prompt V1 只作为历史输入展示或审计，不得补字段后作为新命令重放。

## 5. SourceSnapshot 严格化

当前 DB builder 的“不是 `vertical_scroll` 就当 `paged_comic`”会把任意损坏值静默合法化，必须删除。

目标 helper：

```ts
function parseCanonicalProjectComicFormat(
  value: unknown,
): "vertical_scroll" | "paged_comic" {
  if (value === "vertical_scroll" || value === "paged_comic") return value;
  throw createG2DatabaseError(500, "PROJECT_COMIC_FORMAT_CORRUPTED");
}
```

规则：

1. DB builder 不接受 legacy alias；CHECK 应先阻止它，builder 是第二道防线。
2. file builder 接收的 `LocalProject.comicFormat` 已经过 file read adapter，运行时只能是 canonical。
3. 新 `PreflightSourceSnapshotV1.style.comicFormat`、`styleCheck.comicFormat` 和 output 必须一致。
4. corruption 不能触发新的 sourceDigest，也不能回退 vertical；请求失败且无新 PreflightRevision。
5. 历史 Preflight alias 只能走 `legacy-preflight-read-v1` 只读 adapter，不修改旧 digest。

## 6. 候选图尺寸与 digest

### 6.1 当前兼容策略

```text
vertical_scroll -> 1024 x 1536
paged_comic     -> 1536 x 1024
```

`paged_comic` 的横向尺寸只是保持旧生成行为的临时默认，不能在 UI 或领域文案中写成“分页漫画必然横版”。G5 引入镜头级比例后必须用新 `sizePolicyVersion`，不能改变 `legacy_generation_default_v1` 的含义。

### 6.2 唯一纯函数

建议在 `candidate-generation-spec.ts` 收口：

```ts
export function getLegacyGenerationDefaultSize(
  comicFormat: ComicFormat,
): {
  width: number;
  height: number;
  sizePolicyVersion: typeof LEGACY_GENERATION_DEFAULT_SIZE_POLICY_VERSION;
};
```

所有 file/DB task creator 复用该函数或其 Shared 输出，不允许各自写 ternary。

### 6.3 digest 输入

Candidate V2 digest source 至少包含：

```ts
{
  schemaVersion: 2,
  sizePolicyVersion,
  purpose,
  projectId,
  chapterId,
  shotId,
  positivePrompt,
  negativePrompt,
  requestedSize,
  references,
}
```

验收：只改变 `sizePolicyVersion` 或 `requestedSize` 任一字段，digest 必须改变；相同输入重复构建 digest 必须稳定。

## 7. 新 Task input 契约

### 7.1 file candidate task

```ts
export interface CandidateGenerationTaskInput extends Record<string, unknown> {
  chapterId: string;
  shotId: string;
  candidateCount: number;
  generationPurpose: "shot_clean_plate";
  generationSpecVersion: 2;
  generationSpecDigest: string;
  candidateGenerationSpec: CandidateGenerationSpec;
  image: {
    width: number;
    height: number;
    sizePolicyVersion: "legacy_generation_default_v1";
  };
}
```

以下三处必须完全一致，否则拒绝创建任务：

```text
input.generationSpecDigest
input.candidateGenerationSpec.digest
持久化 GenerationTask.generationSpecDigest（若该路径有独立列）
```

`input.image.width/height/sizePolicyVersion` 也必须等于 spec 的 `requestedSize/sizePolicyVersion`。

### 7.2 DB persistent image task

外层 G2 input 继续 `schemaVersion: 2`，内部目标为：

```json
{
  "schemaVersion": 2,
  "chapterId": "chapter_001",
  "shotId": "shot_001",
  "promptSpec": {
    "schemaVersion": 2,
    "sizePolicyVersion": "legacy_generation_default_v1",
    "image": {
      "width": 1024,
      "height": 1536,
      "sizePolicyVersion": "legacy_generation_default_v1"
    }
  },
  "sourceProjection": {
    "schemaVersion": 1,
    "policyVersion": "g2-task-source-v1"
  }
}
```

`promptSpec.sizePolicyVersion` 与 `promptSpec.image.sizePolicyVersion` 作为同值冗余校验；创建端写入，worker decoder 精确比较。Provider 请求仍只接收支持的 width/height，不把策略字符串发给第三方。

### 7.3 历史输入

- 查询旧 task 可以原样返回 V1 JSON。
- worker claim 到 V1/缺 `sizePolicyVersion` 的 image task 时，返回稳定不可执行分类，例如 `LEGACY_GENERATION_INPUT_UNSUPPORTED`，不得用当前版式重新推导宽高。
- 禁止后台扫描并重写旧 inputJson、outputJson、sourceDigest 或 generationSpecDigest。

## 8. Prompt 与 Layout 边界

### 8.1 Prompt

候选 clean-plate 正向 prompt 不能出现以下 token：

```text
vertical_scroll
paged_comic
page_horizontal
four_panel
竖向条漫
分页漫画
```

理由：候选是单镜头无字干净画面，Project 阅读容器不是镜头画面内容。版式只通过版本化 requested size 影响当前默认画幅。

角色/场景参考图 style guide 可以使用 Shared 的中文 label 和中性 hint；`paged_comic` 的 hint 必须包含 orientation unspecified 的语义。

### 8.2 Legacy Layout adapter

新增并只在 Server legacy layout output 使用：

```ts
type LegacyLayoutPageFormat =
  | "vertical_comic"
  | "page_horizontal"
  | "four_panel";

export function toLegacyLayoutPageFormat(
  format: ComicFormat,
): Exclude<LegacyLayoutPageFormat, "four_panel"> {
  return format === "vertical_scroll" ? "vertical_comic" : "page_horizontal";
}
```

新 Project 不产生 `four_panel` LayoutPage。旧 layout 的 `four_panel` 仍作为历史 JSON 原样读取，不反向提升为 Project ComicFormat。

## 13. rollout_gate 与 importer_deferred

### 13.1 rollout_gate

| ID | 证据 | 通过标准 |
| --- | --- | --- |
| G3-AUD-01 | fixture audit | 分类、计数、退出码精确；内容和 mtime 不变 |

### 13.2 importer_deferred

原验收清单的 `MIG-01`～`MIG-15`、协调备份/恢复、final import、MigrationIssue decision、DB-only activate 属于 G3-M。当前只能审查接口与 fixture 设计，不能标绿运行证据。

`RST-03` 备份/恢复与 `RST-05` migration rollback 也属于 G3-M/发布演练。G3-core 只证明临时 SQLite restart 与 trigger 保持。

## 15. 证据目录

G3-core 实现任务目录内至少保存：

```text

handoff.md
scrutiny_review.md
runtime_user_review.md
evidence/
  commands.md
  g3-core-test-summary.json

```

规则：

- `commands.md` 记录 commit、命令、退出码与时间，不粘贴无关完整日志。
- JSON summary 只引用测试名称和结果，不自建签名/CAS/reviewer 基础设施。
- screenshot 至少包含弹窗空默认、vertical 成功、paged 成功、失败保留四类状态。
- Runtime/User Review 使用临时 workspace 和 fake provider；真实 provider 不属于 G3-core 强制验收。
- 无法执行的 G3-M 用例写 `deferred: dependency_not_implemented`，不能写 `passed` 或 `not_applicable`。

## 16. Scrutiny Review 核对表

只读复核必须逐项回答：

1. Shared 是否只有两值，Server/Web 是否无复制 enum/label。
2. `page_horizontal/four_panel` 是否只出现在 legacy input/output allowlist、fixture 与历史说明。
3. Create 是否无默认，PATCH forbidden 是否早于 persistence mode gate。
4. 0010 是否只新增一个 trigger，0008/0009 是否未修改。
5. G3 ledger 是否精确 0001～0010，G1 只过滤已知 0009/0010。
6. SourceSnapshot 是否不存在“非 vertical 即 paged”。
7. Candidate/Prompt V2 是否同时保存 `sizePolicyVersion` 与宽高，digest 是否覆盖它们。
8. `TaskSourceProjection.policyVersion` 是否仍为 `g2-task-source-v1`。
9. V1 历史 task 是否不会被新 worker 补推并执行。
10. Web 是否保留 error code、使用创建专用状态、成功路径不被 refresh 失败反转。
11. core、rollout、importer 三类证据是否分开，是否存在虚假 production-ready 声明。

任一答案为否，Scrutiny Review 结论不得为通过。

## 17. 完成语义

可写 `G3-D0 completed` 的条件：第 3～9 节全部实现，相关 unit/integration 通过。

可写 `G3-core completed` 的条件：A0～E0、全部 `core_mandatory`、Scrutiny Review 和临时环境 Runtime/User Review 通过。

只有 G3-M、`rollout_gate` 和真实 workspace 用户复核也完成后，才可写 `G3 production-ready`。本施工包不会用更多审查流程替代 migration tree、运行测试或真实用户路径证据。
