# 深思熟虑（Deep Think）

AI 漫游项目复杂功能的规划、执行、复核与留痕主技能。

本技能只按需使用，不是每次对话的默认流程。它的价值在于：把高风险、跨多模块的任务，拆成可复核、可回滚、有证据留痕的阶段，避免一口气回滚成本巨大的改动。

## 何时触发 / 何时不触发

**触发**（满足任一）：

- 用户明确说"深思熟虑""先想清楚""认真规划""好好想想""先别写代码想清楚"。
- 任务涉及多模块、数据库、任务协议、素材路径、导出物或真实用户路径。
- 任务需要多个阶段、存在较高回滚成本或需要正式复核。

**不触发**：

- 普通聊天、解释、轻量讨论。
- 小文案、小样式、单文件小改。
- 用户明确说"先不要规划""先不要写代码""不要使用深思熟虑"。

如果拿不准，先问用户一句："这个任务要不要走深思熟虑流程？"

## 四个角色

同一个 AI 可以在当前会话内分角色执行，但必须在文档和行为上保持职责分离。不要把不同角色的动作混在一个步骤里。

| 角色 | 职责 | 能做什么 / 不能做什么 |
| --- | --- | --- |
| Orchestrator | 读事实源、建任务目录、拆阶段、处理阻塞 | 只规划与协调，不直接写功能代码 |
| Worker | 只执行当前阶段，记录改动和证据 | 只做自己这一阶段，不越界改其他阶段 |
| Scrutiny Review | 只读复核静态证据、契约、测试和 Handoff | 只读，不改代码；只给结论与风险 |
| Runtime/User Review | 验证真实页面、任务状态、导出物和素材追溯 | 由用户在真实环境执行，AI 整理验收口径 |

执行顺序：Orchestrator 建框架 → Worker 逐阶段执行 → Scrutiny Review 静态复核 → Runtime/User Review 运行复核。

## 执行流程

### 1. Orchestrator：建任务目录

在 `文档/05_执行与记录/任务记录/YYYY-MM-DD_<任务短名>/` 下建目录，至少包含：

| 文件 | 作用 |
| --- | --- |
| `task_plan.md` | 目标、阶段、任务、决策、退出标准 |
| `progress.md` | 每次推进的时间线、改动文件、验证结果 |
| `findings.md` | 探索发现、证据、风险、问题与结论 |

任务目录命名用日期 + 任务短名，例如 `2026-06-19_角色版本模型/`。

`task_plan.md` 必须写清楚：目标、非目标、验收标准、阶段划分、退出标准。

### 2. Worker：逐阶段执行

- 一次只执行一个阶段。
- 每个阶段开始前，读 `文档/` 相关事实源（修改前必读：`文档/README.md`、`文档/00_索引/AI上下文入口.md`、`文档/00_索引/写作规范与留痕规则.md`、相关模块文档）。
- 每个阶段完成后，在 `progress.md` 记录：改动文件、验证命令与结果。
- 遇到与预期不符的证据，写进 `findings.md`，不要默默改方案。

### 3. Scrutiny Review：静态复核

只读检查：

- 代码改动是否和 `task_plan.md` 的目标一致。
- 数据结构、任务协议、文件路径是否和 `文档/02_架构与契约/` 一致。
- 测试是否覆盖关键路径。
- Handoff（交接说明）是否清晰。

输出：通过 / 不通过 + 残留风险清单。不改代码。

### 4. Runtime/User Review：运行复核

由用户在真实环境执行：

- 真实页面点击路径。
- 任务状态是否正确推进。
- 导出物（图、素材包）是否正确。
- 素材能否追溯到角色 / 场景 / 镜头。

AI 负责整理验收清单，用户负责执行并反馈。

## 留痕规则

- 改变产品范围、用户路径或验收口径 → 更新 `文档/01_愿景与产品/`。
- 改变架构、数据结构、任务协议、文件路径、异步状态 → 更新 `文档/02_架构与契约/`。
- 改变模块职责、接口边界、上下游依赖 → 更新 `文档/03_模块梳理/`。
- 做出不可轻易回退的技术或产品决策 → 在 `文档/04_方案与决策/` 新增 ADR。
- 做功能开发 → 在任务目录记 `progress.md`。
- 功能完成 → 在 `文档/05_执行与记录/功能完成记录/` 新增完成记录。
- 做验证 → 在 `文档/06_测试与验收/` 或任务目录内记证据、命令、结果、残留风险。

完成记录必须包含：功能摘要、影响范围、修改文件、数据或协议变化、验证命令与结果、已知风险、后续建议。

## 退出标准

任务完成前必须满足：

1. 所有阶段执行完毕，`progress.md` 时间线完整。
2. Scrutiny Review 给出静态复核结论（通过 / 不通过 + 风险）。
3. Runtime/User Review 给出运行复核结论（通过 / 不通过）。
4. `文档/` 对应位置已同步更新。
5. 完成记录已写入 `功能完成记录/`。

确实不适用某一步时（比如纯后端改动无 UI），在 progress 里写明原因，不要默认跳过。

## 与其他技能的关系

- 深思熟虑是本项目复杂功能的主技能。
- `grill-with-docs`（Matt Pocock）可在深思熟虑**之前**使用：带着 `文档/` 和现有代码拷问方案，先把术语、边界、决策问清楚，再进入正式拆任务。
- `diagnosing-bugs` 用于 bug 诊断，不替代深思熟虑。
- `tdd` 是测试先行的方法补充，不替代主流程。
- Matt Pocock 技能中提到的 `CONTEXT.md`，在本项目等价于 `文档/00_索引/AI上下文入口.md` + `文档/01_愿景与产品/` + 相关模块文档。
- Matt Pocock 技能中提到的 `docs/adr/`，在本项目等价于 `文档/04_方案与决策/`。
- 不要因为使用 Matt 技能而新建根目录 `CONTEXT.md`、`CONTEXT-MAP.md` 或 `docs/adr/` 作为新的主事实源。事实源永远是 `文档/`。
